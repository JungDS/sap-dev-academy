Deep Structure — 행 안의 목록

주문 한 건에 상품 여러 개 — 만들어 보고, 이름 붙이고, 판정하는 눈까지.

Track 1Chapter 6Lesson 13초급

한 행 안에 목록을 넣고 싶다

정훈영의 다음 과제는 주문 관리다. 주문 한 건의 모양을 잡아 보는데 —

  • 주문번호: A001
  • 주문자: 김연아
  • 주문 상품: 키보드 1개, 마우스 2개, 모니터 1개

주문번호와 주문자까지는 Chapter 5의 Structure로 충분하다. 문제는 상품이다. 한 건의 주문 안에 여러 줄의 목록이 딸려 있다. 상품마다 주문 행을 따로 만들자니 주문번호·주문자가 세 번 반복되고, 필드를 item1·item2·item3으로 늘리자니 상품이 네 개면 무너진다.

원하는 것은 분명하다 — 행 안에 테이블을 통째로 넣는 것. 그게 될까?

일단 만들어 보자 — 아는 도구만으로

된다. 그것도 이미 배운 도구만으로. Structure의 에는 타입이 오는데, L02에서 만들어 본 Table Type도 엄연한 타입이기 때문이다.

TYPES: BEGIN OF ts_item,              " 상품 한 줄
         item TYPE c LENGTH 20,
         qty  TYPE i,
       END OF ts_item.

TYPES tt_item TYPE TABLE OF ts_item.  " 상품 여러 줄(Table Type)

TYPES: BEGIN OF ts_order,             " 주문 한 건
         order_id TYPE c LENGTH 10,
         customer TYPE c LENGTH 20,
         items    TYPE tt_item,       " 행 안에 테이블!
       END OF ts_order.

DATA: gs_order  TYPE ts_order,
      gs_item   TYPE ts_item,
      gt_orders TYPE TABLE OF ts_order.   " 주문들의 테이블(행마다 상품 목록을 품음)

Chapter 4의 중첩 DO와 같은 겹 구조인데, 이번엔 안쪽이 "횟수"가 아니라 "이 행이 품은 목록" 이다. 마법 같은 새 문법은 하나도 없었다 — 아는 것의 조합이다.

이제 이름을 붙이자 — Flat과 Deep

방금 만든 ts_order 같은 구조에는 공식 이름이 있다. 먼저 낱말 하나 — 여기서 말하는 는 Chapter 5에서 "필드"라 부르던 그것이다.

  • Flat Structure — 모든 Component가 고정 길이 타입. c(고정 길이 문자)·n(숫자문자)· d(날짜)·t(시간)·i(정수)·p(소수) 등이다. 담기는 값이 무엇이든 차지하는 자리의 크기가 처음부터 정해져 있다.
  • — Component 중에 가변 요소가 하나라도 있다. 가변 요소는 셋: string · · 참조(reference).

왜 이 셋일까. 서랍으로 비유하면 — Flat Structure는 폭이 정해진 서랍이라 모든 칸이 제자리에 통째로 들어 있다. 그런데 글자 수에 따라 커지는 string, 행이 계속 느는 Internal Table은 크기가 변해서 서랍 칸에 직접 못 들어간다. 그래서 시스템은 그런 값을 별채에 따로 두고, 서랍 칸에는 "어디 별채에 있는지 적은 쪽지"만 넣는다. 쪽지가 든 칸이 하나라도 있으면 그 서랍 전체가 Deep이다. 참조(reference)는 아예 "쪽지가 본업"인 세 번째 종류인데, 이름만 알아 두자 — 뒤 챕터에서 따로 배운다.

반전 — 우리는 이미 Deep을 쓰고 있었다

이 챕터 내내 쓴 ts_person을 다시 보자.

name이 string이니 — ts_person은 처음부터 Deep이었다. 우리는 Deep을 "이제 배우는" 게 아니라 L01부터 줄곧 써 온 것이다. 그리고 아무 문제도 없었다. Deep은 금지 딱지가 아니라 분류다. 다만 몇몇 상황에서 Flat과 다르게 취급되기에 구분하는 눈이 필요할 뿐이다(잠시 뒤에).

판정하는 눈 — 중첩(Nested)과 헷갈리지 말 것

Structure 안에 Structure가 든 것은 중첩(nested)이라 부른다. 겹쳐 보여서 Deep 같지만 — 안까지 전부 고정 길이면 여전히 Flat이다. 나란히 보자.

         addr TYPE ts_addr,           " Structure 안 Structure — 고정 길이 덩어리
       END OF ts_emp_a.

TYPES: BEGIN OF ts_emp_b,             " 필드 둘뿐이지만 Deep
         name TYPE string,            " 가변 요소
         age  TYPE i,
       END OF ts_emp_b.

판정 규칙은 하나뿐이다 — "겹이 몇 개냐"가 아니라 "가변 요소(string·테이블·참조)가 있느냐". 이 규칙 하나로 어떤 선언이든 판정할 수 있다.

왜 구분하나 — Deep이 다르게 취급되는 자리

  • DB 저장: DB 테이블의 컬럼은 단일(elementary) 타입 하나여야 한다. 이나 참조를 컬럼에 통째로 넣을 수는 없다 — gt_orders를 그대로 DB에 저장하지 못하는 이유다 (주문과 상품을 두 테이블로 나눠 저장하는 해법은 다음 챕터부터 차근차근 배운다). 단, string은 문자열용 컬럼 타입이 따로 있어 DB에 들어간다 — "Deep이면 무조건 DB 불가"가 아니라 테이블·참조가 불가인 것이다.
  • 화면 출력: 결과를 표로 보여 주는 도구(ALV — 뒤에서 배운다)도 기본적으로 평평한 행을 전제한다. 행 안의 목록은 펼쳐서 보여 줄 별도 설계가 필요하다.
  • 통째 복사·비교: 겉보기엔 한 덩어리 같아도 별채(쪽지가 가리키는 곳)까지 따라가야 해서, Flat보다 비용이 크고 동작 규칙이 세밀하다. 지금은 "차이가 있다"까지만.

흔한 오해와 점검

  • 중첩 = Deep이라는 착각 → 중첩은 "겹"의 문제, Deep은 "가변 요소"의 문제. 별개다.
  • "Deep이면 DB에 못 넣는다"는 뭉뚱그림 → 못 넣는 건 테이블·참조 다. string은 들어간다.
  • 행 안 테이블에 바깥 도구를 그대로 → gs_order-items도 엄연한 이라 APPEND·READ·LOOP가 다 된다. 다만 "누구의 목록인가"(어느 행의 items인가)를 항상 분명히 하고 다뤄야 한다.

행 안에 목록까지 담아 봤다. 챕터를 닫기 전에 하나 남았다 — 실무에서 반드시 마주칠 옛날 방식의 코드를 읽는 눈이다 → 옛 코드를 만나면.
