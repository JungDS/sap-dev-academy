Screen Programming / Dynpro 기초

화면에서 F1·F4 직접 만들기

DDIC 도움이 먼저, 그래도 부족할 때만 flow logic로 직접 F4를 만든다.

Track 1Chapter 16Lesson 5중급

외우지 못하는 값, 화면값에 따라 달라지는 후보

사용자는 공연ID C001 같은 코드를 외우지 못한다. 입력칸에서 F4를 누르면 목록이 떠야 하고, F1을 누르면 그 칸이 무엇인지 설명이 나와야 한다.

는 Data Element에 Search Help 붙이기에서 배웠다. 대부분은 그걸로 끝난다. 그런데 이런 경우가 있다.

  • 프로그램 안에서만 만드는 필드라 DDIC Search Help가 없다.
  • 다른 칸 값에 따라 후보가 달라진다. 예를 들어 공연ID를 먼저 고르면, F4에는 그 공연의 회차만 떠야 한다.

이럴 때 화면(Dynpro)에서는 flow logic의 가 F4를, 가 F1을 맡는다. 앞 글자를 딴 POV(PROCESS ON VALUE-REQUEST)· POH(PROCESS ON HELP-REQUEST)라는 줄임말도 자주 쓰이니 함께 기억해 두자.

먼저 규칙 — 입력 도움에는 순서가 있다

이 레슨의 핵심은 "F4를 직접 코딩하는 법"이 아니라 순서다. 좋은 classic 화면은 아래 순서로 내려간다. 위에서 해결되면 아래는 건드리지 않는다.

순서 방법 언제
1 DDIC 입력 도움 의 ·Check Table·Domain 고정값으로 충분할 때 (코드 0줄)
2 화면 필드에 Search Help 직접 연결 그 칸에만 별도 Search Help가 필요할 때
3 Search Help exit Search Help의 동작 자체를 손봐야 할 때 (심화 · 여기선 다루지 않음)
4 PROCESS ON VALUE-REQUEST 직접 구현 다른 화면값으로 후보를 만들거나, 표준으로 안 될 때 (최후수단)

⚠️ DDIC로 충분한 칸에 습관적으로 직접 F4를 만들지 말자. 직접 만든 건 유지보수 책임이 그만큼 커진다. 4번은 정말 필요할 때만.

그래도 직접 만들어야 한다면

flow logic에 처리할 칸과 을 이어 준다.

ABAP
1
2
3
4
5
PROCESS ON VALUE-REQUEST.              " F4 요청 처리
  FIELD gv_perf MODULE value_perf.

PROCESS ON HELP-REQUEST.               " F1 요청 처리
  FIELD gv_conc MODULE help_conc.

FIELD gv_perf MODULE value_perf.는 "gv_perf 칸에서 F4를 누르면 value_perf 모듈을 부르라"는 뜻이다. 모듈은 ABAP 쪽에 MODULE value_perf INPUT.으로 정의한다.

⚠️ 여기서 INPUT은 "PAI에서 불린다"는 뜻이 아니다. Screen Number와 Screen Painter에서 배운 OUTPUT(PBO)/INPUT(PAI) 규칙의 예외로, 입력 도움 모듈도 입력 쪽 처리라 INPUT으로 적을 뿐이다. 실제로 이 모듈을 부르는 건 PAI가 아니라 PROCESS ON VALUE-REQUEST다.

호출당하는 모듈은 반드시 ABAP 쪽에 정의가 있어야 한다. F1 쪽 help_conc는 이렇게 간단히 시작할 수 있다.

ABAP
1
2
3
MODULE help_conc INPUT.                 " F1(도움말) 요청 처리
  MESSAGE '공연ID는 공연 마스터에 등록된 코드입니다' TYPE 'I'.
ENDMODULE.

실무에서는 문서 오브젝트를 띄우기도 하지만, 지금은 "F1을 누르면 내가 준비한 안내가 뜬다"는 뼈대까지만 잡으면 된다. 정의를 빼먹고 flow logic에서 부르기만 하면 화면 활성화 단계에서 "부를 모듈이 없다"며 막힌다.

다른 화면값을 읽어 후보 좁히기

F4를 누른 순간, 지금 화면에 입력된 다른 값(공연ID)을 읽어야 회차 후보를 만들 수 있다. 그 값을 읽어 오는 화면 전용 함수가 DYNP_VALUES_READ다.

🤔 화면값은 PAI에서 변수로 들어온다고 배웠는데 왜 함수까지 필요할까? F4는 PAI보다 먼저 일어나기 때문이다. 사용자가 칸에서 F4를 누른 그 순간은 화면값이 변수로 정식 전송되기 전이라, 변수를 그냥 읽으면 직전 값을 보게 될 수 있다. 그래서 "지금 화면에 떠 있는 값"을 따로 물어보는 함수를 쓴다.

먼저 값을 담을 그릇을 프로그램 전역에 선언한다.

DATA: gv_conc TYPE zconcert-concert_id,          " 공연ID 입력칸
      gv_perf TYPE n LENGTH 3.                   " 회차 입력칸

DATA: gt_dynp TYPE STANDARD TABLE OF dynpread,   " 화면값을 주고받을 표
      gs_dynp TYPE dynpread.

TYPES: BEGIN OF ts_perf,
         perf_no TYPE n LENGTH 3,
         text    TYPE c LENGTH 30,
       END OF ts_perf.
DATA: gt_perf TYPE STANDARD TABLE OF ts_perf,    " F4에 띄울 후보 목록
      gs_perf TYPE ts_perf.

그리고 한 모듈 안에서 값을 읽고, 후보를 만들고, F4 창을 띄운다. Module Pool에는 "아무 데나 떠 있는 실행문"이 없다. 실제로 실행되는 코드는 반드시 MODULE(또는 FORM) 안에 있어야 한다.

MODULE value_perf INPUT.
  CLEAR: gt_dynp, gt_perf.              " 지난번 F4의 찌꺼기 비우기

  gs_dynp-fieldname = 'GV_CONC'.        " 읽고 싶은 화면 칸
  APPEND gs_dynp TO gt_dynp.

  CALL FUNCTION 'DYNP_VALUES_READ'      " 화면의 현재 값 읽기
    EXPORTING  dyname     = sy-repid
               dynumb     = sy-dynnr
    TABLES     dynpfields = gt_dynp
    EXCEPTIONS OTHERS     = 1.
  IF sy-subrc <> 0.
    RETURN.                             " 못 읽었으면 후보를 만들지 않는다
  ENDIF.

  READ TABLE gt_dynp INTO gs_dynp INDEX 1.
  IF sy-subrc <> 0.
    RETURN.
  ENDIF.
  " gs_dynp-fieldvalue 에 사용자가 고른 공연ID가 들어 있다

  IF gs_dynp-fieldvalue = 'C001'.       " 그 공연의 회차만 후보로
    gs_perf-perf_no = '001'.
    gs_perf-text    = '1회차 19:00'.
    APPEND gs_perf TO gt_perf.
    gs_perf-perf_no = '002'.
    gs_perf-text    = '2회차 21:00'.
    APPEND gs_perf TO gt_perf.
  ENDIF.

  CALL FUNCTION 'F4IF_INT_TABLE_VALUE_REQUEST'
    EXPORTING  retfield    = 'PERF_NO'  " 고른 값을 돌려줄 컬럼
               dynpprog    = sy-repid
               dynpnr      = sy-dynnr
               dynprofield = 'GV_PERF'  " 값을 넣어 줄 화면 칸
               value_org   = 'S'
    TABLES     value_tab   = gt_perf
    EXCEPTIONS OTHERS      = 1.
ENDMODULE.

낯선 파라미터 읽는 법

뜻
dyname = sy-repid 지금 실행 중인 프로그램 이름(시스템이 채워 주는 값)
dynumb = sy-dynnr 지금 떠 있는 화면 번호
dynpfields 읽고 싶은 칸 이름을 넣어 보내면 현재 값이 채워져 돌아온다
retfield 사용자가 고른 값을 어느 컬럼으로 돌려줄지
dynprofield 돌려받은 값을 어느 화면 칸에 넣을지
value_org = 'S' 후보 표를 줄 단위(Structure)로 넘긴다는 표시
  • ⚠️ 함수 호출의 TABLES 구역은 Dictionary 화면 필드와 TABLES 운반에서 배운 TABLES 선언문과 이름만 같고 전혀 다른 것이다. 여기서는 "표를 통째로 주고받는 파라미터 자리"를 뜻한다.
  • EXCEPTIONS OTHERS = 1.과 sy-subrc 확인은 CALL FUNCTION 기본 구조에서 배운 그대로다. 실패했는데 그냥 넘어가면 아무 후보도 없는 빈 F4 창이 뜬다.
  • RETURN.은 USING / CHANGING 파라미터에서 본 그 문장이다. 지금 처리 덩어리를 여기서 끝낸다는 뜻이다.
  • CLEAR를 왜 맨 앞에 둘까. Module Pool의 전역 변수는 화면이 도는 사이에 저절로 비워지지 않는다. 안 비우면 F4를 두 번째 누를 때 후보가 쌓여 중복으로 보인다 (화면 요소 — 입력·버튼·체크박스·라디오·드롭다운의 VRM 예제가 CLEAR gt_values.로 시작한 이유와 같다).

지금 이 코드를 통째로 외울 필요는 없다. 기억할 건 큰 그림 하나다. 직접 F4는 최후수단이고, 그때는 DYNP_VALUES_READ로 다른 칸 값을 읽어 후보를 좁힌다.

F1은 PROCESS ON HELP-REQUEST

F1(도움말)은 대부분 문서에 맡기는 게 낫다. DDIC 타입을 참조한 칸은 F1을 누르면 그 Data Element 설명이 자동으로 뜬다(Data Element에서 붙여 둔 그 설명이다). 화면 맥락에 맞는 별도 설명이 정말 필요할 때만 PROCESS ON HELP-REQUEST로 직접 만든다.

선택화면의 F4와 무엇이 다른가

Report Event·선택화면 심화에서 리포트의 F4를 AT SELECTION-SCREEN ON VALUE-REQUEST FOR ...로 만들어 봤다. 뿌리는 같은 POV다. 다만 위치가 다르다.

일반 화면(Dynpro) 선택화면(Report)
어디에 flow logic PROCESS ON VALUE-REQUEST ABAP AT SELECTION-SCREEN ON VALUE-REQUEST
flow logic 직접 작성 자동 생성(감춰짐)

F4IF_INT_TABLE_VALUE_REQUEST 같은 함수는 양쪽에서 똑같이 쓴다. 한 번 익히면 재사용된다.

흔한 실수와 점검

  • DDIC로 될 걸 직접 만든다 → 1번()이 되면 4번(직접 POV)은 만들지 않는다.
  • POV를 일반 PAI처럼 쓴다 → POV 모듈은 후보를 보여 주고 값을 돌려줄 뿐이다. 저장· 잠금 같은 일은 하지 않는다(그건 뒤 챕터의 주제다).
  • ON VALUE-REQUEST(리포트)와 PROCESS ON VALUE-REQUEST(화면)를 섞는다 → 뿌리는 같아도 쓰는 위치가 다르다.
  • FIELD 이름 불일치 → FIELD gv_perf ...의 이름은 화면 요소 이름과 같아야 한다.

정리

  • Dynpro F4의 기본은 DDIC 다. 직접 구현은 최후수단.
  • 직접 만들 땐 flow logic PROCESS ON VALUE-REQUEST(F4)·PROCESS ON HELP-REQUEST(F1)에 칸과 모듈을 잇는다.
  • 다른 칸 값이 필요하면 DYNP_VALUES_READ로 읽고, F4IF_INT_TABLE_VALUE_REQUEST로 목록을 띄운다.
  • 리포트의 AT SELECTION-SCREEN ON VALUE-REQUEST와 뿌리는 같고 위치만 다르다.

화면 요소와 입력 도움까지 갖췄다. 이제 화면이 뜨기 직전 PBO에서 무엇을 준비하는지 자세히 보자 → PBO 처리 흐름.
