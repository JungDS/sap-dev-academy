Open SQL 2차: JOIN·집계

LEFT OUTER JOIN 기본 개념과 NULL 처리

왼쪽은 모두 남긴다 — LEFT OUTER JOIN과 빈 값 처리.

매칭 없어도 남기고 싶다

운항편이 아직 등록 안 된 노선(SPFLI)도 목록에 남기고 싶다. 은 그런 행을 떨군다. 은 왼쪽(기준) 테이블 행을 전부 남긴다.

이름이 길다 보니 현장에서는 LEFT JOIN이나 그냥 LEFT라고 줄여 부르기도 한다. 다만 코드에 적을 때는 LEFT OUTER JOIN이 정식 표기이고, 이 과정도 본문·코드 모두 정식 이름으로 통일해 쓴다.

  INTO CORRESPONDING FIELDS OF TABLE gt_out.
  • 왼쪽 테이블인 spfli(노선)는 짝이 있든 없든 모두 결과에 남는다.
  • 매칭되는 오른쪽(운항편)이 없으면 그 자리의 값이 이 된다. 이게 뭔지 바로 아래에서 보자.

NULL — "값이 없다"는 값

NULL은 DB가 값 자체가 없다는 것을 표시하려고 쓰는 특별한 상태다. 숫자 0이나 공백 문자와는 다르다. "좌석을 0석 예매했다"와 "예매 기록이 아예 없다"가 다른 말인 것과 같다. 에서 오른쪽 짝을 못 찾으면, DB는 그 자리를 억지로 0이나 공백으로 채우지 않고 로 둔다.

문제는 그다음이다. ABAP에는 NULL이라는 것이 없다. 그래서 조회 결과가 ABAP 그릇으로 넘어오는 순간, NULL은 그 필드 타입의 초기값으로 바뀌어 들어온다.

DB 쪽 ABAP으로 넘어오면
숫자 필드의 NULL 0
문자 필드의 NULL 공백
날짜 필드의 NULL 00000000

여기서 헷갈림이 생긴다. 결과 테이블만 들여다봐서는 "짝이 없어서 비었다" 와 "원래 값이 0이라 0이다" 를 구분할 수 없다. 둘 다 그냥 0으로 보이기 때문이다.

그럼 어떻게 구분하나

방법은 간단하다. 오른쪽 테이블의 키 필드를 결과에 함께 담아 두고, 그 키가 비었는지를 본다. 키는 값이 있는 행이라면 절대 비어 있지 않으니, 키가 초기값이면 "짝을 못 찾은 행"이라고 확신할 수 있다.

LOOP AT gt_out INTO gs_out.
  IF gs_out-fldate IS INITIAL.       " 오른쪽 키가 비었다 = 짝이 없던 행
    WRITE: / gs_out-carrid, gs_out-connid, '운항 계획 없음'.
  ELSE.
    WRITE: / gs_out-carrid, gs_out-connid, gs_out-fldate.
  ENDIF.
ENDLOOP.

fldate는 sflight의 키 필드 중 하나라서 이 판단이 성립한다. 반대로 좌석 수처럼 원래 0일 수 있는 일반 필드로 판단하면 멀쩡한 행까지 "짝 없음"으로 잘못 세게 된다. 판단 기준으로 삼을 필드는 오른쪽 테이블의 키에서 고르자.

INNER vs LEFT OUTER — 직접 켜고 보기

아래 체험은 Chapter 09 · 콘서트 모델 만들기에서 넣어 둔 공연 세 건을 쓴다. 그중 C003은 예매가 한 건도 없는 공연이다(그때 일부러 그렇게 넣어 뒀다).

같은 데이터에 과 을 번갈아 적용하면 차이가 분명해진다. C003이 INNER에선 사라지고 LEFT OUTER에선 남는다(오른쪽 값은 초기값). 그리고 오른쪽 필드를 WHERE에 걸면 LEFT OUTER라도 C003이 다시 빠질 수 있다는 함정도 확인하자.

오른쪽 조건은 ON에 둘까 WHERE에 둘까

방금 본 함정은 외워서 피할 것이 아니라 일이 벌어지는 순서로 이해하면 된다. DB는 두 단계로 일한다. 먼저 ON으로 짝을 지어 결과를 만들고, 그다음 WHERE로 이미 만들어진 결과에서 행을 걸러 낸다.

  • ON에 두면 조건은 짝지을 후보를 고르는 데 쓰인다. 조건에 안 맞는 오른쪽 행은 짝에서 빠질 뿐이고, 왼쪽 행은 짝이 없는 상태로 그대로 남는다.
  • WHERE에 두면 조건은 다 만들어진 결과를 검사하는 데 쓰인다. 짝이 없어 오른쪽이 비어 있는() 행도 검사를 받는데, 견줄 값 자체가 없으니 조건을 통과하지 못하고 사라진다.

그래서 "왼쪽을 다 남기겠다"는 목적이라면 오른쪽 테이블에 거는 조건은 ON에 둔다. 반대로 짝지은 뒤 결과 전체를 좁히려는 조건이라면 WHERE가 맞는 자리다.

한 문장에 JOIN을 여러 개

JOIN은 한 문장에 여러 개 이어 붙일 수 있고, 종류를 섞어 쓸 수도 있다. 왼쪽부터 차례로 합쳐 나간다고 생각하면 된다. 앞의 결과에 다음 테이블을 붙이고, 또 그 결과에 다음 테이블을 붙인다.

붙일 때마다 물어볼 것은 하나다. "이쪽은 반드시 있는가, 없을 수도 있는가?" 콘서트 모델의 관계를 떠올려 보자. 예매는 반드시 어떤 회차에 속하고, 회차는 반드시 어떤 공연에 속한다(Chapter 09 · 콘서트 모델 만들기에서 Foreign Key로 그렇게 묶어 뒀다). 반대 방향은 보장이 없다. 공연에 회차가 아직 없을 수도, 회차에 예매가 하나도 없을 수도 있다.

TYPES: BEGIN OF ts_perf,
         concert_id TYPE zperf-concert_id,
         perf_no    TYPE zperf-perf_no,
         perf_date  TYPE zperf-perf_date,
         artist     TYPE zconcert-artist,
         booking_id TYPE zbooking-booking_id,
       END OF ts_perf.

DATA gt_perf TYPE TABLE OF ts_perf.

SELECT pf~concert_id pf~perf_no pf~perf_date c~artist b~booking_id
  FROM zperf AS pf
  INNER JOIN zconcert AS c        " 공연 마스터는 반드시 있다
    ON c~concert_id = pf~concert_id
  LEFT OUTER JOIN zbooking AS b   " 예매는 없을 수도 있다
    ON  b~concert_id = pf~concert_id
    AND b~perf_no    = pf~perf_no
  INTO CORRESPONDING FIELDS OF TABLE gt_perf.
  • 자식에서 부모로 올라갈 때는 INNER. 회차에 적힌 공연 ID는 Foreign Key가 지켜 주니 공연 마스터가 없을 수 없다.
  • 부모에서 자식으로 내려갈 때는 LEFT OUTER. 아직 예매가 없는 회차도 목록에 남겨야 "예매 0건"이 보인다.
  • 이 문장은 회차를 기준으로 시작하므로, 회차가 아직 없는 공연(C003)은 애초에 등장하지 않는다. 공연을 하나도 빠뜨리지 않으려면 위 체험처럼 zconcert에서 시작해 zperf를 으로 붙이면 된다. 어느 테이블을 FROM에 두느냐가 곧 "무엇을 다 보여 줄 것인가" 다.

세 테이블을 한 번에 붙이니 눈에 확 안 들어와도 괜찮다. 두 테이블 JOIN을 두 번 한 것일 뿐이고, 실무에서도 이 정도가 흔한 크기다. 지금은 ON 짝이 각각 어느 두 테이블 사이의 조건인지만 짚어 읽어도 충분하다.

흔한 실수와 점검

  • LEFT OUTER인데 오른쪽 조건을 WHERE에 → 짝이 없어 남겨 둔 행이 그 검사에서 걸러진다. 왼쪽을 다 남기는 게 목적이면 오른쪽 조건은 ON으로 옮기자.
  • 기준 테이블을 반대로 두기 → 다 남기고 싶은 쪽이 FROM 자리(왼쪽)에 와야 한다. "노선을 다 보고 싶다"면 FROM spfli, "공연을 다 보고 싶다"면 FROM zconcert다.
  • 초기값을 "값이 없다"로 단정 → 결과의 0이나 공백이 에서 온 것인지, 원래 들어 있던 값인지는 오른쪽 키 필드로 확인한다.

행을 합쳤다. 이제 묶어서 세고 합산하고 싶다 → GROUP BY·(다음 레슨).
