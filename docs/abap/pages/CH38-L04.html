"상자"가 통제 장치가 되는 순간

Chapter 1 · 이송요청에서 이송요청은 "내 변경을 담는 상자" 정도로 만났다. 저장할 때 팝업이 뜨면 담고, 끝. 그런데 운영에 가까워질수록 이 상자는 품질 통제의 핵심 단위가 된다.

이유는 운영 시스템의 철칙 하나에서 나온다: PRD(운영)는 직접 고치지 않는다. 운영에서 직접 수정하면 누가 언제 무엇을 바꿨는지 추적이 끊기고, 개발기와 운영기의 코드가 달라져 "개발기에선 재현이 안 되는" 유령 장애가 생긴다. 그래서 모든 변경은 DEV(개발)에서 만들어 → QAS(품질)에서 검증하고 → PRD로 승인된 것만 이동한다. 이 흐름을 관리하는 체계가 (Change and Transport System. ABAP 시스템 간 변경 이동을 관리하는 표준 체계)이고, 운영 담당이 쓰는 관리 화면이 STMS(Transport Management System)다.

상자의 내부 — Task와 Request

개발자가 보는 화면은 SE09/SE10(Transport Organizer)이다. 열면 선택화면에 내 사용자가 기본으로 잡혀 있고, 실행하면 내 request들이 트리로 나온다(번호는 DEVK9…처럼 시스템ID+K+일련번호 형식이다. CH01에서 저장할 때 팝업이 적어 주던 그 번호가 이것이다). 상자는 사실 2층 구조다.

용어 의미 비유
Task 개발자 한 사람의 작업 단위 상자 속의 개인 봉투
Request 함께 이동할 변경 묶음(task들을 담음) 배송 상자
Release "더 수정 없음" 확정 → 다음 시스템으로 보낼 준비 상자 밀봉
Import queue 대상 시스템에 들어올 request 대기열 하역장
Import log import의 성공·실패·활성화 결과 기록 배송 확인서

순서가 곧 규칙이다: task를 전부 release해야 request를 release할 수 있고, release된 request가 QAS의 import queue에 줄을 선다(대기열 순서 조정과 import 실행은 Basis·운영 담당 영역이다). release 조작 자체는 단순하다: SE09 트리에서 task/request를 선택하고 Release 버튼(우클릭 메뉴에도 있다)을 누른다. 단 되돌릴 수 없다 — 밀봉한 상자는 다시 열리지 않고, 밀봉 후의 수정은 새 request에 담긴다(QAS 테스트에서 결함이 나왔을 때의 대응도 이것이다: 고치고 새 상자로 다시 보낸다).

왜 상자가 여러 개로 나뉘어 사고가 나는가도 여기서 보인다. 개발자마다·목적마다 release 시점이 달라서 관련 변경이 한 상자에 다 담기지 않는 일이 늘 생긴다. 여기에 잠금이 얽힌다: 한 객체를 고치기 시작하면 그 변경이 담긴 request가 release될 때까지 다른 request가 그 객체를 가져갈 수 없다(나뉜 상자를 나중에 합치기 어려운 이유). 다만 release 전이라면 SE09에서 객체를 내 다른 request로 옮기는 것은 가능하다 — 저장 팝업에서 상자를 잘못 골랐을 때의 답이 이것이다. 그래서 순서 점검이 필요해진다.

연습 시스템이라면 release를 눌러 봐도 된다 — 상자는 소모품이라 새 request는 저장할 때 언제든 다시 생긴다. 두려워할 것은 버튼이 아니라 "검증 안 된 상자가 운영에 가는 것"이다.

길이 보였으면, 그 길 위에서 상자가 어디서 멈추는지를 눌러 보자.

개발자가 release 전에 보는 세 가지

release 버튼을 누르기 전의 점검이 이 레슨의 핵심 기술이다.

  1. Object list가 완전한가 — SE09 트리에서 request를 펼치면 담긴 목록이 그대로 보인다. 프로그램만 있고 DDIC 테이블·Data Element·message class·양식(Chapter 37의 동반 오브젝트 사고 기억)이 빠지지 않았는가. 누락되면 QAS에서 "개발기에선 되는데" 장애가 난다.
  2. 의존 순서가 맞는가 — 프로그램이 참조하는 DDIC 변경이 다른 request에 있다면, 그 request가 먼저 가야 한다. 순서가 뒤집히면 import 자체는 성공처럼 보여도 활성화(activation)에서 깨진다. 참조 객체가 어느 request에 있는지는 SE03(Transport Organizer Tools) 첫 화면의 도구 트리에서 **"Search for Objects in Requests/Tasks"**를 찾아 실행하고 객체 이름을 넣어 역추적한다.
  3. 게이트를 통과했는가 — release 시점에 ATC(L01)와 ABAP Unit(L02)이 자동 실행되도록 연동돼 있다면, 여기서 막힌 것은 고치고 간다(연동 여부 확인법은 L01에서: release 때 검사가 자동으로 돌면 켜진 것). 게이트 없이 나간 request는 QAS가 첫 검증이 된다(늦다).

Import 후 — Return Code를 읽는 법

import가 끝나면 log에 (import 결과 요약 숫자. 0/4/8 순으로 나빠진다)가 남는다.

RC 뜻 대응
0 성공 통과
4 경고 포함 성공(단골: 활성화 경고·번역/텍스트 누락·대상에 없는 참조 경고) log를 열어 경고 내용 확인 — 무시 습관 금지
8 오류 — 일부 는 이미 들어갔고 일부는 활성화 실패(어중간한 상태) 무엇이 들어갔는지부터 log로 확인 — "고쳐서 다시 보내자"로 바로 가지 않는다
12 이상 import 자체가 중단/취소 반영된 것이 없다는 뜻 — 원인 해소 후 재이송

숫자는 요약일 뿐이다. RC 8의 원인이 "의존 순서 역전"인지 "객체 누락"인지는 log 본문이 말해 준다. log는 개발자도 본다: SE09에서 내 request를 선택하면 이송 로그(transport logs)를 바로 열 수 있다 — STMS에 들어가지 않아도 내 상자의 행적은 여기서 추적된다. 그리고 QAS에서 테스트 승인(보통 현업·QA 담당이 테스트하고 회사 절차 — 티켓·결재 — 로 남긴다)이 나기 전에는 PRD import로 넘어가지 않는다 — QAS를 통과 못 한 상자가 PRD에 먼저 가는 길은 없어야 정상이다.

마지막으로 실무 사고 하나를 미리 알자. 급하다고 "제 것 하나만 먼저 태워 주세요"(선행 import)를 요청하면, 그 request는 대기열에 그대로 남아 나중에 전체 import 때 한 번 더 들어간다. 그 사이 다른 개발자가 같은 객체의 더 새 버전을 내보냈다면 옛 버전이 새 버전을 덮어쓴다 — "QAS에선 됐는데 PRD에서 옛날 코드가 도는" 고전 사고의 정체다. 선행 import는 공짜가 아니다.

🔭 기대 관리 — STMS의 실제 import 실행·대기열 조정·경로(route) 설정은 Basis·운영 담당 영역이라 이 과정 범위 밖이다. 개발자의 몫 = **release 전 3점검

  • SE09에서 이송 로그를 읽고 원인을 좁히는 것.** 참고로 CH01의 저장 팝업에서 본 것처럼 request에는 종류가 있다: 우리가 다루는 코드·DDIC는 Workbench request(client-독립 — 어느 client에나 적용), 설정값은 Customizing request(client-종속 — 입력한 client의 데이터만)로 나뉜다. "100번 client엔 반영됐는데 200번엔 안 됐다"는 수수께끼가 이 차이에서 나온다. 이 챕터는 Workbench 쪽 이야기다.

흔한 실수와 점검 🚧

  • PRD 직접 수정 → 운영 통제 실패. 긴급 수정도 추적 가능한 절차로 간다 — 회사마다 승인 절차를 딸린 "긴급 이송" 프로세스가 있다(별도 기능이 아니라 위의 선행 import나 사본 이송을 승인 하에 쓰는 운영 절차다). "그냥 운영에서 고침"은 없다.
  • 누락 → 프로그램만 보내고 DDIC·message class·양식을 빠뜨리는 것이 단골. release 전 object list 확인이 습관이다.
  • 의존 순서 역전 → import 성공처럼 보여도 활성화·런타임에서 깨진다. 참조하는 객체가 어느 request에 있는지 먼저 확인.
  • RC 숫자만 확인 → 4를 무시하는 습관이 8을 놓치는 습관이 된다. log 본문까지가 확인이다.
  • git과 같다고 생각 → 비슷한 것은 "변경 이력" 감각뿐이다. transport는 객체 잠금(한 객체를 고치기 시작하면 그 변경이 담긴 request가 release될 때까지 다른 request로 가져갈 수 없다)·활성화·import 순서라는 SAP 고유 세계로 움직인다.

정리 📌

  • 변경의 길 = DEV → QAS → PRD, PRD 직접 수정 금지. 상자 = task(개인) ⊂ request(묶음), 밀봉 = release.
  • 개발자의 release 전 3점검 = object list 완전성 · 의존 순서 · 게이트(ATC/Unit) 통과.
  • import 결과는 RC 숫자 + log 본문으로 읽는다. QAS 승인 없이 PRD 없음.

운영으로 가는 길은 확보됐다. 그런데 운영의 일 중에는 사람이 화면 앞에 없는 시간에 돌아야 하는 것들이 있다. 야간 정산을 맡길 무인 실행의 세계로 간다.
