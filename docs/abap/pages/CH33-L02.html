인터페이스 실무: BAPI/RFC/BDC/File

RFC Function Module 설계

원격 호출은 함수 로직이 아니라 연결·계약·예외·로그를 설계하는 일이다.

🔁 인터페이스에는 두 방향이 있다

BAPI는 우리가 표준을 부르는 방향이었다. 반대 방향도 있다. 외부 예매 사이트가 SAP에 "이 공연 남은 좌석 알려 줘"라고 묻거나, 다른 SAP 시스템이 "예매 상태를 조회해 줘"라고 요청한다. 시스템과 시스템이 서로 함수를 부르는 것, 그게 (Remote Function Call)다.

입문자가 꼭 챙겨야 할 감각: 원격 호출은 로컬 호출보다 실패 지점이 훨씬 많다. 네트워크가 끊기고, 연결 설정이 틀리고, 로그온 사용자가 잠기고, 권한이 없고, 대상 시스템에서 덤프가 난다. 그래서 RFC 설계는 함수 하나 만드는 일이 아니라 연결·계약· ·로그를 함께 설계하는 일이다.

호출 측 — DESTINATION과 RFC 예외

내 함수를 외부에 열려면 SE37에서 함수 속성을 Remote-Enabled로 만든다. 호출하는 쪽 코드는 이렇게 생겼다.

DATA gv_msg     TYPE c LENGTH 255.   " MESSAGE용 — flat 문자 필드여야 함
DATA gt_booking TYPE TABLE OF zbooking.

CALL FUNCTION 'Z_GET_BOOKINGS'
  DESTINATION 'TARGET_SYS'             " SM59에 등록된 연결 이름
  EXPORTING  iv_concert = 'C001'
  TABLES     et_booking = gt_booking
  EXCEPTIONS communication_failure = 1 MESSAGE gv_msg
             system_failure        = 2 MESSAGE gv_msg
             OTHERS                = 3.

CASE sy-subrc.
  WHEN 0.
    " gt_booking으로 계속
  WHEN 1 OR 2.
    " gv_msg + destination + 함수명 + 입력 key를 로그로
  WHEN OTHERS.
    " 예상 밖 기술 오류도 로그로
ENDCASE.
  • DESTINATION 'TARGET_SYS' — SM59에 등록된 Destination(대상 시스템·로그온 방식·client 같은 연결 정보 묶음)의 이름이다.
  • communication_failure — 통신 계층 실패(네트워크 단절·대상 접속 불가).
  • system_failure — 원격 시스템 안에서 실행 중 오류(덤프 등).
  • 두 뒤에 MESSAGE gv_msg를 붙이면 실패 원인 텍스트를 받아 로그에 남길 수 있다. 원격 장애 분석에서 이 메시지가 가장 중요한 단서다.

⚠️ 빈 DESTINATION 함정. 공식 규칙상 destination 값이 비어 있으면 DESTINATION 부가어가 무시되어 로컬 호출처럼 동작할 수 있다. 설정 누락이 조용히 지나가지 않도록, 변수로 받는 destination은 비어 있지 않은지 먼저 검증한다.

어떻게 확인하는가

  1. 함수 속성 — 대상 함수가 Remote-Enabled인지. 외부에서 불리는 함수는 화면을 띄우거나 입력을 기다리면 안 된다(호출자는 사람이 아니다).
  2. 계약() — 외부가 이해할 구지. 화면 필드·전역 상태 의존 금지. 입력 key·출력 테이블·메시지 구조를 명확히.
  3. SM59 — destination 실존·connection test 성공·로그온 사용자 상태.
  4. 실패 재현 — destination 오타·네트워크 차단·원격 덤프를 테스트로 만들어 sy-subrc와 gv_msg가 로그에 어떻게 남는지 확인한다.

원격 호출 시나리오

정상·연결 누락·통신 실패·원격 덤프를 바꿔 가며 sy-subrc와 gv_msg, 운영 로그가 어떻게 갈리는지 확인해 보라.

흔한 실수와 점검 🚧

  • 를 로컬 함수처럼 → 원격은 대상 시스템 상태·네트워크·로그온·권한의 영향을 받는다. 실패 지점이 다르면 설계도 달라야 한다.
  • RFC 함수 안에 대화형 처리 → popup·CALL SCREEN·WRITE 출력은 원격 호출자에게 무의미하거나 장애가 된다. 입력/출력 로만 말하게 설계한다.
  • 를 OTHERS 하나로 → communication_failure(인프라부터 본다)와 system_failure(대상 시스템 덤프부터 본다)는 운영 대응이 다르다. 뭉개면 분석이 늦어진다.
  • 권한·감사 로그 생략 → RFC 사용자 권한이 과하면 보안 사고, 부족하면 운영 장애. 누가 어떤 destination으로 뭘 불렀는지 추적 가능해야 한다.

정리 📌

  • = 시스템 간 원격 함수 호출. 함수는 SE37에서 Remote-Enabled로, 연결은 SM59 Destination으로.
  • 문법의 핵심은 CALL FUNCTION ... DESTINATION + RFC 2종 + MESSAGE gv_msg.
  • 설계의 핵심은 연결·계약·예외·권한·로그. 원격 실패 메시지를 남기는 코드가 좋은 RFC 코드다.

표준 API도 RFC도 있으면 좋다. 그런데 API가 아예 없고 화면만 있는 오래된 은? 화면 입력을 자동화하는 레거시 수단, BDC로 간다.
