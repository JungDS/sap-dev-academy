🛡️ 운영팀의 Quality Gate

정훈영의 최종 요청이다. "파트너에서 들어오는 텍스트를 등록 전에 한 번 거르는 품질 게이트를 만들어 주세요. 통과/반려만 말고, 뭐가 왜 걸렸는지까지요."

검사 대상은 세 종류다.

대상 요구 사용 부품 레슨
운영 로그 오류 코드 E***를 전부 찾아 위치 표시 FIND ALL ... RESULTS L03
이메일 이메일처럼 보이는지 1차 검증 matches( pcre ) L07
코드 텍스트 obsolete 명령 SEARCH 사용 적발 FIND PCRE + \b L01·L03

설계 — 패턴·입력·결과·피드백의 분리

DATA(gv_log) =
  `E100 booking failed, W210 retry scheduled, E404 concert missing`.

FIND ALL OCCURRENCES OF PCRE `E\d{3}`
     IN gv_log
     RESULTS DATA(gt_error).

LOOP AT gt_error INTO DATA(gs_error).
  APPEND VALUE #(
    category = `LOG`
    input    = substring( val = gv_log
                          off = gs_error-offset
                          len = gs_error-length )
    ok       = abap_false
    message  = |오류 코드 발견 (offset { gs_error-offset })|
  ) TO gt_result.
ENDLOOP.

오류 코드는 "발견 = 반려 신호"이므로 ok = abap_false로 적재한다. offset을 메시지에 남겨 두면 원문 어디를 보라는 안내가 된다.

DATA(gv_email)   = `hunyoung@example.com`.
DATA(gv_pattern) = `[\w.+-]+@[\w.-]+\.[A-Za-z]{2,}`.

APPEND VALUE #(
  category = `EMAIL`
  input    = gv_email
  ok       = xsdbool( matches( val = gv_email pcre = gv_pattern ) )
  message  = COND #( WHEN matches( val = gv_email pcre = gv_pattern ) = abap_true
                     THEN `이메일 1차 형식 통과`
                     ELSE `이메일 형식 아님` )
) TO gt_result.

패턴을 gv_pattern 변수로 분리한 것에 주목하라. L07의 습관이다. 그리고 이건 여전히 1차 검사다. 게이트의 역할은 "명백히 이상한 것 거르기"지 국제 표준 검증기가 아니다.

검사 ③ obsolete 명령 적발 — word boundary

DATA(gv_code) = `SEARCH gv_text FOR 'ABAP'.`.

FIND PCRE `\bSEARCH\b`
     IN gv_code
     IGNORING CASE
     MATCH OFFSET DATA(gv_offset).

IF sy-subrc = 0.
  APPEND VALUE #(
    category = `CODE`
    input    = gv_code
    ok       = abap_false
    message  = |obsolete 명령 SEARCH (offset { gv_offset }) — FIND로 교체|
  ) TO gt_result.
ENDIF.

새 얼굴 \b는 word boundary(단어 경계: 단어 문자와 비단어 문자의 사이 지점)다. 이게 없으면 RESEARCH 안의 SEARCH까지 잡는 오탐이 난다. IGNORING CASE는 search라고 소문자로 써도 잡기 위해서다.

흔한 실수와 점검 🚧

  • 정규식 만능주의 — 로그 검사는 파서가 아니다. 필드가 구조화될 수 있으면 구조가 먼저고, 정규식은 텍스트로만 올 때의 차선이다.
  • 완벽한 이메일 정규식 추구 — 끝이 없는 길이다. 게이트의 요구 수준을 먼저 정한다.
  • 사용자 입력을 패턴으로 그대로 실행 — 빈 패턴 ·CX_SY_REGEX_TOO_COMPLEX· 성능 문제의 입구다. 패턴은 개발자가 관리하는 목록에서만.
  • 성공 케이스만 시연 — 검사기의 가치는 반려 사유 안내에 있다. 실패 피드백이 없는 게이트는 절반짜리다.

정리 📌

  • 검증기의 뼈대 = 패턴·입력·결과·피드백의 분리. 결과는 ts_check 같은 행 타입으로.
  • 도구 선택 복습: 전부 찾아 표로 = RESULTS · 전체 형식 판정 = matches · 단어 단위 적발 = \b + IGNORING CASE.
  • 정규식은 강력하지만 읽기 어려운 도구다. 좋은 코드는 "짧은 패턴 한 줄"이 아니라 패턴 이름·테스트 케이스·실패 피드백이 함께 있는 코드다.
