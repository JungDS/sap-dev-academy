SELECT carrid connid FROM sflight          " ① 운항편을 읽고
  INTO CORRESPONDING FIELDS OF TABLE gt_flight.

SELECT carrid carrname FROM scarr          " ② 항공사를 또 읽고
  INTO CORRESPONDING FIELDS OF TABLE gt_carr.

LOOP AT gt_flight INTO gs_flight.          " ③ 한 줄씩 손으로 맞춘다
  READ TABLE gt_carr INTO gs_carr
       WITH KEY carrid = gs_flight-carrid.
  " 여기서야 gs_carr-carrname을 꺼내 쓸 수 있다
ENDLOOP.

SELECT를 두 번 쓰고, 그릇을 네 개 만들고, 루프에서 짝을 직접 찾았다. 얻은 건 "운항편 옆 항공사 이름" 하나뿐인데 코드는 세 배가 됐다. 게다가 운항편이 1만 건이면 READ TABLE도 1만 번 돈다. 이런 짝짓기는 원래 DB가 훨씬 잘하는 일이다. DB에게 키로 합쳐 달라고 부탁하면 위 코드가 SELECT 한 문장으로 줄어든다. 이것이 이다.

carrid가 같은 행끼리 옆으로 이어 붙인다. 그래서 운항편 줄 옆에 항공사명이 따라온다. 왼쪽 맨 아래 ZZ 운항편처럼 짝이 없는 줄은 결과에서 통째로 빠진다. 이 성질이 바로 다음 절에서 볼 의 핵심이다.

이 챕터의 SQL은 전부 classic 표기다. 읽을 필드는 콤마 없이 공백으로 나열하고, 별칭~필드처럼 ~로 잇는다. 요즘 SAP 코드에서 자주 보이는 @는 "이 자리는 DB 필드가 아니라 ABAP 변수다"를 표시하는 modern Open SQL 기호인데 classic에서는 쓰지 않는다. modern 표기는 Chapter 19 · Modern Open SQL에서 정식으로 배우니 지금은 "저런 게 따로 있구나" 정도만 알아 두자.

TYPES: BEGIN OF ts_out,
         carrid   TYPE sflight-carrid,
         connid   TYPE sflight-connid,
         carrname TYPE scarr-carrname,
       END OF ts_out.

DATA gt_out TYPE TABLE OF ts_out.   " JOIN 결과를 담을 그릇

SELECT f~carrid f~connid s~carrname
  FROM sflight AS f
  INNER JOIN scarr AS s
    ON f~carrid = s~carrid
  INTO CORRESPONDING FIELDS OF TABLE gt_out
  WHERE f~seatsocc > 0.
  • 결과 그릇은 읽어 올 필드만 모아 직접 만든다. 결과는 두 테이블에서 골라 온 조합이라 sflight에도 scarr에도 그대로 맞는 모양이 없기 때문이다.
  • AS f, AS s — 테이블 별칭(긴 테이블 이름 대신 쓸 짧은 이름표).
  • f~carrid — 별칭~필드 형태. 어느 테이블의 필드인지 가리키는 classic 구분자가 ~다.
  • ON ... = ... — 두 테이블을 합치는 키 조건.
  • 은 양쪽에 다 매칭되는 행만 결과에 남긴다.

💡 받는 방법은 둘이다. INTO CORRESPONDING FIELDS OF TABLE은 이름이 같은 필드끼리 맞춰 담고, INTO TABLE은 적은 순서대로 담는다(Chapter 08 · INTO 대상 형태). 여러 테이블 필드가 섞이는 JOIN 결과는 이름으로 맞추는 쪽이 헷갈릴 일이 적어 이 챕터도 주로 이 형태를 쓴다.

다만 이름 맞추기에는 함정이 하나 있다. 철자가 어긋나거나 별칭을 바꾸다 이름이 달라지면 그 필드만 조용히 초기값(0·공백)으로 남는다. 오류도 경고도 뜨지 않는다. 결과에 유독 한 필드만 비어 있다면 문법보다 양쪽 이름이 정말 같은지를 먼저 확인하자.

결과 확인 — sy-subrc와 sy-dbcnt

을 실행하면 "성공했나"만 보지 말고 왜 이 행 수인가를 설명할 수 있어야 한다. 시스템 필드 두 개가 그 실마리다.

  • sy-subrc — 결과가 한 행이라도 있으면 0, 한 행도 없으면 4.
  • sy-dbcnt — 실제로 담긴 행 수.

행 수가 예상과 다르면 대개 ON 조건 때문이다. 이 결과는 INNER JOIN이라 양쪽에 짝이 있는 행만 남은 수라는 점을 기억하고 세어 보자.

아래에서 운항편·항공사 카드를 ON 조건으로 짝지어 보고, 짝이 없는 운항편이 INNER JOIN에서 어떻게 빠지는지(항공사를 숨겨 가며) 확인해 보자.

ON에는 짝이 확정될 만큼 적는다

ON에는 오른쪽 행 하나가 딱 정해질 만큼 키를 적는 게 기본이다. 항공사는 키가 carrid 하나뿐이라 ON f~carrid = s~carrid 한 줄로 끝난다.

여기서 잠깐 소재를 바꿔 보자. Chapter 09 · 콘서트 모델 만들기에서 직접 만든 공연·회차·예매 테이블이다. 회차 zperf는 키가 concert_id와 perf_no 둘이라 ON도 두 줄이 된다.

" 발췌 — 예매(zbooking AS b)와 회차(zperf AS pf)를 잇는 ON 부분만 떼어 왔다
  ON  b~concert_id = pf~concert_id
  AND b~perf_no    = pf~perf_no      " 키가 둘이면 AND로 둘 다
  • 키를 덜 적으면 짝이 벌어진다. 위에서 perf_no 줄을 빼면 예매 한 건이 그 공연의 모든 회차와 각각 짝지어져, 결과 행이 회차 수만큼 불어난다. 원치 않은 중복이다.
  • 그렇다고 행이 늘어난 것 자체를 오류로 볼 일은 아니다. 공연 하나에 예매가 열 건 달려 있으면 공연을 기준으로 봤을 때 열 줄이 나오는 게 정상이다. 데이터가 원래 여러 건이라 늘어난 것인지, ON이 헐거워 같은 건이 반복된 것인지를 구분하면 된다. 헷갈리면 ON에 적은 키만으로 오른쪽 행 하나가 정해지는지 되짚어 보자.

흔한 실수와 점검

  • ON을 통째로 빼먹기 → 활성화가 안 된다. classic Open SQL의 은 ON 조건을 문법적으로 반드시 요구해서, 조건 없는 JOIN은 실행 전에 구문 오류로 막힌다. 참고로 두 표의 모든 행을 서로 한 번씩 짝지은 조합 전체를 (Cartesian product)이라 부른다. 100행과 100행이면 1만 행이다. 실무에서 만나는 행 폭증은 ON을 안 써서가 아니라, 바로 앞 절처럼 ON에 키를 덜 적어 생기는 쪽이 대부분이다.
  • 별칭 없이 같은 이름 필드 쓰기 → 두 테이블 모두에 carrid가 있으면 DB는 어느 쪽을 말하는지 알 수 없다. f~·s~처럼 별칭을 붙여 가리키자.
  • 콤마·@ 섞어 쓰기 → classic 표기를 벗어난다. 필드는 공백으로 나열하고 @는 붙이지 않는다.

INNER는 양쪽 다 있어야 남는다. 한쪽만 있어도 살리려면? → LEFT OUTER JOIN(다음 레슨).
