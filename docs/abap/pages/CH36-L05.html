CDS Table Function과 AMDP Function

AMDP 함수의 결과를 CDS 뷰처럼 읽는 다리를 잇는다.

Track 3Chapter 36Lesson 5고급

프로시저의 결과를 뷰의 세계로

CH36-L02의 AMDP 프로시저는 ABAP에서 처럼 호출했다. 그런데 Chapter 23에서 만든 CDS의 세계가 있다. 뷰 위에 뷰를 쌓고, OData와 RAP이 그 뷰를 소비한다. SQLScript로 계산한 결과를 그 뷰의 세계에서 데이터 소스처럼 읽고 싶다면?

그 다리가 (AMDP 함수로 구현되고, CDS 엔티티처럼 SELECT되는 테이블 함수)이다. AMDP에는 프로시저만 있는 게 아니다.

구분 핵심 구문 소비하는 방법
AMDP Procedure (L02) BY DATABASE PROCEDURE ABAP에서 메서드 호출 · EXPORTING 여러 벌 가능
AMDP Function BY DATABASE FUNCTION 직접 호출 불가 — DB에 '함수'로 생성되어 SQL 문장 안에서만 평가된다
CDS Table Function DEFINE TABLE FUNCTION … implemented by method SELECT의 데이터 소스 · RETURN 한 벌

판별 문장으로 기억하자. 결과를 ABAP 프로그램 하나가 받으면 프로시저, SELECT·뷰의 세계가 소비해야 하면 함수 + Table Function이다. 직접 호출이 안 되는 이유도 이 그림에 있다: 함수를 부르는 주체는 ABAP 런타임이 아니라 SQL을 실행하는 DB 엔진이다. 그래서 구현 메서드가 static 필수인 것도 자연스럽다 — DB 엔진이 평가하는 함수에는 ABAP 라는 문맥이 존재하지 않는다.

세 조각을 잇는다 — DDL, 클래스, 소비

조각 1 · CDS DDL — 함수의 얼굴. 와 반환 구조를 선언하고, 구현 를 지정한다.

@EndUserText.label: '공연별 예매 집계 Table Function'
// 학습 예제라 접근 제어(DCL) 생략 선언
@AccessControl.authorizationCheck: #NOT_REQUIRED
define table function ZTF_BOOKING_STAT
  with parameters
    p_client  : abap.clnt,
    p_from    : abap.dats,
    p_to      : abap.dats
  returns
  {
    client      : abap.clnt;
    concert_id  : abap.char(10);
    booking_cnt : abap.int4;
    total_seats : abap.int4;
  }
  implemented by method
    zcl_booking_tf=>get_stat;

이 DDL에는 Chapter 23에서 못 본 표기가 세 가지 있다. 처음 보는 게 맞으니 기억을 의심하지 말자.

  • with parameters — CDS 엔티티도 파라미터를 받을 수 있다. CH23의 뷰들은 파라미터가 없었지만, Table Function은 파라미터가 흔하다. (이름의 p_는 CDS 쪽에서 흔한 관례로, 선택화면의 pa_와는 무관한 자유 명명이다.)
  • abap.clnt·abap.dats·abap.char(10) — CDS 안에서 ABAP 내장 타입을 직접 지정하는 표기다(Data Element 대신 쓰는 abap.타입 형식).
  • implemented by method — 이 계약을 구현할 AMDP =>메서드를 지정한다.

조각 2 · AMDP 클래스 — 함수의 몸. 선언은 FOR TABLE FUNCTION으로 DDL과 잇고(이 구현 메서드는 static이 필수라 CLASS-METHODS다), 구현은 BY DATABASE FUNCTION이다.

CLASS zcl_booking_tf DEFINITION
  PUBLIC FINAL CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES if_amdp_marker_hdb.

    " 파라미터·반환 구조는 DDL이 정한다 — 여기선 연결 선언만
    CLASS-METHODS get_stat
      FOR TABLE FUNCTION ztf_booking_stat.
ENDCLASS.

CLASS zcl_booking_tf IMPLEMENTATION.
  METHOD get_stat BY DATABASE FUNCTION   " PROCEDURE가 아니라 FUNCTION
                  FOR HDB
                  LANGUAGE SQLSCRIPT
                  OPTIONS READ-ONLY
                  USING zbooking.

    -- 함수이므로 결과를 RETURN으로 돌려준다 (created_on = 예매 생성일)
    RETURN
      SELECT mandt AS client,
             concert_id,
             COUNT(*)     AS booking_cnt,
             SUM( seats ) AS total_seats
        FROM zbooking
       WHERE mandt = :p_client
         AND created_on BETWEEN :p_from AND :p_to
       GROUP BY mandt, concert_id;

  ENDMETHOD.
ENDCLASS.

(이 구현부는 구조를 읽기 위한 최소형이다. 이 정도 는 파라미터 있는 일반 CDS 뷰로도 표현할 수 있다. Table Function이 필수가 되는 순간은 몸이 L02의 체이닝 같은 SQLScript 절차일 때다 — 그 결과를 뷰의 세계가 소비해야 하니까.)

" 테이블 이름 자리에 괄호를 열고 파라미터를 넘긴다 — 파라미터 있는
" CDS 엔티티를 읽는 문법이다
SELECT FROM ztf_booking_stat(
              p_client = @sy-mandt,
              p_from   = @gv_from,
              p_to     = @gv_to )
  FIELDS concert_id, booking_cnt, total_seats
  INTO TABLE @DATA(gt_stat).

핵심 그림은 이것이다. 클래스 메서드를 직접 호출하는 구조가 아니다. CDS Table Function이라는 엔티티를 SELECT하면, 그 뒤에서 AMDP 함수가 DB 안에서 돈다.

"Open SQL은 client를 자동으로 챙긴다더니 왜 파라미터로 넘기나?" 좋은 질문이다. 자동 처리는 읽는 대상이 client 처리를 스스로 선언한 경우의 이야기다. 이 예제의 Table Function은 그 선언(client 처리 어노테이션 계열 — 이 과정 범위 밖) 없이 만든 형태라서, L02와 같은 원칙으로 파라미터를 받아 직접 거른다.

어떤 순서로 만드는가

서로 참조하는 두 라 순서가 헷갈리기 쉽다. 공식 규칙이 기준을 준다: FOR TABLE FUNCTION 선언은 DDL로 정의된 Table Function을 전제로 한다.

  1. DDL부터 작성 — ADT에서 CDS 정의(Data Definition — CH23에서 뷰 만들던 그 종류)로 define table function을 작성한다. 이 시점엔 구현 가 아직 없어 경고가 보여도 정상이다.
  2. AMDP 클래스 작성 — FOR TABLE FUNCTION ztf_… 선언과 BY DATABASE FUNCTION 구현을 채운다.
  3. 활성화 — 두 객체가 다 있으니 이제 활성화가 통과한다(중간 상태의 빨간 줄에 놀라지 말 것).
  4. 확인 — 를 넣은 SELECT를 테스트 리포트에서 돌려 결과를 본다(ADT의 미리보기 기능 지원 여부는 시스템에서 확인).

연결을 눈으로 잇기

세 조각(DDL··소비)이 어떻게 연결되는지 단계 버튼으로 이어 보라. 마지막 client 점검까지.

어떻게 확인하는가

  1. DDL — define table function에 ·returns가 있고 implemented by method 클래스=>메서드가 연결돼 있는가.
  2. 선언 — IF_AMDP_MARKER_HDB + CLASS-METHODS … FOR TABLE FUNCTION … (PUBLIC SECTION에)인가.
  3. 구현 — BY DATABASE FUNCTION FOR HDB LANGUAGE SQLSCRIPT + USING인가. 반환 구조가 DDL의 returns와 일치하는가.
  4. client — L02와 같은 원칙이다. client 파라미터를 받아 WHERE mandt로 직접 제한했는가. (returns의 client 열을 시스템이 자동으로 걸러 주는 어노테이션 계열도 있지만 이 과정 범위 밖이다 — 여기서는 파라미터로 직접 거른다.)
  5. 소비 위치 — "를 부른다"가 아니라 "SELECT FROM ztf_…로 읽는다"로 기억하는가.

흔한 실수와 점검 🚧

  • 프로시저와 함수를 동일시 → 프로시저는 처럼 호출하고, 테이블 함수는 CDS 엔티티로 SELECT한다. 소비 경로가 다르다.
  • FOR TABLE FUNCTION 선언 누락 → DDL과 가 연결되지 않아 활성화가 실패한다.
  • returns와 결과 구조 불일치 → DDL이 약속한 컬럼과 SQLScript 결과가 어긋나면 깨진다. DDL이 계약서다.
  • client 방심 → 함수여도 AMDP다. 자동 client는 없다.
  • "Table Function이 CDS View보다 항상 낫다" → 반대다. 일반 View Entity로 표현 가능하면 View가 먼저다. Table Function은 SQLScript 계산이 꼭 필요할 때의 다리다.

정리 📌

  • AMDP의 나머지 반쪽 = AMDP Function(BY DATABASE FUNCTION). 직접 호출하지 않고 을 통해 SELECT된다.
  • 세 조각: DDL(계약) → (FOR TABLE FUNCTION + 구현) → 소비(SELECT FROM ztf_…).
  • 원칙은 그대로다: client 직접, USING 선언, View로 충분하면 View 먼저.

이 챕터의 도구는 다 모였다. 마지막 질문이 남는다. 이 강한 도구들을 운영에 들일 때 무엇을 책임져야 하는가.
