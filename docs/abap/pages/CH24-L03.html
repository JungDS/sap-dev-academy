Projection View ZC_* 설계

서비스·화면에 노출할 소비용 뷰 — transactional projection.

Track 2Chapter 24Lesson 3고급

왜 root를 그대로 노출하지 않을까

Interface View ZI_* 설계 (Root)에서 만든 root view를 그대로 외부에 노출하면 안 되는 경우가 많다. 기반 모델은 내부 안정성을 위해 존재하고, 외부 소비자는 화면·API 목적에 맞춘 모델을 원한다.

내부 감사 필드(audit — 누가 언제 만들고 고쳤는지 추적하는 이력 필드)를 숨기고 싶을 때가 있다. UI annotation을 따로 두고 싶을 때도 있고, RAP transactional service에서 쓸 projection 계약을 명확히 하고 싶을 때도 있다. Interface View와 Consumption View 계층에서 배운 ZI_/ZC_ 분리를, 이제 RAP 트랜잭션 모델에 맞게 적용한다.

무엇인가 — transactional projection

RAP의 는 root entity를 소비자에게 노출하기 위한 CDS projection view다. CH23의 읽기 전용 소비 뷰와 달리, 를 붙여 트랜잭션 BO에 소속시킨다. 이 레슨에서 Projection View와 transactional projection은 같은 것을 가리킨다 — 문서에 따라 두 이름이 섞여 나올 뿐이다.

@AccessControl.authorizationCheck: #NOT_REQUIRED
@Metadata.allowExtensions: true
define root view entity ZC_Booking
  provider contract transactional_query
  as projection on ZI_Booking
{
  key booking_id,
      concert_id,
      perf_no,
      customer,
      seats,
      status
}

핵심은 세 가지다.

코드 뜻
define root view entity ZC_Booking 기반 ZI_Booking이 root이므로 projection도 root 위치를 반영한다.
provider contract transactional_query 이 projection의 용도를 시스템에 약속하는 계약이다. 값 transactional_query는 "RAP 트랜잭션 BO의 조회·쓰기 창구로 쓰인다"는 시나리오 이름이다.
as projection on ZI_Booking 기반 root view를 외부 소비 목적에 맞게 투영한다.

transactional projection은 RAP BO의 projection 계층을 맡는다. 조건이 하나 있다 — 이 projection은 어떤 BO에 소속되어야 하고, 그 BO의 root(또는 root 아래 매달린 하위 entity)를 투영해야 한다. entity 여러 개가 root 아래 매달린 구조를 composition tree(root를 뿌리로 entity가 가지처럼 이어진 나무)라 부르는데, 우리는 root ZI_Booking 하나뿐인 가장 단순한 나무라 이 조건이 저절로 충족된다.

직접 검사해 보기

아래에서 provider contract를 넣고 빼 보고, projection이 root 위치를 맞추는지, 어떤 필드를 외부에 노출할지 정해 보자. 감사 필드를 숨겨도 기반에는 그대로 남는다는 점을 payload preview로 확인하자.

어떻게 확인하는가

  1. 활성화 — provider contract transactional_query 위치, as projection on ZI_Booking, 필드 목록이 올바른지 본다.
  2. root 위치 일치 — ZI_Booking이 root인데 ZC_Booking이 root가 아니면 투영한 나무(projection tree)에서 자리가 어긋난다. "기반이 root면 소비 projection도 root로 맞춘다"로 기억한다.
  3. 필드 노출 — ZC_Booking은 외부 소비 모델이므로 어떤 필드를 보여 줄지 의도적으로 결정한다. 내부 감사 필드는 이 projection에서 뺄 수 있다.
  4. Metadata Extension 계획 — DDLX를 붙일 거면 @Metadata.allowExtensions: true가 있는지 본다(Metadata Extension 기초).

흔한 실수와 점검 🚧

  • 를 장식처럼 → transactional projection에서는 어떤 runtime 시나리오용인지 계약을 드러낸다. contract가 없으면 활성화 때 "이 시나리오에 맞게 짜였는지" 검사를 받지 못한다.
  • ZI_Booking을 서비스에 직접 expose → 작은 실습에서는 동작하는 것처럼 보여도, 실무에서는 소비 계층 ZC_*를 따로 두는 편이 변경에 강하다.
  • 모든 내부 필드를 무조건 올리기 → projection은 소비 계약이다. 외부에 보여 줄 필요 없는 필드는 숨긴다.
  • CDS 계층 분리와 transactional projection을 동일시 → Interface View와 Consumption View 계층에서 배운 건 계약 없이 뷰를 쌓는 읽기 전용 소비 계층(nesting)이다. 여기서는 그 위에 provider contract를 붙여 RAP transactional BO에 소속시키는 를 배운다 — 계약이 있고 없고가 갈림길이다.

노출 모델까지 만들었다. 이제 사용자가 무엇을 할 수 있는지(생성·수정·삭제·검증)를 선언하는 Behavior Definition → Behavior Definition 기초.
