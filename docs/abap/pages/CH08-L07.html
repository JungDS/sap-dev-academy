조회 실패와 MESSAGE (기초)

결과가 없을 수도 있다

조회가 늘 성공하는 것은 아니다. 우리 ZGUGUDAN에는 2·3단만 넣었으니 5단을 조회하면 한 건도 안 나온다. 이때 빈 화면만 두면 사용자는 영문을 모른다. 알려 줘야 한다.

DATA gt_gugu TYPE TABLE OF zgugudan.
DATA gs_line TYPE zgugudan.

SELECT * FROM zgugudan INTO TABLE gt_gugu
  WHERE dan = 5.

IF sy-subrc <> 0.
  WRITE: / '5단 데이터가 없습니다.'.
ELSE.
  LOOP AT gt_gugu INTO gs_line.
    WRITE: / gs_line-dan, 'x', gs_line-mul, '=', gs_line-result.
  ENDLOOP.
ENDIF.

LOOP AT … INTO …는 Chapter 06 · LOOP에서 쓰던 그 순회 문장이다. 우리가 APPEND로 채운 Internal Table이든 DB에서 읽어 온 Internal Table이든 다루는 법은 똑같다.

MESSAGE — 사용자에게 알리기 (맛보기)

WRITE로 화면에 찍는 것보다, MESSAGE로 알림을 띄우는 게 더 적절할 때가 많다.

ABAP
1
2
3
IF sy-subrc <> 0.
  MESSAGE '해당 단의 데이터가 없습니다.' TYPE 'S'.   " S = 상태바 알림
ENDIF.
  • TYPE 'S'(Status, 상태바)·TYPE 'I'(Information, 팝업)가 가벼운 알림이다.
  • 여기선 맛보기만. 메시지 타입 전체(I/S/W/E/A/X)와 메시지 클래스는 Chapter 15 · MESSAGE에서 정식으로 배운다.

dan을 바꿔 조회하고(2·3=있음, 5=없음), 실패했을 때 세 가지 피드백이 화면에서 어떻게 다른지 직접 확인해 보자.

흔한 실수와 점검

  • 결과 미확인 진행 → 없을 때 다르게 처리해야 하는 흐름이라면 sy-subrc로 분기한다. 판단 기준은 "없을 때 사용자에게 알려야 하나, 다음 로직이 값이 있다고 전제하나"다. 빈 테이블을 그냥 LOOP로 돌리는 경우처럼 없어도 자연스럽게 지나가는 흐름이라면 굳이 분기를 만들지 않아도 된다.
  • SINGLE 실패 후 Work Area 신뢰 → SELECT SINGLE이 실패(sy-subrc <> 0)해도 gs_에는 직전 값이 남아 있을 수 있다. 값을 쓰기 전에 sy-subrc부터 확인한다.
  • 모든 걸 E로 → 단순 "없음"은 S/I가 적절. E(오류)는 흐름을 막는다(Chapter 15 · MESSAGE).

여기까지가 읽기 기초의 완성이다. 돌아보면 값을 담는 그릇이 한 단계씩 커져 왔다. 변수 하나에서 시작해(Chapter 02 · 변수 선언), 관련된 값을 Structure로 묶고 (Chapter 05 · Local Structure), 같은 모양의 행을 Internal Table에 쌓고 (Chapter 06 · 구구단 캡스톤), 그것을 DB 테이블에 영구 저장했다 (Chapter 07 · Transparent Table). 그리고 이번 챕터에서 마침내 그 저장한 값을 다시 읽어 왔다.

그런데 방금 읽어 온 그 값은 우리가 SE11 화면에서 손으로 한 자씩 쳐 넣은 것이다. 그때 DAN에 엉뚱한 숫자를 넣어도 시스템은 아무 말이 없었고, 없는 값이 그대로 저장됐다. 읽기가 아무리 정확해도 애초에 잘못 들어간 값은 잘못된 채로 나온다. 입력하는 순간에 막을 수는 없을까. 있는 값 중에서만 고르게 하고, 무엇이 있는지 목록으로 띄워 주면 된다. 그 입력 도움말 목록이 F4(입력칸에서 F4를 누르면 뜨는 선택 목록)이고, 그것을 가능하게 하는 DDIC 관계가 Foreign Key다 → Chapter 09 · Foreign Key와 Check Table.

여기서부터는 소재도 바뀐다. 구구단으로 문법을, SFLIGHT로 읽기를 익혔으니, 다음 챕터부터는 이 과정을 관통하는 콘서트 예매 앱을 직접 만들어 나간다.
