PDF가 기본인 세상의 양식

Smart Forms로도 인쇄 양식은 만든다. 그런데 요즘 요구는 다르다. 고객은 이메일로 PDF 확인서를 받고, 법적 양식은 PDF 모양이 정확해야 하며, 어떤 문서는 사용자가 입력까지 하는 interactive form(PDF 안에 입력 칸이 있어 사용자가 값을 써서 되돌려 보내는 양식. 이 과정에서는 존재만 알아 둔다)이다. 이 자리의 도구가 (SFP에서 다루는 PDF 기반 양식 도구)다.

참고로 SAP이 PDF를 직접 그리지 않고 Adobe 기술을 쓰는 것은, PDF가 Adobe에서 태어난 형식이고(지금은 ISO 개방 표준) 렌더링 품질·디자인 도구를 Adobe와의 협력으로 해결했기 때문이다. 그래서 그리는 일은 Adobe 엔진(아래의 )이 맡는다. 한 가지 현실 정보: 단순 출력용 PDF는 기본 사용권으로 되지만, 입력 가능한 interactive form은 별도 라이선스가 필요하다. "그냥 입력형으로 하죠"가 라이선스에서 막히는 일이 실무에 흔하다.

도구가 하나 더 생기는 게 아니라 역할이 갈리는 것이다: 기존 Smart Forms 자산은 유지보수로 계속 만나고, PDF 품질·interactive가 중요한 신규는 Adobe Forms를 검토한다. "옛것/새것"의 단순 서열이 아니다.

구조 — 세 층 + 렌더링 인프라

가 어려워 보이는 이유는 층이 셋으로 나뉘기 때문이다. 반대로 말하면, 이 셋을 구분하는 순간 문제 추적이 쉬워진다.

구성 쉬운 설명 문제가 생기면 볼 것
Interface ABAP → 양식 데이터 계약(Smart Forms의 Form Interface 격) 이름·타입
Context Interface 값 중 레이아웃에 넘길 재료 목록 필요한 필드가 포함됐는가
Layout 실제 PDF 디자인(Adobe 디자이너로 편집) 필드 binding·페이지 넘김
Adobe Document Services. PDF를 실제로 그려 주는 렌더링 서버 연결·구성·로그

왜 Interface와 Context를 굳이 둘로 나눌까. 하나의 Interface를 여러 Form이 재사용할 수 있게 하고, Form마다 필요한 재료만 골라 담기 위해서다(같은 예매 계약으로 확인서 Form과 영수증 Form을 따로 만들 수 있다). 그 대가로 단계가 하나 늘었다: Interface에 필드를 만들었다고 PDF에 바로 보이지 않는다. Context에 담고, Layout 필드에 binding까지 되어야 값이 찍힌다. 그리고 셋이 다 맞아도 ADS가 구성돼 있지 않으면 PDF 자체가 안 만들어진다. "코드만 맞으면 끝"인 주제가 아닌 이유다. 정리하면 구조는 세 층(Interface·Context·Layout)이고, 문제를 추적할 때는 ADS까지 네 번째 신호등으로 함께 본다.

어떻게 만드는가 — 도구에서 네 걸음

L01의 다섯 걸음처럼, 만드는 순서부터 잡자. 는 Interface와 Form이 별개 오브젝트라 순서가 중요하다.

  1. Interface 생성 — SFP 초기화면에서 Interface를 선택해 먼저 만든다 (ZAFI_TICKET 등). 예매 데이터를 Import (IS_BOOKING, 타입 ZBOOKING)로 선언한다. L01의 Form Interface와 같은 역할, 별도 오브젝트라는 점만 다르다.
  2. Form 생성 — 다시 SFP에서 Form(ZAF_TICKET)을 만들면서 1의 Interface를 지정한다. 이 연결이 있어야 다음 걸음이 가능하다.
  3. Context 구성 — Form 편집 화면에서 Interface의 필드 중 레이아웃에 쓸 것을 Context로 끌어다 담는다. 여기 안 담긴 필드는 4에서 아예 보이지 않는다.
  4. Layout 작성·활성화 — Layout 탭에서 디자이너로 PDF 모양을 만들고, Context 필드를 화면 필드에 binding(끌어다 연결)한 뒤 활성화한다.

🔭 기대 관리 — Layout을 편집하는 디자이너(Adobe LiveCycle Designer)는 SAP 화면이 아니라 개발자 PC에 깔려 있어야 하는 Adobe 도구다(보통 SAP GUI 설치 시 선택 로 함께 설치한다). Layout 탭을 눌렀는데 아무것도 안 열리면 코드 잘못이 아니라 설치 문제부터 의심하라. 화면 세부는 실습 시스템에서 확인하고, 구성은 개발자가 아니라 Basis 영역이다.

어떻게 부르는가 — 열고, 찾고, 부르고, 닫는다

호출 흐름은 네 박자다(SAP Help의 표준 순서): FP_JOB_OPEN → 생성 함수 이름 조회(FP_FUNCTION_MODULE_NAME) → 생성 함수 호출 → FP_JOB_CLOSE. L01과 같은 "이름 조회 후 동적 호출" 원리에, 출력 작업(job)의 여닫기가 감싸진 모양이다. 왜 여닫는 틀이 필요한가: 확인서 100장을 뽑을 때 한 장마다 따로 처리하지 않고 하나의 출력 작업으로 묶기 위한 구조다(OPEN과 CLOSE 사이에서 생성 함수를 여러 번 부를 수 있다). 한 장만 뽑아도 틀은 같다.

REPORT z_ticket_pdf.

DATA gs_booking TYPE zbooking.
DATA gv_fm      TYPE funcname.         " L01의 rs38l_fnam과 역할 동일
DATA gs_out     TYPE sfpoutputparams.  " 출력 옵션(구조는 시스템 제공)
DATA gs_doc     TYPE sfpdocparams.     " 문서 옵션
DATA gs_formout TYPE fpformoutput.     " 결과(PDF 바이트 포함)

START-OF-SELECTION.
  SELECT SINGLE * FROM zbooking
    WHERE booking_id = '0001'
    INTO @gs_booking.

  " ① 출력 작업 열기 — PDF를 돌려받는 옵션으로
  gs_out-getpdf   = abap_true.     " 결과를 PDF 바이트로
  gs_out-nodialog = abap_true.     " 인쇄 대화상자 생략
  CALL FUNCTION 'FP_JOB_OPEN'
    CHANGING ie_outputparams = gs_out  " 시스템이 값을 보완해 돌려줘 CHANGING
    EXCEPTIONS OTHERS = 1.
  IF sy-subrc <> 0.
    MESSAGE '출력 작업을 열 수 없습니다' TYPE 'E'.
  ENDIF.

  " ② Form 이름 → 생성 함수 이름 조회 (L01과 같은 원리)
  CALL FUNCTION 'FP_FUNCTION_MODULE_NAME'
    EXPORTING i_name     = 'ZAF_TICKET'
    IMPORTING e_funcname = gv_fm
    EXCEPTIONS OTHERS = 1.
  IF sy-subrc <> 0.
    " 실패해도 ①에서 연 작업은 닫고 나간다 — 짝 규율은 오류 경로에도 적용
    CALL FUNCTION 'FP_JOB_CLOSE' EXCEPTIONS OTHERS = 1.
    MESSAGE '양식을 찾을 수 없습니다' TYPE 'E'.
  ENDIF.

  " ③ 생성 함수 호출 — 결과 구조에 PDF가 담겨 돌아온다
  gs_doc-langu = sy-langu.             " 문서 언어(최소 옵션)
  CALL FUNCTION gv_fm
    EXPORTING
      /bcdwb/docparams  = gs_doc
      is_booking         = gs_booking
    IMPORTING
      /bcdwb/formoutput = gs_formout   " ← gs_formout-pdf = PDF 바이트
    EXCEPTIONS OTHERS = 1.
  IF sy-subrc <> 0.
    CALL FUNCTION 'FP_JOB_CLOSE' EXCEPTIONS OTHERS = 1.
    MESSAGE 'PDF 생성에 실패했습니다' TYPE 'E'.
  ENDIF.

  " ④ 출력 작업 닫기 (①과 반드시 짝 — 성공 경로의 닫기)
  CALL FUNCTION 'FP_JOB_CLOSE'
    EXCEPTIONS OTHERS = 1.

낯선 조각 셋을 짚는다.

  • ie_outputparams가 왜 CHANGING인가 — 우리가 넣은 옵션에 시스템이 기본값·보완값을 채워 되돌려 주기 때문이다(주고 돌려받는 자리 = CHANGING, Chapter 10에서 배운 그대로). 접두어 ie_도 그 성격(in/out)을 담은 관례다.
  • 타입이 L01과 다르다? — L01의 rs38l_fnam도, 여기의 funcname도 "함수 모듈 이름"을 담는 타입이다. 각 조회 API가 요구하는 타입을 그대로 따랐을 뿐, 역할은 같다.
  • /1bcdwb/docparams처럼 슬래시로 시작하는 이름 — 오타가 아니다. 생성 함수는 SAP이 자동으로 만드는 산출물이라 이름에 SAP 전용 네임스페이스(/1BCDWB/…)가 붙는다(생성 함수 이름 /1BCDWB/SF…와 같은 접두어). 호출할 때 슬래시까지 그대로 쓰면 된다.

이 코드는 교육용 최소 흐름이다. 실제로는 국가·프린터·미리보기 같은 옵션이 더 붙고, sfpoutputparams 같은 시스템 제공 구조의 세부 필드는 실습 시스템의 ADT/SE11에서 확인한다. 지금 고정할 것은 네 박자 순서와 "PDF는 gs_formout-pdf로 돌아온다"는 사실이다.

한 가지 미리 알아 둘 것: 이 리포트는 nodialog·getpdf 옵션 때문에 실행해도 화면에 아무것도 안 뜬다. 를 돌려받았을 뿐이다. 성공을 눈으로 확인하는 방법은 두 가지다. 지금 바로 보고 싶으면 ①의 옵션 두 줄을 잠시 주석 처리하면 L01처럼 인쇄 대화상자가 떠서 미리보기로 확인할 수 있다(확인 후 반드시 되돌리자 — 뒤의 L04 파이프라인은 getpdf로 돌려받은 바이트가 있어야 돈다). 파일로 만들어 확인하는 정식 경로는 다음다음 레슨(L04)에서 잇는다.

가 내 시스템에 있는지 먼저 확인하자. 세 층을 다 맞춰도 ADS가 없으면 PDF는 안 나온다. 표준 점검 리포트 FP_PDF_TEST_00을 SE38로 실행하면 ADS 버전 정보가 표시된다(고전 구성에서 ADS는 별도 Java 서버라, 연결 통로인 RFC 대상 ADS가 등록돼 있어야 한다 — 존재만 알아 두자). 버전 대신 오류가 나오면 코드를 고칠 문제가 아니라 Basis에 문의할 문제다(문제 시 확인하는 "ADS 로그"도 Basis가 관리하는 서버 쪽 기록이다 — 개발자 쪽 1차 점검은 이 테스트 리포트까지). ADS가 없는 실습 환경이라면 이 레슨은 구조·호출 순서 이해로 읽고, 실습은 L01의 Smart Forms로 진행하면 된다.

Smart Forms와의 자리 구분도 눈으로 정리하자.

흔한 실수와 점검 🚧

  • "신규는 무조건 Adobe"라는 암기 → 판단 재료는 요구와 인프라다: PDF 품질· 이메일 첨부·interactive가 필요한가(→ Adobe), 인프라와 디자이너 도구·다룰 인력이 준비돼 있는가(없으면 도입 비용부터 든다), 기존 자산이 어느 쪽인가. 안정 운영 중인 단순 인쇄 양식은 Smart Forms 유지보수가 현실적일 수 있다.
  • Context 누락 → Interface에 필드를 만들고 Context에 안 담으면 Layout에서 쓸 수 없다. Interface → Context → binding 세 단계가 다 이어져야 한다.
  • ADS 오류를 데이터 오류로 착각 → 데이터·binding이 다 맞는데 렌더링이 실패하면 ADS 인프라 문제다. 양식 디자인과 렌더링 인프라를 분리해서 본다.
  • JOB_OPEN/CLOSE 짝 깨기 → 생성 함수 호출은 반드시 열고 닫는 사이에.

정리 📌

  • = PDF 중심 양식. Interface(계약) → Context(재료) → Layout(모양) 세 층 + (렌더링 서버).
  • 호출 네 박자 = OPEN → 이름 조회 → 생성 함수 호출 → CLOSE. PDF는 결과 구조의 -pdf로 돌아온다.
  • 값이 안 보이면 층 순서대로: ABAP 값 → Interface → Context → binding → ADS.

양식 두 개를 갖췄다. 그런데 예매가 확정될 때 이 양식이 자동으로 나가게 하려면 누가 결정하나. 출력 결정의 층, Output Control로 간다.
