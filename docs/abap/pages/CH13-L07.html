JOIN / FAE / ABAP 처리 선택 기준

셋 중 무엇을

여러 데이터를 합치는 길은 셋이다. DB의 , (FAE), 그리고 ABAP에서 읽어와 직접 맞추기. 상황별로 정리한다.

한눈에

방법 일을 누가 적합
DB 두 테이블을 키로 합쳐 한 번에 — 보통 1순위
FAE DB(1회 이상, 목록 크기·설정에 따라 나뉨) 이미 에 있는 목록 기준으로 조회
ABAP 루프 앱 서버 단순·소량, 또는 JOIN/FAE가 부적절할 때

원칙(직관)

  • 가능하면 — DB가 합치게 둔다(데이터 이동 최소).
  • 합칠 대상이 이미 Internal Table로 있으면 FAE(빈 테이블·중복 주의).
  • 루프 안에서 SELECT — 이 형태는 피한다. 성능을 무너뜨리는 대표적인 이다. 안티패턴은 "얼핏 자연스러워 보이지만 실제로는 문제를 만드는, 피해야 할 전형적인 코드 모양"을 말한다.

ABAP에서 직접 맞춘다면 — 두 가지 모양

같은 "ABAP에서 처리"라도 모양에 따라 결과가 하늘과 땅 차이다. 두 예제는 같은 그릇을 쓴다.

" ✅ 권장형 — 필요한 목록을 미리 한 번에 읽어 두고, 메모리에서 맞춘다
SELECT carrid carrname FROM scarr
  INTO CORRESPONDING FIELDS OF TABLE gt_carr.

LOOP AT gt_flight INTO gs_flight.
  READ TABLE gt_carr INTO gs_carr
       WITH KEY carrid = gs_flight-carrid.

위쪽은 운항편이 1만 건이면 DB에 1만 번 다녀온다. 아래쪽은 딱 두 번 읽고 나머지는 전부 에서 끝난다(Chapter 06 · 단일 행 제어에서 배운 READ TABLE이 그 역할이다). INNER JOIN 레슨 도입부에서 없이 해 본 코드가 바로 이 권장형이었다. 그러니 "ABAP 루프는 무조건 나쁘다"가 아니라, DB 왕복이 루프 안에 들어가 있느냐가 갈림길이다.

직접 골라 보기

상황마다 데이터가 어디 있고 질문이 무엇인지 먼저 묻고, 알맞은 도구로 분류해 보자.

흔한 실수와 점검

  • LOOP 안에 SELECT → 행마다 DB 왕복이다. 1만 건이면 1만 번 왕복한다. 목록 한 번에 더해 행마다 한 번씩 더 조회한다고 해서 N+1 문제라고도 부른다(다른 언어·프레임워크 에서도 같은 이름으로 통한다). 성능 문제는 보통 문법보다 이 왕복 횟수에서 시작하니, 이나 FAE로 바꾸자.
  • 무조건 JOIN → 테이블을 너무 많이 붙인 JOIN도 DB에 부담이다. 필요한 테이블만 붙이고, 결과가 정말 그만큼 필요한지 따져 보자.

이제 classic Open SQL로 합치고·하고·정렬하고·도구를 고르는 큰 줄기를 다 봤다. 마지막으로 이 판단을 공연별 예매현황 리포트(LEFT OUTER JOIN + GROUP BY + SUM)로 묶어 실습하자 → 다음 레슨. (그리고 Chapter 19 · Modern Open SQL에서 이 모든 SQL을 modern @·인라인 표기로 다시 만난다.)
