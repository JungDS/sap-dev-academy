Classic DDIC View·유지보수 객체

Help View와 Search Help 연결

F4 도움말을 풍부하게 — 여러 테이블을 묶는 Help View.

Track 1Chapter 14Lesson 3중급

사용자는 코드를 외우지 않는다

회차 등록 화면에서 "C001을 입력하라"고 하면 개발자는 당연하지만, 업무 담당자는 "안유진 콘서트가 어느 코드인지"를 찾아야 한다. F4 입력도움말이 이 간격을 줄인다. 사용자는 코드나 설명 일부로 검색하고, 고른 값이 입력 필드로 돌아온다.

Chapter 9 · Elementary Search Help에서 의 기본을 배웠다. 그때 selection method를 지정했다. Search Help가 목록에 뿌릴 값을 어디서 읽어 올지 정하는 칸이다. 값의 출처가 테이블 하나면 그 칸에 테이블 이름을 적으면 끝이다. 하지만 코드에 설명과 보조 정보까지 함께 보여 주려면 테이블 하나로는 모자랄 때가 있다. 그때 selection method 자리에 넣는 것이 다.

Help View = Search Help의 소스

는 에서 값의 출처로 쓰는 DDIC View다. 성격이 둘이다.

  • F4 전용 — Open SQL로 직접 읽는 대상이 아니다(프로그램 조회는 Database·Projection View).
  • primary table 보존(outer join 성격) — 로 보조 테이블을 묶되, 주 테이블 행은 남고 보조 설명이 없으면 그 칸만 비어 보일 수 있다.

🧩 같은 "View"인데 왜 어떤 건 SELECT가 되고 어떤 건 안 될까. 이 챕터의 View 네 종류는 이름만 같지 태어난 목적이 다르다. Database View는 DB에 SQL View까지 만들어져 프로그램이 읽고, Projection View는 런타임이 basis table 읽기로 바꿔 실행한다. 반면 Help View와 다음 레슨의 Maintenance View는 화면 도구가 쓰라고 만든 DDIC 설계도라서, SELECT의 FROM 자리에 넣을 수 있는 데이터 소스가 애초에 아니다. "View라니까 당연히 조회되겠지"가 통하지 않는 자리다.

  Import Parameter : CONCERT_ID        (사용자 검색어 → 검색에 반영)
  Export Parameter : CONCERT_ID        (선택한 행의 key → 화면 필드로 복귀)
  Display Fields   : CONCERT_ID, NAME, ARTIST, VENUE

ZHV_CONCERT는 공연 마스터 zconcert에 공연명 Text table zconcert_t를 붙인 Help View다. 둘 다 Chapter 9 · 콘서트 모델 실습에서 만들어 뒀다. ZSH_CONCERT도 그 레슨에서 만들었다. 이번에는 그 Search Help의 selection method를 테이블에서 Help View로 바꿔 다는 것이 할 일이다.

직접 만들어 보기 (SE11)

  1. SE11 → View 칸에 ZHV_CONCERT → Create → 종류는 Help view.
  2. Tables 칸 첫 줄에 primary table로 ZCONCERT를 적는다.
  3. Relationships 버튼으로 ZCONCERT_T를 붙인다. 두 테이블 사이 Foreign Key가 이미 있어서 조건은 자동으로 채워진다.
  4. View Flds 탭에서 CONCERT_ID·ARTIST·VENUE(ZCONCERT)와 NAME(ZCONCERT_T)을 고른다.
  5. 저장 → 활성화 → SE11의 Search Help ZSH_CONCERT를 열어 Selection Method를 ZCONCERT에서 ZHV_CONCERT로 바꾸고 다시 활성화한다.

💡 이 예제는 일부러 가장 단순한 형태다. Chapter 9 · Text Table에서 본 것처럼, selection method에 테이블만 지정해도 그 테이블에 Text Table이 붙어 있으면 이름 컬럼은 자동으로 따라온다. 즉 지금 예제는 Help View 없이도 된다. 여기서는 구조를 눈에 익히려고 아는 테이블로 만들어 본 것이고, Help View가 정말 값을 하는 건 텍스트 테이블이 아닌 다른 보조 테이블까지 목록에 끌어와야 할 때다.

Database View와 목적이 다르다.

질문 Database View Help View
Open SQL에서 읽나 예 아니오
주 사용처 프로그램 조회 F4 Search Help
여러 테이블 결합 inner join primary table 보존(outer)

아래에서 concert_id 필드에 F4를 눌러, 사용자가 설명을 보고 고르면 key가 화면에 돌아오는 흐름을 확인하자. 설명 테이블이 누락되거나 Export가 꺼지면 어떻게 되는지도 보자.

흔한 실수와 점검

  • 를 프로그램 조회용으로 → Open SQL의 데이터 소스가 아니다. 조회는 Database·Projection View나 코드 JOIN.
  • parameter를 대충 둔다 → 표시 필드가 많아도 Export가 안 맞으면 선택값이 화면에 안 돌아오고, Import가 틀리면 입력 검색어가 반영되지 않는다.
  • F4를 너무 복잡하게 → 처음엔 코드·대표명·상태면 충분하다. 목록을 프로그램으로 직접 채우거나 조건에 따라 바꾸는 search help exit(에 연결해 두는 프로그램 조각) 같은 장치는 심화 주제다.

정리

  • 는 F4 를 풍부하게 만드는 View다(프로그램 조회용 아님).
  • primary table을 기준으로 보조 정보를 붙여 사용자의 선택을 돕는다.
  • F4는 단순 팝업이 아니라 DDIC와 화면 필드가 연결된 데이터 흐름이다.

조회용·F4용 View까지 봤다. 이제 데이터를 입력·수정하는 유지보수 관점의 View다 → 다음 레슨(Maintenance View).
