Internal Table

옛 코드를 읽는 법 — Header Line과 OCCURS

첫 출근에 만날 20년 된 코드 — 읽을 줄 알되, 쓰지는 않는다.

Track 1Chapter 6Lesson 14초급

첫 출근, 20년 된 프로그램

SAP 시스템은 오래 산다. 실무에 나가면 높은 확률로 당신보다 나이가 많은 프로그램을 유지보수하게 된다. 그 코드들 속에서 반드시 마주치는 것이 오늘의 주제 — 지금은 쓰지 않지만 읽을 줄은 알아야 하는 Internal Table의 옛 선언 방식이다.

미리 말해 두면: 이 레슨엔 외울 것이 없다. 새 코드에 쓸 일도 없다. 목표는 딱 하나 — 옛 코드를 만났을 때 "아, 그 방식이구나" 하고 알아보는 눈이다. 가볍게 보자.

옛 선언 두 가지

" 옛 방식 ① — WITH HEADER LINE
DATA it_person TYPE TABLE OF ts_person WITH HEADER LINE.

" 옛 방식 ② — 더 오래된 OCCURS 선언 (행 모양 정의와 테이블 선언을 한 번에)
DATA: BEGIN OF it_person OCCURS 0,
        name TYPE string,
        age  TYPE i,
      END OF it_person.
  • ①은 우리가 아는 선언에 WITH HEADER LINE이 붙은 형태다.
  • ②의 OCCURS는 "이건 Internal Table이고 도 딸려 있다"를 한 단어로 암시하는 가장 오래된 표기다(숫자 0은 초기 힌트였는데 지금은 의미가 없다).
  • 어느 쪽이든 결과는 같다 — Header Line이 딸린 테이블이 만들어진다.

Header Line — 같은 이름의 그림자 한 행

이란 테이블 옆에 테이블과 똑같은 이름의 Work Area 한 장이 자동으로 붙어 있는 것이다. 그림으로 보면:

ABAP
1
2
it_person ──┬── [테이블 본체]  행1, 행2, 행3, ...
            └── [Header Line]  같은 이름의 한 행짜리 그림자

그래서 옛 코드에서 it_person이라는 이름은 문맥에 따라 테이블 전체를 뜻하기도, 그림자 한 행을 뜻하기도 한다.

ABAP
1
2
3
4
5
it_person-name = '정훈영'.        " Header Line(한 행)에 값 채우기
APPEND it_person.                 " Header Line을 테이블 본체에 붙이기 — TO가 없다!
READ TABLE it_person WITH KEY name = '정훈영'.   " 결과도 Header Line으로 들어온다
CLEAR it_person.                  " ⚠️ Header Line'만' 비워진다(본체는 그대로)
CLEAR it_person[].                " 본체를 비우려면 대괄호!

마지막 두 줄이 핵심 해독 포인트다 — 테이블 본체를 콕 집을 땐 it_person[]처럼 대괄호를 붙인다. 옛 코드에서 []를 보면 "아, 본체 쪽 이야기구나"로 읽으면 된다. APPEND it_person.처럼 TO가 없는 축약 문장들도 "그림자를 본체에" 가 생략된 것이다.

왜 퇴출됐나 — 네 가지 이유

편해 보이는데 왜 안 쓰게 됐을까. 이유를 알면 지금 방식이 왜 표준인지가 함께 보인다.

  1. 한 이름의 두 얼굴. MOVE it_person TO ...가 테이블을 옮기는지 한 행을 옮기는지 코드만 봐서는 모른다. 읽는 사람마다 해석이 갈리는 코드는 그 자체로 사고다.
  2. 암묵 동작. APPEND it_person.은 무엇을 어디에 붙이는지가 문장에 없다. 우리가 L08에서 세운 원칙 — "무슨 일이 일어나는지 코드에 드러나야 한다" — 의 정반대다.
  3. 공식적으로 obsolete. 언어 차원에서 퇴출 중인 형태로, 특히 클래스·메서드 안에서는 아예 구문 오류로 금지된다(클래스는 뒤 챕터에서 배운다). 취향 문제가 아니라 미래가 없는 문법이다.
  4. 현대 도구와의 불화. 새로 추가되는 문법·도구들은 없는 테이블을 전제한다. 옛 방식을 붙들면 새 도구를 쓸 때마다 벽을 만난다.

그래서 현재 표준이 바로 이 챕터 내내 해 온 방식이다 — 테이블(gt_)과 Work Area(gs_)를 서로 다른 이름으로 분리 선언. 여러분은 이미 권장 방식만 배웠다.

it_ 접두어 — 이름으로 알아보기

이 과정에서는 이 딸린 옛 방식 테이블에만 it_ 접두어를 쓴다(위 예제들이 그랬다). 다만 현업에는 평범한 Internal Table에도 it_를 붙이는 팀이 있으니, 이름만 보고 Header Line이 있다고 단정하지는 말자 — 판별 기준은 어디까지나 선언문(WITH HEADER LINE· OCCURS)이다.

🔭 이 "같은 이름의 그림자 행" 구조는 완전히 사라진 게 아니다 — 뒤에서 배울 선택화면 도구 중에 이 구조를 그대로 물려받은 것이 있어서(Chapter 12에서 재회한다), 오늘의 눈이 그때 그대로 쓰인다.

흔한 실수와 점검

  • 새 코드에 옛 방식 사용 → 금지. 이 레슨은 읽기 전용 지식이다.
  • CLEAR it_person으로 본체를 비웠다고 착각 → 만 비워진다. 옛 코드를 고칠 일이 생기면 [] 유무를 반드시 확인.
  • it_ 이름만 보고 단정 → 판별은 선언문으로.

이제 정말 마지막이다. 챕터에서 배운 전부를 한 프로그램에 모은다 — CH05에서 미완으로 남겨 둔 그 숙제, 구구단 72행 전체다 → 캡스톤.
