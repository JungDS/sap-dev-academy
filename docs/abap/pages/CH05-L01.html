Structure (Local · DDIC)

Local Structure (BEGIN OF ~ END OF)

BEGIN OF ~ END OF로 Structure를 만들어 관련된 값을 하나로 묶는다.

Track 1Chapter 5Lesson 1초급

사람 한 명에 변수가 셋

지난 챕터의 구구단 프로그램에서 gv_dan·gv_mul·gv_res 변수 세 개를 따로 들고 다녔다. 이번엔 더 실전적인 데이터인 사람을 다뤄 보자. 이름(문자)· 나이(정수)·금액(소수)을 담으려면 역시 변수 셋(gv_name·gv_age·gv_amount)이 필요하다.

한 명이면 참을 만하다. 그런데 사람이 두 명, 세 명이 되면? 변수 이름에 번호를 붙이기 시작한다. gv_name2, gv_age2, gv_name3… 선언은 사람마다 3줄씩 불어나고, "이 셋이 한 사람"이라는 묶음은 코드 어디에도 없이 머릿속에만 있다. 게다가 같은 선언을 반복해서 적다 보면 오타·타입 실수가 끼어드는데, 이를 막아 줄 장치도 없다. 아래에서 직접 눈으로 확인해 보자. 숨은 실수 세 개도 찾아보자.

관련된 값을 하나로 묶는 그릇이 필요하다. 그게 (구조체)다.

🧑‍💻 다른 언어를 해 봤다면 — Structure는 C의 struct나 파이썬의 dataclass처럼 값만 묶어 두는 그릇이다. 여기에 동작(메서드)을 붙이지는 않는다. 데이터와 동작을 함께 묶는 도구는 한참 뒤 챕터에서 따로 배운다.

BEGIN OF ~ END OF

문에서 BEGIN OF 뒤에 이름을 적고, END OF로 닫기 전까지 묶을 필드를 나열하면 Structure 변수가 선언된다.

ABAP
1
2
3
4
5
DATA: BEGIN OF gs_person,
        name   TYPE string,
        age    TYPE i,
        amount TYPE p LENGTH 8 DECIMALS 2,
      END OF gs_person.

BEGIN OF와 END OF 사이에 적은 name·age·amount는 Structure를 구성하는 (구성 요소)라 부른다. 이렇게 만든 Structure 변수가 한 건()을 담아 처리하는 자리에 놓이면, ABAP에서는 그 변수를 (작업 영역)라고 부른다. 새로운 타입이 아니라 쓰임새에 붙은 이름이다. gs_person은 여전히 그냥 Structure 변수이고, 한 사람의 정보를 담아 처리하는 동안 맡은 역할이 Work Area인 것이다.

변수를 선언할 때는 아래처럼 접두어만으로 변수의 모양을 파악할 수 있도록 한다.

접두어 뜻 담는 것 예
gv_ global variable 값 하나 (단일 값) gv_age
gs_ global structure 값 여러 개 (Component 칸으로 묶음) gs_person

⚠️ 여기서 g(global)는 한 프로그램 안 어디서나 쓸 수 있다는 뜻이다. 다음 레슨에 나오는 의 'Global'은 여러 프로그램이 함께 쓴다는 더 넓은 뜻이라, 같은 단어지만 가리키는 범위가 다르다. 지금 만든 gs_person은 이 프로그램 밖으로는 나가지 못한다.

🧑‍💻 다른 언어를 해 봤다면 — 이름 앞에 타입을 박아 넣는 방식(헝가리안 표기법)을 안티패턴으로 배웠을 수 있다. ABAP은 사정이 조금 다르다. 한 프로그램이 수천 줄이고 선언은 저 위에 몰려 있어서, 접두어가 지금 이 변수가 값 하나인지 묶음인지를 알려 주는 거의 유일한 단서다. 그래서 SAP 표준 교재와 대부분의 프로젝트 가이드가 지금도 이 관례를 쓴다.

잠깐 정리 — 여기까지가 Structure의 기본

  • 만들기 — DATA: 뒤에 BEGIN OF <이름>을 적고, 담을 칸을 나열한 뒤 END OF <이름>.으로 닫는다.
  • 넣고 읽기 — <이름>-<Component>, 하이픈 하나로 칸 안에 들어간다.
  • 이름 짓기 — 값 하나면 gv_, 묶음이면 gs_.

여기까지가 의 뼈대 전부다. 남은 이야기는 이 뼈대를 덜 반복해서 쓰는 요령이다.

이번엔 모양 선언이 반복된다

gs_person으로 한 명은 깔끔하게 묶었다. 그런데 사람이 두 명, 세 명이 되면 사람마다 변수를 만들 텐데, 그때마다 BEGIN OF ~ END OF 모양 선언이 통째로 따라붙는다. 사람마다 5줄씩이다. 모양은 한 번만 적고, 변수만 여러 개 찍어내고 싶다.

타입으로 빼두기 (재사용)

의 모양을 로 선언하면 여러 변수가 같은 모양을 공유한다. 모양은 한 번만 선언하고, 변수는 TYPE ts_person으로 여러 개 만든다. 한 명이 아니라 여러 명을 같은 틀로 찍어내는 셈이다. Structure Type 이름은 ts_(type structure)로 시작하는 게 SAP 표준 교재의 관례다.

" 같은 타입으로 변수 여러 개, 모양은 매번 다시 안 적는다
DATA: gs_p1 TYPE ts_person,
      gs_p2 TYPE ts_person,
      gs_p3 TYPE ts_person.

gs_p1-name   = '정훈영'.
gs_p1-age    = 30.
gs_p1-amount = '1500.50'.

gs_p2-name   = '손흥민'.     " 이 사람은 amount를 일부러 비워 둔다
gs_p2-age    = 32.          " 안 넣은 칸은 초기값 0.00으로 남는다

gs_p3-name   = '유재석'.
gs_p3-age    = 51.
gs_p3-amount = '980.00'.

타입으로 묶으면 얼마나 나아지는지는 규모가 커질수록 또렷해진다. 실무의 "사람"은 정보가 셋일 리 없다. 성별·생일·부서·직급·입사일·연봉·연락처만 더해도 정보 10개다. 단일 값 변수는 사람 수 × 정보 수로 폭발하지만(겨우 3명인데 변수 30개), 타입 하나로 묶으면 얘기가 달라진다. 아래 비교와 "실무 스케일"을 열어 확인해 보자.

💡 gv_name2 같은 번호 붙은 변수가 보이면 그건 "묶어야 한다"는 신호다. 단일 값 변수 9줄이 여기서 타입 정의 한 번 + 변수 세 줄로 줄어들었다.

LIKE 다시 만나기 — 변수를 보고 똑같은 모양으로

LIKE는 Chapter 2 · 변수 선언(DATA)에서 이미 배운 키워드다. 거기서는 단일 값 변수를 다른 변수와 같은 모양으로 선언했는데, 에도 그대로 쓴다. 새 문법을 배우는 게 아니라, 아는 문법을 묶음에 적용해 보는 자리다.

TYPE이 타입을 보고 만든다면, LIKE는 이미 선언된 변수를 보고 똑같은 모양으로 만든다. 그래서 둘은 쓰는 자리가 갈린다. 모양에 이름을 붙여 여러 곳에서 쓸 거라면 앞 절의 TYPES, 잘 만들어 둔 변수가 이미 하나 있고 그 짝을 하나 더 두고 싶을 뿐이라면 LIKE다.

ABAP
1
2
3
4
5
6
7
gs_p1-name   = '정훈영'.     " 원본 gs_p1에 값이 채워진 상태에서
gs_p1-age    = 30.
gs_p1-amount = '1500.50'.

DATA gs_p4 LIKE gs_p1.      " gs_p1과 똑같은 "모양"의 새 변수

gs_p4-name = '강호동'.       " 값이 필요하면 이렇게 따로 넣는다

LIKE gs_p1은 "gs_p1이 가진 모양 그대로"라는 뜻이다. 이름·타입·길이가 모두 같다. 여기서 오해하기 쉬운 것 하나: LIKE가 변수를 통째로 "복사"한다고 생각하면 안 된다. 복사되는 건 모양뿐이고, 원본 gs_p1에 들어 있던 값(정훈영·30·1500.50)은 한 글자도 넘어오지 않는다. gs_p4는 선언되는 순간 모든 Component가 타입별 초기값(정수 0, 문자열 '', p는 0.00)으로 시작한다. 아래 디버거에서 직접 확인해 보자.

코드에서 DATA gs_p4가 중간에 끼어 있다고 해서 "이 줄에 도달해야 변수가 생긴다"고 읽으면 안 된다. DATA 같은 선언문은 실행 순서와 상관없이 프로그램이 시작될 때 한꺼번에 처리된다. gs_p4는 첫 줄부터 이미 빈 그릇으로 준비돼 있다. 디버거에서 선언문에는 아예 멈추지 않는 이유이기도 하다. 그래도 읽는 사람을 생각하면 선언은 코드 위쪽에 모아 두는 편이 좋다.

💡 TYPE이든 LIKE이든, 변수는 선언되는 순간 반드시 초기값을 가진다. ABAP에는 "값이 없는(미지정) 변수"가 없다. 안 넣었으면 그건 그냥 그 타입의 초기값이다.

🧑‍💻 SQL을 해 봤다면 — 여기 LIKE는 SQL의 패턴 검색 LIKE와 이름만 같고 아무 관계가 없다. 선언문에서 쓰는 LIKE는 "이 변수와 같은 모양으로"라는 뜻이다.

흔한 실수와 점검

  • END OF 이름 → END OF gs_person. 처럼 같은 이름으로 닫는다.
  • 선언 체인의 구두점 → DATA:로 시작했으면 항목마다 쉼표로 잇고 맨 끝에만 마침표를 찍는다. BEGIN OF와 END OF 사이의 도 쉼표로 잇는다.
  • 칸에 들어갈 땐 하이픈(-) → gs_person.name처럼 점을 찍으면 거기서 문장이 끝난 것으로 읽혀 오류가 난다. 안으로 들어가는 문은 하이픈 하나뿐이다.
  • LIKE는 값까지 복사하지 않는다 → LIKE로 만든 변수는 모양만 같고 값은 초기값이다. 값이 필요하면 따로 넣는다.

사람 한 명을 깔끔히 묶었다. 그런데 이 Structure도 프로그램마다 또 선언하긴 마찬가지다. 프로그램 밖으로 꺼내 여러 프로그램이 함께 쓰고 싶다 → DDIC Structure.
