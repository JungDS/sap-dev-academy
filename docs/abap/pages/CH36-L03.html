문자열 SQL을 실행할 통로

Chapter 28 · REF TO data와 CREATE DATA 무렵, 동적으로 조립한 SQL 문자열을 실행하는 이야기는 이 챕터로 미뤄 두었다. 그 통로가 여기 있다.

(ABAP Database Connectivity)는 (DB 제품 고유 문법의 SQL)을 ABAP에서 직접 실행하는 API다. 사다리의 마지막 칸이고, 과거의 EXEC SQL 내장 문법을 대체한다(공식 문서도 새 코드에는 ADBC를 권장한다).

강력한 만큼 대가가 있다. 이 문자열은 ABAP 문법 검사를 받지 않고, client 조건도 자동으로 붙지 않으며, 오타는 컴파일이 아니라 런타임 오류로 나타난다. 이 레슨의 목표는 두 가지다. ADBC 코드를 읽고 쓸 줄 알 것, 그리고 어떤 순간에만 꺼내야 하는지 판정할 줄 알 것.

💡 이 레슨의 코드는 전부 평범한 ABAP이다. AMDP와 달리 ADT 전용이 아니라서 SE38 리포트에든 클래스에든 넣을 수 있다. 따라 해 볼 껍데기는 SE38 테스트 리포트면 충분하다.

REPORT z_adbc_practice.        " 평범한 리포트에서 실행 가능

TYPES:
  BEGIN OF ts_cnt,
    concert_id TYPE zbooking-concert_id,
    cnt        TYPE i,
  END OF ts_cnt,
  tt_cnt TYPE STANDARD TABLE OF ts_cnt WITH EMPTY KEY.

DATA gt_cnt TYPE tt_cnt.

START-OF-SELECTION.
  TRY.
      " ① 문장 객체 생성 → 문자열 실행 (client 조건을 직접 쓴다!)
      DATA(go_stmt) = NEW cl_sql_statement( ).
      DATA(go_rs) = go_stmt->execute_query(
        `SELECT concert_id, COUNT(*) AS cnt `   &&
        `FROM zbooking `                        &&
        `WHERE mandt = '` && sy-mandt && `' `   &&
        `GROUP BY concert_id` ).

      " ② 결과 그릇(내부 테이블)의 '참조'를 넘기고 → 전량 수신 → 닫기
      go_rs->set_param_table( REF #( gt_cnt ) ).
      go_rs->next_package( ).
      go_rs->close( ).

      " ③ 결과 확인은 평소처럼 — 받은 내부 테이블을 출력
      WRITE: / '공연 수:', lines( gt_cnt ).

    CATCH cx_sql_exception INTO DATA(gx_sql).
      " ④ 오류를 삼키지 않는다 — SQL code·message를 로그로
      WRITE: / 'DB 오류:', gx_sql->sql_code, gx_sql->sql_message.
      " 운영 코드라면 여기서 Application Log에 남긴다(Chapter 25 방식)
  ENDTRY.

②의 세 줄은 한 세트다. 처음 보는 것들이니 하나씩:

  • REF #( gt_cnt ) — [선행 사용] gt_cnt의 참조(Data Reference)를 그 자리에서 만드는 생성자 표현식이다. Chapter 28에서 배운 REF TO data의 표현식 버전이라고 보면 된다(분석 불필요). set_param_table이 "결과를 부어 넣을 그릇의 참조"를 요구하기 때문에 이렇게 넘긴다.
  • next_package( ) — 결과를 그릇에 채운다. 이름과 달리 한도(UPTO)를 지정하지 않으면 한 번 호출로 전량을 받는다(공식 규칙). 대량이라 나눠 받고 싶을 때만 UPTO를 주고 반복 호출하며, 그 감각은 Chapter 35 · Package 설계와 같다.
  • close( ) — 결과셋 자원을 닫는다. 읽었으면 닫는 것까지가 한 세트다.

sy-mandt를 문자열에 붙인 ①은 우리 코드가 만든 값이라 injection 위험은 없다(학습용 최단형). 다만 실무 권장은 다음 예제처럼 client까지 바인딩하는 쪽이다. 두 의 선택 기준도 여기서 갈린다: 문장에 들어갈 값이 있으면 prepared(바인딩), 값 없는 고정 문장이면 statement로 충분하다. 그리고 사용자 입력이 문자열에 섞이는 순간은 언제나 사고다.

외부 입력은 바인딩으로 — SQL injection

사용자 입력 pa_conc를 이렇게 붙였다고 하자.

" ❌ 위험 — 입력이 SQL 문법으로 해석될 수 있다 (SQL injection)
`WHERE concert_id = '` && pa_conc && `'`

입력에 따옴표와 SQL 조각을 섞으면 문장의 의미 자체가 바뀐다. 이를 (입력값이 SQL 문법으로 해석되게 만들어 의도하지 않은 문장을 실행시키는 공격)이라 한다. 방어는 값을 문자열에 잇지 않고 ? 자리에 바인딩하는 것이다.

PARAMETERS pa_conc TYPE zconcert-concert_id.

TYPES:
  BEGIN OF ts_book,
    concert_id TYPE zbooking-concert_id,
    perf_no    TYPE zbooking-perf_no,
    seats      TYPE zbooking-seats,
  END OF ts_book,
  tt_book TYPE STANDARD TABLE OF ts_book WITH EMPTY KEY.

DATA gt_book TYPE tt_book.

START-OF-SELECTION.
  TRY.
      " ✅ 값은 ? 자리로, set_param으로 바인딩 (공식 예제 패턴)
      DATA(go_prep) = NEW cl_sql_prepared_statement(
        `SELECT concert_id, perf_no, seats ` &&
        `FROM zbooking `                     &&
        `WHERE mandt = ? AND concert_id = ?` ).

      DATA(gv_client) = sy-mandt.
      go_prep->set_param( REF #( gv_client ) ).
      go_prep->set_param( REF #( pa_conc ) ).

      DATA(go_rs2) = go_prep->execute_query( ).
      go_rs2->set_param_table( REF #( gt_book ) ).
      go_rs2->next_package( ).
      go_rs2->close( ).
      go_prep->close( ).             " 다 쓴 prepared statement도 닫는다
                                     " (공식 예제 패턴)

    CATCH cx_sql_exception INTO DATA(gx_bind).
      WRITE: / 'DB 오류:', gx_bind->sql_code, gx_bind->sql_message.
  ENDTRY.

set_param을 부른 순서가 곧 ?의 순서다(첫 호출=첫 ?). 그리고 값이 아닌 부분(컬럼명·정렬 방향 등)은 ?로 처리할 수 없다. 그런 동적 조각은 허용 목록(미리 정한 후보 중에서만 선택)으로 제한한다.

그럼 언제 ADBC가 불가피한가

여기까지의 예제는 전부 Open SQL로도 되는 문장이었다. 그럼 진짜 의 자리는 어디인가. 대표 사유는 **"우리 DDIC 바깥"**이다.

Open SQL과 AMDP는 우리 시스템이 아는 세계 안에서 논다. Open SQL은 DDIC에 정의된 테이블·CDS만 읽고, AMDP도 USING에 올릴 수 있는 ABAP 관리 가 대상이다. 그런데 이런 요구가 온다. "외부 티켓 판매사의 DB(우리 SAP이 아닌 별도 DB)에 있는 정산 테이블을 매일 읽어 와라." 그 테이블은 DDIC에 없다. Open SQL도 AMDP도 문 자체가 없다. 이때가 ADBC다.

TRY.
    " 보조 DB 접속(Basis가 구성해 둔 접속 이름)으로 문을 연다
    DATA(go_con) = cl_sql_connection=>get_connection( `TICKET_DB` ).

    " 이 접속 객체에 statement를 연결해 외부 테이블(DDIC에 없음)을

    "   execute_query → set_param_table → next_package → close

  CATCH cx_sql_exception INTO DATA(gx_ext).
    WRITE: / 'DB 오류:', gx_ext->sql_code, gx_ext->sql_message.
ENDTRY.

접속 이름·외부 테이블은 시스템마다 다르며 Basis가 구성한다. 위 코드는 구조를 보여주는 개념 예제이고, 접속 객체에 statement를 연결하는 세부 시그니처는 릴리스별로 다를 수 있어 실제 시스템의 ADT(F2 도움말)에서 확인한다.

경계를 정리하면 이렇다. 같은 시스템 HANA 안의 절차 로직 = AMDP(관리라도 받는다), 다른 접속·DDIC 밖 테이블·DB 전용 구문 = ADBC(관리 밖, 전부 내 책임). 참고로 "client 직접" 원칙은 MANDT 열이 있는 SAP 테이블 이야기다. 외부 DB 테이블엔 그 개념이 없을 수 있고, 그땐 그쪽 DB의 데이터 격리 규칙을 따른다. 그리고 어느 쪽이든, 쓰기 전에 "위 칸으로 안 되는 이유"를 적을 수 있어야 한다.

흐름을 눈으로, 위험을 판정으로

호출 경로를 지도로 확인한 뒤, 코드 카드 5장을 "적절/위험"으로 판정해 보라.

흔한 실수와 점검 🚧

  • 문자열에 사용자 입력 잇기 → . 값은 언제나 ? + set_param.
  • client 누락 → 은 MANDT를 자동으로 안 챙긴다. 조건에 직접 쓰거나 바인딩한다. client 100에서 000 데이터까지 읽히는 사고는 운영에서 치명적이다.
  • close( ) 누락 → 결과셋 자원이 새어 나간다. 읽었으면 닫는다.
  • 오류 삼키기 → sql_code·sql_message 없는 오류는 운영에서 원인 추적이 불가능하다(Chapter 25 · 오류 로그와 재처리 구조).
  • COMMIT을 문자열로 실행 → Chapter 25의 SAP LUW와 어긋난다. 경계는 ABAP 쪽에서 관리한다.
  • 버퍼·권한 우회를 잊음 → Native SQL은 테이블 버퍼링을 지나치고 CDS 접근 제어(Chapter 23의 DCL — 행 단위 권한 규칙)도 적용하지 않는다. Open SQL의 보호가 전부 사라진 상태다.
  • Open SQL로 되는 문장을 로 → 이 레슨의 연습 예제처럼 학습용이 아니라면, 그 자체가 안티패턴이다.

정리 📌

  • = 을 실행하는 API. EXEC SQL의 후계자이며 최후의 수단.
  • 기본 흐름: statement → execute_query → 결과셋(set_param_table(REF #()) → next_package(UPTO 없으면 전량) → close) → CX_SQL_EXCEPTION의 sql_code·sql_message 로그.
  • 외부 입력은 바인딩, client는 직접, 자원은 닫기.
  • 불가피한 순간 = DDIC 밖: 보조 접속(get_connection)의 외부 테이블, DB 전용 구문. 같은 HANA 안의 절차면 AMDP가 먼저다.

이제 사다리의 모든 칸을 밟아 봤다. 남은 것은 고르는 눈이다. 네 수단을 나란히 놓고 비교한다.
