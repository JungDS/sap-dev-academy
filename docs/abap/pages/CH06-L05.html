Internal Table

한 행 제어 ① — 넣기와 찾기 (INSERT · READ TABLE)

자리로 할까, 키로 할까 — 한 행을 다루는 두 좌표를 잡는다.

Track 1Chapter 6Lesson 5초급

두 개의 좌표 — 자리, 아니면 키

그릇 설계(3속성)가 끝났으니 이제 본격적으로 부린다. 한 행을 콕 집어 다루는 방법은 이 챕터 내내 딱 두 갈래다.

  • 자리(INDEX)로 — "3번째 행"처럼 번호로 집는다. 번호가 있는 Index Table(STANDARD·SORTED)에서만.
  • 키(KEY)로 — "name이 정훈영인 행"처럼 값으로 집는다. 모든 종류에서.

오늘 배우는 넣기·찾기도, 다음 레슨의 고치기·지우기도 전부 이 두 좌표의 반복이다. 이 틀 하나만 잡으면 문법이 절반으로 줄어든다.

넣기 — APPEND vs INSERT

APPEND(끝에 쌓기)는 이미 안다. INSERT는 자리를 고를 수 있는 넣기다.

ABAP
1
2
3
APPEND gs_person TO gt_person.            " 끝에
INSERT gs_person INTO gt_person INDEX 1.  " 자리로: 맨 앞에 끼워 넣기
INSERT gs_person INTO TABLE gt_person.    " 키로: 종류가 정한 자리에

INTO TABLE이 실제로 어디에 넣는지는 테이블 종류가 정한다. 하나로 외우면 틀린다.

종류 INSERT ... INTO TABLE이 넣는 자리
STANDARD 맨 끝. 결과가 APPEND와 같다(입력 순서 유지)
SORTED 키 순서에 맞는 자리
HASHED 해시가 관리하는 자리(눈에 보이는 순서는 의미가 없다)

INTO(자리 지정)와 INTO TABLE(종류에게 위임)은 다른 문장이다. HASHED는 번호가 없어 INTO TABLE만 가능하다. SORTED는 INDEX 문법 자체는 되지만 삽입이 정렬 순서를 깨면 런타임 오류가 난다. 그래서 SORTED/HASHED엔 INTO TABLE을 쓴다(자리는 시스템이 잡는다).

정리하면, 행을 넣는 방법은 세 형제다. 셋째는 아직 이름만 알아 두자.

형제 하는 일 배우는 곳
APPEND 무조건 끝에 붙인다 L01에서 배움
INSERT 자리를 골라 넣는다(직접 지정 또는 종류에 위임) 지금
COLLECT 같은 키의 행이 이미 있으면 행을 늘리는 대신 숫자를 합산한다 집계 레슨에서 — 지금 외울 필요 없음

한 가지만 덧붙이면, APPEND는 번호 있는 그릇(Index Table: STANDARD·SORTED) 전용이다. "끝에"라는 자리 자체가 행 번호가 있어야 성립하기 때문이다. 번호표 없는 HASHED에 넣는 길은 INSERT ... INTO TABLE뿐이다.

찾기 — READ TABLE

찾기도 같은 두 좌표다. 자리로 찾거나, 키로 찾거나.

ABAP
1
2
3
4
5
6
7
READ TABLE gt_person INTO gs_person INDEX 3.               " 자리로: 3번 행
READ TABLE gt_person INTO gs_person WITH KEY name = '수지'. " 키로: 즉석 조건
READ TABLE gt_person INTO gs_person
     WITH TABLE KEY name = '수지'.                         " 키로: 선언된 키 전체
IF sy-subrc = 0.
  WRITE: / '찾음:', gs_person-age.
ENDIF.

키로 찾는 문장은 다시 둘로 갈린다. 이름이 비슷해서 헷갈리기 쉬운데, 구분 기준은 "선언한 그 키냐, 즉석 조건이냐"다.

  • WITH KEY field = ... — 아무 필드나 즉석 조건으로 찾기. 키가 아닌 필드도 된다 (WITH KEY age = 30도 합법). 대신 STANDARD에서는 앞에서부터 순차 탐색이다.
  • WITH TABLE KEY ... — 선언에 정의된 키 전체를 지정해 찾기. 키 필드를 빠짐없이 적어야 하며, SORTED/HASHED가 자기 방식(이진/해시)으로 가장 빠르게 찾는 경로다. (위 예제에서 이 형태가 성립하는 이유: 이 챕터의 기본 예제처럼 키를 안 적고 선언한 gt_person이라면 키는 standard key, 곧 문자 필드 name 하나다. 그래서 name만 적으면 "키 전체"가 된다.)

조건에 맞는 행이 여러 개면? 키 레슨에서 못 박은 답 그대로 — 앞에서부터 처음 만나는 행 하나만 Work Area로 들어온다. 전부 다루려면 찾기가 아니라 순회다(순회 레슨에서 배운다).

결과 확인 — sy-subrc와 sy-tabix

먼저 가 무엇인지부터. READ처럼 "잘 됐나?"를 물어야 하는 문장이 실행된 뒤, 시스템이 그 결과(성공/실패)를 숫자로 채워 주는 시스템 변수다. sy-index·sy-tabix와 같은 sy- 가족이고, 0이면 성공이라는 약속이다. 위 예제의 IF sy-subrc = 0.이 바로 "방금 그 READ, 성공했나?"라는 질문이었던 것이다. (다른 언어를 해 봤다면: 실패를 예외로 던지는 대신 반환 코드로 알리는 방식이다.)

단, 모든 문장이 이 변수를 채우는 것은 아니다. 결과를 알리기로 정해진 문장(지금은 READ TABLE, 앞으로 배울 훑기·DB 읽기 문장들이 더 있다)만 채우고, 그 밖의 문장 뒤에는 직전 값이 그대로 남아 있다. 말하자면 sy-subrc는 "가장 최근에 보고한 문장"의 성적표다. 그래서 확인은 READ 바로 다음 줄에서 한다. 사이에 다른 문장이 끼어들수록, 지금 보는 값이 누구의 성적인지부터 흐려진다.

READ가 성공했는지는 언제나 sy-subrc가 0인지로만 판정한다. 못 찾으면 0이 아닌 값이 들어오는데, 그 값이 상황에 따라 다르므로 "0이냐 아니냐"만 보는 것이 규율이다. (IF sy-subrc = 4처럼 실패 코드를 콕 집어 비교하면 조용히 어긋나는 날이 온다.)

이 성적표는 READ만의 것이 아니다. 예컨대 UNIQUE 키 그릇(UNIQUE SORTED·HASHED)에 INSERT ... INTO TABLE로 이미 있는 키를 또 넣으면, 행은 삽입되지 않고 sy-subrc에 4가 들어온다(판정은 역시 0인지로만).

찾기에 성공하면 에 그 행의 번호가 들어온다. 몇 번 행에서 찾았는지를 시스템이 알려 주는 것이다 — 다음 레슨의 고치기에서 바로 써먹는다. 단, 번호가 있는 Index Table(STANDARD·SORTED) 이야기고, 번호표가 없는 HASHED에서는 0이 들어온다. "행은 찾았는데 번호는 없다"는 이 묘한 상태의 정체는 빠르게 찾기에서 실험으로 확인한다.

값은 필요 없고 있는지만 알고 싶을 때는 TRANSPORTING NO FIELDS를 쓴다. "옮길(transporting) 필드가 없다(no fields)", 즉 Work Area 복사 없이 존재만 확인한다(그래서 빠르다).

ABAP
1
2
3
READ TABLE gt_person TRANSPORTING NO FIELDS WITH KEY name = '수지'.
IF sy-subrc = 0.  " 존재만 확인
ENDIF.

🔭 실무 미리보기. 지금은 행을 전부 손으로 APPEND해 채우고 있지만, 실무에서는 대부분 데이터베이스에서 읽어 와 한 번에 채운다. 그 도구(SELECT)는 Chapter 8 · Open SQL에서 배운다 — 그때 이 챕터의 테이블 지식이 그릇 역할로 그대로 재등장한다.

흔한 실수와 점검

  • 미확인 → READ 실패 시 Work Area엔 이전 값이 그대로 남는다. 그걸 새로 읽은 값인 줄 알고 쓰는 버그가 정말 잦다. READ 다음 줄은 반드시 IF sy-subrc = 0.
  • 실패 코드 콕 집어 비교 → 판정은 "0이냐 아니냐"로만. 실패 값의 종류는 문장에 따라 다르다.
  • INTO vs INTO TABLE 혼동 → 자리를 내가 지정하는 문장인지, 종류에 맡기는 문장인지 구분.
  • WITH KEY와 WITH TABLE KEY 혼동 → 즉석 조건(아무 필드)인지, 선언된 키 전체인지.

넣고 찾는 두 좌표를 잡았다. 같은 좌표가 그대로 반복되는 고치기와 지우기로 → 한 행 제어 ②.
