Dynamic ABAP: Field Symbol 심화와 Generic

typed vs generic Field Symbol

이름표의 두 얼굴 — 모양을 아는 이름표와 모르는 이름표.

Track 3Chapter 28Lesson 1고급

타입을 미리 모른다면

Internal Table에서 배운 은 한 가지 목적이 분명했다 — 한 행을 복사하지 않고 바로 고치기. (그때는 FIELD-SYMBOLS 선언형이었고, 아래처럼 자리에서 선언하는 inline 형은 Chapter 18 이후 습관이 된 모양이다.)

ABAP
1
2
3
LOOP AT gt_booking ASSIGNING FIELD-SYMBOL(<ls_booking>).
  <ls_booking>-status = 'C'.        " 원본 행이 바로 바뀐다
ENDLOOP.

여기서 <ls_booking>의 모양은 분명하다. gt_booking의 한 줄 타입이니 -status라고 쓰면 syntax check가 필드 존재까지 확인해 준다. 이것이 typed Field Symbol이다.

그런데 실무 코드는 이런 요구를 만난다.

  • 공통 로그 도구가 어떤 구조든 받아서 필드명·값을 보여 줘야 한다.
  • 화면 설정에서 사용자가 고른 필드만 읽어야 한다 — 필드 이름이 실행 중에 정해진다.
  • 마이그레이션 도구가 "어떤 테이블이든" 처리해야 한다.

들어올 데이터의 모양을 컴파일 시점에 모르면, 이름표의 허용 범위를 넓힌 generic Field Symbol이 필요하다.

무엇인가 — 상자가 아니라 이름표

먼저 의 정체부터 다시 잡자. Field Symbol은 자기 값을 가진 상자(변수)가 아니라, 이미 존재하는 영역에 붙이는 이름표다.

구분 일반 변수 Field Symbol
자기 값 자기 메모리 상자를 가진다 없다 — 남의 상자를 가리킨다
선언 직후 초기값으로 바로 사용 가능 아무것도 안 가리킴 — ASSIGN 전 사용 불가
값을 바꾸면 자기 상자가 바뀐다 가리키는 원본이 바뀐다
선언 타입의 의미 상자의 모양 "무엇을 가리킬 수 있나"의 제한

typed와 generic은 그 제한의 폭이 다르다.

ABAP
1
2
3
4
5
FIELD-SYMBOLS <ls_typed> TYPE ts_booking.   " 이 모양만 가리킬 수 있음

FIELD-SYMBOLS:
  <lt_any_tab> TYPE ANY TABLE,              " 어떤 내부 테이블이든
  <lv_any>     TYPE any.                    " 어떤 데이터든

여기서 TYPE any는 "아무거나 마음대로"가 아니다. "어떤 타입이 올지 컴파일러가 모른다"는 뜻이라, <lv_any>-status처럼 특정 필드를 바로 쓸 수 없다. 구지, 그 구조에 STATUS가 있는지를 실행 중에 확인할 책임이 개발자에게 넘어온다.

직접 만져 보기

왼쪽 상자(gs_booking)에 typed/generic 이름표를 붙였다 떼며, 할당 전 사용과 generic의 필드 접근 제한이 어떻게 다른지 확인해 보라.

어떻게 확인하는가

같은 구조를 두 방식으로 다뤄 본다. typed는 바로 접근한다.

ABAP

DATA gs_booking TYPE ts_booking.       " ts_booking = 정본 ZBOOKING의 축소판(실습 필드만)
gs_booking-booking_id = '0001'.
gs_booking-status     = 'N'.

FIELD-SYMBOLS <ls_typed> TYPE ts_booking.
ASSIGN gs_booking TO <ls_typed>.

IF <ls_typed> IS ASSIGNED.
  <ls_typed>-status = 'C'.          " 필드명은 syntax check가 보증
ENDIF.

generic은 확인 단계를 거친다. (필드를 실행 중에 고르는 ASSIGN COMPONENT는 뒤 레슨에서 정식으로 — 여기선 "바로 못 쓴다"는 감각만.)

확인 질문 typed generic
필드명을 syntax check가 확인해 주나 예 아니오
어떤 구조든 받을 수 있나 아니오 예 — 단 실행 중 확인 필요
실패 가능성을 코드가 다뤄야 하나 적음 반드시

흔한 실수와 점검 🚧

  • 선언만 하고 사용 → 은 선언 직후 아무것도 안 가리킨다. ASSIGN 후 IS ASSIGNED 확인이 먼저다.
  • TYPE any = 자유이용권으로 착각 → 유연해진 만큼, 컴파일러가 잡아 주던 실수를 내가 검증해야 한다.
  • 이름표에 값 대입 = 이름표가 바뀐다고 생각 → 바뀌는 건 이름표가 아니라 가리키는 원본이다.
  • generic 남용 → 업무 구조가 분명하면 typed가 먼저다. generic이 늘수록 코드는 읽기 어려워진다.

정리 📌

  • = 값 상자가 아니라 원본 에 붙는 이름표.
  • typed = 모양 고정(안전·명확), generic(TYPE any·ANY TABLE) = 무엇이든 받되 확인 책임이 생긴다.
  • 동적 ABAP의 출발선: "정적으로 충분하면 정적으로, 정말 필요할 때만 동적으로."

이름표의 범위를 넓혔다. 그럼 의 입력 자리도 넓힐 수 있을까 — generic → TYPE any · ANY TABLE 파라미터.
