Projection View 개념과 한계

한 테이블에서 필요한 필드만 노출 — Projection View와 그 한계.

Track 1Chapter 14Lesson 2중급

모든 필드를 다 보여줄 필요는 없다

테이블을 만들면 모든 필드를 그대로 보여 주는 게 자연스러워 보인다. 하지만 실무는 다르다. 예매 테이블에 감사 필드(누가·언제 만들고 고쳤나) 여섯 개가 함께 있어도, 업무 담당자는 예매 번호·공연·좌석·상태만 필요하다. 다 보여 주면 화면이 복잡해지고, 안 봐도 될 정보가 노출되며, 엉뚱한 필드를 업무 필드로 착각한다.

는 "같은 테이블을 더 좁게 보여 주는 관점"이다.

Projection View — 한 테이블, 열 솎아내기

는 하나의 basis table(기반 테이블)에서 일부 필드만 보이게 하는 DDIC View다. 도 계산도 하지 않고, 행을 거르는 조건도 두지 않는다. 한마디로 "한 테이블에서 열을 줄이는 View"다.

우리 zbooking이 정확히 그렇다. 업무 필드가 여섯(booking_id, concert_id, perf_no, customer, seats, status)이고, 여기에 감사 필드 여섯(created_by, created_on, created_at, changed_by, changed_on, changed_at)이 붙어 모두 열두 필드다(Chapter 9 · 콘서트 모델 실습에서 만든 그 테이블이다). 업무 담당자가 기본 목록만 보면 된다면 Projection View ZPV_BOOKING은 감사 필드를 걷어 내고 업무 여섯 필드만 노출할 수 있다(client 구분 필드 MANDT는 View에도 그대로 남는다. 바로 아래에서 이유를 본다). 읽는 모습은 테이블 읽기와 거의 같다.

직접 만들어 보기 (SE11)

  1. SE11 → View 칸에 ZPV_BOOKING → Create → 종류는 Projection view.
  2. Basis table 칸에 ZBOOKING 하나만 적는다(Projection View는 테이블 하나가 전부다).
  3. Table fields 버튼 → 목록에서 업무 필드 여섯 개를 고른다. 감사 필드는 고르지 않는다. 단 client 구분 필드 MANDT는 첫 필드로 반드시 남긴다. 테이블처럼 View도 CLNT 타입 필드가 맨 앞에 있어야 클라이언트별로 데이터가 갈리고, 빼 버리면 다른 클라이언트의 예매 행까지 읽히는 View가 되어 버린다.
  4. 저장 → 패키지 지정 → 활성화.

그런데 DB에는 이 View가 없다

앞 레슨의 는 활성화하면 DB 쪽에도 SQL View가 만들어졌다. Projection View는 다르다. DB에는 아무것도 만들어지지 않고 DDIC 안에만 존재한다. 그럼 위 코드의 SELECT는 무엇을 읽는 걸까?

🔑 ABAP 런타임이 대신 번역해 준다. SELECT ... FROM zpv_booking을 만나면 런타임은 그 View의 정의를 보고 basis table인 ZBOOKING을 읽는 문장으로 바꿔 실행한다. 우리가 고른 여섯 필드만 담아서 돌려주는 것도 이때 처리된다. 그래서 DB에 SQL View가 없어도 프로그램은 아무 일 없이 읽는다. 대신 이 이름은 ABAP 안에서만 통한다. DB 관리 도구로 직접 접속해 ZPV_BOOKING을 찾으면 그런 객체는 없다.

아래에서 노출할 필드를 켜고 끄며 사용자가 보게 되는 결과가 어떻게 바뀌는지, key 필드를 빼면 무슨 일이 생기는지 직접 보자.

한계와 오해

  • 행을 거르는 필터 View가 아니다 → 특정 status만 보이게 하는 행 조건을 에는 둘 수 없다. 이 View가 다루는 건 열뿐이다. (고정 행 조건이 필요하면 Chapter 14 · Database View의 Selection Conditions를 쓰거나, 프로그램의 SELECT에 WHERE로 건다. "DDIC View에는 조건을 걸 자리가 아예 없다"는 아니다.)
  • key 필드를 빼지 말 것 → 결과가 깔끔해 보여도 어떤 행인지 식별 못 하면 못 쓴다. 최소한 업무 식별 key와 설명 필드는 남긴다.
  • 권한 설계를 대신하지 않는다 → "안 보이게 했으니 보안 끝"이 아니다. 권한·유지보수 허용·프로그램 권한 체크는 별도 주제다.
  • 여러 테이블 결합 → Projection View는 단일 테이블 전용. 결합은 나 코드 JOIN. 계산·가공 컬럼은 클래식 View가 아니라 CDS의 영역이다 (Chapter 23 · CDS View Entity 예고).

정리

  • 는 단일 테이블에서 필요한 필드만 드러내는 DDIC View다.
  • DB에 SQL View를 만들지 않는다. 런타임이 basis table 읽기로 바꿔 실행한다.
  • 데이터를 복사하지 않고, 행을 새 조건으로 거르지도 않는다.
  • "사용자에게 필요한 컬럼만 보여 주는 것도 설계"라는 감각이 핵심이다.

조회용·필드제한 View는 봤다. 이제 F4 입력도움말의 원천으로 쓰는 View가 있다 → 다음 레슨(Help View).
