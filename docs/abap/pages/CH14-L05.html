Classic DDIC View·유지보수 객체

Table Maintenance Generator / SM30

테이블·View에 표준 유지보수 화면을 생성 — SM30로 운영.

Track 1Chapter 14Lesson 5중급

설계도는 있는데 문이 없다

앞 레슨에서 무엇과 무엇을 함께 유지보수할지 로 적어 뒀다. 그런데 담당자에게 "이제 공연을 등록하세요"라고 넘길 화면이 없다. 설계도만 있고 문이 안 달린 셈이다. 화면을 직접 짜는 방법이 없는 건 아니지만, 입력칸을 하나씩 배치하고 저장 버튼의 동작까지 코드로 쓰는 일이라 기준 데이터 하나 관리하자고 할 일은 아니다.

다행히 SAP은 그 화면을 자동으로 찍어 내 준다.

화면을 찍어 내는 도구 — TMG

테이블이나 에 표준 입력 화면을 자동으로 만들어 주는 도구가 다. 이름이 길어서 현장에서도 앞 글자만 따 TMG라고 부른다. 이 레슨부터 나오는 TMG는 전부 Table Maintenance Generator를 가리킨다. 만든 뒤엔 SM30으로 데이터를 입력·수정한다.

🧷 앞 레슨의 Maintenance View는 "무엇을 함께 관리할지" 적은 DDIC 설계도였다. TMG가 만들어 내는 Maintenance Dialog는 그 설계도로 찍어 낸 실제 화면과 프로그램이다. 이름이 비슷해도 층이 다르다.

먼저 정할 것 — One Step vs Two Step

곧 생성 화면에서 Maintenance Type(유지보수 유형)을 고르라고 한다. 두 선택지의 뜻을 먼저 알고 들어가자.

  • One Step(1단계) — 목록 화면 하나에서 바로 입력·수정한다. 필드가 적은 단순 테이블에 알맞다.
  • Two Step(2단계) — 목록(개요) 화면 + 상세 화면 둘로 나뉜다. 한 행에 필드가 많아 한 화면에 다 안 들어갈 때, 목록에서 행을 고르고 상세 화면에서 편집한다.

💡 필드가 적으면 One Step, 많으면 Two Step. 나중에 바꿔 재생성할 수도 있다.

생성 (SE11 → Utilities)

SE11에서 대상 테이블이나 View를 열어 둔 채 Utilities 메뉴 → . (앞 레슨에서 봤듯 SE54로 들어가도 같은 화면이다.)

생성 화면에서 채우는 칸은 넷이다. 무엇을 넣는 칸인지 알고 채우자.

칸 무엇을 넣나
Authorization Group 이 화면을 열 수 있는 사람을 묶는 권한 그룹 이름. 교육 시스템에서는 안내받은 값을 넣는다.
Function Group 생성될 화면과 프로그램이 담길 그릇 이름. 필수다. 보통 대상 이름을 따 ZCONCERT처럼 새로 만든다(없으면 그 자리에서 만들지 묻는다).
Maintenance type 위에서 정한 One Step / Two Step.
Maintenance screen number 만들어질 화면에 붙일 번호. 직접 정하는 게 아니라 Find scr. number(s) 버튼을 누르면 비어 있는 번호를 시스템이 채워 준다. 그대로 쓰면 된다(Two Step이면 개요·상세 두 칸이 채워진다).

네 칸을 채운 뒤 Create를 누르면 표준 유지보수 화면(추가·수정·삭제)이 만들어진다.

📌 Function Group은 비워 둘 수 없다. 이 이름이 나중에 화면을 다시 찾거나 재생성할 때 기준이 되니, 아무 이름이나 넣지 말고 대상 테이블·View를 알아볼 수 있는 이름으로 정하자.

운영 (SM30)

TEXT
1
SM30 → 테이블·View 입력 → Maintain → 행 추가·수정·삭제 → 저장
  • SM30 — 단일 View·테이블 유지보수.
  • 저장 시 (이송 대상이면) 에 함께 담긴다(Chapter 1 · 로컬 오브젝트와 이송의 그 흐름).

SM30 문이 열리기까지

SM30은 "마법 주소"가 아니다. 테이블 활성화 → 유지보수 허용(Display/Maintenance) → TMG 생성 → 권한까지 모두 맞아야 열린다. 어느 하나라도 빠지면 화면이 안 열리거나 저장이 막힌다. 직접 게이트를 켜며 어디서 막히는지 확인해 보자.

Maintenance Dialog — 장단점

Generator가 만들어 주는 표준 유지보수 화면(Maintenance Dialog)은 공짜로 얻는 게 많다.

장점 단점
코딩 없이 입력·수정·삭제 화면 자동 생성 레이아웃 커스터마이즈가 제한적
입력검증(Chapter 9 · Foreign Key)·F4(Chapter 9 · Elementary Search Help)·이송 연동이 그대로 복잡한 업무 로직엔 부족
권한 그룹으로 접근 통제 (일부는 이벤트로 보완)

단순 마스터데이터 유지보수엔 이걸로 충분하다. 화면을 마음대로 꾸미거나 복잡한 로직이 필요하면 별도 화면(Chapter 16 · Dynpro 기초)을 고려한다.

흔한 실수와 점검

  • Generator 없이 SM30 → "유지보수가 정의되지 않았다"는 오류를 만난다. 먼저 Generator로 화면을 만든다.
  • 권한 그룹 미지정 → 통제가 사라지는 게 아니라, 그 테이블이 &NC&(미분류) 그룹으로 묶인다. 권한 검사는 계속 일어나지만 미분류 권한을 가진 사람 전체에게 한꺼번에 열리는 셈이라, 결과적으로 통제가 헐거워진다.
  • Delivery Class·Recording Routine 무시 → 둘 다 "이 데이터가 시스템 사이를 옮겨 다니느냐"에 관한 설정이다. Delivery Class(전달 클래스)는 테이블을 만들 때 정하는 성격 표시로, 개발 시스템에서 정해 운영 시스템으로 함께 옮겨 갈 customizing 데이터(설정값)인지, 각 시스템에 각자 쌓이는 local 데이터(그 시스템 안에서만 쓰는 데이터)인지를 나타낸다. Recording Routine(기록 방식)은 TMG 화면에서 저장할 때 그 변경을 에 담을지 말지를 정하는 칸이다. 둘을 성격과 다르게 두면, 옮겨 가야 할 설정이 개발 시스템에만 남거나 반대로 옮길 필요 없는 데이터가 매번 이송요청에 딸려 온다.
  • 생성 성공 ≠ 유지보수 가능 → 반드시 SM30에서 열어·저장·재조회까지 확인한다.

정리

  • (TMG)는 테이블·View에 표준 입력 화면을 찍어 내는 도구다.
  • 생성 화면에서 권한 그룹·Function Group·유지보수 유형·화면 번호를 정한다(Function Group은 필수).
  • 만든 화면은 SM30으로 연다. 활성화·유지보수 허용·생성·권한이 모두 맞아야 열린다.
  • 설계도()와 찍어 낸 화면(Maintenance Dialog)은 다른 층이다.

이제 한 테이블에 표준 화면을 붙였다. 그런데 연관된 여러 테이블을 함께 유지보수하려면? → 다음 레슨(View Cluster).
