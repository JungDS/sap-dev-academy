실습 — 예매 RAP 따라 짓기와 시뮬레이터 검증

콘서트 예매 RAP를 따라 짓고 시뮬레이터로 검증 — 정원 validation·취소 action·상태 determination.

🎫 조각을 하나의 예매 흐름으로

이제 이 챕터의 조각을 하나의 콘서트 예매 흐름으로 묶는다. 목표는 "RAP 앱 전체를 완벽히 운영 배포한다"가 아니라, RAP 구조를 실제 예매 시나리오에 연결해 보는 것이다. 산출물 코드는 아래 순서대로 따라 짓고, 동작 흐름은 이 페이지의 시뮬레이터로 검증한다. 실습의 핵심은 둘이다 — 정원 초과 예매는 validation으로 막고, 취소는 action으로 명시 실행한다. 여기에 생성 시 기본 상태를 determination으로 채우면 세 로직의 차이를 한 번에 확인할 수 있다.

Projection BDEF — 서비스에 노출할 동작을 고른다

여기까지의 BDEF와 behavior pool은 전부 기반 BO ZI_Booking 쪽 이야기다. 그런데 서비스가 노출하는 건 Projection View ZC_* 설계에서 만든 ZC_Booking이다. ZC_Booking에는 아직 "무엇을 할 수 있는지"가 하나도 붙어 있지 않다 — 이대로 서비스를 열면 조회만 되고, 생성 버튼도 cancel도 보이지 않는다. 그래서 소비 모델 쪽에도 behavior가 필요하다. 다만 새로 구현하는 게 아니라, 기반 BDEF가 이미 허용한 동작 중 무엇을 노출할지 고르는 BDEF다. 이것이 Projection BDEF(ZC_Booking용 behavior definition)다.

코드 뜻
projection; 이 BDEF가 기반 BDEF를 투영하는 projection BDEF임을 선언한다(맨 앞에 반드시 온다).
define behavior for ZC_Booking 투영 대상은 projection view ZC_Booking이다. 이름이 ZI_가 아니라 ZC_인 점을 확인한다.
use create; use update; use delete; 기반 BDEF의 표준 operation을 재사용해 소비 모델에 노출한다.
use action cancel; 기반 BDEF에 선언한 cancel action을 서비스까지 노출한다. 이 한 줄이 없으면 화면에 취소 버튼이 안 생긴다.

세 가지만 기억하면 된다.

  • 자동 은 없다. 기반 BDEF에 있어도 여기 use로 적지 않은 동작은 ZC_Booking에서 쓸 수 없다. "서비스에서 cancel이 안 보여요"의 단골 원인이다.
  • 구현은 다시 안 짠다. use한 동작은 기반 behavior pool의 구현을 그대로 쓴다. 그래서 이 projection BDEF에는 implementation in class도, 별도 behavior pool도 필요 없다.
  • validation·determination은 use 대상이 아니다. 둘은 소비자가 호출하는 operation이 아니라 저장 흐름 안에서 기반 BO가 스스로 실행하는 내부 로직이라, 기반 BDEF에만 선언하면 projection을 거쳐도 자동으로 함께 동작한다.

저장은 언제 일어나나 — EML 개념 지도

입문자가 RAP에서 가장 크게 오해하는 지점은 "예매를 만들면 곧바로 DB에 저장된다"는 것이다. 실제로는 두 단계다. 예매자 정훈영이 새 예매를 넣으면, 그 변경은 먼저 에만 반영된다. DB에 실제로 쓰이는 것은 그다음이다.

프로그램에서 RAP BO를 직접 다루는 언어를 (Entity Manipulation Language)이라 한다. 흐름은 이렇다.

문장 무엇을 하나
MODIFY ENTITIES 생성·수정·삭제 요청을 buffer에 넣는다(아직 DB 아님).
COMMIT ENTITIES 를 트리거해 buffer를 검사·조정한 뒤 DB에 all-or-nothing(전부 저장되거나 전부 안 되거나 — 일부만 저장은 없다)으로 저장한다.
ROLLBACK ENTITIES 현재 트랜잭션의 buffer·lock을 정리(취소)한다.

핵심 두 가지만 기억하면 된다.

  • 저장 트리거는 COMMIT ENTITIES다. MODIFY ENTITIES 직후 테이블을 SELECT하면 아직 안 보일 수 있다 — 버퍼에만 있으니까.
  • behavior pool은 스스로 COMMIT하지 않는다. 위 validate_capacity·cancel 안에서 우리가 본 IN LOCAL MODE는 같은 BO를 내부에서 다루는 특수 형태이고, 실제 저장 확정은 Fiori/OData runtime이나 외부 consumer가 맡는다.

🔎 여기서는 "언제 저장되나"라는 개념 지도까지만. 외부 프로그램이 MODIFY → COMMIT/ROLLBACK ENTITIES로 RAP BO를 직접 호출하고 failed/reported를 처리하는 실전 코드는 외부 EML Consumer — MODIFY에서 COMMIT까지에서, Draft·Lock·ETag 같은 동시성 심화는 Draft · Lock · ETag · Authorization 심화에서 다룬다.

직접 실행해 보기

아래 시뮬레이터에서 예매를 생성하면 determination이 상태를 채우고 validation이 정원을 검사한다. 정원을 넘으면 failed/reported로 거부되고, 취소는 action으로 실행된다 — 어느 RAP 단계에서 무엇이 바뀌는지 보자.

확인 체크리스트

케이스 입력 기대 결과
정상 생성 좌석 2, 잔여 10 저장 성공, 상태 N
정원 초과 좌석 12, 잔여 10 validation 실패, failed/reported 메시지
취소 상태 N 예매에 cancel 상태 C
중복 취소 이미 C인 예매에 cancel 상태 변화 없음 + "이미 취소된 예매" 안내(no-op — 요청은 받되 아무것도 바꾸지 않는 처리)
service preview binding 활성화 후 preview Booking 목록·cancel action 노출

흔한 실수와 점검 🚧

  • validation 실패를 화면 메시지로만 → 실패 instance를 failed에, 사용자 메시지를 reported에 기록해야 runtime·UI가 제대로 반응한다.
  • 정원 계산을 현재 입력 좌석만 보기 → 같은 회차의 기존 예약 좌석 합계(취소된 예매는 빼고)에 이번 요청 좌석과 아직 저장 전인 현재 transaction의 변경분까지 더해서 정원과 비교해야 한다(실습에선 이 기준을 설계 질문으로 적어 둔다).
  • 동시 예매 경합까지 막았다고 믿기 → lock master의 잠금은 예매 건 단위다. 서로 다른 두 예매가 같은 회차의 마지막 좌석을 동시에 요청하면 둘 다 검증을 통과할 수 있다. 회차 정원 같은 공유 자원 보호는 Lock Object 설계 기준의 잠금 설계 주제다(지금은 한계만 알아 두자).
  • action과 determination 섞기 → 취소는 사용자가 명시 실행하므로 action, 생성 시 기본 상태는 자동 결정이므로 determination이 자연스럽다(Validation / Determination / Action 개요).
  • IN LOCAL MODE 남용 → behavior implementation에서 해당 RAP BO 자체를 읽는 특수 형태다(Behavior Implementation 기초). 일반 소비 프로그램에 습관적으로 붙이는 문법이 아니다.
  • 직접 DML로 우회 → behavior pool 안에서 테이블을 직접 바꾸면 RAP buffer·를 우회할 수 있다. 직접 DB 변경은 INSERT / UPDATE / MODIFY / DELETE 실무 기준에서 따로 다룬다.

🎓 기초·Modern 두 트랙을 마치며 — 환경(Chapter 1)부터 RAP까지, 읽고 → 모델링하고 → 화면을 만들고 → 로 설계하고 → 트랜잭션 앱의 골격까지 한 바퀴를 돌았다. 이 과정에서 키운 콘서트 예매 앱이 그 여정의 산출물이다.

이번 실습에서는 그 예매 앱의 RAP 골격을 따라 짓고, 시뮬레이터로 validation·determination·action의 동작을 검증했다. 여기까지가 기초(Track 1)와 Modern(Track 2)의 여정이다. 이제 실무 심화(Track 3) — 직접 DB 변경(DML) → INSERT / UPDATE / MODIFY / DELETE 실무 기준.
