ABAP Unit 운영 — 회귀를 막는 게이트

고친 코드가 기존 약속을 깨지 않았는가 — 테스트를 운영 게이트로 쓴다.

Track 2Chapter 38Lesson 2고급독립 모듈

고쳤더니 다른 게 깨졌다

정산 로직에서 잔여 좌석 계산식을 조금 손봤다. 수정한 기능은 잘 돈다. 그런데 일주일 뒤, 전혀 안 건드린 줄 알았던 다른 회차의 잔여 표시가 틀린다는 티켓이 온다. 이런 사고를 (수정이 기존에 잘 되던 기능을 깨뜨리는 것)라 부른다. 화면에서 한두 번 눌러 본 확인으로는 못 막는다. 모든 기존 약속을 사람이 매번 다시 검증할 수는 없기 때문이다.

테스트 문법은 이미 배웠다. Chapter 27 · Testable Class와 ABAP Unit에서 FOR TESTING class와 cl_abap_unit_assert, 의존성 주입과 Mock까지 만들었다. 이 레슨의 질문은 문법이 아니라 운영이다: 그 테스트를 언제, 어디서, 무엇을 막는 데 쓰는가.

테스트 = 업무 약속의 자동 감시자

관점을 이렇게 바꾸자. 테스트 하나는 업무 약속 하나를 코드로 박제한 것이다.

재료는 Chapter 27에서 만든 그대로다: zcl_booking_manager는 정원과 예약 수를 주입받은 mo_repo(repository interface)에 물어서 정원 − 예약 = 잔여를 계산한다. 테스트용 Mock이 어떤 값을 돌려주는지부터 표로 못 박자(계산 전제가 코드 밖에 숨지 않게).

Mock get_capacity(정원) get_booked(예약) 기대 잔여
ltd_booking_repo(CH27 그대로) 100 50 50
ltd_repo_empty(이번에 추가 — 반환값 두 줄만 다르다) 100 0 100

CLASS ltd_repo_empty DEFINITION FOR TESTING.
  PUBLIC SECTION.
    INTERFACES zif_booking_repo.
ENDCLASS.
CLASS ltd_repo_empty IMPLEMENTATION.
  METHOD zif_booking_repo~get_capacity. rv_capacity = 100. ENDMETHOD.
  METHOD zif_booking_repo~get_booked.   rv_booked   = 0.   ENDMETHOD.
ENDCLASS.

CLASS ltcl_settlement DEFINITION
  FOR TESTING RISK LEVEL HARMLESS DURATION SHORT.
  PRIVATE SECTION.
    " 약속: "정원 100, 예약 50이면 잔여는 50이다"
    METHODS remaining_is_total_minus_booked FOR TESTING.
    " 약속: "지난달 회귀(예약 0건 회차에서 잔여가 0으로 나오던 버그)는 다시 없다"
    METHODS regression_of_last_month FOR TESTING.
ENDCLASS.

CLASS ltcl_settlement IMPLEMENTATION.
  METHOD remaining_is_total_minus_booked.
    DATA(lo_mgr) = NEW zcl_booking_manager(
      iv_concert = 'C001'
      iv_perf    = '01'
      io_repo    = NEW ltd_booking_repo( ) ).   " Mock 주입(CH27 그대로)
    cl_abap_unit_assert=>assert_equals(
      act = lo_mgr->remaining( )
      exp = 50 ).
  ENDMETHOD.

  METHOD regression_of_last_month.
    " 지난달 사고: 예약이 한 건도 없는 새 회차에서 잔여가 100이 아니라
    " 0으로 나왔다(빈 결과 처리 버그). 위의 정상 케이스(예약 50)로는 안
    " 잡히던 입력이다 — 버그를 고치며 그 입력을 재현하는 테스트를 남긴다
    DATA(lo_mgr) = NEW zcl_booking_manager(
      iv_concert = 'C001'
      iv_perf    = '01'
      io_repo    = NEW ltd_repo_empty( ) ).
    cl_abap_unit_assert=>assert_equals(
      act = lo_mgr->remaining( )
      exp = 100 ).                      " 정원 100 − 예약 0
  ENDMETHOD.
ENDCLASS.

문법은 전부 CH27에서 본 그대로다. 새로 볼 것은 테스트 이름이다. test1이 아니라 regression_of_last_month — 이름 자체가 약속을 설명한다. 그래야 이 테스트가 빨간불이 됐을 때 "어떤 약속이 깨졌는지"가 이름만으로 읽힌다. (반환값만 다른 Mock을 매번 복제하는 게 번거롭게 느껴진다면 정확한 감각이다 — 그 노동을 없애는 도구가 다음 레슨의 framework다.)

한 가지 경계도 그어 두자. "취소(status C)된 좌석은 예약에서 빠진다"는 약속도 있는데, 그 필터링은 manager가 아니라 repository의 SELECT(WHERE 조건) 책임 이다. Mock을 주입한 unit test는 manager의 계산만 보므로 그 약속은 여기서 검증할 수 없다 — SELECT 자체를 검증하는 방법이 다음 레슨에 있다(거기서 이 약속을 회수한다).

이제 누군가 계산식을 잘못 바꾸면, 배포 전에 이 테스트가 red(실패)로 바뀐다. 사람이 기억하지 않아도 약속이 스스로 감시한다. 이것이 회귀 방어선이다.

게이트에 거는 법 — 어디서 실행되는가

테스트는 실행되는 자리에 따라 값어치가 달라진다. 세 단계로 본다.

단계 실행 방식 막아 주는 것
Local run ADT에서 Ctrl+Shift+F10(또는 우클릭 → Run As → ABAP Unit Test). 결과는 ABAP Unit 탭 — 실패한 를 열면 expected/actual이 나온다 내 실수를 내 자리에서, 배포 전에
Release gate 이송 release 시점에 ATC와 함께 자동 실행(앞 레슨의 게이트에 테스트가 포함됨) 깜빡하고 안 돌린 채 내보내는 사고
CI(지속 통합) 변경이 모일 때마다 자동 실행되는 별도 파이프라인(ABAP에서는 보통 git 연동 도구 위에 구성). 존재만 알아 두자 — 구성은 프로젝트 인프라 영역 여러 사람의 변경이 합쳐질 때의 충돌

핵심은 두 번째다. local run은 성실함에 의존하지만, release gate는 강제된다. "테스트가 있다"와 "테스트가 release를 막을 수 있다"는 운영에서 완전히 다른 문장이다. 알아 둘 현실 셋: ① 게이트에 unit test까지 포함되는 것은 기본값이 아니라 설정이다(release 소요 시간 때문에 의도적으로 빼는 프로젝트도 흔하다 — 켜져 있는지는 release 때 검사가 자동으로 도는지로 확인, L01). ② 게이트는 그 이송에 담긴 에 붙은 테스트만 돌린다 — 로직을 고쳤는데 테스트가 엉뚱한 class에 있으면 게이트는 침묵한다. 테스트를 대상 class의 로컬 테스트 에 두는 이유다. ③ 테스트는 DEV/QAS의 장치이고 운영(PRD)에서는 실행되지 않는 것이 정상이다. 개발자의 몫은 게이트에서 돌 자격을 갖춘 테스트를 만들어 두는 것 — 그 자격이 다음 절이다.

게이트에 넣을 수 있는 테스트의 조건

아무 테스트나 게이트에 걸 수는 없다. 게이트는 자주, 자동으로, 아무 시스템에서나 돌기 때문이다.

  • 외부 상태에 흔들리지 않는다 — 실 DB 데이터·오늘 날짜·화면 입력에 의존하면, 코드가 멀쩡해도 데이터 사정으로 red가 된다. "가끔 실패하는 테스트"는 곧 무시되고, 무시되는 순간 게이트가 죽는다. 의존성을 끊는 도구가 다음 레슨이고, 거기서 격리한 테스트는 실 DB 의존이 아니므로 게이트에 넣을 수 있다.
  • 선언이 실제와 맞다 — RISK LEVEL HARMLESS라고 적고 실제로는 데이터를 바꾸면 게이트가 그 테스트를 신뢰할 수 없다(시스템 설정이 위험 등급별 실행 허용을 제한할 수 있어, 거짓 선언은 "돌면 안 되는 곳에서 도는" 사고로 이어진다). DURATION SHORT인데 오래 걸리는 테스트는 자주 돌리기 어렵다(두 선언의 뜻은 Chapter 27 복습).
  • 공개 동작을 검증한다 — private 내부 변수까지 파고드는 테스트는 리팩터링 때마다 억울하게 깨진다. 결과(잔여=50)를 검증하면 구현을 바꿔도 약속만 지키면 초록이다.

어느 테스트가 게이트감인지 판별해 보자.

흔한 실수와 점검 🚧

  • red를 보고 expected를 고침 → 테스트가 깨졌다는 것은 약속이 깨졌다는 뜻이다. 먼저 물을 것은 "약속이 바뀐 게 맞는가?"이지 "어떻게 초록으로 만들까"가 아니다.
  • 거대 테스트 하나 → 실패해도 어디가 깨졌는지 모른다. 약속 하나 = 테스트 하나로 작게 나눈다.
  • 실 DB 의존 테스트를 게이트에 → 데이터 상태 따라 흔들려 "늑대가 나타났다"가 된다. 흔들리는 테스트는 게이트에서 빼고 의존성부터 끊는다.
  • 테스트 없는 수정의 반복 → 회귀를 겪은 지점이야말로 테스트 1순위다. 버그를 고칠 때 "그 버그를 재현하는 테스트"부터 추가하면 같은 사고가 두 번 나지 않는다.

정리 📌

  • 회귀 = 수정이 기존 약속을 깨는 사고. 방어선 = 약속을 이름에 담은 작은 테스트들.
  • 실행 자리 3단계 = local run(성실함) → release gate(강제) → CI(통합). 게이트에 걸려야 운영 장치다.
  • 게이트감 테스트 = 외부 상태 무의존 + 선언과 실제 일치 + 공개 동작 검증.

그런데 현실의 코드는 DB를 직접 읽고, 권한을 검사하고, legacy라 분리도 안 돼 있다. 이런 의존성을 끊고 테스트하는 전문 도구들로 간다.
