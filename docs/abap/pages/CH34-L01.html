📦 파일보다 똑똑한 봉투가 필요하다

Chapter 33 · File Interface에서 서버 파일로 데이터를 주고받았다. 그런데 기업 간 거래나 SAP 시스템끼리의 표준 연계에는 파일 한 줄로는 부족한 정보가 있다. 누가 보냈고, 누가 받아야 하고, 무슨 업무 메시지이고, 지금 어디까지 처리됐고, 실패했다면 왜 인지가 메시지 자체에 붙어 다녀야 한다.

그 답이 (Intermediate Document)이다. 등기우편을 떠올리면 정확하다. 일반 쪽지 (파일)와 달리 등기우편에는 송장(누가→누구에게)이 붙고, 내용물이 들어 있고, 배송 조회 이력(접수→발송→배달 완료/반송)이 남는다. IDoc은 주문·송장·예매 통지 같은 업무 문서를 시스템 사이에서 비동기로 나른다. 비동기란 보낸 쪽이 상대의 처리 완료를 기다리지 않고 다음 일을 한다는 뜻이다(즉시 응답을 기다리는 RFC와 다른 점).

🖥️ 이 챕터의 실습 방식 — IDoc/ALE/Gateway는 연결된 시스템 두 대와 별도 구성이 있어야 실제로 돌려볼 수 있는 영역이다. 그래서 이 장은 구조와 상태를 눈으로 읽는 장이고, 직접 해보기는 각 레슨의 시뮬레이터가 대신한다.

이 구조가 왜 중요한가. 파트너 예매 통지 1,000건 중 37건이 실패했다고 하자. "연계가 실패했습니다"로는 아무도 움직일 수 없다. 운영자는 어느 메시지가, 어느 단계에서, 어떤 값 때문에 실패했는지 알아야 한다. IDoc은 그 추적을 표준으로 만들어 둔 봉투다.

3층 구조 — 송장·내용물·배송 이력

층 등기우편 비유 담는 것
Control Record 송장 발신자·수신자·메시지 종류·방향· 번호
Data Records 내용물 실제 업무 데이터 — Segment(데이터 조각)들의 묶음
Status Records 배송 조회 이력 생성→전송→수신 처리→성공/실패의 단계별 기록

세 층은 각각 표준 테이블(EDIDC·EDIDD·EDIDS)에 저장되지만, 지금 외울 것은 테이블명이 아니라 "송장 따로, 내용물 따로, 이력 따로"라는 분리다. 장애 분석이 빠른 이유가 이 분리에 있다: 주소가 틀렸으면 송장을, 값이 틀렸으면 내용물을, 어디까지 갔는지는 이력을 보면 된다.

용어 두 개는 꼭 갈라 두자.

용어 뜻 예
Message Type 무슨 업무 메시지인가 ORDERS(주문)
Basic Type 그 메시지의 구조 버전(어떤 Segment 구성인가) ORDERS05

같은 주문(ORDERS)이라도 구조 버전(ORDERS05)이나 고객 확장(extension)에 따라 내용물 구성이 다를 수 있다. "업무 의미"와 "실제 구조"가 별도 이름을 가진다는 것만 기억하면 현장 대화의 절반이 풀린다.

내용물은 Segment 반복 묶음

주문 이라면 내용물(Data Records)은 이렇게 생겼다: 헤더 Segment 1건 + 품목 Segment 여러 건 + 파트너 Segment…. Chapter 6 · Internal Table을 배운 이유가 여기서 드러난다. 연계 데이터는 납작한 한 줄이 아니라 반복되는 조각의 묶음으로 온다.

수신(Inbound) 처리 프로그램의 뼈대를 개념으로만 보자. 실제 함수 구조는 메시지 종류마다 다르지만, "Segment 이름을 보고 갈라 읽는다"는 감각은 같다.

직접 열어 보기

봉투의 세 층을 클릭해 열어 보라. 오류 보기에서는 상태만 보면 "실패"뿐이지만, 내용물의 특정 Segment를 열면 원인 값이 보인다. 상태와 내용물을 함께 읽는 습관이 이 레슨의 목표다.

화면 참조표 🗂

본문에서는 역할 이름으로 불렀다. 실제 화면(T-code)은 참조용으로만 묶어 둔다.

역할 T-code
모니터(목록·상세) WE02 / WE05
Basic Type 구조 문서 WE60

흔한 실수와 점검 🚧

  • 을 "큰 문자열 하나"로 → 송장·내용물·이력이 분리된 구조다. 분석도 "IDoc 실패"에서 멈추지 말고 "어느 상태에서, 어느 Segment 값 때문에"로 좁힌다.
  • Message Type과 Basic Type 혼용 → ORDERS는 업무 의미, ORDERS05는 구조 버전. 같은 업무라도 구조가 다를 수 있다.
  • 방향 혼동 → Inbound(우리가 받음)·Outbound(우리가 보냄)에 따라 같은 상태도 담당 지점이 달라진다. 상세를 열면 방향부터 말로 설명해 보라.
  • 정상 구조를 안 봄 → 실패 건만 보면 뭐가 "있어야 할 값"인지 모른다. 정상 IDoc의 구조 문서를 먼저 봐 둔다.

정리 📌

  • = 등기우편. **송장(Control)·내용물(Data=Segment 묶음)·배송 이력(Status)**의 3층.
  • Message Type = 업무 의미, Basic Type = 구조 버전. 별개의 이름이다.
  • 장애 분석 = 이력에서 단계 확인 → 내용물에서 원인 값 확인. 둘을 함께 읽는다.

봉투는 이해했다. 그럼 이 봉투를 누가 누구에게 보내는지는 어디서 정할까? 배송망을 설계하는 ALE로 간다.
