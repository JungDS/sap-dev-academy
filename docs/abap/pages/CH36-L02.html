DB 프로시저에 ABAP의 옷을 입힌다

사다리 3번째 칸이다. DB 안에서 중간 결과를 만들고 그걸 다시 조합하는 절차 로직이 필요하다고 하자. SQL 한 문장으로는 안 되고, 그렇다고 전부 ABAP으로 끌어오면 이동량이 폭발한다.

(ABAP Managed Database Procedure)가 그 자리의 도구다. DB 프로시저를 ABAP 의 모습으로 관리한다. 호출하는 쪽은 평범한 메서드 호출로 보이지만, 구현부는 (HANA의 프로시저 언어)로 쓰여 DB 안에서 실행된다.

첫 목표는 SQLScript 전문가가 되는 것이 아니다. ABAP과 DB 실행부가 어디서 갈라지는지 읽어내고, 직접 하나 만들 수 있게 되는 것이다.

🔭 기대 관리 — AMDP 클래스는 ADT(Eclipse 기반 ABAP 개발 도구, Chapter 23에서 만난 그 도구)에서만 만들고 고칠 수 있다. SE38/SE80에서는 열람만 된다. 실행에는 HANA DB가 필요하므로, 이 페이지에서는 구조와 실행 흐름을 시뮬레이션으로 해부한다.

CLASS zcl_booking_amdp DEFINITION
  PUBLIC FINAL CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES if_amdp_marker_hdb.     " ① HANA AMDP 클래스 표시

    TYPES:
      BEGIN OF ts_stat,                " 결과 한 행(공연별 집계)
        mandt       TYPE mandt,        " GROUP BY 키를 그대로 반환(빼도 됨)

        concert_id  TYPE zconcert-concert_id,
        booking_cnt TYPE i,
        total_seats TYPE i,
      END OF ts_stat,
      tt_stat TYPE STANDARD TABLE OF ts_stat
        WITH EMPTY KEY.               " 키로 찾을 일 없는 결과용 관례

    CLASS-METHODS get_stats
      IMPORTING VALUE(iv_client)  TYPE mandt
                VALUE(iv_concert) TYPE zconcert-concert_id
      EXPORTING VALUE(et_stats)   TYPE tt_stat
      AMDP OPTIONS READ-ONLY.          " ② 읽기 전용 AMDP 선언
ENDCLASS.

CLASS zcl_booking_amdp IMPLEMENTATION.
  METHOD get_stats BY DATABASE PROCEDURE  " ③ 구현부 = DB 프로시저
                   FOR HDB
                   LANGUAGE SQLSCRIPT
                   OPTIONS READ-ONLY
                   " ④ 접근할 DB 객체 선언 ↓
                   USING zbooking.

    -- 여기부터는 SQLScript다 (주석도 ABAP의 "가 아니라 --)
    et_stats =
      SELECT mandt,
             concert_id,
             COUNT(*)     AS booking_cnt,
             SUM( seats ) AS total_seats
        FROM zbooking
       WHERE mandt      = :iv_client    -- :파라미터 표기(@ 아님)
         AND concert_id = :iv_concert
       GROUP BY mandt, concert_id;

  ENDMETHOD.
ENDCLASS.
  • ① INTERFACES if_amdp_marker_hdb — "이 에 HANA AMDP가 있다"는 표시. 이런 용도의 를 marker interface라 부른다: Chapter 21에서 배운 "메서드 약속"과 달리, 구현할 메서드가 하나도 없는 빈 인터페이스를 시스템에 알리는 표지판으로만 쓴다. 이게 없으면 AMDP 구현 자체가 안 된다.
  • ② AMDP OPTIONS READ-ONLY — 선언부의 읽기 전용 표시. 성능 옵션이 아니라 쓰기 금지 제약이다. 이 안에서 DB 변경이 금지되고, 호출 가능한 다른 AMDP도 읽기 전용으로 제한된다. 선언부는 호출자에게 알리는 계약, 구현부의 OPTIONS READ-ONLY(③ 아래)는 실제 프로시저에 거는 옵션이라 둘을 함께 쓰는 것이 표준형이다. ABAP Cloud(제약된 클라우드용 ABAP 환경)에서는 이런 제약 준수가 전제라 특히 중요하다.
  • ③ BY DATABASE PROCEDURE FOR HDB LANGUAGE SQLSCRIPT — 이 메서드의 몸은 ABAP이 아니라 HANA에서 도는 라는 선언.
  • ④ USING zbooking — SQLScript가 접근하는 테이블·뷰·다른 AMDP를 정적으로 알린다. 이 목록이 있어야 시스템이 의존성(where-used·패키지 검사)을 추적한다.

가 전부 VALUE( )인 것도 우연이 아니다. AMDP 파라미터는 값 전달만 허용된다(DB로 건너가는 순간 참조가 의미 없어지기 때문). CLASS-METHODS(static)로 선언한 것은 관례다: 메서드도 가능하지만 상태 없는 DB 절차라 static이 자연스럽고, 이 챕터 뒤의 Table Function 구현(L05)은 아예 static이 필수다.

어떻게 만드는가 — ADT에서 네 걸음

Chapter 21에서 Global Class를 만들던 절차에 조금만 얹으면 된다.

  1. 생성(까지 한 번에) — ADT의 새 ABAP Class 마법사에는 Interfaces 입력란이 있다. 클래스 이름(zcl_booking_amdp)과 함께 IF_AMDP_MARKER_HDB를 여기서 추가하면 생성 시점에 골격이 잡힌다. (마법사에서 빠뜨렸다면 소스의 PUBLIC SECTION에 INTERFACES if_amdp_marker_hdb. 한 줄을 직접 추가해도 같다.)
  2. 선언 — 를 전부 VALUE( )로, 읽기 전용이면 AMDP OPTIONS READ-ONLY까지.
  3. 구현부 작성 — METHOD … BY DATABASE PROCEDURE FOR HDB LANGUAGE SQLSCRIPT … USING …을 쓰고, 몸통을 로 채운다.
  4. 활성화 — 이 순간이 AMDP의 "Managed"다. 활성화하면 시스템이 HANA에 프로시저를 만들어 관리한다. 개발자가 DB에 직접 들어가 프로시저를 만들 필요가 없다.

호출은 놀랄 만큼 평범하다. 그냥 static 메서드 호출이다.

호출부만 보면 DB 프로시저인지 알 수 없다. 그게 AMDP의 설계다. 복잡함은 클래스 안에 격리되고, 쓰는 쪽은 메서드 하나를 부른다. 세 가지 실전 메모:

  • ADT 전용은 편집이지 호출이 아니다. 이 호출 코드는 SE38 테스트 리포트에 넣어도 된다.
  • SQLScript 안은 디버거로 못 들어가지만, 결과 확인은 평소와 같다. 돌려받은 gt_stats를 WRITE나 ALV로 보면 된다.
  • 실습 전에 시스템 DB가 HANA인지 확인하라(모르면 운영/Basis 담당에게). HANA가 아니면 FOR HDB AMDP는 만들 수 없다.

Open SQL과 다른 세 가지

  1. 표기가 다르다 — ABAP SQL은 @iv_concert(Chapter 19), 안에서는 :iv_concert다. @를 쓰면 활성화가 실패한다.
  2. client를 직접 챙긴다 — Open SQL이 자동으로 넣어 주던 client 조건이 여기엔 없다. 위 예제가 iv_client를 받아 WHERE mandt = :iv_client를 직접 쓴 이유다. 빠뜨리면 다른 client의 데이터까지 읽는 사고가 난다.
  3. ABAP 문장 금지 — 구현부에 DATA·LOOP·READ TABLE을 쓸 수 없다. 몸은 SQLScript다.

그럼 왜 CDS가 아니라 AMDP인가 — 체이닝

여기서 정당한 질문이 나온다. "ABAP LOOP도 못 쓰는데, CDS View 대신 이걸 쓸 이유가 뭔가?"

답은 가 자기만의 절차를 갖고 있다는 데 있다. ABAP 문장을 못 쓸 뿐, SQLScript 안에서는 중간 결과를 테이블 변수에 담아 두고 다음 단계가 :변수로 재사용할 수 있다(공식 예제의 패턴이다). 이걸 체이닝이라 부르자.

CDS View (Chapter 23)
본질 선언 한 장 — "이 조회는 이렇게 생겼다" 절차 여러 단계 — 담고, 재사용하고, 나눠 돌려준다
중간 결과 재사용 불가 — 뷰는 결과를 저장하지 않는 정의라서, 쌓아도 단계마다 다시 계산 :변수로 몇 번이든
결과 개수 하나(그 뷰의 결과) 여러 개(EXPORTING 여러 벌)
어울리는 일 공유 조회 모델 다단계 ·다중 출력 리포트

그래서 판별 질문은 이것이다. "중간 결과를 두 번 이상 다른 용도로 쓰는가?" 그렇다면 AMDP의 제자리, 아니라면 CDS나 Open SQL의 자리다.

의미 있는 예제 — 한 번 집계해서 두 번 쓰기

공연 운영팀의 실제 요구다. "예매 현황에서 매진 임박 회차(예매율 80% 이상)와 부진 회차(30% 미만)를 한 번에 뽑아 달라."

정직하게 짚고 시작하자. 공연이 몇십 개뿐이라면 결과가 작으니, Open SQL로 집계해 ABAP에서 나누는 것도 정답이다. 가 이기는 지점은 따로 있다: ① 원천 스캔(100만 행)이 비싸고 ② 그 중간 결과를 여러 갈래로 재사용하며 ③ 갈래가 계속 늘어날 때(다음 달엔 "평균 대비"·"회차별"이 추가된다). Open SQL이면 갈래마다 비싼 스캔이 반복되거나 ABAP 후처리가 자라지만, AMDP는 비싼 집계 1회 + DB 안 재사용 N회로 고정된다.

  METHOD get_report BY DATABASE PROCEDURE FOR HDB
                    LANGUAGE SQLSCRIPT
                    OPTIONS READ-ONLY
                    USING zbooking zconcert.

    -- 단계 1: 회차별 예매 좌석을 '한 번만' 집계(정원=공연 단위·소진=회차별).
    --   lt_stat은 선언이 없다: SQLScript 테이블 변수는 대입으로 생긴다
    lt_stat = SELECT b.mandt,
                     b.concert_id,
                     b.perf_no,
                     c.capacity,
                     SUM( b.seats ) AS booked
                FROM zbooking AS b
                INNER JOIN zconcert AS c
                  ON  c.mandt      = b.mandt
                  AND c.concert_id = b.concert_id
               WHERE b.mandt  = :iv_client
                 AND b.status <> 'C'   -- 취소 제외
               GROUP BY b.mandt, b.concert_id, b.perf_no, c.capacity;

    -- 단계 2: 중간 결과 재사용 (1) 매진 임박 회차(예매율 80% 이상)
    et_hot  = SELECT * FROM :lt_stat
               WHERE booked >= capacity * 0.8
               ORDER BY booked DESC;

    -- 단계 3: 같은 중간 결과 재사용 (2) 부진 회차(30% 미만)
    et_slow = SELECT * FROM :lt_stat
               WHERE booked < capacity * 0.3
               ORDER BY booked ASC;

  ENDMETHOD.

(공연 50개 규모라면 이 예제도 ABAP 후처리로 충분하다는 점은 위에서 말한 그대로다. 포인트는 비싼 스캔이 한 번으로 고정되는 구조이고, 갈래가 늘수록 이 구조가 이긴다.)

단계별로 중간 변수에 무엇이 담기는지 직접 실행해 보라.

이제 최소 예제로 돌아가, 각 부품의 역할과 "무엇이 왜 깨지는지"를 확인하자.

어떻게 확인하는가

  1. tag interface — 에 IF_AMDP_MARKER_HDB가 있는가.
  2. 선언↔구현 일치 — 선언부 ·테이블 타입과 가 채우는 결과 구조가 맞는가. 어긋나면 활성화 또는 실행 시점에 깨진다.
  3. USING 완전성 — SQLScript가 읽는 모든 DB 가 USING에 있는가(위 예제라면 zbooking zconcert 둘 다).
  4. client 처리 — client 의존 테이블을 읽는다면 client 파라미터와 WHERE mandt 조건이 있는가.
  5. 재측정 — 로 바꿨다면 ST05 수치가 실제로 줄었는가. 같다면 복잡도만 늘린 것이다.

흔한 실수와 점검 🚧

  • USING 누락 → 가 읽는 테이블이 USING에 없으면 의존성 추적이 끊기고 활성화가 실패한다.
  • @ 혼용 → SQLScript 안에서는 :파라미터·:테이블변수다.
  • client 누락 → Open SQL 습관대로 자동 client를 기대하면 안 된다.
  • 단순 를 로 포장 → 공식 문서도 명시한다. 옮기는 것만으로 자동으로 빨라지지 않는다. 체이닝이 필요 없다면 Open SQL로.
  • ABAP 디버거 기대 → 구현부는 DB에서 돈다. Chapter 4의 ABAP 디버거로는 SQLScript 내부에 못 들어간다(SQLScript 디버깅은 ADT·DB 권한 필요).

정리 📌

  • = DB 프로시저를 ABAP 로 관리. 부품 4개 = marker interface · AMDP OPTIONS READ-ONLY · BY DATABASE PROCEDURE… · USING.
  • 만드는 절차 = 클래스 생성(마법사에서 marker interface 동시 추가) → 선언(VALUE( ) 필수) → 구현 → 활성화(시스템이 DB 프로시저를 생성·관리). 호출은 평범한 메서드 호출.
  • CDS와의 차이 = 체이닝: 중간 결과를 :변수로 재사용하고 여러 출력을 돌려준다. 판별 질문은 "중간 결과를 두 번 이상 쓰는가".
  • READ-ONLY는 성능 옵션이 아니라 쓰기 금지 제약. client는 언제나 직접.

프로시저는 ABAP에서 메서드처럼 불렀다. 그런데 더 아래 칸, DB 고유 SQL을 문자열로 직접 보내야 하는 순간도 있다. ADBC로 간다.
