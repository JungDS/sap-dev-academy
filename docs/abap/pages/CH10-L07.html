🎫 2단계 — 핵심 로직 모듈화

Chapter 09 · 콘서트 모델 실습에서 만든 테이블에, "이 회차 잔여석이 몇인가?", "이 예매가 가능한가?"를 계산하는 로직을 더한다. 여기저기 흩어 놓지 말고 모듈로 묶는다.

왜 FORM으로 만드나 — 바로 앞 Subroutine / Function Module / Class 선택 기준에서 "신규 로직은 클래스 메서드"라고 정리했다. 그런데도 이 실습을 FORM으로 여는 건 지금까지 배운 것만으로 처음부터 끝까지 완성해 보기 위해서다. 실무에서 새로 만드는 로직이라면 처음부터 메서드로 짠다. 그 모습은 아래 과제 3번에서 직접 만들어 본다.

잔여석 = 정원 − 예매 합계

집계 SQL(SUM)은 Chapter 13 · JOIN·집계에서 배우니, 지금은 예매를 읽어 LOOP로 합산한다(LOOP·SELECT).

FORM get_remaining
  USING    iv_concert TYPE zbooking-concert_id
           iv_perf    TYPE zbooking-perf_no
  CHANGING cv_left    TYPE i.

  DATA: lt_book TYPE TABLE OF zbooking,
        ls_book TYPE zbooking,
        lv_sum  TYPE i,
        lv_cap  TYPE zconcert-capacity.

  SELECT * FROM zbooking INTO TABLE lt_book
    WHERE concert_id = iv_concert AND perf_no = iv_perf
      AND status <> 'C'.                 " 취소 제외

  LOOP AT lt_book INTO ls_book.
    lv_sum = lv_sum + ls_book-seats.
  ENDLOOP.

  SELECT SINGLE capacity FROM zconcert INTO lv_cap
    WHERE concert_id = iv_concert.
  IF sy-subrc <> 0.          " 그런 공연이 아예 없다
    cv_left = -1.            " 매진(0)과 구분되는 '없음' 표시
    RETURN.
  ENDIF.

  cv_left = lv_cap - lv_sum.
ENDFORM.

공연이 없을 때 cv_left를 0으로 돌려주면 부르는 쪽에서 매진과 구분할 수 없다. 그래서 -1을 "그런 공연이 없다"는 표시로 정해 두고, 부르는 쪽에서 음수인지 먼저 확인한다.

⚠️ 위 SELECT *는 학습용 임시 형태다. 정작 필요한 건 seats 한 컬럼인데 전 컬럼을 다 읽어 왔고, 합계도 프로그램에서 LOOP로 더했다. 실무에서는 합계를 DB에 맡기는 쪽이 훨씬 빠르다. 그 방법이 위에서 예고한 Chapter 13 · JOIN·집계다.

예매 가능 판정

판정 결과는 참/거짓 하나다. ABAP에는 이런 값을 담는 표준 타입 abap_bool이 있고, 넣을 값도 abap_true(참)·abap_false(거짓)라는 이름으로 준비돼 있다. 'X'나 ' '를 직접 적는 것보다 뜻이 분명하다.

FORM can_book
  USING    iv_concert TYPE zbooking-concert_id
           iv_perf    TYPE zbooking-perf_no
           iv_want    TYPE i
  CHANGING cv_ok      TYPE abap_bool.

  DATA lv_left TYPE i.

  PERFORM get_remaining USING iv_concert iv_perf CHANGING lv_left.

  IF iv_want > 0 AND lv_left >= 0 AND iv_want <= lv_left.
    cv_ok = abap_true.     " 요청 좌석이 잔여석 안에 들어온다
  ELSE.
    cv_ok = abap_false.    " 요청이 0 이하거나, 공연이 없거나(-1), 자리가 모자라다
  ENDIF.
ENDFORM.

iv_want > 0을 왜 넣었을까. 상한만 검사하면 "0석 예매"나 "-2석 예매" 같은 요청도 버젓이 통과한다. 판정 모듈은 말이 안 되는 입력부터 걸러야 한다.

⚠️ 이 판정에도 빈틈은 있다. 두 사람이 거의 동시에 예매하면 둘 다 "자리 있음"을 확인한 뒤 둘 다 저장해, 정원을 넘겨 버릴 수 있다. 확인과 저장 사이를 잠금(ENQUEUE)으로 막는 방법은 Chapter 26 · Lock Object와 동시성 제어에서 배우니, 지금은 "혼자 쓸 땐 이걸로 충분하다"까지만 알아 두자.

직접 해 보기

get_remaining이 예매를 한 줄씩 합산해 잔여석을 만들어 내는 과정을 디버거처럼 따라가 보자.

잔여석이 나왔으면, 요청 좌석과 비교하는 can_book 판정도 만져 보자. 취소 건을 합산하면 왜 틀리는지도 확인할 수 있다.

직접 해 볼 과제

  1. get_remaining을 호출해 한 회차의 잔여석을 출력한다.

  2. 잔여석보다 많은 좌석을 요청해 can_book이 abap_false를 돌려주는지 확인한다. 0석으로도 요청해 보자.

  3. 같은 로직을 메서드로 옮겨 본다. Local Class로 모듈화에서 배운 대로 lcl_booking 클래스를 만들고, get_remaining을 정적 메서드로 바꿔 lcl_booking=>get_remaining( ... )으로 부른다. 는 이렇게 갈아 끼운다.

    • 받는 값 USING iv_... → IMPORTING iv_...
    • 돌려주는 값 CHANGING cv_left → RETURNING VALUE(rv_left) (돌려줄 값이 하나일 때)

    실무에서 새로 만든다면 이쪽이 기본형이다. 여러 프로그램이 함께 쓰게 하려면 같은 클래스를 전역 클래스(ZCL_...)로 올리면 된다.

흔한 실수와 점검

  • 취소 건 합산 → status <> 'C'로 취소 예매는 제외.
  • 전역변수 의존 → 입력은 USING, 결과는 CHANGING으로(USING / CHANGING 파라미터).
