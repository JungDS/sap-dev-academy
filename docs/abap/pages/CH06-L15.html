캡스톤 — 구구단 72행 전체

CH05의 미완성 숙제를 끝낸다 — 쌓고, 정렬하고, 찾고, 소계까지.

Track 1Chapter 6Lesson 15초급

그 숙제를 끝낼 시간

Chapter 5 · 구구단 캡스톤의 마지막 장면을 기억하는가. 구구단 한 줄을 Structure로 묶는 데는 성공했지만, gs_line은 반복마다 덮어써졌고 에는 늘 마지막 한 줄뿐이었다. 이 챕터의 첫 문장이 그 불편에서 출발했다 — 그리고 이제 도구가 전부 모였다. 72줄을 통째로 들고, 마음대로 주무를 시간이다.

배운 개념 구구단에서의 역할 배운 곳
Line Type dan·mul·result를 묶은 행 모양(ts_line) L02
Work Area 지금 만들고 있는 한 줄(gs_line) L01
Internal Table 72줄을 담는 표(gt_gugu) L01
APPEND + CLEAR 한 줄씩 쌓기(습관 포함) L01
SORT 결과 기준 재배열 L07
READ TABLE 원하는 한 줄 콕 집기 L05
LOOP + WRITE 쌓인 72줄 출력 L08
AT END OF + SUM 단별 소계 L12

TYPES: BEGIN OF ts_line,
         dan    TYPE i,
         mul    TYPE i,
         result TYPE i,
       END OF ts_line.

DATA: gs_line TYPE ts_line,
      gt_gugu TYPE TABLE OF ts_line,
      gv_cnt  TYPE i.

DO 8 TIMES.
  CLEAR gs_line.                         " 새 단을 시작할 때 비우기 — L01의 그 습관
  gs_line-dan = sy-index + 1.            " 2~9단
  DO 9 TIMES.
    gs_line-mul    = sy-index.
    gs_line-result = gs_line-dan * gs_line-mul.
    APPEND gs_line TO gt_gugu.           " 한 줄씩 쌓는다
  ENDDO.
ENDDO.

DESCRIBE TABLE gt_gugu LINES gv_cnt.     " gv_cnt = 72

Chapter 4의 중첩 DO 골격 그대로에 APPEND 한 줄이 더해졌을 뿐인데, 결과는 완전히 다르다 — 프로그램 어딘가에 72행이 전부 살아 있다.

안쪽 루프에 들어가면 는 안쪽 회차로 바뀐다. 바깥에서 정한 단 값을 안쪽 루프 전에 gs_line-dan에 저장해 두는 이유다(CH05에서 배운 패턴 그대로).

SORT gt_gugu BY result DESCENDING.       " 결과 큰 순서로

LOOP AT gt_gugu INTO gs_line.
  WRITE: / gs_line-dan, 'x', gs_line-mul, '=', gs_line-result.
ENDLOOP.

한 줄씩 출력하고 버리던 지난 챕터와 달리, 모아 두었기에 "결과가 큰 순서" 같은 원하는 기준으로 마음대로 재배열할 수 있다. 이것이 쌓아 두는 것의 힘이다.

디버거로 행들 보기

APPEND 다음 줄에 BREAK-POINT를 걸고(L01에서 익힌 그 확인 습관) gt_gugu를 펼치면, 안쪽 루프가 돌 때마다 행이 1개, 2개, 3개 … 72개로 하나씩 늘어나는 모습이 보인다.

미션 — 직접 붙여 보기

이 챕터에서 배운 문장들을 이 프로그램에 직접 붙여 보자. 순서대로 난도가 오른다.

  • 미션 1 · 한 줄만 콕 집어 찾기 — gt_gugu에서 "7 x 8" 줄을 찾아 결과만 출력해 보자. READ TABLE gt_gugu INTO gs_line WITH KEY dan = 7 mul = 8.으로 찾고, 찾았는지는 sy-subrc = 0으로만 확인한다(L05의 규율). 없는 값(mul = 10)으로 실패도 한 번 겪어 보자 — 실패해도 Work Area에 이전 값이 남아 있다는 것까지 확인하면 만점.
  • 미션 2 · 빠르게 찾기 — 미션 1의 READ에 BINARY SEARCH를 붙여 보자. 그냥 붙이면 이상한 결과가 나온다 — 왜인지, 무엇을 먼저 해야 하는지는 L07에서 배웠다(힌트: 지금 테이블은 result DESCENDING으로 정렬돼 있다).
  • 미션 3 · 단마다 소계 내기 — SORT gt_gugu BY dan.으로 단 순서를 맞춘 다음, LOOP 안에 AT END OF dan.과 SUM.을 넣어 단별 합계를 찍어 보자(dan이 첫 필드라 그룹 키가 단순하다). 그리고 SUM 전과 후에 gs_line-result를 한 번씩 찍어 보자 — 전에는 초기값 0(L12의 마스킹), 후에는 그 단의 합계가 나온다. 같은 자리에서 값이 바뀌는 것을 눈으로 보면 마스킹과 SUM의 관계가 완전히 정리된다.

흔한 실수와 점검

  • 바깥 sy-index와 안쪽 sy-index 혼동 → 안쪽 루프에서는 안쪽 회차다. 단 값은 안쪽 루프 전에 저장.
  • APPEND 위치 → mul·result가 채워진 뒤에 실행돼야 한다. 안쪽 루프 밖에 두면 단마다 한 줄만 쌓인다.
  • 정렬 후 원래 순서 기대 → SORT 후에는 되돌릴 방법이 없다. 원래 순서가 필요하면 쌓을 때 순번 필드를 하나 더 두고 1, 2, 3 … 을 같이 넣어 둔다. 나중에 그 필드로 SORT하면 입력 순서로 돌아온다.
  • 미션 2에서 정렬 없이 BINARY SEARCH → 의도된 함정이다. 있는 행도 "없음"이 나온다.
다른 언어를 해 봤다면 — 이번 챕터 개념 대조표 (더 보기)

낯선 이름이 많았지만, 대부분은 이미 쓰던 물건에 다른 이름이 붙은 것이다.

  • STANDARD / SORTED / HASHED — 순서대로 담는 리스트 / 키 순서가 유지되는 정렬 맵 / 해시로 찾는 맵에 각각 대응한다(SORTED·HASHED 모두 "맵"에 가깝지만, SORTED는 순서와 번호 접근이 남아 있는 쪽이다).
  • COLLECT — 키로 묶어 합계를 내는 그룹 합산이다. SQL을 안다면 GROUP BY 뒤의 합계, 맵을 쓴다면 "키가 있으면 더하고 없으면 새로 넣기"와 같다.
  • ASSIGNING <fs> — 복사가 아니라 그 자리를 가리키는 참조다. 다른 언어에서는 이쪽이 기본 동작이라 오히려 익숙할 텐데, ABAP에서는 INTO(복사)가 기본이고 이쪽이 선택이라는 방향 차이만 기억하면 된다.
  • sy-subrc 확인 — 실패를 예외로 던지지 않고 반환 코드로 알리는 방식이다. 확인하지 않으면 프로그램은 아무 일 없다는 듯 그대로 진행한다. READ 다음 줄의 IF sy-subrc = 0이 습관이어야 하는 이유이자, 경력자가 가장 자주 걸리는 지점이다.
  • Header Line — 다른 언어에 대응물이 없는 ABAP 고유의 옛 유산이다. L14의 해독법만 챙기면 된다.

정리 — 그리고 다음 불편

CH05에서 못 끝낸 숙제를 끝냈다. 구구단 72행을 에서 자유롭게 다뤘다 — 쌓고, 세고, 정렬하고, 콕 집어 찾고, 단별 소계까지. 그런데 프로그램이 끝나면 gt_gugu는 흔적도 없이 사라진다. 다시 실행하면 또 처음부터 만들어야 한다. 값을 영구히 저장해 두고 싶다 → Chapter 7 · Transparent Table.
