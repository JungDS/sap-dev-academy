SELECT in LOOP 제거

1+N 왕복 폭발을 잡는다 — 키 모으기·한 번에 읽기·메모리에서 찾기.

💥 1번 + N번 = 폭발

성능 사고 1순위 패턴이다. 예매 1,000건을 읽어 놓고, 각 건마다 공연명을 찾겠다고 DB에 SELECT SINGLE을 1,000번 보낸다.

" ❌ 안티패턴 — 예매 한 건마다 DB에 다시 간다
LOOP AT gt_booking INTO DATA(gs_booking).
  SELECT SINGLE artist
    FROM zconcert
    WHERE concert_id = @gs_booking-concert_id
    INTO @DATA(gv_artist).
ENDLOOP.

교활한 점은 개발 중엔 안 보인다는 것이다. 테스트 5건이면 순식간에 끝난다. 운영에서 5만 건이 되면 DB 왕복이 5만 1번. ST05에서는 같은 SQL의 Executions가 입력 건수만큼 찍히는 모습으로 드러난다. 지난 레슨들의 "반복 SQL" 분류가 정확히 이 장면이다.

목표는 "LOOP 안 SELECT 금지"라는 주문 암기가 아니다. 구조를 바꾸는 것이다: 필요한 키를 먼저 모으고 → 관련 데이터를 한 번에 읽고 → 루프 안에서는 에서 찾는다.

" ① 키만 모아 중복 제거 (concert_id 목록)
DATA gt_keys TYPE STANDARD TABLE OF zbooking-concert_id WITH EMPTY KEY.

gt_keys = VALUE #( FOR ls IN gt_booking ( ls-concert_id ) ).
SORT gt_keys.
DELETE ADJACENT DUPLICATES FROM gt_keys.

" ② 비어 있지 않을 때만, 한 번에 읽기
IF gt_keys IS NOT INITIAL.
  SELECT concert_id, artist
    FROM zconcert
    FOR ALL ENTRIES IN @gt_keys
    WHERE concert_id = @gt_keys-table_line
    INTO TABLE @DATA(gt_concert).

  SORT gt_concert BY concert_id.
ENDIF.

" ③ 루프 안에서는 DB가 아니라 메모리에서 찾기
LOOP AT gt_booking INTO DATA(gs_book).
  READ TABLE gt_concert INTO DATA(gs_concert)
       WITH KEY concert_id = gs_book-concert_id
       BINARY SEARCH.
  IF sy-subrc = 0.
    " gs_concert-artist 사용
  ENDIF.
ENDLOOP.
  • FOR ALL ENTRIES(FAE)는 Chapter 13에서 배운 그 기능이다. 내부 테이블 값들을 SQL 조건으로 쓴다. gt_keys처럼 낱값 테이블은 열 이름이 없어 예약 이름 table_line으로 그 값 자체를 가리킨다.
  • READ TABLE ... BINARY SEARCH는 Chapter 6의 그 탐색이다. 해당 키로 정렬돼 있어야 한다. SORTED/HASHED 테이블을 쓰면 의도가 더 명확해진다.

FAE의 공식 함정 2종 🚨

공식 문서가 명시하는, 반드시 알아야 할 두 가지다.

  1. 빈 driver 테이블 = WHERE 전체 무시. 키 테이블이 비어 있으면 조건이 통째로 무시되어 DB 테이블 전 행이 읽힌다. 그래서 ②의 IF ... IS NOT INITIAL guard는 장식이 아니라 필수다.
  2. 결과 중복 제거 = DISTINCT와 동등. FAE 결과에서는 중복 행이 제거된다. 그래서 용으로는 위험하다. 같은 값의 행이 여러 개여야 하는 합계 계산에 FAE 결과를 쓰면 수치가 줄어든다. 키 조회(마스터 붙이기)에는 적합, 집계에는 부적합.

JOIN이냐 FAE냐

선택 어울리는 경우 주의
JOIN (Chapter 13) DB 테이블끼리 관계가 명확 — 한 문장으로 끝 관계 중복(1:N)로 행이 불어나는지 확인
FAE 이미 에 키 목록이 있음 빈 driver guard·키 중복 제거· 금지
사전 조회+SORTED/HASHED 같은 참조 데이터를 여러 곳에서 재사용 메모리 사용량·키 설계

어떻게 확인하는가

  1. ST05 before — 같은 SQL의 Executions가 입력 건수와 비슷하면 1+N 확정.
  2. 코드 구조 — LOOP 안에 SELECT·함수 호출·원격 호출이 있는지. (대량 루프의 키 조회 반복이 우선 제거 대상이다.)
  3. 결과 동등성 — 빨라졌는데 결과가 달라지면 실패다. 전후로 같은 건수·같은 매핑· 누락 건 처리(sy-subrc 분기)를 비교한다.
  4. ST05 after — 반복 SQL이 1,000회→2회로 줄었는지. SAT로 ABAP 루프 시간이 과하게 늘지 않았는지도.

N을 키워 보면

건수를 키우며 왕복이 폭발하는(1+N) 쪽과 사전 조회(2회) 쪽을 비교해 보라. N=0에서 guard를 끄면 무슨 일이 나는지도 꼭.

흔한 실수와 점검 🚧

  • 빈 driver로 FAE 실행 → 전체 조회 사고. guard 필수.
  • 키 중복 방치 → 조건만 커지고 trace 해석도 어려워진다. SORT + 중복 제거.
  • 정렬 없이 BINARY SEARCH → 잘못된 결과가 조용히 나온다. 정렬 기준=검색 키.
  • FAE 결과로 → 중복 제거 때문에 합계가 준다. 집계는 JOIN + GROUP BY나 집계 SQL로.
  • 왕복은 줄였는데 폭발 → 사전 조회 테이블이 너무 크면 다음 레슨의 package 설계로 넘어갈 신호다.

정리 📌

  • 1+N = 반복 SQL의 정체. ST05의 Executions로 확진한다.
  • 처방 = 키 수집(중복 제거) → 한 번에 읽기(FAE/JOIN) → 탐색(BINARY SEARCH·SORTED/HASHED).
  • FAE 공식 함정 2종: 빈 driver=전체 조회, 결과 중복 제거= 왜곡.
  • 완료 조건은 속도가 아니라 결과 동등 + 수치 개선의 기록이다.

왕복은 잡았다. 그런데 데이터가 수백만 건이라면? 빠른 SELECT 하나로는 부족한 세계, 메모리··재시작을 함께 설계하는 대량 처리로 간다.
