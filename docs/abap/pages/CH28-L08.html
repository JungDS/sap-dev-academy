Dynamic ABAP: Field Symbol 심화와 Generic

실습 — 동적 구조 검사기

챕터 전부를 조립한다 — describe → 검증 → ASSIGN → 결과.

Track 2Chapter 28Lesson 8고급

🔍 어떤 구조든 검사하는 도구

운영팀 정훈영이 요청한다 — "예매든 공연이든, 아무 구조나 주면 원하는 필드의 값만 뽑아 보여 주는 도구를 만들어 주세요. 없는 필드를 시키면 조용히 무시하지 말고 알려 주고요."

이 챕터에서 배운 부품이 전부 들어간다.

단계 사용 부품 레슨
어떤 구조든 받기 TYPE any L02
구지 확인 RTTS describe_by_data + CAST L07
요청 필드가 실제 있는지 components metadata 대조 L07
값 접근 ASSIGN COMPONENT ... ELSE UNASSIGN L04·L03
실패를 안내로 sy-subrc·IS ASSIGNED + 메시지 L03

CLASS lcl_struct_inspector DEFINITION.
  PUBLIC SECTION.
    TYPES:
      tt_field_name TYPE STANDARD TABLE OF string WITH EMPTY KEY,
      BEGIN OF ts_result,
        field_name TYPE string,
        value_text TYPE string,
        found      TYPE abap_bool,
        message    TYPE string,
      END OF ts_result,
      tt_result TYPE STANDARD TABLE OF ts_result WITH EMPTY KEY.

    METHODS inspect
      IMPORTING is_data          TYPE any
                it_requested     TYPE tt_field_name
      RETURNING VALUE(rt_result) TYPE tt_result.
ENDCLASS.

CLASS lcl_struct_inspector IMPLEMENTATION.
  METHOD inspect.
    FIELD-SYMBOLS <lv_value> TYPE any.

    " ① 구조인지 먼저 확인 — 아니면 정중히 종료
    TRY.
        DATA(lo_struct) = CAST cl_abap_structdescr(
          cl_abap_typedescr=>describe_by_data( is_data ) ).
      CATCH cx_sy_move_cast_error.
        rt_result = VALUE #( ( found   = abap_false
                               message = `입력이 구조가 아닙니다` ) ).
        RETURN.
    ENDTRY.

    " ② 요청 필드마다: metadata 대조 → ASSIGN → 결과 기록
    LOOP AT it_requested INTO DATA(lv_requested).
      IF NOT line_exists( lo_struct->components[ name = lv_requested ] ).
        APPEND VALUE #( field_name = lv_requested
                        found      = abap_false
                        message    = `구조에 없는 필드입니다` ) TO rt_result.
        CONTINUE.
      ENDIF.

      ASSIGN COMPONENT lv_requested OF STRUCTURE is_data
             TO <lv_value> ELSE UNASSIGN.

      IF sy-subrc = 0 AND <lv_value> IS ASSIGNED.
        APPEND VALUE #( field_name = lv_requested
                        value_text = |{ <lv_value> }|
                        found      = abap_true
                        message    = `OK` ) TO rt_result.
      ELSE.
        APPEND VALUE #( field_name = lv_requested
                        found      = abap_false
                        message    = |ASSIGN 실패 sy-subrc={ sy-subrc }| ) TO rt_result.
      ENDIF.
    ENDLOOP.
  ENDMETHOD.
ENDCLASS.

설계 포인트: 입력 구조(is_data)만 generic으로 열고, 요청 목록은 string 테이블로 고정했다. 동적 ABAP에서도 전부를 generic으로 만들 필요는 없다 — 정말 모르는 값만 연다.

직접 검사해 보기

예매 구조를 넣고 요청 필드 목록(BOOKING_ID·STATUS·UNKNOWN…)을 바꿔 가며 파이프라인이 어디서 통과하고 어디서 거절되는지 확인해 보라. 구조가 아닌 입력도 넣어 보라.

확인 체크리스트

입력 기대 결과
gs_booking + BOOKING_ID·STATUS 둘 다 OK + 값 표시
요청에 UNKNOWN 포함 그 행만 "구조에 없는 필드" — 나머지는 정상
구조가 아닌 값(숫자 등) 즉시 "입력이 구조가 아닙니다"
요청 목록이 빈 테이블 결과 0행(오류 아님)

흔한 실수와 점검 🚧

  • generic을 필요 이상으로 → 요청 목록까지 TYPE any로 열면 검증 코드만 늘어난다. 아는 모양은 고정 타입으로.
  • 대소문자 → 필드 이름은 대문자로 맞춰 비교한다(status ≠ STATUS로 어긋나기 쉬움).
  • 실무 확장 시 — 노출 금지 필드 whitelist(L04)·deep 필드(내부 테이블 등) 표시 정책·읽기/쓰기 권한 분리를 더한다. 이 실습은 읽기 전용이 안전선이다.

정리 📌

  • 동적 도구의 정석 파이프라인 = describe(정체 확인) → metadata 대조(있는가) → ASSIGN(접근) → 실패는 안내.
  • 전부 generic이 아니라 모르는 것만 generic — 이 절제가 동적 ABAP를 읽을 만한 코드로 만든다.

ℹ️ 참고로 SQL 문장· 이름까지 실행 중에 정하는 동적 SQL·동적 호출도 존재한다. 여기서는 다루지 않는다 — SQL 문자열 실행은 AMDP / ADBC 계열에서 만난다. 지금은 "그런 것도 있다"까지만.
