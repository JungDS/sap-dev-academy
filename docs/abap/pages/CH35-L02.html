성능 분석과 튜닝

SAT Runtime Analysis

전신 촬영 — 시간이 ABAP·DB·외부 중 어디서 새는지 가른다.

Track 2Chapter 35Lesson 2고급

🩻 SQL은 깨끗한데 왜 느리지?

ST05로 정밀 검사를 했는데 DB 접근은 생각보다 멀쩡하다. 그런데 리포트는 여전히 느리다. 이럴 때 병목은 ABAP 코드 안에 있을 수 있다. 큰 내부 테이블을 매번 앞에서부터 뒤지거나, 루프 안에서 같은 테이블을 반복 정렬하거나, 필요 없는 변환을 수만 번 하거나.

(Runtime Analysis, 구 SE30)는 전신 촬영이다. 실행 시간 전체가 어느 statement··블록에서 소비됐는지 보여 준다. ST05가 "DB와 무슨 대화를 했나"라면, SAT는 "시간이 어디에 쓰였나"다.

이 레슨의 진짜 기술은 촬영 판독 후의 분기 판단이다:

시간의 성격 다음 행동
DB 시간이 크다 ST05로 그 SQL을 정밀 검사
ABAP 시간이 크다 루프·내부 테이블 접근·정렬 중복을 점검(이 레슨)
외부(External) 시간이 크다 RFC·HTTP·GUI 왕복(Chapter 33 감각)을 점검

Hit List — 시간 소비 순위표

측정 결과의 중심은 Hit List(시간을 많이 쓴 항목 순위)다. 먼저 볼 항목:

항목 뜻 판단 질문
Hits 호출 횟수 반복 때문에 커졌나
Own(Net) time 그 항목 자체가 쓴 시간 내부 처리 자체가 무거운가
Total time 하위 호출까지 포함한 시간 이 블록 전체가 병목인가

주의 하나: Total time 1위가 "범인"이라는 보장은 없다. 하위 호출을 다 품은 껍데기일 수도 있고, 업무상 원래 큰 처리일 수도 있다. Own time·Hits·호출 계층을 함께 봐야 한다.

그리고 는 절대값이 아니라 상대 비교 도구다. 측정 자체가 오버헤드를 만들고, 시스템 상태에 따라 절대 시간은 흔들린다. "142ms"보다 "루프 가 전체의 70% → 수정 후 15%"가 의미 있는 기록이다.

어떻게 확인하는가

  1. 대표 데이터로 측정 — 운영은 10만 건인데 테스트 10건으로 촬영하면 병목이 안 찍힌다.
  2. Hit List 정렬 — Own time 기준으로 "스스로 무거운 놈", Hits 기준으로 "너무 자주 불리는 놈"을 찾는다.
  3. 시간 성격 분류 — ABAP/DB/외부 비율을 보고 위 분기표대로 다음 도구를 고른다.
  4. 코드 위치 확인 — 항목을 열어 실제 라인으로 이동한다. "어느 라인에서 어떤 데이터 크기로 반복됐나"까지.
  5. 개선 후 재촬영 — 예: 표준 테이블 순차 탐색을 SORTED/HASHED 접근 (Chapter 6)으로 바꿨다면, 같은 데이터로 다시 측정해 해당 블록 비중이 줄었는지 확인한다.

직접 판독해 보기

막대(ABAP↔DB 비율)를 읽고, 각 항목의 다음 행동을 골라 보라. 원인 성격에 맞는 선택인지 즉시 피드백이 나온다.

흔한 실수와 점검 🚧

  • Hit List 1위 무조건 수술 → Own/Total/Hits/호출 계층을 함께. 1위가 정상적인 큰 처리일 수 있다.
  • 소량 데이터로 측정 → 병목은 데이터 크기에서 나온다. 대표 규모로.
  • ST05와 역할 혼동 → 에서 DB 시간이 크면 다음은 ST05다. 반대로 ST05가 깨끗한데 느리면 SAT다.
  • 절대 수치 신봉 → 측정 오버헤드가 있다. 같은 조건의 전후 비율 변화로 말한다.
  • 시스템 전체가 느린 문제를 SAT로 → 그건 Basis 모니터링 영역과의 협업이다. SAT는 특정 프로그램 분석에 강하다.

정리 📌

  • = 전신 촬영. Hit List에서 Hits·Own·Total을 함께 읽는다.
  • 판독의 끝은 분기: DB 크면 ST05, ABAP 크면 루프·내부 테이블, 외부 크면 RFC/HTTP.
  • 절대값이 아니라 같은 조건 전후의 상대 비교로 기록한다.

한 실행의 정밀 검사(ST05)와 전신 촬영(SAT)을 익혔다. 그런데 운영에는 프로그램이 수백 개다. 무엇부터 고쳐야 효과가 가장 클까? 전 직원 건강검진 통계, SQLM으로 간다.
