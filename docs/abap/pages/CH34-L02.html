ALE Distribution Model

배송망 설계 — 주소록·배포 규칙·계약서·통로가 다 맞아야 흐른다.

Track 3Chapter 34Lesson 2고급독립 모듈

🗺️ 봉투는 있는데 배송망이 없다

IDoc은 봉투와 내용물이다. 그런데 봉투만으로 배달이 될 리 없다. 어느 주소로 보낼지, 어떤 종류의 우편을 누구와 주고받기로 했는지, 어떤 운송 수단으로 나를지 가 정해져 있어야 한다. SAP 시스템 사이에서 이 배송망을 설계·운영하는 틀이 (Application Link Enabling)다.

이 레슨이 중요한 이유는 하나다. 실무 연계 장애의 상당수가 코드가 아니라 설정에서 난다. IDoc 생성 프로그램은 멀쩡한데 파트너 계약이 없어 처리가 안 되고, 통로가 엉뚱한 시스템을 가리키고, 시스템 이름이 꼬여 남의 주소로 발송된다. 개발자가 설정을 직접 다 만들지는 않더라도, 어디가 끊겼는지 읽을 수는 있어야 한다.

배송망의 다섯 부품

부품 비유 하는 일
Logical System 주소록의 시스템 이름 SAP client·외부 시스템을 논리 이름으로 식별
Distribution Model 배포 규칙표 누가 → 누구에게 → 어떤 Message Type을 보내는지 정의
Partner Profile 상대별 계약서 그 상대와는 어떤 메시지를 어떻게 주고받는지(처리 방식·통로 지정)
Port 운송 수단 실제 전송 경로(tRFC·파일 등)
RFC Destination 접속 정보 통로가 참조하는 원격 연결(Chapter 33 · RFC의 그것)

암기 열쇠는 **"주소록 → 규칙 → 계약 → 통로"**다. 규칙표(모델)가 "보낼 관계"를 정하고, 계약서(Partner Profile)가 "처리 방법"을 정하고, 통로(Port)가 실제로 나른다. 넷 중 하나라도 빠지면 봉투는 어딘가에 멈춘다.

한 가지 함정: 규칙표는 만드는 것과 배포(distribute)하는 것이 다르다. 내 시스템에 모델이 보여도 상대에게 배포하지 않았다면 양쪽의 약속이 어긋난 상태다.

어디서 끊겼는지 읽는 순서

  1. 시스템 이름(주소록) — client에 어떤 논리 이름이 붙어 있나. 시스템 복사 후 이 이름이 꼬이면 엉뚱한 상대로 발송된다.
  2. 배포 규칙표 — 발신·수신·Message Type 관계가 있나, 그리고 배포까지 했나.
  3. 상대별 계약서 — Outbound라면 어느 통로로 내보낼지, Inbound라면 어떤 처리 방식으로 받을지가 상대·메시지별로 있어야 한다. "IDoc은 생성됐는데 처리가 안 된다"의 1순위 용의자.
  4. 통로와 접속 — 통로가 가리키는 원격 접속이 살아 있나(연결 테스트·로그온 사용자). Chapter 33 · RFC에서 배운 확인 그대로다.
  5. 실제 한 건의 이력 — 설정 화면만 보고 끝내지 말 것. 테스트 한 건을 보내 이력 (Status)이 단계별로 넘어가는지 증명한다.

어디가 빠졌는지 직접 진단해 보기

다섯 부품을 켜고 끄면서 발행해 보라. 부품 하나가 꺼질 때마다 봉투가 멈추는 지점이 달라진다. 코드가 아니라 설정이 흐름을 끊는 감각이 이 레슨의 전부다.

전체 흐름은 지도 한 장으로 정리해 두자.

화면 참조표 🗂

역할 T-code
Logical System 정의 BD54 (SALE 경로)
Distribution Model(배포 규칙표) BD64
Partner Profile(상대별 계약서) WE20
Port(통로) WE21
RFC Destination(접속 정보) SM59

흔한 실수와 점검 🚧

  • 규칙표만 만들고 계약서 누락 → 모델은 "보낼 관계", Partner Profile은 "처리 방법". 둘 다 있어야 흐름이 완성된다.
  • Port = RFC Destination이라는 착각 → Port는 IDoc 전송 설정이고, Destination은 원격 접속 대상이다. Port가 Destination을 참조할 뿐 같은 것이 아니다.
  • 개발 설정을 운영에 그대로 복사 → 시스템 이름·접속·파트너 번호는 환경마다 다르다. 이송으로 옮길 것과 운영에서 직접 맞출 것을 구분한다.
  • filter 조건 미문서화 → 규칙표에는 "특정 조직만 보낸다" 같은 filter가 붙을 수 있다. 문서가 없으면 "왜 이 데이터만 안 나가요?"를 추적할 수 없다.

정리 📌

  • = IDoc의 배송망. 주소록(Logical System) → 배포 규칙(Model) → 상대별 계약 (Partner Profile) → 통로(Port/Destination).
  • 모델은 만들기와 배포가 별개다. 양쪽이 같은 규칙을 알아야 한다.
  • 연계 장애의 절반은 설정이다. 다섯 부품을 순서대로 점검하고, 마지막은 실제 한 건의 이력으로 증명한다.

배송망까지 갖췄다. 그런데 배송은 실패할 수 있다. 반송된 봉투를 찾아 원인을 고치고 다시 보내는 운영 루프로 간다.
