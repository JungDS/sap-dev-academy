끝나면 사라진다

Chapter 06 · 구구단 캡스톤에서 구구단 72행을 gt_gugu에 담았지만, 프로그램이 끝나면 째 사라졌다. 다시 실행하면 또 처음부터다. 값을 디스크에 영구 저장하고 다른 사용자와도 공유하고 싶다. 그게 (투명 테이블)이다.

Transparent Table이란

은 에 정의하는 테이블로, DB의 실제 물리 테이블과 1:1로 대응한다. DDIC는 Data Dictionary의 줄임말이다. 회사가 함께 쓰는 타입·테이블 정의를 한곳에 모아 둔 사전이고, Chapter 03 · Domain에서 이미 열어 봤다.

"투명(transparent)"은 DDIC 정의와 DB 테이블이 같은 모양으로 들여다보인다는 뜻이다. 예전에는 여러 테이블을 한 덩어리에 몰아 담아 DB 쪽에서는 그대로 보이지 않는 저장 방식도 있었는데(Pooled Table·Cluster Table), 그것과 구분하려고 붙은 이름이다. 지금 새로 만드는 업무 테이블은 사실상 전부 Transparent Table이다.

🧑‍💻 다른 언어를 해 봤다면 transparent는 보통 "속을 감춰 줘서 신경 안 써도 된다"는 뜻으로 쓰이는데 여기서는 반대다. 감추지 않고 그대로 비쳐 보인다는 쪽이다.

SE11에서 ZGUGUDAN 만들기

구구단을 영구 저장할 테이블 ZGUGUDAN을 만든다. SE11 → Database Table → ZGUGUDAN → Create.

필드는 넷이다. 아래 값 그대로 넣으면 다음 레슨과 다음 챕터까지 그대로 이어진다.

필드 키 타입 — (권장) Built-In으로 대신할 때 뜻
MANDT ✅ MANDT(SAP 표준, 타입 CLNT·길이 3) 고정 클라이언트
DAN ✅ ZDE_DAN INT4 단
MUL ✅ ZDE_MUL INT4 곱하는 수
RESULT ZDE_RESULT INT4 결과

ZDE_DAN·ZDE_MUL·ZDE_RESULT는 Chapter 03 · Data Element에서 만들던 요령대로 정수용 Data Element를 셋 만들어 두면 된다. 아직 없다면 이번 실습에 한해 Built-In INT4로 채워도 테이블은 똑같이 만들어진다. 두 방식이 무엇이 다른지는 바로 아래 '필드 타입' 절에서 본다.

⚠️ 키 필드는 맨 앞에 연속으로. 키로 지정한 필드들은 테이블 구조의 시작 부분에 모여 있어야 한다. 키 필드 사이에 일반 필드가 끼면 활성화(Activate. 정의를 실제 DB 테이블로 만드는 절차이고, 잠시 뒤에 다시 나온다)가 막힌다. ·DAN·MUL을 앞에, RESULT를 뒤에 둔 이유가 이것이다.

🧑‍💻 다른 언어를 해 봤다면 일반 RDBMS의 PRIMARY KEY는 그 컬럼이 몇 번째에 있든 상관없다. 키를 앞에 모아 두라는 건 SAP DDIC 쪽 규칙이다.

저장을 누르면 패키지를 묻는다. 학습 중에는 Local Object($TMP)를 고른다. $TMP에 넣은 객체는 내 시스템에만 남고 다른 시스템으로 이송되지 않는다.

이어서 나머지 설정을 정한다. 아래 첫 두 항목은 Delivery and Maintenance 탭에 있다.

항목 내용
Delivery Class 보통 A(업무 데이터용)
Data Browser/Table View Maint. Display/Maintenance Allowed로 둔다. 다음 레슨에서 손으로 값을 넣으려면 이 설정이 필요하다
Key 행을 유일하게 식별(여기선 MANDT+DAN+MUL)
Technical Settings Data Class·Size Category를 지정한 뒤 활성화

Delivery Class는 이 테이블에 든 데이터를 누가 채우는 것으로 볼지를 정한다. 우리 구구단처럼 고객이 직접 쌓는 업무 데이터(마스터 데이터·트랜잭션 데이터)면 A가 맞다. SAP이 설치·업그레이드 때 채워 주는 표준 설정값용 테이블에는 다른 값을 쓴다. 지금은 A 하나만 기억하면 된다.

🧑‍💻 여기서 Class는 객체지향의 클래스가 아니라 분류라는 뜻이다. 곧 나올 Data Class도 마찬가지다.

그리고 활성화(Activate)하는 순간 DDIC 정의에 대응하는 실제 DB 테이블이 생성된다. 활성화 전에는 설계도일 뿐, 아직 쓸 수 있는 테이블이 아니다.

필드 타입 — Data Element vs Built-In

각 컬럼의 타입을 주는 방법은 두 가지다.

  • 참조(권장) — DAN에 ZDE_DAN 같은 Data Element를 주면, Chapter 03 · Data Element에서 봤듯 라벨과 도움말이 따라온다. 그 아래 에 고정값 같은 준비가 돼 있으면 (입력 도움말) 목록까지 따라온다.
  • Built-In 타입 직접 — INT4(정수) 같은 내장 타입을 바로 지정. 간단하지만 라벨·도움말이 없다.

업무 테이블은 거의 항상 Data Element로 준다. 그래야 전사적으로 의미·라벨이 일관된다.

💡 라벨을 붙여 두면 나중에 이 테이블을 표 형태로 뽑아 주는 표준 도구 (ABAP List Viewer)에서도 컬럼 제목이 그대로 나온다. ALV는 Chapter 11 · SALV에서 정식으로 배우니 지금은 이름만 알아 두면 된다.

MANDT — 클라이언트 분리

대부분 업무 테이블의 첫 키는 (클라이언트)다. Chapter 01 · 로그온에서 본 "방(Client)"별로 데이터가 갈리게 하는 장치다. 정확히는 첫 키 필드의 타입이 CLNT이면 그 테이블은 클라이언트별로 데이터가 나뉜다. MANDT가 바로 그 CLNT 타입 필드다.

무엇이 자동인지 갈라 두자. 필드 MANDT 자체는 내가 직접 첫 키로 넣는다. 자동인 쪽은 그다음이다. 프로그램이 이 테이블을 읽고 쓸 때 지금 로그온한 클라이언트의 행만 골라 주는 일은 시스템이 알아서 한다.

🧑‍💻 다른 언어를 해 봤다면 여기 Client는 client-server의 그 client가 아니다. 한 시스템 안에 여러 회사를 나눠 담는 테넌트에 가깝고, MANDT는 그 tenant_id 컬럼에 해당한다.

Technical Settings — 저장 방식 지정

활성화 전, Technical Settings(기술 설정)에서 DB에 어떻게 저장할지를 정한다(앞 표의 그 항목).

  • Data Class(데이터 클래스) — 테이블의 성격(예: 마스터 데이터·트랜잭션 데이터). DB가 비슷한 성격끼리 같은 저장 영역에 모은다.
  • Size Category(크기 범주) — 예상 행 수 규모(0~4 등). DB가 처음 잡을 공간을 가늠하는 힌트다(나중에 늘어나도 됨).

💡 이 둘은 지정해야 활성화된다. 비워 두면 활성화가 거부된다. 대신 고민할 것은 없다. 성격에 맞는 표준값을 하나씩 고르면 충분하다. "성격(Data Class)과 규모(Size Category)를 미리 알려 주는 것" 정도로 이해하면 된다.

💡 활성화하면 로그에 Enhancement Category(확장 범주)를 지정하지 않았다는 경고가 뜰 수 있다. 오류가 아니라 경고라 테이블은 정상적으로 만들어진다. 메뉴 Extras → Enhancement Category에서 값을 한 번 골라 주면 사라진다.

🔎 곁가지 — Where-Used List (지금은 몰라도 된다)

SE11에서 어떤 ··테이블을 어디서 쓰는지 한 번에 찾아 준다. 객체를 고치기 전 "이걸 바꾸면 어디가 영향받지?"를 이걸로 먼저 확인한다.

흔한 실수와 점검

  • 키 미지정 → 최소 하나의 키 필드 필요. 보통 + 업무 키.
  • 키 사이에 일반 필드 → 키 필드는 맨 앞에 연속으로. 사이에 일반 필드가 끼면 활성화가 막힌다.
  • Technical Settings 비움 → Data Class·Size Category를 고르지 않으면 활성화가 거부된다.
  • 활성화 안 함 → 활성화해야 DB 테이블이 실제로 생긴다.
  • 필드를 Built-In으로만 → 라벨·도움말을 잃는다. 가능하면 .
  • 활성 후 타입·길이 변경 ⚠️ → 이미 데이터가 든 테이블의 필드 타입·길이를 바꾸면 데이터 변환·손실 위험이 있고, 행이 많을수록 오래 걸린다. 이 필드 값을 참조하던 다른 테이블과의 연결(, Chapter 09 · Foreign Key와 Check Table에서 배운다)이 어긋나기도 한다. 운영 테이블 구조 변경은 신중히·이송 절차로(Chapter 38 · Transport 관리).

그릇(ZGUGUDAN)은 만들었다. 이제 값을 직접 넣어 보자 → Create Entries로 구구단 입력(다음 레슨).
