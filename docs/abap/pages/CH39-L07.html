Service Binding과 Fiori Elements Preview

계약이 화면이 되는 순간 — OData V4 노출과 Preview 검증 체크리스트.

Track 3Chapter 39Lesson 7고급

지금까지의 전부를 눈으로 본다

Service Definition/Binding의 문법과 역할은 Chapter 24에서 배웠다. Capstone에서 이 단계가 중요한 이유는 따로 있다: Preview 화면 하나에 지금까지의 모든 계층이 동시에 드러난다. 목록 컬럼은 L03의 @UI.lineItem, 생성 버튼은 L04의 create;, 저장 거부 메시지는 L05의 validation, Draft 배너는 L04의 with draft — 화면은 결과물이 아니라 통합 검증 도구다.

Service Definition — 노출 목록 확정

CH24에서 만든 Service Definition이 있으면 그 파일을 열어 expose 목록만 갱신한다(이름이 달라도 무방 — 새로 만들 필요 없다). Binding도 CH24의 것을 그대로 쓰되, 없다면 새로 만든다.

서비스가 노출하는 것은 언제나 **소비자의 표면(ZC_)**이다 — L03의 원칙을 서비스 목록에서도 지킨다. 공연·회차는 참조용이므로 얇은 projection 두 장을 만들어(각 4 줄짜리 — annotation 없이 통과만) 그것을 노출한다.

노출도 결정이다: 소비자가 공연·회차 정보를 따라가야 하므로(_Concert·_Perf association) 대상 entity를 함께 노출한다 — 노출 안 하면 화면에서 그 길이 끊긴다. ZI를 직접 노출하지 않는 이유는 L03 그대로다: 외부 계약이 내부 모델에 묶이면 내부를 못 바꾼다.

Service Binding — OData V4 UI로 연결

ADT에서 Service Binding을 만들고(유형: OData V4 – UI), 활성화 후 Publish한다. Binding 화면의 entity 목록에서 Booking을 선택하면 Preview 버튼이 Fiori Elements 화면을 띄운다(전부 CH24-L06에서 밟은 경로 — 이번엔 확인할 것이 훨씬 많다).

Preview 검증 체크리스트 — 계층별로 짚는다

확인 무엇의 검증인가
목록 컬럼이 position 순서대로 L03 @UI.lineItem
상세 화면에 Booking 구역 L03 @UI.facet + identification
Create 버튼 → 입력 화면 L04 create;
생성 직후 Status N L05 determination
정원 초과 저장 → 오류 메시지 L05 validation의 failed/reported
취소 버튼 표시·실행 후 C L04 action 선언 + L05 result
Draft: 입력 중 나갔다 와도 초안 복구(Resume) L04 with draft + draft action
읽기 전용 필드에 입력 불가 L04 field ( readonly )

이 표를 위에서 아래로 통과하면, L01 완료 기준의 앞 세 줄(정원 차단·action 취소·Draft 복구)이 화면 경로에서 증명된 것이다. 남은 세 줄(동시성·권한·운영)이 L08·L09다.

Draft 확인의 실제 조작도 적어 두자(처음이니까): 새 예매 Create → 필드 몇 개만 입력 → 저장하지 않고 목록으로 이동(이 순간 초안이 생긴다) → 목록에서 해당 건에 Draft 표시가 붙은 것을 확인 → 열면 이어서 쓰는 흐름(Resume)이 제안된다 → 계속 편집 후 저장(Activate)하거나 폐기(Discard).

🔭 기대 관리 — Preview는 개발자 검증 도구다. 실제 사용자 배포에는 역할· 카탈로그·타일 같은 Launchpad 설정이 따로 있고(환경 의존이라 범위 밖), 외부 시스템 호출에는 L09의 통신 설정이 필요하다. "Preview가 뜬다 ≠ 배포 완료"를 이 챕터의 언어로 말하면: 화면은 여섯 완료 기준 중 세 개까지만 증명한다.

문제가 생기면 — 층으로 좁힌다

Chapter 37-L05의 추적 감각 그대로, 화면 문제도 층으로 가른다.

증상 볼 층
Preview 자체가 안 열림 Binding 활성화·publish 상태
목록이 비었거나 컬럼 누락 L03 annotation / 접근 제어(#CHECK인데 DCL이 없는 경우 — 우리 연습은 #NOT_REQUIRED라 해당 없음, 운영 전환 시 1순위)
버튼이 없음 L04 계약 — 특히 projection behavior의 use 목록
저장이 조용히 실패 L05 validation의 reported 누락(이유 없는 거부)
초안이 복구 안 됨 / Create가 초안 흐름을 안 탐 L04 — projection behavior의 use draft;·draft action 배정

흔한 실수와 점검 🚧

  • Definition만 만들고 Binding 생략 → 소비 경로가 없다(CH24의 그 함정 — 여전히 1순위).
  • annotation 없이 "자동으로 좋은 화면" 기대 → Fiori Elements는 선언을 읽는 기계다. 화면이 이상하면 선언(L03)부터.
  • Preview에서 안 되는 것을 코드 탓 → 위 증상 표로 층부터 가른다. 우리 연습(#NOT_REQUIRED)에서는 annotation·projection behavior부터 보고, 운영(#CHECK 전환) 후에는 **권한(DCL)**이 "빈 목록"의 1순위가 된다.
  • Preview 통과 = 운영 준비 완료 착각 → 남은 것: 동시성·권한(L08), 통신·release contract·ATC(L09).

정리 📌

  • Service Definition = 노출 목록의 결정, Binding = OData V4 UI 연결 + publish, Preview = 전 계층 통합 검증 도구.
  • 검증 체크리스트 여덟 줄로 완료 기준 앞 세 줄을 증명했다.
  • 화면 문제는 층으로 좁힌다: Binding → annotation → 계약 → 구현 → 권한.

혼자 쓰는 앱은 여기서 끝이어도 된다. 하지만 운영은 여럿의 세계다 — 두 사람이 같은 예매를 고치는 순간과 권한의 문제로 간다.
