Communication Arrangement와 운영 마감

화면 너머의 소비자 — 통신 설정·release contract·최종 릴리스 보드.

Track 2Chapter 39Lesson 9고급

Preview 너머의 소비자들

지금까지의 검증은 전부 개발자인 나의 것이었다. 운영에서는 다르다: 외부 시스템이 예매 API를 호출하고, 통합 도구가 데이터를 읽어 가고, 업그레이드가 분기마다 돌아온다. 마지막 레슨의 질문은 하나다 — 이 서비스는 남이 안전하게 쓸 수 있는 상태인가.

통신 설정 — 누가, 어떤 자격으로 부르는가

🔭 환경 경계 먼저 — 이 절의 통신 설정(Communication Management)은 ABAP Cloud·S/4HANA Cloud 계열의 도구다. 우리 기준 환경(온프렘, L01)에는 이 화면이 없거나 다르므로, 온프렘 학습자는 이 레슨을 "읽고 설계하는" 레슨으로 삼으면 된다. 온프렘에서 커스텀 OData 서비스를 외부에 여는 길은 별도다: Binding publish 후 게이트웨이 등록·서비스 활성화·역할 배정의 경로(Chapter 34에서 본 그 세계)로 간다 — 개요만 알아 두자.

ABAP Cloud·S/4HANA Cloud 계열에서 외부 호출의 연결은 Communication Management가 관리한다. 네 개념의 관계만 잡으면 된다(설정 화면은 제품·테넌트마다 달라 체크리스트 중심으로 간다 — 기대 관리).

개념 뜻 비유
Communication Scenario 어떤 서비스들을 어떤 인증 방식으로 열지 묶은 정의 출입 가능 구역과 출입 방식의 규정
Communication System 통신 상대 시스템의 정보(호스트·인증) 상대 회사의 신원 등록
Communication User 기술 호출에 쓰는 사용자(사람 아님) 시스템끼리 쓰는 출입증
Communication Arrangement 위 셋을 실제로 연결한 운영 설정 서명된 출입 계약서

Service Binding과의 경계가 중요하다: Binding은 개발 의 노출(문을 만드는 일)이고, Arrangement는 운영의 연결(누가 그 문을 열 수 있는지의 계약)이다. Preview가 됐다고 외부 호출이 되는 것이 아닌 이유다. 문 자체도 하나 더 필요할 수 있다: L07의 Binding은 UI용(OData V4 – UI)이었고, 외부 시스템용은 같은 Service Definition에 Web API 유형의 Binding을 따로 만든다.

외부 노출의 운영 체크리스트(예고했던 그 표 — 각 줄이 실패 시 401/403/404의 원인 후보이기도 하다):

# 확인 실패하면 보이는 증상
1 Web API Binding이 활성·publish됐는가 404
2 Communication Scenario에 이 inbound 서비스가 포함됐는가(Scenario는 ADT에서 개발 객체로 만든다 — 서비스 목록·허용 인증 방식을 적는다) 404/403
3 Communication System에 상대의 호스트·인증 방식이 등록됐는가 401
4 Communication User가 만들어지고 System에 연결됐는가 401
5 Arrangement가 Scenario+System(+User)을 실제로 묶었는가 403
6 그 사용자의 권한(역할·DCL·BDEF auth)이 충분한가 403 또는 빈 목록
7 테스트 호출: metadata → read → create/action 순서로 기대 응답이 오는가 400/500이면 payload·provider 층

호출이 실패하면 HTTP 상태로 층을 가른다 — Chapter 34의 OData 감각 그대로: 401/403 = 인증·권한(User·역할·DCL/BDEF auth), 404 = endpoint/Binding, 400 = payload/validation, 412 = ETag 충돌(L08의 그 거부가 HTTP로 나타난 것 — 428은 표식을 아예 안 보낸 경우), 500 = provider 로직. 단 배치(batch) 호출은 겉 응답이 200이어도 안의 개별 요청이 실패할 수 있다 — 겉 상태코드만 보지 말 것.

Release Contract — 업그레이드를 견디는 약속

Chapter 24에서 released API 원칙을 배웠다. 운영 마감에서는 그 약속의 등급까지 읽는다: (SAP이 오브젝트마다 "어떤 용도로 안정적으로 써도 된다"고 붙이는 계약 등급. 업그레이드에도 깨지지 않을 범위를 정한다).

등급 약속 우리와의 접점
C1 시스템 안에서 쓰는 public API로 안정 우리가 소비하는 SAP API의 자격
C2 외부 원격 소비자용 API로 안정 외부가 소비하는 서비스의 자격
C0 확장 지점으로 안정 확장(CH32 감각)과 관련 — 개요만

번호는 높낮이(위계)가 아니라 용도의 축이다 — "어떤 방식의 사용에 대해 안정을 약속하나"가 다를 뿐이다(특히 C1은 "ABAP Cloud 개발에서 써도 되는가"의 축이라, ATC Cloud readiness가 실제로 거르는 것이 바로 이것이다). 오브젝트의 등급은 ADT에서 오브젝트를 열고 Properties 뷰의 API state로 확인한다. 우리 Z 오브젝트들은 아직 아무 계약도 붙지 않은 상태다 — 남이 쓰게 하려면 내 오브젝트의 API state를 released로 선언하는 절차가 따로 있는데(범위 밖), 그건 SAP의 C 등급을 다는 게 아니라 내 오브젝트에 대한 나의 계약 선언이다. 지금 방향은 "내가 의존하는 SAP 오브젝트의 계약을 확인한다"가 먼저다.

의미는 실용적이다: unreleased 오브젝트에 의존한 코드는 지금 돌아도 업그레이드 후 깨질 수 있다. 그 위반을 기계로 잡는 것이 Chapter 38에서 본 ATC의 Cloud readiness 검사다 — "release contract는 문서가 아니라 ATC가 검사하는 계약"으로 기억하자.

릴리스 보드 — Capstone 최종 채점

L01에서 고정한 완료 기준으로 돌아와, 전 계층을 한 번에 채점한다.

영역 완료 조건 증명한 곳
Data Model ZI/ZC(+ZI_Concert/ZI_Perf) 활성·관계 노출·변경 추적 필드 L02·L03
Behavior CUD·검증·action·기본값 동작 + projection behavior L04·L05
Draft 초안 보관·Resume·Discard + 복귀 안전(total ETag) L04·L07·L08
동시성 잠금·ETag·total ETag 충돌 통제 L08
권한 auth(자격)+features(상태) 서버 판정 — 운영 전환 시 DCL 승급 L08
EML MODIFY→COMMIT/ROLLBACK·두 관문의 FAILED 처리 L06
Service/UI Binding publish·Preview 8항목 L07
운영 통신 설정·released API/ATC·이송(전 오브젝트 동반) 이 레슨 + CH38

마지막 줄의 이송 항목을 풀어 두면: CDS 여섯 장(ZI 셋 + ZC 셋)·BDEF 둘(root+projection)·behavior pool·Service Definition/Binding·Metadata Extension·테이블(+draft table)까지 한 벌이 같은 경로로 가야 한다. 단 둘은 상자에 안 실린다: Binding의 publish 상태(대상 시스템에서 재-publish/등록)와 권한 오브젝트·역할(별도 경로 관리). 그리고 — 운영 승급 시에는 DCL·message class(즉석 텍스트에서 승급)·권한 오브젝트·테스트 class(Chapter 27의 몫)도 이 벌에 합류한다. Chapter 38의 object list 점검이 여기서 마지막으로 일한다.

흔한 실수와 점검 🚧

  • Binding = Arrangement 혼동 → 노출과 연결 계약은 다른 층이다. Preview 성공이 외부 호출 성공을 보증하지 않는다.
  • 권한 오류를 URL/네트워크 탓 → 같은 endpoint라도 사용자·역할·DCL·BDEF auth· Communication User에 따라 결과가 다르다. 401/403은 자격의 문제부터.
  • unreleased API 의존 방치 → 지금 돈다고 안전한 게 아니다. ATC Cloud readiness finding은 미래의 업그레이드 사고 예고다.
  • 오브젝트 일부만 이송 → RAP 앱은 오브젝트 한 벌이다. 하나가 빠지면 대상 시스템에서 활성화부터 무너진다(CH38의 그 사고).

정리 📌

  • 외부 소비 = Scenario → System → User → Arrangement의 연결 계약. Binding과는 다른 층.
  • Release contract(C0/C1/C2)는 업그레이드 내구성의 약속이고, 검사기는 ATC다.
  • 릴리스 보드 여덟 줄이 전부 초록일 때 — 그것이 "운영 가능한 RAP 앱"의 정의다.

🧩 도전 과제 (서브퀘스트)

마지막 서브퀘스트 — 나의 릴리스.

  1. 릴리스 보드 여덟 영역을 내 실습 시스템에서 직접 채점하고, 빨간 칸의 원인을 층으로 적는다.
  2. L06의 EML 리포트에 정원 초과 케이스를 넣어, 화면과 같은 메시지로 거부되는지 확인한다.
  3. (설계) 예매 API를 외부 파트너에게 열어 준다고 가정하고, 운영 체크리스트 7행의 각 줄에 무엇을 적을지(어느 서비스·어떤 인증·어떤 사용자·어떤 역할) 표로 설계한다.
  4. (심화) L05가 남긴 두 한계 — 같은 회차 다건 합산 판정, LOOP 밖으로 SELECT 빼기 — 를 직접 고쳐 본다.
  5. (회고) CH01의 첫 WRITE부터 이 릴리스 보드까지 — 각 챕터가 이 앱의 어느 층이 되었는지 한 장으로 그려 본다.

39개 챕터의 여정이 끝났다. 이제 여러분은 "화면을 띄워 본 사람"이 아니라, 어떤 문제가 어느 계층의 책임인지 분해할 수 있는 사람이다. 그 분해 능력이 UI5· Gateway·BTP 통합으로 나아가는 다음 여정의 출발점이다. CH01에서 정훈영과 함께 WRITE 한 줄로 시작한 여러분 — 수고했다, 이제 개발자다.
