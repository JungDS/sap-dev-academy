Dynamic ABAP: Field Symbol 심화와 Generic

RTTS — 실행 중 타입 정보 읽기

들어온 값의 정체를 묻는다 — 타입 설명서와 describe.

Track 3Chapter 28Lesson 7고급

무엇이 들어왔는지 모른다

generic 파라미터의 남은 숙제가 이것이다 — TYPE any로 받은 값이 숫자인지 문자열인지 구지 테이블인지 모르면 안전한 처리를 할 수 없다. 감으로 판단할 수는 없으니, 실행 중에 타입 정보를 읽는 서비스가 필요하다. 그게 (Runtime Type Services)다.

용어 뜻 이 레슨에서
RTTI Runtime Type Identification — 기존 데이터/타입 이름의 정보를 읽기 describe_by_data·describe_by_name
RTTC Runtime Type Creation — 새 타입 설명을 만들기 개념만(과밀 방지)
RTTS 둘을 합친 전체 체계 이름

무엇인가 — 타입 설명서 객체

의 반환물은 값이 아니라 타입 설명서 (type description object)다.

DATA(lo_type) = cl_abap_typedescr=>describe_by_data( iv_value ).

WRITE: / lo_type->absolute_name,   " 타입의 전체 이름
         lo_type->type_kind.       " 종류 코드(낱값/구조/테이블…)

설명서 는 계층을 이룬다 — 종류를 알았으면 그 종류의 설명서로 CAST 해서 더 깊은 정보를 읽는다. (이 그림은 이 레슨에 필요한 일부만 — 참조·객체용 설명서 등이 더 있다.)

TRY.
    DATA(lo_struct) = CAST cl_abap_structdescr(
      cl_abap_typedescr=>describe_by_data( gs_booking ) ).

    LOOP AT lo_struct->components ASSIGNING FIELD-SYMBOL(<ls_comp>).
      WRITE / <ls_comp>-name.        " BOOKING_ID, CONCERT_ID, SEATS, STATUS
    ENDLOOP.
  CATCH cx_sy_move_cast_error.
    WRITE / '구조가 아닙니다'.       " 낱값·테이블이면 CAST 실패
ENDTRY.

🔎 components는 값이 아니라 metadata다. 필드의 이름·타입 정보가 나올 뿐, 값을 읽으려면 여전히 ASSIGN COMPONENT가 필요하다 — 설명서 따로, 실물 따로.

렌즈로 비춰 보기

낱값·구조·테이블 카드를 렌즈에 올려 type_kind가 어떻게 나오는지, 구조일 때만 components 목록이 열리는지, 잘못된 CAST가 어떻게 실패하는지 확인해 보라.

어떻게 확인하는가

  • 데이터에서: describe_by_data( 값 ) — generic 로 받은 값의 정체 확인.
  • 이름에서: describe_by_name( 'SYST' ) — DDIC 타입 이름으로 설명서를 얻는다. 이 설명서를 CREATE DATA ... TYPE HANDLE에 꽂으면 그 타입의 데이터가 만들어진다 — 와 CREATE DATA가 만나는 지점.
  • 종류별 CAST 실패는 cx_sy_move_cast_error로 받는다 — "구조라고 가정"하지 말고 확인 후 진행.

흔한 실수와 점검 🚧

  • components에서 값을 꺼내려 함 → 거긴 필드 목록(metadata)이다. 값은 ASSIGN COMPONENT.
  • CAST를 확인 없이 → 낱값을 cl_abap_structdescr로 CAST하면 다. type_kind를 먼저 보거나 TRY/CATCH.
  • describe_by_name에 검증 안 된 이름을 변수로 → 미지 타입 이름은 TRY/CATCH로 잡히지 않는 오류로 이어질 수 있다. 이름은 ·허용 목록으로 한정하고, 동적 이름으로 데이터를 만들 땐 CREATE DATA TYPE (이름)의 예외 경로가 안전하다.
  • RTTC까지 욕심 → 실행 중 새 구조 타입 만들기(RTTC)는 강력하지만 입문 범위 밖이다. 이 챕터는 "읽기(RTTI) + TYPE HANDLE 연결"까지만.
  • 만능주의 → 타입을 이미 안다면 설명서를 읽을 이유가 없다. generic 도구에서만.

정리 📌

  • = 실행 중 타입 설명서를 읽는 서비스. describe_by_data/describe_by_name → 종류 확인 → 종류별 설명서로 CAST.
  • 구조 설명서(cl_abap_structdescr)의 components = 필드 목록(metadata) — 값 접근은 여전히 ASSIGN COMPONENT.
  • 설명서(TYPE HANDLE) → CREATE DATA 연결로 "읽기"가 "만들기"로 이어진다.

부품이 다 모였다 — generic 수신·상태 관리·필드 선택·타입 확인. 이걸 하나의 안전한 도구로 조립하자 → 실습 — 동적 구조 검사기.
