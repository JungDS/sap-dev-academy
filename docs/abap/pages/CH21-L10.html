🎫 배운 OO를 한 클래스에 모으기

잔여석 계산·예매 판정 모듈화에서 절차적으로 만들었던 잔여석·예매 판정을, 이제 하나의 업무 ZCL_BOOKING_MANAGER로 캡슐화한다. 상태는 숨기고(PRIVATE), 외부는 로만 다루며, 실패는 로, 사건은 로 표현한다. (목표는 멋진 OO를 많이 쓰는 게 아니라, 이 챕터에서 배운 것을 제자리에 놓는 것.)

🚧 실제 예약 행을 INSERT하거나 취소를 UPDATE하는 건 이후 DML 챕터의 영역이다. 여기선 읽기·검증·예외/이벤트 설계까지가 경계다.

CLASS zcl_booking_manager DEFINITION PUBLIC CREATE PUBLIC.
  PUBLIC SECTION.
    EVENTS sold_out
      EXPORTING VALUE(ev_concert) TYPE zconcert-concert_id
                VALUE(ev_perf)    TYPE zbooking-perf_no.

    METHODS constructor IMPORTING iv_concert TYPE zconcert-concert_id
                                  iv_perf    TYPE zbooking-perf_no
                        RAISING   zcx_concert_not_found.
    METHODS remaining  RETURNING VALUE(rv_remaining) TYPE i.
    METHODS can_book   IMPORTING iv_seats TYPE i
                       RETURNING VALUE(rv_ok) TYPE abap_bool.
    METHODS book       IMPORTING iv_seats TYPE i
                       RAISING   zcx_fully_booked.
  PRIVATE SECTION.
    DATA mv_concert TYPE zconcert-concert_id.
    DATA mv_perf    TYPE zbooking-perf_no.
    DATA mv_cap     TYPE i.
ENDCLASS.

CLASS zcl_booking_manager IMPLEMENTATION.
  METHOD constructor.
    mv_concert = iv_concert.
    mv_perf    = iv_perf.
    SELECT SINGLE capacity FROM zconcert
      WHERE concert_id = @iv_concert INTO @mv_cap.
    IF sy-subrc <> 0.                            " 없는 공연이면 유효하지 않은 객체를 만들지 않는다
      RAISE EXCEPTION TYPE zcx_concert_not_found.
    ENDIF.
  ENDMETHOD.

  METHOD remaining.
    SELECT COALESCE( SUM( seats ), 0 ) FROM zbooking
      WHERE concert_id = @mv_concert AND perf_no = @mv_perf
        AND status <> 'C'                       " 취소 제외
      INTO @DATA(lv_booked).
    rv_remaining = mv_cap - lv_booked.
  ENDMETHOD.

  METHOD can_book.
    rv_ok = xsdbool( iv_seats > 0 AND iv_seats <= me->remaining( ) ).
  ENDMETHOD.

  METHOD book.
    DATA(lv_remaining) = me->remaining( ).
    IF iv_seats > lv_remaining.
      RAISE EXCEPTION TYPE zcx_fully_booked.     " 실패 = 예외(원인: 매진)
    ENDIF.
    " 실제 INSERT(예약 저장)는 이후 DML 챕터에서 이 자리에 들어간다.
    IF iv_seats = lv_remaining.
      RAISE EVENT sold_out                       " 사건 = 이벤트(저장이 끝난 다음에 알린다)
        EXPORTING ev_concert = mv_concert ev_perf = mv_perf.
    ENDIF.
  ENDMETHOD.
ENDCLASS.

두 군데를 눈여겨보자.

  • 생성자가 스스로 확인한다. Constructor와 객체 초기화에서는 "공연이 실제로 있다"는 전제로 뒀지만, 종합판은 SELECT SINGLE 뒤 sy-subrc를 보고 없는 공연이면 ZCX_CONCERT_NOT_FOUND를 던진다. 정원을 모르는 채 태어나는 가 없어진다.
  • 통지는 저장 뒤에. 매진 통지는 상태를 실제로 바꾼(저장이 끝난) 다음의 일이다. 그래서 INSERT 자리가 RAISE EVENT보다 앞에 있다. '통지 먼저, 저장 나중' 순서가 굳으면 저장이 실패해도 매진 알림이 나가는 버그가 된다.

⚠️ 이름은 원인 그대로. book은 잔여석 초과만 ZCX_FULLY_BOOKED로 알린다. 좌석 수가 0 이하인 입력 오류까지 이 예외로 던지면 이름이 원인을 거짓말하게 되고, 호출자는 매진인 줄 알고 다른 회차를 안내할 수도 있다. 좌석 수가 1 이상인 것은 선택화면 검증에서 걸러진다는 전제이고, 실무에서는 ZCX_INVALID_INPUT처럼 사유별 예외를 나눈다. VIP 상한 위반(Inheritance / Redefinition)도 같은 이유로 실무라면 별도 예외가 맞다.

호출부는 public 만 쓴다(정원·회차를 직접 못 바꾼다). 생성자도 예외를 던질 수 있으니 NEW까지 TRY 안에 둔다.

TRY.
    DATA(lo_mgr) = NEW zcl_booking_manager( iv_concert = 'C001' iv_perf = '01' ).
    lo_mgr->book( iv_seats = 2 ).
    MESSAGE '예약 가능' TYPE 'S'.
  CATCH zcx_concert_not_found.
    MESSAGE '없는 공연입니다.' TYPE 'I'.
  CATCH zcx_fully_booked INTO DATA(lx_booked).
    MESSAGE lx_booked->get_text( ) TYPE 'I'.
ENDTRY.

직접 해 볼 과제

  1. ZCX_FULLY_BOOKED·ZCX_CONCERT_NOT_FOUND 두 (CX_STATIC_CHECK )를 SE24에서 만든다(절차는 Global Class 생성과 객체의 SE24 스텝, 클래스 유형은 Exception Class).
  2. 를 만들고 remaining( )이 취소 제외 좌석 합계를 정원에서 빼는지 확인한다. 없는 공연 ID로 만들면 ZCX_CONCERT_NOT_FOUND가 잡히는지도 본다.
  3. 잔여석보다 큰 좌석 수로 book을 불러 ZCX_FULLY_BOOKED가 CATCH로 잡히는지 확인한다.
  4. (도전) OO 이벤트에서 만든 zcl_booking_monitor의 객체 lo_monitor를 SET HANDLER로 등록하고, 잔여석과 같은 좌석을 예약해 sold_out 가 호출되는지 본다.

흔한 실수와 점검 🚧

  • remaining( )에서 취소 미제외 → status = 'C'까지 합산하면 잔여석이 실제보다 적게 나온다.
  • can_book과 book 기준 불일치 → 둘이 다른 잔여석 판단을 가지면 호출자가 혼란스러워진다. book이 내부에서 remaining( )을 다시 확인한다.
  • 너무 넓은 이름 → ZCX_ERROR는 이유 구분이 안 된다. ZCX_FULLY_BOOKED처럼 업무 상황을 말하는 이름.
  • 동시 예약을 잊음 → remaining( )으로 조회한 뒤 book이 판정하는 사이에 다른 사용자가 먼저 예약하면 초과 판매가 날 수 있다. 여러 사용자가 함께 쓰는 프로그램에는 잠금이 필요한데, 다중 사용자 변경 충돌 시나리오에서 배운다. 지금은 위험이 있다는 것만 기억하자.
  • 상태 캡슐화 → 정원·회차는 PRIVATE, 외부는 로만(Attribute / Method / Visibility). 없는 공연 ID는 선택화면 검증에서 한 번 거르고, 생성자가 sy-subrc로 한 번 더 확인한다(이중 방어).

예약 로직을 로 설계·검증·예외·까지 다뤘다. 이제 이 객체와 이벤트를 화면·ALV로 이어 가자 → SALV Sort / Filter / Function 제어.
