🌙 새벽 2시, 파일이 도착한다

운영 는 사람이 버튼을 누르는 방식으로 끝나지 않는다. 물류 시스템이 매일 밤 서버 경로에 결과 파일을 내려놓고, SAP 배치 job이 새벽에 읽어 상태를 갱신한다. 이때 주인공은 application server의 파일이다. PC 파일(gui_upload)과 무대가 다르다.

기술 키워드는 네 개지만, 이 레슨의 진짜 목표는 문법 암기가 아니다. 파일 수신부터 재처리까지의 운영 구조를 한 바퀴 도는 것이다.

DATA gv_path TYPE string VALUE '/usr/sap/interfaces/in/booking_20260729.txt'.
DATA gv_msg  TYPE string.

OPEN DATASET gv_path FOR INPUT IN TEXT MODE ENCODING UTF-8
  MESSAGE gv_msg.
IF sy-subrc <> 0.
  " gv_path·sy-subrc·gv_msg(OS 원인)를 로그로 남기고 중단
  RETURN.
ENDIF.

DO.
  READ DATASET gv_path INTO DATA(gv_record).
  IF sy-subrc <> 0.
    EXIT.                            " 더 읽을 줄 없음
  ENDIF.
  " 한 행 파싱 → 검증 → 처리
ENDDO.

CLOSE DATASET gv_path.
  • FOR INPUT(읽기) · FOR OUTPUT(새로 쓰기) · FOR APPENDING(이어쓰기).
  • MESSAGE gv_msg를 항상 붙인다 — 못 열었을 때 sy-subrc만으론 권한 문제인지 경로 오타인지 파일 없음인지 알 수 없다. OS 오류 텍스트가 로그의 핵심이다.
  • 쓸 때는 TRANSFER <데이터> TO <경로>로 한 줄씩 내보낸다. 오류 행만 모은 오류 파일을 만들 때도 이 조합이다.

OPEN DATASET gv_err_path FOR OUTPUT IN TEXT MODE ENCODING UTF-8
  MESSAGE gv_msg.
IF sy-subrc = 0.
  TRANSFER gv_err_line TO gv_err_path.
  CLOSE DATASET gv_err_path.

⚠️ 경로 보안 — Directory Traversal. 외부에서 받은 파일명을 그대로 경로에 붙이면, ../가 섞인 이름으로 허용하지 않은 상위 경로에 접근당할 수 있다. 고정 root 디렉터리 + 파일명 whitelist·확장자 검사·경로 정규화로 반드시 막는다.

운영 구조 — 한 바퀴가 전부 있어야 한다

BAPI·RFC·BDC·Excel·File, 기술 이름은 달라도 운영 골격은 같다.

단계 하는 일 로그에 남길 것
수신 지정 경로에 파일 확인 파일명·크기·수신 시각
열기 OPEN DATASET ... MESSAGE sy-subrc·OS 메시지
검증 행별 필수·타입·중복·업무 규칙 행 번호·오류 사유
처리 BAPI·DML 등으로 등록 처리 방식·Return
확정 commit 단위 결정 성공/실패 건수
보관 처리 완료 파일 이동·오류 파일 생성 보관 경로·처리 ID
재처리 실패 건 수정 후 재투입 retry 횟수·마지막 오류

여기에 하나 더, (Idempotency). 같은 파일·같은 행이 두 번 들어와도 중복 등록되지 않는 성질이다. 외부 시스템은 같은 파일을 다시 보낼 수 있고, 배치는 중간 실패 후 재실행된다. 파일 ID·행 key·외부 문서번호를 처리 이력과 대조해 "이미 처리한 건"을 걸러야 한다. Chapter 25 · 오류 로그와 재처리에서 세운 원칙이 파일 세계로 확장된 것이다.

  • commit 단위도 정책이다: 파일 전체 한 LUW(정합성↑, 한 건 오류에 전체 정지) vs 행/묶음 단위 commit(재처리 쉬움, 부분 성공 관리 필요).

운영 흐름 체험

파일 수신부터 재처리까지 한 바퀴 돌려 보라. 권한 오류로 못 여는 경우, 오류 행의 오류 파일 생성과 재처리 큐, 같은 파일을 다시 받았을 때 차단까지.

전체 공통 골격은 지도 한 장으로 정리해 두자.

흔한 실수와 점검 🚧

  • CLOSE DATASET 누락 → 파일 핸들 누수. 프로그램 종료가 치워 주길 기대하지 말고 명시적으로 닫는다.
  • 외부 파일명 신뢰 → 파일명도 입력 데이터다. 경로 조작·이상 확장자·재전송을 전부 의심한다.
  • 실패 파일 즉시 삭제 → 원인 분석도 재처리도 불가능해진다. 원본과 오류 로그는 보관 정책대로 남긴다.
  • 미설계 → 배치 재실행 시 성공했던 행이 또 등록된다. 외부 key+처리 이력으로 중복을 막는다.
  • 실패를 개발자만 아는 구조 → 운영자가 파일명·행 번호·key·메시지·재처리 상태를 화면/로그에서 직접 볼 수 있어야 한다.

정리 📌

  • 서버 파일은 OPEN DATASET(+MESSAGE) → READ DATASET → TRANSFER → CLOSE DATASET. PC 파일(gui_upload)과 무대가 다르다.
  • 운영 품질 = 경로 보안 + 행 검증 + commit 단위 + 로그 + 재처리 + . 파일을 읽는 능력이 아니라 실패를 안전하게 다시 처리하는 능력이 실력이다.
  • 이 골격은 BAPI·RFC·BDC·Excel에도 똑같이 적용된다.

🧩 도전 과제 (서브퀘스트)

선택 과제 — 예매 데이터를 외부와 주고받는다.

  1. 예매 조회를 RFC 함수(Remote-Enabled)로 노출해 외부에서 호출 가능하게 한다(RFC 설계).
  2. 엑셀 예매 파일을 업로드해 검증 후 등록하고(Excel Upload · BAPI), 실패 건을 로그에 남긴다.
  3. (심화) 서버 파일 배치로 바꾸고 재처리 큐와 key를 설계한다. 표준 등록이 필요하면 BDC Session으로.

단건·파일 를 두루 다뤘다. 다음은 표준 메시지 기반 연계다. 문서를 전자문서(IDoc)로 주고받고 서비스로 노출하는 세계, Chapter 34 · IDoc / ALE / Gateway로 간다.
