Background Job 운영 — 무인 실행

사람이 없는 시간의 실행 — SUBMIT과 잡 스케줄, 상태와 증거.

Track 2Chapter 38Lesson 5고급

새벽 2시의 정산은 누가 실행하나

공연이 끝난 날의 정산은 데이터가 많아 오래 걸린다. 낮에 화면에서 돌리면 사용자는 기다리다 지치고, 화면(dialog) 실행에는 실행 시간 상한이 있어서 길어지면 시스템이 끊어 버린다. 이런 일은 부하가 적은 새벽, 사람 없이 돌아야 한다 — 그리고 background 실행에는 그 시간 상한이 적용되지 않는다. "긴 작업은 배치로"의 기술적 근거가 이것이다.

그 방식이 (사용자 화면(dialog) 없이 서버가 정해진 시각·조건에 프로그램을 실행하는 방식)이다. 단, 사람이 지켜보지 않기 때문에 요구가 하나 더 붙는다: 모든 것이 기록으로 남아야 한다. 언제 시작했고, 어떤 조건으로 돌았고, 몇 건을 처리했고, 실패했다면 왜인지 — 화면이 없으니 증거가 화면을 대신한다.

먼저 SUBMIT — 프로그램이 프로그램을 실행한다

잡을 코드로 만들기 전에, 부품 하나가 처음 등장한다. 지금까지 리포트는 SE38에서 사람이 실행했다. (다른 실행 프로그램(리포트)을 프로그램 코드에서 실행하는 ABAP 문장)은 그 실행을 코드가 대신한다(공식 keyword doc 확인).

" 기본형: 리포트를 실행하고, 끝나면 이 자리로 돌아온다
SUBMIT zbook_settle
  USING SELECTION-SET 'NIGHTLY'   " 저장해 둔 variant로 선택화면을 채움
  AND RETURN.
  • USING SELECTION-SET — 선택화면 값을 사람이 입력할 수 없으니, Chapter 15 · Variant에서 배운 variant로 채운다(만들기는 SE38 실행 화면에서 값을 넣고 저장 버튼 → 이름 NIGHTLY). 무인 실행에서 variant가 필수인 이유가 이것이다. 함정 하나: 날짜 조건을 고정값으로 저장하면 매일 도는 잡이 영원히 그 날짜만 처리한다(에러도 없이 0건 처리 — 가장 조용한 사고). 우리 정산처럼 "미처리 건만 집는" 설계면 날짜 자체가 없어 안전하고, 날짜가 꼭 필요한 잡은 variant의 동적 날짜 기능(저장 화면의 선택 변수 — "어제", "전월 말일" 등)을 쓴다는 것만 알아 두자.
  • AND RETURN — 실행이 끝나면 호출한 프로그램으로 돌아온다. 없으면 제어가 넘어간 채 돌아오지 않는다.

잡으로 감싸기 — 열고, 넣고, 닫는다

SUBMIT을 지금 즉시가 아니라 "새벽 2시에, background로" 실행하려면 잡이라는 틀에 넣어야 한다. 리듬은 Chapter 37의 FP_JOB과 같은 "열고-넣고- 닫고" 3박자다: JOB_OPEN(잡 생성) → VIA JOB(단계 등록) → JOB_CLOSE(확정·예약). 이름이 비슷하지만 다른 물건이라는 것도 같이 기억하자: FP_JOB은 PDF 양식의 출력 작업, JOB_OPEN은 background 잡이다 — 리듬만 닮았다.

이 예약 리포트 자체는 사람이 화면에서 실행하는 dialog 프로그램이다(예매 마감을 확인한 담당자가 정산을 예약하는 그림). 그래서 오류를 MESSAGE로 띄워도 된다 — background 세계의 제약은 이 리포트가 아니라 예약되는 쪽(zbook_settle) 에 적용된다.

REPORT z_schedule_settle.

DATA gv_jobname  TYPE tbtcjob-jobname VALUE 'ZBOOK_SETTLE_NIGHTLY'.
DATA gv_jobcount TYPE tbtcjob-jobcount.   " 같은 이름 잡을 구분하는 번호

START-OF-SELECTION.
  " ① 잡 껍데기 생성 — 번호(jobcount)를 돌려받는다
  CALL FUNCTION 'JOB_OPEN'
    EXPORTING  jobname  = gv_jobname
    IMPORTING  jobcount = gv_jobcount
    EXCEPTIONS OTHERS   = 1.
  IF sy-subrc <> 0.
    MESSAGE '잡을 생성할 수 없습니다' TYPE 'E'.
  ENDIF.

  " ② 이 잡의 단계로 리포트를 등록 — VIA JOB에는 AND RETURN이 필수(공식 규칙)
  SUBMIT zbook_settle
    VIA JOB gv_jobname NUMBER gv_jobcount
    USING SELECTION-SET 'NIGHTLY'
    AND RETURN.

  " ③ 잡 확정 — 새벽 2시로 예약(sdlstrtdt = 시작 날짜, sdlstrttm = 시작 시각)
  "   지금 당장 돌리려면 이 두 줄 대신 strtimmed = abap_true 한 줄
  CALL FUNCTION 'JOB_CLOSE'
    EXPORTING  jobname   = gv_jobname
               jobcount  = gv_jobcount
               sdlstrtdt = sy-datum + 1     " 내일
               sdlstrttm = '020000'         " 02:00:00
    EXCEPTIONS OTHERS    = 1.
  IF sy-subrc <> 0.
    MESSAGE '잡을 확정할 수 없습니다' TYPE 'E'.
  ENDIF.

②의 SUBMIT은 기본형과 달리 즉시 실행되지 않는다. VIA JOB 덕분에 "이 잡의 단계"로 등록만 되고, 실행은 ③에서 확정된 시작 조건이 정한다. 그래서 VIA JOB에는 AND RETURN이 문법 규칙으로 강제된다(등록 후 반드시 이 코드로 돌아와 ③을 마쳐야 하므로). ③이 끝나면 잡은 상태표(아래)의 Released가 된다 — 시작 조건이 확정돼 때를 기다리는 상태다. gv_jobcount가 필요한 이유도 여기 있다: 매일 도는 정산 잡은 이름은 같고 실행마다 번호가 다른 여러 개가 쌓인다(SM37에서 이름으로 찾으면 날짜별로 여러 줄이 나오는 게 정상이다).

같은 잡을 화면으로 만드는 길이 실무에선 더 흔하다. SM36에서 네 걸음이다: ① 잡 이름 입력 → ② Step에 프로그램(ZBOOK_SETTLE)과 variant(NIGHTLY) 등록 → ③ Start condition에서 Date/Time을 고르고 날짜·시각 입력(Periodic 체크를 켜면 매일/매주 반복) → ④ 저장. 결과물은 코드 방식과 같은 잡이다. 코드 방식은 "프로그램이 프로그램을 예약"할 때(예: 접수 완료 시 후속 정산 예약) 쓴다.

실행 사용자도 잡 정의에 기록된다(SM36의 Step 정의에서 지정, 기본값은 예약한 나 자신). background에는 로그인한 사람이 없으므로 권한 검사(AUTHORITY-CHECK)는 잡에 지정된 실행 사용자 기준으로 돈다. 여기서 실무의 조용한 사고 하나: 내 계정으로 만든 야간 잡은 내가 퇴사·잠금되는 날 몇 달 잘 돌다가 갑자기 권한 오류로 죽는다. 그래서 운영 잡은 개인 계정이 아니라 전용 시스템 사용자로 돌리는 것이 관례다(남의 사용자로 예약하려면 별도 권한이 필요하다).

SM37 — 잡의 일생을 읽는 화면

예약된 잡은 상태를 갈아타며 산다. SM37(job overview)에서 그 일생을 조회한다 (선택화면에 잡 이름·사용자·날짜를 넣고 실행).

상태 뜻
Scheduled 정의만 됨(시작 조건 미확정)
Released 시작 조건 확정 — 때를 기다리는 중
Ready 시작 조건이 충족돼 실행 차례를 기다리는 중(보통 짧게 지나가지만, 실행 자원이 부족하면 여기 머문다 — 잡 지연의 대표 원인)
Active 실행 중
Finished 정상 종료
Canceled 비정상 종료(중단) — 원인을 고친 뒤 다시 예약한다(SM37의 잡 복사 기능으로 같은 조건 재예약이 가능하다. 스풀 재출력 같은 "재시작 버튼"은 아니다)

목록에서 잡을 선택하고 Job log 버튼을 누르면 기술 로그(시작·종료·중단 메시지)가, 스풀 아이콘이 있으면 그 잡의 출력물이 열린다. Canceled의 원인이 런타임 오류(short dump)라면 job log에는 "중단됐다" 한 줄만 남는 경우가 많다 — 진짜 원인은 ST22(덤프 분석 화면)에 있다. 야간 잡 장애 대응의 첫 손이 ST22인 이유다.

여기에 운영 감각 하나를 얹어야 한다. Finished는 "프로그램이 안 죽었다"는 뜻이지 "업무가 성공했다"는 뜻이 아니다. 1만 건 중 3천 건이 오류로 건너뛰어도 프로그램이 끝까지 돌면 Finished다. 그래서 잡의 증거는 세 겹으로 본다: job log(기술 기록: 시작·종료·중단 메시지) + spool(Chapter 37의 그 스풀 — 잡의 출력물) + 업무 로그(몇 건 성공·실패 — 다음 레슨의 Application Log).

dialog용 프로그램을 그대로 잡에 태우면

background에는 사용자 PC도, 화면도 없다. 그래서 dialog 전제가 깔린 코드는 잡에서 그대로 죽는다 — 이미 배운 경계들이 전부 재등장한다.

dialog 전제 잡에서의 운명
gui_download·frontend 파일(Chapter 37 · 실행 위치 경계) 사용자 PC가 없어 실패
팝업·확인 창·MESSAGE TYPE 'E' 누를 사람이 없다 — E 메시지는 잡을 Canceled로 끝낸다
선택화면 수동 입력 입력할 사람이 없음 → variant로(이 레슨)

하나 더, 주기 잡의 고전 사고: 중복 처리다. 매일 도는 정산 잡이 어제 실패해서 오늘(수동 재예약으로) 두 번 돌면, 같은 예매가 두 번 정산될 수 있는가? 방어의 뼈대는 Chapter 25 · 오류 로그와 재처리에서 배운 처리 상태 설계 그대로다: 정산이 끝난 예매에 상태를 남기고(예: settled 플래그·정산 일시), 프로그램 첫머리의 SELECT가 미처리 건만 고르게 한다. 단 전제가 하나 있다 — 정산 반영과 상태 갱신이 같은 LUW(한 COMMIT)에 묶여야 한다(CH25). 따로 되면 "상태만 남고 정산은 "이라는 최악이 가능하다. 묶여 있으면 중간에 죽은 경우도 안전하다: 커밋된 건 상태가 남았고, 롤백된 건 상태가 없어 다음 실행이 다시 집는다.

재실행 안전이 첫 질문이면 동시 실행 안전이 두 번째 질문이다. 어제 잡이 아직 Active인데 오늘 잡이 시작되면(스케줄이 겹치는 일은 흔하다), 두 가 같은 "미처리 건"을 동시에 읽어 이중 정산할 수 있다 — 상태 플래그만으로는 이 틈이 안 막힌다. 표준 방어는 Chapter 26 · 잠금의 lock object(ENQUEUE)로 잡 단위 배타 실행을 보장하는 것이다(시작하자마자 잠금을 잡고, 못 잡으면 "이미 도는 중"으로 조용히 끝낸다). 이 두 성질을 갖춘 프로그램만 주기 잡에 태운다.

흔한 실수와 점검 🚧

  • dialog 리포트를 그대로 잡에 → 팝업·frontend 접근에서 죽는다. 위 경계 표로 먼저 점검.
  • variant 없이 예약 → 어떤 조건으로 돌았는지 아무도 모른다. 무인 실행 = variant 필수.
  • Finished만 보고 퇴근 → 업무 성공은 Application Log·처리 건수로 확인한다. Finished ≠ 성공.
  • 재실행 안전장치 없는 주기 잡 → 실패 후 재실행에서 중복 처리 사고. "다시 돌려도 안전한가"가 잡 설계의 첫 질문이다.
  • VIA JOB에 AND RETURN 누락 → 문법 규칙 위반. 3박자(OPEN→ VIA JOB→CLOSE)를 한 덩어리로 기억한다.

정리 📌

  • SUBMIT = 코드가 리포트를 실행. 무인 실행의 선택화면은 variant(USING SELECTION-SET)로.
  • 잡 예약 3박자 = JOB_OPEN → VIA JOB … AND RETURN → JOB_CLOSE. 화면 방식은 SM36.
  • SM37의 상태 + 세 겹의 증거(job log·spool·업무 로그)로 읽는다. Finished ≠ 업무 성공.
  • 주기 잡의 자격 = 재실행해도 안전(중복 방지 설계).

잡이 실패한 새벽, 운영자는 무엇을 보고 원인을 찾는가. "실패했다"만 남기고 "왜"를 안 남기면 아무도 도울 수 없다. 운영 표준 로그로 간다.
