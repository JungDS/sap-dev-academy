Forms / Output / PDF

양식 오류 추적과 변경 대응

"안 나와요" 티켓을 다섯 단계로 좁힌다 — 그리고 양식도 코드처럼 이송한다.

Track 2Chapter 37Lesson 5중급

"확인서가 안 나와요"

양식 개발은 "내 PC에서 PDF가 한 번 열렸다"로 끝나지 않는다. 고객에게 나가는 문서라서, 이름이 비거나 금액이 틀리거나 아예 안 나가면 바로 운영 사고다. 그리고 이 사고의 원인은 여러 층 중 하나다: 데이터가 비었을 수도, 매핑이 깨졌을 수도, 출력 결정이 안 됐을 수도, 렌더링이 실패했을 수도, 전달 채널이 막혔을 수도 있다.

운영에서 성장하는 개발자는 "안 나옵니다"를 듣고 바로 코드를 여는 사람이 아니라, 어느 단계까지 성공했는지부터 확인하는 사람이다. 이 챕터에서 배운 모든 층이 그대로 추적 순서가 된다.

다섯 단계 추적표

단계 질문 확인 지점 원인일 때의 조치
1 데이터 출력할 값이 ABAP에 있는가 디버거·입력 구조 조회·매핑 수정
2 매핑 양식이 그 값을 받는가 Form Interface·Node 참조(&…&, L01) 계약·참조 수정
3 결정 출력하기로 결정됐는가 문서 화면의 출력 메뉴 — 메시지 상태·output item(L03) 조건·rule·수신자 설정
4 렌더링 PDF·인쇄 데이터가 생겼는가 OTF 수령·CONVERT_OTF 반환(L02)·빈 xstring(L04) 양식·변환·폰트 점검
5 전달 실제로 도착했는가 SP01(인쇄)·SOST(메일)·프린터 재출력·채널 설정

이 챕터의 Output Control 레슨에서 예고한 (인쇄용 출력 데이터를 저장·관리하는 SAP의 출력 대기 영역. 공식 용어로 출력 요청 = spool request)을 여기서 정식으로 본다. 인쇄 채널의 출력은 스풀에 spool request로 쌓였다가 프린터로 간다. 여기엔 층이 하나 더 있다: spool request는 인쇄할 데이터이고, 그것을 실제 장치로 보내는 output request(전송 시도 기록)가 따로 생긴다. 운영 장애의 대부분은 "spool request는 정상인데 output request가 오류"로 나타나고 오류 로그도 output request 쪽에 붙는다. "인쇄 데이터가 만들어졌다"(spool request 정상)까지만 보고 "출력됐다"고 판정하면 안 되는 이유다.

SP01 화면에 들어가면 선택화면이 뜨는데, 기본으로 내 사용자·오늘 날짜가 채워져 있어 그대로 실행하면 내 요청 목록이 나온다. 목록에서 상태(완료·오류·대기)를 확인하고, 오류면 그 요청을 열어 로그로 원인을 본다. 재출력도 이 화면에서 요청을 선택해 다시 보낸다. 단 두 가지 주의: spool request에는 보존 기간이 있어 만료·삭제되면 재출력이 불가능하고(그때는 원 업무 화면에서 다시 발행한다), 고객 발송물의 재출력은 중복 발송이 될 수 있으니 운영 절차에 따라 한다.

이메일 채널의 대응물은 SOST(메일 등 외부 발송을 담당하는 표준 발송 계층(SAPconnect)의 요청 목록 화면)다. 메일이 발송 대기인지· 실패했는지·언제 나갔는지를 여기서 본다. 요청들이 "대기"에서 움직이지 않는다면 1순위 원인은 발송을 실제 수행하는 정기 작업이 스케줄되지 않은 것이다 — 이건 화면만 보고도 판별해 Basis에 넘길 수 있다. 인쇄는 SP01, 메일은 SOST — 채널마다 확인처가 따로 있다.

핵심 원리는 하나다. 단계 N이 실패했으면 단계 N만 고친다. output item이 안 생겼는데(3) 양식 매핑(2)을 붙잡고 있으면 시간만 간다. 판별에 쓰는 경험칙 하나 더: 특정 대상만 실패하면(예: VIP 고객만 안 옴) 3단계(결정)부터 본다. 조건· 수신자 설정이 대상을 가르는 층이기 때문이다.

표의 4단계 조치에 있는 "폰트 점검"이 낯설 텐데, 양식이 지정한 폰트가 출력 장치 설정에 없으면 데이터가 다 맞아도 4단계에서 깨진다. 증상은 주로 다른 폰트로 대체되어 레이아웃이 밀리는 모양으로 나타나고, PDF 변환 결과도 양식· 장치 설정의 폰트 정보를 따르므로 같은 원인이 PDF에서도 드러난다. 한글 문서에서 특히 자주 만나는 원인 후보라는 것까지만 알아 두자.

티켓 보드로 연습하기

실제 장애 티켓 다섯 장이다. 각 단계 버튼을 눌러 어디까지 초록불인지 확인하고, 멈춘 단계를 짚어 보라.

변경 대응 — 양식도 코드다

양식은 "코드가 아니니까 가볍게 고쳐도 된다"고 생각하기 쉽다. 반대다. 로고·법적 문구·금액 표시는 전부 고객 문서에 직접 드러나는 변경이라 더 무겁다.

  • 이송으로 간다 — 운영에서 직접 수정하면 누가 언제 무엇을 바꿨는지 추적이 끊긴다. 양식 변경도 Chapter 1 · 이송요청의 길을 그대로 밟는다 (개발 → 테스트 → 운영). 이때 동반 오브젝트를 빠뜨리는 게 단골 사고다: 양식이 쓰는 스타일(글꼴·문단 규격 묶음)·텍스트 모듈/표준텍스트(여러 양식이 공유하도록 시스템에 등록해 둔 문구 조각)·그래픽(로고 이미지)이 전부 함께 실려야 한다. 경계는 이렇게 긋는다: 문서의 모양·문구가 바뀌면 양식(이송), "언제 누구에게"의 조건 는 설정 등록(이송 없음), 출력 유형 같은 **설정 틀은 Customizing(또 이송 대상)**이다(이 챕터의 Output Control 레슨의 경계 그대로). 그리고 이송 후 대상 시스템에서 활성 상태와 호출을 확인하는 것까지가 이송의 끝이다(생성 함수는 대상 시스템이 다시 만드는데, 그쪽 DDIC가 안 맞으면 그때야 실패가 드러난다).
  • 샘플 검증 후 배포 — 정상 1건만 보고 배포하면 안 된다. 최소한 긴 고객명· 좌석 여러 건(페이지 넘김)·금액 0원·데이터 누락 케이스로 테스트 출력을 뽑는다.
  • 구조 변경은 짝으로 — 예매 테이블에 필드가 추가되면 Form Interface도 함께 바꾸고 재활성화한다(활성화 방법은 L01의 만드는 걸음 그대로). 한쪽만 바꾸면 2단계(매핑)에서 깨진다. 참고로 이송되는 것은 양식이고 생성 함수 모듈은 대상 시스템이 다시 만든다 — L01에서 함수명을 하드코딩하지 말라던 이유가 여기서 다시 확인된다.
  • 오류는 기록으로 — 출력 실패 시 양식 이름·문서 번호·단계·원문 메시지를 로그에 남긴다(Chapter 25 · 오류 로그와 재처리 구조). "출력 실패" 한 줄로는 운영자가 아무것도 좁힐 수 없다.

판정 연습

여섯 상황을 "올바름/잘못"으로 판정해 보라. 이 챕터 운영 감각의 총정리다.

흔한 실수와 점검 🚧

  • 운영 양식 직접 수정 → 추적 불가·환경 불일치. 양식도 이송으로.
  • 정상 샘플 1건으로 배포 → 문서는 edge case(긴 이름·다건·페이지 넘김)에서 깨진다.
  • 단계 건너뛰고 코드부터 → 5단계 표 순서대로. 실패한 단계만 고친다.
  • rule 문제를 layout 문제로 오판 → output item이 없으면 3단계(결정)다. 양식을 고쳐도 소용없다.
  • 오류 메시지 삼키기 → 단계·원문 메시지 없는 "실패" 로그는 재처리를 막는다.

정리 📌

  • 출력 장애 = 데이터 → 매핑 → 결정 → 렌더링 → 전달의 5단계로 좁힌다. 실패한 단계만 고친다.
  • 인쇄 채널의 확인처 = 스풀(SP01의 spool request 상태).
  • 양식 변경 = 코드 변경과 같은 규율: 이송 + 샘플 검증 + 짝 변경 + 오류 기록.

🧩 도전 과제 (서브퀘스트)

선택 과제 — 예매 확인서를 끝까지 책임진다.

  1. 예매 확인서 양식을 Smart Forms로 설계하고, L01의 조회-호출 리포트로 미리보기까지 연결한다. 여력이 되면 L01에서 예고한 좌석 목록 확장까지: Form Interface에 테이블 (Table Type)를 더하고 MAIN에 Table node를 배치해, 좌석 여러 줄이 페이지를 타고 흐르는지 확인한다.
  2. L02의 OTF→PDF 변환을 거쳐 L04의 파이프라인으로 BIN 저장한다. 텍스트 모드('ASC')로도 저장해 비교해 보라 — 아예 안 열릴 수도, 열리되 일부만 깨질 수도 있는데, 원본과 가 달라진 시점에 이미 실패라는 게 판정 기준이다.
  3. (설계) 예매 확정 시 자동 발송되도록 Output Control의 결정 조건(누구에게·어떤 채널)을 표로 설계한다.
  4. (운영) "VIP 고객만 확인서가 안 온다"는 티켓을 받았다고 가정하고, 5단계 추적표로 점검 계획을 적어 본다.

문서가 고객에게 나가는 길까지 다 밟았다. 남은 것은 이 모든 개발물을 안전하게 운영으로 보내고 지키는 일이다. Chapter 38 · ATC / Code Inspector로 간다.
