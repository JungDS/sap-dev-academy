운영 리스크와 DB 종속성

강한 수단을 운영에 들이는 조건 — 책임의 목록을 만든다.

Track 3Chapter 36Lesson 6고급

개발기에서 빠른 것과 운영에서 안전한 것

성능 개선은 개발 서버에서 빨라 보이는 것으로 끝나지 않는다. 운영에서 client가 섞이거나, DB 업그레이드 후 Native SQL이 깨지거나, 보안 리뷰에서 injection 위험이 나오면 그 코드는 개선이 아니라 장애 원인이 된다.

AMDP와 ADBC는 빠른 길을 열어 주지만 보호막 일부를 벗어난다. 그래서 이 레슨은 "어떻게 쓰는가"가 아니라 **"쓴 뒤 무엇을 책임지는가"**를 다룬다.

관점도 다시 확인하자. "DB로 내리면 현대적"이 아니다. Clean Core의 기준은 released API와 업그레이드 안정성이라서, DB 종속 코드는 오히려 더 엄격한 사유서가 필요하다(Chapter 24).

판정 연습

여섯 상황을 "적절/부적절"로 판정해 보라. 이 챕터 전체의 감각 점검이다.

흔한 실수와 점검 🚧

  • "DB로 내리면 " → 반대다. DB 종속은 더 무거운 검토 대상이다.
  • 버퍼·접근 제어를 잊음 → Native SQL은 테이블 버퍼를 지나치고 CDS 접근 제어를 적용하지 않는다. 기대한 보호가 없다.
  • 오류를 메시지 한 줄로 삼킴 → SQL code·message 없는 오류는 운영에서 재현도 재처리도 안 된다.
  • 흩어진 DB 종속 코드 → 격리 없이 퍼뜨리면 전환 비용이 폭발한다. 별도 + 사유 기록.
  • 테스트 생략 → SQLScript와 Native SQL은 ABAP 단위 테스트가 자동 보장하지 않는다. 대표 데이터로 결과 동등성을 비교한다.

정리 📌

  • AMDP/ADBC는 빠른 길이자 책임이 커지는 길이다: DB 종속·client·보안·보호 우회· 테스트의 다섯 축.
  • 배포 전 승인 체크리스트 7항목. 특히 위 칸 불가 사유 + 측정 근거 + 격리.
  • 이 챕터의 결론: 먼저 Open SQL과 CDS로 해결하고, 강한 수단은 이유와 측정과 운영 통제가 있을 때만.

🧩 도전 과제 (서브퀘스트)

선택 과제 — 공연별 예매 를 사다리 순서로 밀어 본다.

  1. 공연별 예매 건수·좌석 합계를 Modern Open SQL(GROUP BY + 집계)로 구현한다. ST05로 records·시간을 기록한다.
  2. 같은 집계를 CDS View로 올려 두 소비자(리포트·프로그램)가 공유하게 한다.
  3. (심화) 기간 가 필요한 버전을 CDS Table Function + AMDP Function으로 만들고, 1번과 결과 동등성을 비교한다(두 결과를 같은 키로 SORT한 뒤 IF gt_a = gt_b면 충분하다).
  4. (설계) 위 세 버전에 대해 운영 승인 체크리스트 7항목을 채워 보고, 어느 버전을 배포할지 사유와 함께 결정한다.
