Action / Validation / Determination 구현 완성

계약이 약속한 판단을 채운다 — 다건 안전·failed/reported·action result.

Track 2Chapter 39Lesson 5고급

계약은 있는데 판단이 비었다

Chapter 24-L09에서 세 로직의 역할을 나눴다: 기본값은 determination, 저장 가부는 validation, 사용자 명령은 action. Capstone에서는 그 구현을 운영 기준으로 완성한다 — 운영 기준이란 두 가지다: ① 어떤 요청이 와도 (한 건이든 백 건이든) 안전할 것, ② 실패가 사용자가 이해할 메시지로 돌아갈 것.

문법 부품(%tky·%control·READ/MODIFY ENTITIES IN LOCAL MODE)은 전부 CH24-L05에서 배운 그대로이고, 코드가 들어갈 자리도 그때 그 파일이다: zbp_i_booking의 로컬 handler class(lhc_booking) IMPLEMENTATION — L04의 DEFINITION과 한 벌이다(CH24 때의 구현이 남아 있으면 같은 이름 는 교체, 새 메서드는 추가). readonly인 Status를 여기서 채우고 바꿀 수 있는 근거 = L04에서 정리한 "내부 IN LOCAL MODE " — readonly는 바깥(소비자) 기준의 잠금이다.

METHOD setDefaults.
  " 생성된 건들을 읽어(다건!) 상태가 빈 것만 채운다
  " (CreatedBy·LastChangedAt은 @Semantics 관리 필드라 런타임이 채운다 — L02)
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    FIELDS ( Status )
    WITH CORRESPONDING #( keys )
    RESULT DATA(lt_bookings).

  DATA lt_updates TYPE TABLE FOR UPDATE ZI_Booking.

  LOOP AT lt_bookings INTO DATA(ls_booking)
       WHERE Status IS INITIAL.
    APPEND VALUE #(
      %tky            = ls_booking-%tky
      Status          = 'N'
      %control-Status = if_abap_behv=>mk-on
    ) TO lt_updates.
  ENDLOOP.

  MODIFY ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    UPDATE FROM lt_updates
    FAILED   DATA(ls_failed)      " 내부 갱신 실패 — 이 최소형에선 받기만 한다
    REPORTED DATA(ls_reported).   " (기본값 세팅 실패는 뒤 validation이 잡는다)
ENDMETHOD.

정원 검증 — validateCapacity (validation)

CH24 실습에서 "정원 계산 기준"을 설계 질문으로 남겨 뒀다. 여기서 답한다: 공연 정원(Chapter 9의 zconcert-capacity — 우리 앱은 모든 회차가 같은 정원을 쓰는 설계다) − 같은 회차의 기존 예약 합계(취소 제외) ≥ 이번 요청 좌석. 정원은 공연 단위 값이지만 소진은 회차별로 세는 것이니, 회차마다 정원이 다른 공연장이라면 정원 필드를 zperf로 옮기는 확장이 필요하다(설계 판단의 문제 — 우리는 관통예제 정본을 따른다).

METHOD validateCapacity.
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    FIELDS ( BookingId ConcertId PerfNo Seats )
    WITH CORRESPONDING #( keys )
    RESULT DATA(lt_bookings).

  LOOP AT lt_bookings INTO DATA(ls_booking).
    " ① 공연 정원(전 회차 공통)
    SELECT SINGLE capacity
      FROM zconcert
      WHERE concert_id = @ls_booking-ConcertId
      INTO @DATA(lv_capacity).

    " ② 같은 회차의 기존 예약 합계 — 취소 제외, 그리고 자기 자신 제외.
    "    자기 제외의 이유: 수정 건의 '옛 좌석 수'는 이 시점(on save, 커밋 전)
    "    까지 DB에 남아 있다 — 그걸 빼고 새 값을 더해 판정해야 이중 계산이
    "    없다(신규 건에는 이 조건이 그냥 무해하게 지나간다)
    SELECT COALESCE( SUM( seats ), 0 )
      FROM zbooking
      WHERE concert_id  = @ls_booking-ConcertId
        AND perf_no     = @ls_booking-PerfNo
        AND status     <> 'C'
        AND booking_id <> @ls_booking-BookingId
      INTO @DATA(lv_booked).

    " ③ 판정 — 넘치면 거부(failed)와 이유(reported)를 함께 채운다
    IF lv_booked + ls_booking-Seats > lv_capacity.
      APPEND VALUE #( %tky = ls_booking-%tky ) TO failed-booking.
      APPEND VALUE #(
        %tky = ls_booking-%tky
        %element-Seats = if_abap_behv=>mk-on   " 화면에서 이 필드에 오류 표시
        %msg = new_message_with_text(
                 severity = if_abap_behv_message=>severity-error
                 text     = '남은 좌석보다 많은 좌석은 예약할 수 없습니다.' )
      ) TO reported-booking.
    ENDIF.
  ENDLOOP.
ENDMETHOD.

validation의 계약은 명확하다: 고치지 않는다, 판정한다. 거부는 failed-booking(어느 건이), reported-booking(왜)의 짝으로 돌려준다 — 이 짝이 Fiori 메시지 영역과 EML consumer의 FAILED/REPORTED로 그대로 흘러간다. new_message_with_text( )는 handler 기반 class(cl_abap_behavior_handler)가 물려주는 헬퍼로, message class 없이 즉석 텍스트 메시지를 만든다 — 연습용 지름길이고, 운영에서는 Chapter 15의 message class(SE91)로 승급해 번역·재사용이 되게 한다.

이 최소형의 정직한 한계 둘도 그어 둔다. ① 이 SELECT는 DB만 본다 — 같은 요청( 버퍼)에 함께 들어온 다른 신규 예매는 아직 DB에 없어 합계에 안 잡힌다. 그래서 같은 회차 예매 여러 건이 한 요청에 오면 합계 초과가 뚫릴 수 있다. 운영형은 buffer의 요청분을 READ ENTITIES … IN LOCAL MODE로 함께 모아 합산에 더한다(도전 과제로 남긴다 — RAP behavior 안에서 자기 테이블을 직접 SELECT하는 것 자체가 "버퍼를 못 본다"는 대가를 치르는 일이라는 게 교훈이다). ② LOOP 안 SELECT는 Chapter 35 기준의 개선 대상이다 — 회차 목록을 모아 한 번에 읽는 개선도 같은 과제다. 그리고 설계 사실 하나: 초안 상태의 예매는 초안 테이블에 있어 이 합계에 안 잡힌다 — "초안은 좌석을 점유하지 않는다"는 우리 설계의 결정이다(점유가 필요하면 별도 설계가 필요하다). 서로 다른 두 사용자의 마지막 좌석 동시 경합은 이 validation도 L08의 네 장치도 다 막지 못하는 별개 주제인데, L08 끝에서 경계를 긋는다.

METHOD cancelBooking.
  " 이미 취소된 건은 걸러낸다 — 화면 버튼은 features(L08)가 비활성해 주지만,
  " 상태 전이의 마지막 방어선은 action 자신이다
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    FIELDS ( Status ) WITH CORRESPONDING #( keys )
    RESULT DATA(lt_check).
  LOOP AT lt_check INTO DATA(ls_check) WHERE Status = 'C'.
    APPEND VALUE #( %tky = ls_check-%tky ) TO failed-booking.
  ENDLOOP.

  " 상태를 C로 — 사용자가 명시적으로 누른 업무 명령
  MODIFY ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    UPDATE FROM VALUE #(
      FOR ls_ok IN lt_check WHERE ( Status <> 'C' )   " 방어를 통과한 건만
      ( %tky            = ls_ok-%tky
        Status          = 'C'
        %control-Status = if_abap_behv=>mk-on ) )
    FAILED   DATA(ls_failed)
    REPORTED DATA(ls_reported).

  " action result: 바뀐 뒤의 모습을 돌려준다(result [1] $self 계약)
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    ALL FIELDS WITH CORRESPONDING #( keys )
    RESULT DATA(lt_changed).

  result = VALUE #( FOR ls_changed IN lt_changed
                    ( %tky   = ls_changed-%tky
                      %param = ls_changed ) ).
ENDMETHOD.

BDEF의 result [1] $self는 "실행 후 자기 자신 한 건을 돌려준다"는 약속이었다 — 채우지 않으면 Fiori 화면이 실행 후 최신 상태를 못 받는다.

확인하는 법

확인 방법
기본값 생성 직후 Status가 N인가
정원 초과 잔여보다 큰 Seats 저장 → 거부 + 메시지가 보이는가
취소 action 실행 후 Status C + 화면이 최신 상태로 갱신되는가
다건 한 요청에 여러 건을 넣어도 전 건이 각각 판정되는가
실패 짝 거부된 건의 failed와 reported가 둘 다 채워지는가

흔한 실수와 점검 🚧

  • validation에서 데이터 수정 → 판정과 보정이 섞이면 추적 불능. 보정은 determination의 몫.
  • keys의 첫 건만 처리 → 단건 테스트는 통과하고 다건 요청(OData batch)에서 깨진다. 모든 handler는 다건이 기본이다.
  • 다건을 각각만 판정 → "각각 판정"으로도 부족한 케이스가 위의 한계 ①이다. 같은 회차 다건은 묶어 합산해야 진짜 다건 안전이다.
  • failed만 채우고 reported 생략 → 거부는 되는데 사용자는 이유를 모른다. 거부와 이유는 항상 짝.
  • action 없이 상태 필드 직접 update 허용 → "취소는 action으로만"이라는 완료 기준이 깨진다. 상태 전이는 명시적 명령으로. 재취소 방어는 이중이다 — 화면 가용성은 L08의 features가, 최종 방어선은 action 자신이 갖는다(위 코드의 첫 블록).

정리 📌

  • 세 로직의 완성 기준 = 다건 안전 + failed/reported 짝(+%element로 필드 지목) + result 계약 이행. action은 상태 전이의 마지막 방어선을 스스로 갖는다.
  • 정원 검증의 실체 = 공연 정원 − 같은 회차 기존 합계(취소·자기 제외) 비교. 판정만 하고 고치지 않는다. 남긴 한계(같은 회차 다건 합산·LOOP 밖 SELECT)는 도전 과제다.
  • 이 판단들은 화면 전용이 아니다 — 다음 레슨에서 화면 없이(EML) 같은 규칙이 작동하는 것을 확인한다.

화면이 없어도 이 앱은 완전한가. 외부 프로그램이 예매를 만드는 길 — EML consumer 실전으로 간다.
