화면 없이 예매를 만들어야 한다

요구사항 7번이 남아 있다: 외부 프로그램도 예매를 넣을 수 있어야 한다(야간 배치가 단체 예매를 등록하는 그림). Chapter 24-L09에서 EML 개념 지도를 봤다 — MODIFY ENTITIES는 버퍼, COMMIT ENTITIES가 저장 트리거. 이번엔 그 지도를 들고 실제로 걷는다. 실전에서 처음 만나는 부품이 셋 있다: %cid, MAPPED, 그리고 commit의 책임이 우리에게 넘어온다는 사실이다.

완결 코드 — 만들고, 판정받고, 확정하거나 되돌린다

실행 그릇부터: ADT에서 새 class를 만들고 if_oo_adt_classrun을 구현해 main 안에 아래 코드를 넣고 F9로 실행하는 것이 표준 경로다(Cloud에서도 그대로 통한다. 온프렘이라면 SE38 리포트도 물론 된다). behavior pool 밖이므로 IN LOCAL MODE는 없다 — 우리는 일반 소비자이고, 권한·검증을 전부 정면으로 통과해야 한다(CH24-L09의 그 경계).

Draft를 켠 BO인데 초안 얘기가 없는 것도 미리 답하자: EML은 초안 지정을 따로 하지 않으면 active 를 곧장 다룬다. 초안 단계(Edit→Resume→Activate)는 화면 사용자의 흐름이고, 프로그램은 최종 상태로 직행하는 것이 기본이다(초안까지 프로그램으로 다루는 지정자가 따로 있지만 심화 — 범위 밖). 그리고 같은 시스템 안의 ABAP은 BO의 원본(ZI_)을 직접 다룬다 — ZC_는 서비스 소비자의 표면이다(L03의 분업이 여기서도 유지된다). 단 이것은 같은 팀·같은 안의 특권이다 — 다른 팀·다른 시스템이 소비한다면 서비스(L07)나 released (L09)를 거치게 하는 것이 실무 규율이다.

" ① 생성 요청 데이터 — %cid는 CREATE 요청마다 붙이는 이름표(필수)
"   BookingId는 아직 안 쓰인 번호로 — 연습 전용 대역 '9***'를 정해 두자.
"   (SELECT MAX 채번은 두 실행이 같은 번호를 집는 실무 금기 — 운영은 번호
"    범위 오브젝트나 RAP numbering이 맡는다. 존재만 알아 둘 것)
DATA lt_create TYPE TABLE FOR CREATE ZI_Booking.

lt_create = VALUE #(
  ( %cid     = 'NEW1'                 " 이 요청을 부를 이름표(내가 정함)
    BookingId = '9001'
    ConcertId = 'C001'
    PerfNo    = '01'
    Customer  = '정훈영'
    Seats     = 2
    %control-BookingId = if_abap_behv=>mk-on
    %control-ConcertId = if_abap_behv=>mk-on
    %control-PerfNo    = if_abap_behv=>mk-on
    %control-Customer  = if_abap_behv=>mk-on
    %control-Seats     = if_abap_behv=>mk-on ) ).

" ② 버퍼에 생성 요청 — 아직 DB가 아니다
MODIFY ENTITIES OF ZI_Booking
  ENTITY Booking
  CREATE FROM lt_create
  MAPPED   DATA(ls_mapped)     " 이름표(%cid) ↔ 확정 key의 대응표
  FAILED   DATA(ls_failed)     " 이 단계에서 거부된 건
  REPORTED DATA(ls_reported).  " 거부 이유 메시지

" ③ 판정 후 확정 또는 되돌림 — commit의 책임이 우리에게 있다
IF ls_failed-booking IS INITIAL.
  COMMIT ENTITIES
    RESPONSE OF ZI_Booking
    FAILED   DATA(ls_c_failed)      " 저장 단계에서 거부된 건
    REPORTED DATA(ls_c_reported).   " 그 이유(우리 validation의 메시지!)
  IF sy-subrc <> 0 OR ls_c_failed-booking IS NOT INITIAL.
    ROLLBACK ENTITIES.  " 런타임이 이미 정리했더라도 명시적 정리는 무해
    " 이유 없는 거부는 없다 — validation이 채운 메시지를 그대로 꺼내 보여준다
    LOOP AT ls_c_reported-booking INTO DATA(ls_msg).
      out->write( ls_msg-%msg->if_message~get_text( ) ).
    ENDLOOP.
  ELSE.
    LOOP AT ls_mapped-booking INTO DATA(ls_map).   " 다건이 기본 — 전 건 출력
      out->write( |예매 { ls_map-BookingId } 저장 완료| ).
    ENDLOOP.
  ENDIF.
ELSE.
  ROLLBACK ENTITIES.                " 버퍼·잠금 정리
  out->write( '예매 요청이 거부되었습니다(요청 단계)' ).
ENDIF.

새 부품을 짚는다.

  • %cid — CREATE 요청마다 붙이는 **요청 이름표(필수)**다. 우리처럼 key를 직접 주는 BO에서는 사족처럼 보이지만, 응답(MAPPED)이 "어느 요청이 어느 key로 확정됐나"를 이 이름표로 알려 주는 구조라 항상 쓴다 — key를 시스템이 채번하는 BO에서는 이 이름표가 유일한 연결 고리가 된다.
  • 거부의 두 관문 — ②의 FAILED는 요청 즉시 단계의 거부이고, 우리의 정원 검증(on save)은 ③ COMMIT의 save sequence에서 돈다. 그래서 ②가 조용히 지나가도 ③에서 거부될 수 있다 — 두 관문 모두 FAILED/REPORTED를 받는 것이 consumer의 책임이다(③의 RESPONSE OF … 절이 그 수단. sy-subrc는 성공/실패 요약이고, 이유는 REPORTED가 담는다).
  • ROLLBACK ENTITIES — 실패했으면 버퍼와 잠금을 정리하고 나온다. 정리 없이 다음 으로 넘어가는 것은 Chapter 25에서 배운 LUW 규율 위반과 같은 급의 습관이다.

transaction owner — 누가 COMMIT을 부르는가

여기서 경계 하나가 결정적이다. Fiori/OData로 들어온 요청은 RAP 런타임이 의 주인이라 commit/rollback을 런타임이 수행한다. 그래서 behavior pool(handler) 안에는 COMMIT ENTITIES가 없다 — 있어야 할 곳은 이 레슨처럼 외부 consumer가 주인일 때뿐이다.

누가 호출했나 transaction owner COMMIT은 누가
Fiori / OData 요청 RAP 런타임 런타임(우리 코드엔 없음)
외부 ABAP 프로그램(EML) 그 프로그램 우리가 명시적으로
behavior pool 내부 (주인이 아님) 금지 — 계약 위반

화면과 같은 규칙인지 확인하기

이 레슨의 진짜 목적은 코드가 아니라 확인이다. L05의 검증이 화면 전용이 아니라는 것을 눈으로 본다.

  1. 정상 데이터로 실행 → SELECT 또는 Fiori 목록에서 새 예매 확인.
  2. 정원 초과 데이터로 실행 → ③에서 거부되고 DB에 없다. 콘솔에 L05가 채운 바로 그 메시지("남은 좌석보다…")가 찍히는지까지 봐야 완성이다 — 화면에서 막히던 규칙이 같은 문장으로 EML에서도 막는다(업무 규칙을 Behavior에 둔 보상).
  3. MODIFY 직후(COMMIT 전) 다른 에서 SELECT → 아직 없다. 버퍼의 실감. (classrun은 한 번에 끝나 버리니, MODIFY 다음 줄에 브레이크포인트를 걸어 멈춘 사이에 확인한다 — CH04의 디버거 그대로.)
  4. 운영 감각 하나: 누군가 그 건의 초안을 잡고 있으면 EML 수정은 잠금으로 실패할 수 있다 — 야간 배치가 이따금 실패하는 전형적 원인이라, 배치에는 재시도·스킵 전략이 따른다(개요만).

권한도 짚어 두자: 이 실행은 로그인한 나의 자격으로 돈다. 야간 배치라면 Chapter 38의 그 원칙대로 잡의 실행 사용자 자격이고, 외부 시스템의 호출이라면 L09의 Communication User 자격이다 — 누가 호출하든 L08의 서버 판정을 정면으로 만난다는 사실만 변하지 않는다.

흔한 실수와 점검 🚧

  • MODIFY 직후 SELECT로 저장 기대 → 아직 버퍼다. 저장 트리거는 COMMIT ENTITIES(CH24-L09의 그 문장이 실전에서 제일 많이 틀리는 지점).
  • FAILED 무시 → 거부된 요청을 성공으로 착각한다. 두 관문(②와 ③) 모두 확인.
  • LOOP 안 EML → 요청은 internal table로 모아 한 번의 EML로(CH24-L05의 anti-pattern 그대로 — 다건이 기본).
  • behavior pool 안에서 COMMIT → transaction owner가 아니다. 계약 위반이자 런타임과의 충돌.
  • 실패 후 ROLLBACK 생략 → 버퍼·잠금이 남은 채 다음 작업으로 — 유령 잠금의 출처가 된다.

정리 📌

  • 외부 consumer 3박자 = MODIFY(버퍼) → 판정(FAILED/REPORTED, 두 관문) → COMMIT(저장) 또는 ROLLBACK(정리).
  • %cid = CREATE 요청의 이름표(필수), MAPPED = 이름표↔확정 key 대응표. EML은 초안 지정이 없으면 active를 직접 다룬다.
  • commit의 주인은 호출 맥락이 정한다: Fiori는 런타임, 외부 프로그램은 우리, behavior pool은 금지.
  • 검증이 Behavior에 있으니 화면과 EML이 같은 규칙으로 움직인다 — Capstone 완료 기준 하나가 여기서 증명됐다.

백엔드가 완전해졌다. 이제 이 BO를 실제 서비스로 노출하고 Fiori 화면으로 눈에 보이게 만든다.
