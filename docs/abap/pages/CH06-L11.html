지역별 매출 합계 — 쌓지 말고 모으자

이번 과제는 매출 집계다. 판매 기록이 한 건씩 들어오는데, 원하는 결과는 기록 목록이 아니라 지역별 합계다: 서울 기록이 두 건(100원·30원) 들어왔으면 결과 테이블엔 "서울 130" 한 행만 있으면 된다.

APPEND로 쌓으면 기록이 두 행이 되고, 합계는 나중에 따로 계산해야 한다. 그런데 L05의 넣기 3형제 표에서 이름만 알아 둔 막내 — 넣는 순간 합산까지 해 주는 문장이 있다. COLLECT다.

COLLECT의 동작

이 절에서 쓸 테이블부터. 지역(문자)과 금액(숫자) 두 필드다.

TYPES: BEGIN OF ts_sales,
         region TYPE c LENGTH 10,   " 지역 이름(문자)
         amount TYPE i,             " 매출 금액(숫자, 원 단위)
       END OF ts_sales.

DATA: gs_sales TYPE ts_sales,
      gt_sales TYPE TABLE OF ts_sales.

(금액을 TYPE i, 원 단위 정수로 둔 것은 예제를 단순하게 하려는 선택이다. 실무의 금액 필드는 소수점과 통화 정보까지 다루는 전용 타입을 쓰는데, 뒤 챕터에서 만난다.)

COLLECT는 키가 같은 행이 이미 있으면 숫자 필드를 합산하고, 없으면 새 행으로 넣는다.

gs_sales-region = '서울'. gs_sales-amount = 100.
COLLECT gs_sales INTO gt_sales.   " 서울이 없었다 → 새 행 [서울 100]

gs_sales-region = '서울'. gs_sales-amount = 30.
COLLECT gs_sales INTO gt_sales.   " 서울이 있다 → 100 + 30 = [서울 130]

gs_sales-region = '부산'. gs_sales-amount = 50.
COLLECT gs_sales INTO gt_sales.   " 부산이 없었다 → 새 행 [부산 50]

세 번 넣었지만 결과는 두 행이다. 이게 COLLECT의 전부다 — "있으면 더하고, 없으면 넣는다."

여기서 "키"는 무엇일까. 위 선언은 키를 안 적었으니 키 레슨의 standard key, 즉 문자 필드인 region이다. 그래서 region이 같은 행끼리 amount가 더해진 것이다.

제약 — 하나씩 차근차근

COLLECT가 성립하려면 테이블 모양이 조건을 갖춰야 한다. 순서대로 셋이다.

  1. 키가 "묶는 기준"이 된다. 문자 필드(standard key) 또는 직접 지정한 키가 그룹의 기준이다. ts_sales에선 region.
  2. 키가 아닌 필드는 전부 숫자 타입이어야 한다. 합산 대상이기 때문이다. ts_sales의 비키 필드(키가 아닌(非) 필드)는 amount 하나뿐이고 숫자라 합격. 만약 비키 필드에 문자가 섞여 있으면 그 문장은 성립하지 않는다(무엇을 "합산"하겠는가).
  3. 한 테이블엔 COLLECT만. 같은 테이블에 APPEND와 COLLECT를 섞으면, APPEND가 만든 중복 키 행 때문에 합계가 두 행으로 갈라진다. 쌓는 테이블과 모으는 테이블은 분리하는 것이 정석이다.

극단적인 경우도 하나 알아 두자 — 문자 필드가 하나도 없어 키가 텅 비면, 모든 행이 "같은 키"로 취급돼 넣는 족족 첫 행에만 합산된다. 그런 테이블이라면 키를 직접 적어 주는 편이 안전하다.

성능 이야기 — 왜 "다른 문장이 건드리면" 느려지나

COLLECT는 매번 "같은 키가 이미 있나?"를 찾아야 한다. 이걸 빠르게 하려고 시스템은 STANDARD 테이블에 대해 자기만의 임시 찾기표(해시)를 만들어 관리한다 — 사물함 방식(L04)을 몰래 빌려 쓰는 셈이다. 그래서 COLLECT만 연달아 하는 동안은 행이 많아도 빠르다.

그런데 이 찾기표는 COLLECT만 보고 있을 때만 유효하다. 중간에 다른 문장(SORT·DELETE· MODIFY 등)이 테이블을 건드리면 찾기표가 현실과 어긋날 수 있으니 시스템이 그것을 버린다. 그다음 COLLECT부터는 처음부터 순차로 훑는 방식이 되어, 행이 많을수록 느려진다.

정리하면 — 모으는 동안은 COLLECT만, 정렬·가공은 다 모은 뒤에. 애초에 대량이라면 그릇을 SORTED·HASHED로 잡는 것도 방법이다(자기 구조로 찾으니 찾기표가 필요 없다).

흔한 실수와 점검

  • COLLECT를 단순 추가로 착각 → 같은 키면 행이 늘지 않고 숫자가 누적된다. 무조건 뒤에 붙일 거면 APPEND다.
  • APPEND와 혼용 → 합계가 갈라진다. 한 테이블엔 한 방식.
  • 비키 필드에 문자 포함 → 합산할 수 없는 모양이다. 집계 전용 테이블(키+숫자)을 따로 설계하자.
  • 모으는 중간에 SORT → 찾기표가 버려져 이후 COLLECT가 느려진다. 정렬은 다 모은 뒤.

COLLECT는 넣는 시점에 즉시 합산한다. 그런데 이미 다 쌓여 있는 테이블에서 그룹별 소계를 내야 한다면? 그건 다른 도구의 일이다 → 컨트롤레벨.
