ST05 SQL Trace

감이 아니라 측정 — 한 실행의 DB 대화를 기록해 병목을 분류한다.

Track 3Chapter 35Lesson 1고급독립 모듈

🐌 "동작은 하는데 너무 느립니다"

Chapter 34에서 창구를 열자마자 나온 그 불편이다. 예매현황 리포트가 느리다는 제보가 왔다. 초보 개발자는 코드를 열고 눈에 띄는 LOOP나 SELECT부터 고치고 싶어진다. 멈추자. 성능은 감으로 고치는 일이 아니다.

이유는 간단하다. 800ms짜리 SQL 한 번이 문제일 수도 있고, 1ms짜리 SQL이 1만 번 반복되어 문제일 수도 있다. 두 경우는 처방이 완전히 다른데, 코드를 눈으로 훑어서는 어느 쪽인지 알 수 없다. 그래서 이 챕터 전체를 관통하는 루프가 있다.

측정 → 원인 분류 → 수정 → 같은 조건 재측정 → 수치 기록. 튜닝의 완료 조건은 "코드를 바꿨다"가 아니라 "수치가 어떻게 바뀌었는지 설명할 수 있다"이다.

도구는 병원 진단에 비유하면 셋이다. 이번 레슨의 (SQL Trace)는 의심 부위 정밀 검사(한 실행의 DB 대화를 낱낱이 기록), 다음 레슨의 SAT는 전신 촬영(시간이 어디에 쓰였나), 그다음의 SQLM은 전 직원 건강검진 통계(운영 전체에서 누가 제일 아픈가)다.

💡 이 챕터의 수치(800ms·1만 회 등)는 전부 감각을 위한 가상 예시다. 실제 값은 시스템·데이터 분포에 따라 완전히 다르다. 도구 화면·컬럼 구성도 시스템 버전에 따라 다를 수 있다 — 여기서는 "무엇을 보는 도구인가"에 집중한다.

ST05 — 한 실행의 DB 대화 기록

는 프로그램 한 번 실행 동안 일어난 실제 DB 접근을 기록한다. 사용 흐름은 넷: Trace On → 대상 프로그램 실행 → Trace Off → Display Trace. 켜 둔 채 방치하지 않는 것까지가 사용법이다.

결과에서 입문자가 먼저 볼 것은 세 숫자다.

항목 뜻 판단 질문
Total time 그 SQL의 누적 시간 전체 병목에서 비중이 큰가
Executions 실행 횟수 같은 SQL이 비정상적으로 반복되나
Records 읽어 온 행 수 필요 이상으로 많이 가져오나

그리고 Identical/Redundant Selects(동일·불필요 반복 SELECT) 표시: 같은 걸 여러 번 읽고 있다면 한 번 읽어 재사용할 후보다.

읽는 법이 곧 분류법이다.

  • 시간 큰 단일 SQL → WHERE 조건··JOIN 방식·반환 행 수 점검(처방 = 조건·구조 수정).
  • 횟수 큰 동일 SQL → LOOP 안 SELECT 의심(L04의 주제. 처방 = 왕복 제거).
  • Records 폭주 → 필요한 컬럼·행만 가져오는지 점검(Chapter 8의 WHERE 정신).

어떻게 확인하는가 — 측정 루프 실전

  1. 재현 조건 고정 — 선택 화면 값·데이터 건수·실행 시간대를 기록한다. 조건이 다르면 전후 비교가 무의미하다.
  2. 범위 좁혀 짧게 측정 — 대상 사용자·프로그램을 한정하고 짧게 켠다. 운영에서 장시간 trace는 부하와 거대한 기록을 남긴다.
  3. 정렬 두 번 — 먼저 Total time 내림차순으로 "비싼 SQL", 다음 Executions 내림차순으로 "반복 SQL"을 찾는다. 하나만 보면 반쪽 진단이다.
  4. 코드 위치와 연결 — 찾은 SQL의 테이블·조건으로 소스의 SELECT 위치를 찾는다. "어떤 SQL이 느렸다"에서 끝나면 튜닝이 아니다.
  5. 수정 후 같은 조건 재측정 — 좋은 기록은 "빨라졌다"가 아니라 "동일 SELECT 5,000회 → 2회, total 2,400ms → 90ms"처럼 수치를 남긴다.

직접 분석해 보기

컬럼 헤더로 정렬을 바꿔 가며 "비싼 SQL"과 "반복 SQL"을 각각 찾아보라. 반복 SQL을 찾았다면 수정 후 재측정으로 before/after 수치가 어떻게 남는지도.

흔한 실수와 점검 🚧

  • 측정 없이 부터 → 인덱스는 읽기를 도울 수 있지만 쓰기 비용·공간을 늘린다. 근거 없는 추가는 L03에서 다시 경고한다.
  • Total time만 보고 Executions를 놓침 → 1ms×10,000회가 800ms×1회보다 큰 병목일 수 있다.
  • 운영에서 장시간 trace → 는 정밀 검사지 상시 모니터링이 아니다. 장기 누적은 SQLM(L03)의 몫.
  • 한 번의 측정으로 결론 → 데이터 분포·조건에 따라 결과가 달라진다. 문제 조건과 정상 조건을 구분해 측정한다.

정리 📌

  • 성능의 첫 문장은 "측정했습니다"여야 한다. 루프: 측정→분류→수정→재측정→기록.
  • = 한 실행의 DB 대화 정밀 검사. Total time·Executions·Records 세 숫자로 "비싼 SQL / 반복 SQL / 과다 조회"를 분류한다.
  • 짧게 켜고, 코드 위치와 연결하고, 같은 조건으로 재측정한다.

DB 검사 결과가 의외로 깨끗할 때가 있다. 그런데도 느리다면? 시간이 ABAP 코드 안에서 새고 있을 수 있다. 전신 촬영, SAT로 간다.
