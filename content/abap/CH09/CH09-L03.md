## 코드만으론 못 읽는다

마스터 테이블은 보통 **코드**(예: 공연 ID `C001`)만 키로 사용한다. 그런데 화면·목록엔
사람이 읽을 **이름**(공연명)이 필요하다. 게다가 이름은 **언어마다** 다르다(한국어
"콘서트", 영어 "Concert"). 이 이름을 **별도 테이블**에 두는 것이
[[Text Table]](텍스트 테이블)이다.

## Text Table의 모양

핵심은 키 구성이다 — **마스터 키 + 언어(`SPRAS`)**.

| 테이블 | 키 | 담는 것 |
|---|---|---|
| `ZCONCERT`(마스터) | `CONCERT_ID` | 정원·장소 등 |
| `ZCONCERT_T`(Text) | `CONCERT_ID` + `SPRAS` | `NAME`(공연명, 언어별) |

- 같은 `C001`이라도 언어(`SPRAS`)가 다르면 **다른 줄** → 언어별 이름을 따로 보관.

## SE11에서 Text Table로 인정받으려면

"이름 담은 테이블을 하나 더 만들었다"고 저절로 Text Table이 되지는 않는다. 시스템이
그렇게 **인정해 주는 조건**이 정해져 있다. 헷갈리기 쉬운 건 **방향**이다.

1. **키를 이렇게 짠다** — Text Table의 기본키 = **마스터의 기본키 그대로 + 언어 필드
   하나**. 언어 필드는 타입이 `LANG`이어야 한다(우리의 `SPRAS`).
2. **Foreign Key는 Text Table 쪽에서 건다** — `ZCONCERT`가 아니라 **`ZCONCERT_T`의
   `CONCERT_ID`** 에 [[Foreign Key]]([Foreign Key와 Check Table](CH09-L01.html))를 걸고,
   [[Check Table]]로 마스터 `ZCONCERT`를 지정한다. 이름표가 마스터를 가리키는 것이지
   그 반대가 아니다.
3. **그 Foreign Key의 "필드 유형"을 바꾼다** — 유형 목록에서
   **"텍스트 테이블의 키 필드"**(Key fields of a text table)를 고른다. **이 선택이
   결정적이다.** 이걸 골라야 시스템이 "이 테이블은 저 마스터의 Text Table이구나"라고
   알아본다. [[Cardinality]]는 짝이 맞게 `1:CN`으로 둔다(공연 하나에 언어별 이름 여러 줄).
4. **마스터 하나에 Text Table은 하나뿐** — 둘 이상 지정하면 활성화할 때 경고가 뜬다.

## 무엇이 좋아지나

- 화면·[[F4]]·Search Help가 코드 옆에 **이름을 자동으로** 보여 준다(코드만 보면 무슨 공연인지 모르니까).
- 사용자의 **로그인 언어**에 맞는 이름이 자동으로 뜬다.

> 💡 표준 예: 많은 마스터가 코드(마스터 테이블)와 **언어별 텍스트**(Text Table)를 나눠 둔다. "코드는 마스터, 이름은 Text Table"로 기억하자.

## 직접 해 보기

로그인 언어를 KO/EN으로 바꿔 F4 목록의 이름이 어떻게 달라지는지, SPRAS를 빼면 왜 다국어가 깨지는지 확인해 보자.

## 흔한 실수와 점검

- **언어 키(SPRAS) 누락** → Text Table의 키엔 반드시 언어가 들어간다. 빠지면 다국어가 안 된다.
- **Foreign Key 방향 반대** → 마스터에서 Text Table로 걸면 인정되지 않는다. **Text Table 쪽에서** 마스터를 향해 건다.
- **필드 유형 방치** → 관계만 걸고 유형을 "텍스트 테이블의 키 필드"로 바꾸지 않으면 그냥 평범한 Foreign Key로 남아 이름이 자동으로 따라오지 않는다.
- **마스터에 이름 직접** → 다국어가 필요하면 텍스트는 Text Table로 분리한다.
