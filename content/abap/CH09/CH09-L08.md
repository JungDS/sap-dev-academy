## 검증은 누가 하나

DDIC의 [[Foreign Key]]·[[고정값]]은 **선언적 검증**을 해준다. 설정만 해 두면 시스템이
알아서 잘못된 값을 막아 준다는 뜻이다.

[[Search Help]]는 여기서 성격이 다르니 갈라 두자. Search Help는 값을 **검사하지
않는다.** 고를 **후보를 보여 줄 뿐**이다. 목록에서 고르지 않고 손으로 아무 값이나 쳐
넣으면 그대로 통과한다. "고르기 편하게 해주는 것"과 "틀린 값을 막는 것"은 다른 일이다.

그런데 "취소된 공연은 못 고른다", "좌석 수가 잔여석보다 크면 거부" 같은 **업무
규칙**은? 어디까지 DDIC가 하고 어디부터 코드가 해야 하는지 가른다.

## 두 계층

| 검증 | 담당 | 예 |
|---|---|---|
| **존재/형식** | DDIC(선언적) | 공연 ID가 실제 존재? 고정값 범위? |
| **업무 규칙** | 프로그램(코드) | 잔여석 초과? 상태 전이 허용? 권한? |

표의 **상태 전이**는 "지금 상태에서 저 상태로 넘어가도 되나"를 따지는 일이다. 예매
상태가 신규(`N`)에서 취소(`C`)로 바뀌는 건 정상이지만, **이미 취소한 예매를 또
취소**하거나 공연이 끝난 뒤에 취소하는 건 막아야 한다. 이런 판단은 DDIC가 대신해 줄
수 없다. "지금 값이 뭐였는지"를 읽어 봐야 알 수 있어서다.

## DDIC 검증의 한계

- DDIC 검증(Foreign Key 등)은 **화면·유지보수 레벨**(SE11·SE16처럼 SAP이 기본
  제공하는 데이터 관리 화면)에서 동작한다.
- 프로그램이 `INSERT`/`MODIFY`로 **직접 DB에 쓰면** 그 검증은 **자동 적용되지
  않는다.** 직접 쓰기 전엔 프로그램이 책임지고 확인해야 한다.

```abap
DATA gv_dummy   TYPE zconcert-concert_id.
DATA gs_booking TYPE zbooking.

" 직접 쓰기 전, 존재 여부를 코드로 확인(예)
SELECT SINGLE concert_id FROM zconcert
  INTO gv_dummy WHERE concert_id = gs_booking-concert_id.
IF sy-subrc <> 0.
  " 잘못된 공연 ID — 업무 처리(메시지/중단)
ENDIF.
```

> ⚠️ **이 패턴에도 빈틈은 있다.** 두 사람이 거의 동시에 예매하면 둘 다 "자리 있음"을
> 확인한 뒤 둘 다 저장해, 정원을 넘겨 버릴 수 있다. 확인과 저장 사이를 **잠금**으로
> 막는 방법은 [Chapter 26 · Lock Object와 동시성 제어](CH26-L01.html)에서 배우니,
> 지금은 "혼자 쓸 땐 이걸로 충분하다"까지만 알아 두자.

## 원칙

- **할 수 있으면 DDIC로**(선언적·재사용·일관). 존재·형식·코드 목록은 DDIC.
- **DDIC로 표현 못 하는 업무 규칙만** 코드로. 중복 검증은 피한다.

## 흔한 실수와 점검

- **코드로 다 검증** → DDIC가 해줄 걸 중복 구현. 유지보수 부담.
- **DDIC만 믿고 직접 쓰기** → 직접 DB 쓰기는 DDIC 검증을 우회한다. 코드로 보완.
