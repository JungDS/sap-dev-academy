## 🎫 콘서트 예매 앱 — 첫 삽

[Foreign Key와 Check Table](CH09-L01.html)에서 본 콘서트 모델을 **이번 챕터부터 직접 만들어**
이후 [Chapter 24 · RAP](CH24-L01.html)까지 한 단계씩 키운다. RAP은 RESTful Application
Programming Model의 줄임말로, 화면까지 갖춘 요즘 SAP 앱을 짓는 방식이다. 아직 멀었으니
"저기까지 간다"는 것만 알아 두자. 첫 단계는 데이터 토대다. 세 테이블과 이름표,
관계, 그리고 도움말이다.

## 1) 세 테이블 (SE11)

만들 필드를 하나씩 적어 둔다. 이대로 따라 만들면 뒤 챕터의 예제가 그대로 돌아간다.

**`ZCONCERT` — 공연 마스터**

| 필드 | 키 | Data Element | 타입·길이 | 뜻 |
|---|:---:|---|---|---|
| `MANDT` | ✔ | `MANDT` | `CLNT 3` | 클라이언트 구분 |
| `CONCERT_ID` | ✔ | `ZDE_CONCERT_ID` | `CHAR 4` | 공연 ID(`C001`) |
| `ARTIST` | | `ZDE_ARTIST` | `CHAR 40` | 아티스트 |
| `VENUE` | | `ZDE_VENUE` | `CHAR 40` | 공연장 |
| `CAPACITY` | | `ZDE_CAPACITY` | `INT4` | 정원(좌석 수) |

**`ZPERF` — 회차**

| 필드 | 키 | Data Element | 타입·길이 | 뜻 |
|---|:---:|---|---|---|
| `MANDT` | ✔ | `MANDT` | `CLNT 3` | 클라이언트 구분 |
| `CONCERT_ID` | ✔ | `ZDE_CONCERT_ID` | `CHAR 4` | 어느 공연의 회차인가 |
| `PERF_NO` | ✔ | `ZDE_PERF_NO` | `NUMC 3` | 회차 번호(`001`) |
| `PERF_DATE` | | `ZDE_PERF_DATE` | `DATS` | 공연 날짜 |

**`ZBOOKING` — 예매**

| 필드 | 키 | Data Element | 타입·길이 | 뜻 |
|---|:---:|---|---|---|
| `MANDT` | ✔ | `MANDT` | `CLNT 3` | 클라이언트 구분 |
| `BOOKING_ID` | ✔ | `ZDE_BOOKING_ID` | `NUMC 4` | 예매 번호(`0001`) |
| `CONCERT_ID` | | `ZDE_CONCERT_ID` | `CHAR 4` | 어느 공연 |
| `PERF_NO` | | `ZDE_PERF_NO` | `NUMC 3` | 어느 회차 |
| `CUSTOMER` | | `ZDE_CUSTOMER` | `CHAR 30` | 예매자 |
| `SEATS` | | `ZDE_SEATS` | `INT4` | 좌석 수 |
| `STATUS` | | `ZDE_BOOK_STATUS` | `CHAR 1` | 예매 상태(`N`·`C`) |

- 필드 타입은 **Data Element**로 준다(라벨·F4가 딸려 오니까, [Chapter 03 · Data Element](CH03-L02.html)).
  `ZDE_BOOK_STATUS`의 Domain에는 **고정값 `N`(신규)·`C`(취소)** 를 넣어 둔다. 이 두 글자가
  이 앱의 예매 상태 코드이고, 뒤 챕터에서도 계속 이 값을 쓴다.
- **`MANDT`는 우리가 첫 키 필드로 직접 넣는다.** Data Element `MANDT`를 그대로 쓰면 된다
  (타입 `CLNT`·길이 3, [Chapter 07 · Transparent Table 생성](CH07-L01.html)에서 본 그 필드다).
  이 클라이언트 구분 칸이 있어야 데이터가 방(Client)별로 갈린다. 자동인 쪽은 그다음이다.
  프로그램이 읽고 쓸 때 지금 로그온한 클라이언트의 행만 골라 주는 일은 시스템이 알아서 한다.
  [Chapter 09 첫 레슨](CH09-L01.html)의 모델 표에는 업무 필드만 보여 주려고 생략했을 뿐,
  실제 테이블에는 항상 맨 앞에 있다.
- 활성화하면 실제 DB 테이블이 생긴다([Chapter 07 · Transparent Table 생성](CH07-L01.html)).

**`ZBOOKING`의 감사필드 6칸** — "누가·언제 만들고 바꿨나"를 남기는 칸이다. 위 `ZBOOKING`
표의 필드 뒤에 이어서 잡아 둔다. 키는 아니고, 타입은 SAP이 이미 갖고 있는 표준 Data
Element를 그대로 쓰면 된다.

| 필드 | 키 | Data Element | 타입·길이 | 뜻 |
|---|:---:|---|---|---|
| `CREATED_BY` | | `SYUNAME` | `CHAR 12` | 만든 사람(사용자 ID) |
| `CREATED_ON` | | `SYDATUM` | `DATS` | 만든 날짜 |
| `CREATED_AT` | | `SYUZEIT` | `TIMS` | 만든 시각 |
| `CHANGED_BY` | | `SYUNAME` | `CHAR 12` | 바꾼 사람(사용자 ID) |
| `CHANGED_ON` | | `SYDATUM` | `DATS` | 바꾼 날짜 |
| `CHANGED_AT` | | `SYUZEIT` | `TIMS` | 바꾼 시각 |

지금은 자리만 잡아 두면 된다. 값을 채우는 법은
[Chapter 25 · 데이터 변경](CH25-L01.html)에서 배운다.

> ⚠️ **`CONCERT_ID` 세 개는 반드시 같은 Data Element를 쓴다.** [[Foreign Key]]는 양쪽
> 필드가 **같은 Domain을 공유**해야 성립하는데, 세 테이블 모두 `ZDE_CONCERT_ID`를
> 그대로 재사용하면 그 아래 Domain도 자연히 같아져 조건이 저절로 맞는다. 테이블마다
> 공연 ID용 DE를 새로 만들면 나중에 관계를 걸 때 막힌다. `PERF_NO`도 마찬가지다.

## 2) 공연명은 Text Table로 — `ZCONCERT_T`

`ZCONCERT`에는 공연명 칸이 없다. 일부러 없다. 이름은 언어마다 다르니
[Text Table](CH09-L03.html)로 분리하는 게 제자리이기 때문이다. 하나 더 만들자.

| 필드 | 키 | Data Element | 타입·길이 | 뜻 |
|---|:---:|---|---|---|
| `MANDT` | ✔ | `MANDT` | `CLNT 3` | 클라이언트 구분 |
| `CONCERT_ID` | ✔ | `ZDE_CONCERT_ID` | `CHAR 4` | 어느 공연 |
| `SPRAS` | ✔ | `SPRAS` | `LANG` | 언어 키 |
| `NAME` | | `ZDE_CONCERT_NAME` | `CHAR 60` | 공연명(언어별) |

만든 뒤 [Text Table 레슨](CH09-L03.html)의 조건대로 **`ZCONCERT_T` 쪽에서** `ZCONCERT`로
[[Foreign Key]]를 걸고, 필드 유형을 **"텍스트 테이블의 키 필드"** 로 바꿔 준다. 이걸
해 둬야 뒤에서 F4 목록에 코드 옆 이름이 함께 뜬다.

## 3) Foreign Key — 관계는 셋이다

관계를 하나만 걸면 모델이 반쯤 뚫린 채로 남는다. **없는 회차의 예매**가 그대로
저장되기 때문이다. 셋을 차례로 건다.

1. **`ZPERF-CONCERT_ID` → `ZCONCERT`**
   `ZPERF`의 `CONCERT_ID` 필드 → **Foreign Keys** → Check Table `ZCONCERT`.
   키 대응은 `ZPERF-CONCERT_ID` ↔ `ZCONCERT-CONCERT_ID` 하나다.
   [[Cardinality]]는 `1:CN`으로 둔다(회차가 아직 없는 공연도 정상이니까).
2. **`ZBOOKING-CONCERT_ID` → `ZCONCERT`**
   같은 방식이다. 이제 없는 공연 ID는 입력이 거부되고, 그 칸에서 F4로 공연 목록이 뜬다.
3. **`ZBOOKING`(`CONCERT_ID` + `PERF_NO`) → `ZPERF`** ← 여기가 핵심
   `ZBOOKING`의 `PERF_NO` 필드에서 **Foreign Keys** → Check Table `ZPERF`.
   `ZPERF`의 **업무 키가 두 칸**이니 업무 대응도 두 줄이다.
   `ZBOOKING-CONCERT_ID` ↔ `ZPERF-CONCERT_ID`, `ZBOOKING-PERF_NO` ↔ `ZPERF-PERF_NO`.
   (맨 앞 클라이언트 키 `MANDT`끼리의 대응은 SE11이 알아서 맞춰 준다.)
   이렇게 묶어야 "존재하는 공연이지만 없는 회차"라는 어긋난 조합이 막힌다.

> 💡 3번처럼 키가 여러 칸인 마스터를 참조하면 **대응 줄도 그 수만큼** 생긴다. 한 줄만
> 채우고 넘어가면 검사가 헐거워지니, 저장 전에 줄 수를 세어 보자.

## 4) 공연 Search Help

- **`ZSH_CONCERT`**(Elementary) — Selection Method `ZCONCERT`. 공연 ID·아티스트·장소에
  **공연명**(`NAME`)까지 목록에 보여 주고 `CONCERT_ID`를 돌려준다(EXP).
  공연명은 `ZCONCERT`에 없는 칸인데도 고를 수 있다. Selection Method로 고른 테이블에
  [Text Table](CH09-L03.html)이 붙어 있으면 SE11이 그 텍스트 필드까지 파라미터 후보로
  함께 내주기 때문이다. 2)에서 `ZCONCERT_T`를 제대로 걸어 뒀다면 `NAME`이 목록에 있다.
- **`ZSH_CONCERT_ART`**(Elementary) — 같은 소스에 아티스트로 찾는 경로 하나 더.
- **`ZSH_CONCERT_COLL`**(Collective) — 위 둘을 묶는다([Collective Search Help 기초](CH09-L05.html)).
  포함된 Elementary의 파라미터를 Collective 파라미터와 **대응**시키는 것을 잊지 말자.
  (레슨의 예시는 세 경로였지만 실습은 **두 경로로 간소화**했다. 장소 검색이 필요하면 같은
  방식으로 Elementary를 하나 더 만들어 붙이면 된다.)
  앞 레슨들의 `MATCHCODE OBJECT zsh_concert_coll.` 예제가 가리키는 게 바로 이 객체다.
  실제로 만들어 둬야 그 코드가 활성화된다.

> ⚠️ **`ZBOOKING-CONCERT_ID`에 붙이는 건 `ZSH_CONCERT_COLL` 하나다.** 한 입력칸에 뜨는
> 도움말은 어차피 하나뿐이라([Input Help 호출 우선순위](CH09-L07.html)), Elementary 둘은
> 필드에 직접 붙이지 않고 Collective의 구성요소로만 둔다. 그래야 한 칸에서 두 경로를
> 탭으로 모두 쓸 수 있다.

## 직접 해 볼 과제

### ① 데이터 넣기

세 테이블을 만들고 **Create Entries**([Chapter 07](CH07-L02.html))로 아래 값을 넣는다.
**입력 순서가 중요하다.** 공연 → 회차 → 예매 차례로 넣어야 관계 검사를 통과한다.
마스터가 아직 없는데 예매부터 넣으면 당연히 거부된다.

**공연 `ZCONCERT` (3건)**

| CONCERT_ID | ARTIST | VENUE | CAPACITY |
|---|---|---|---|
| `C001` | 안유진 | KSPO DOME | 100 |
| `C002` | ABAP Trio | 올림픽홀 | 50 |
| `C003` | UI5 Night | 블루스퀘어 | 80 |

**회차 `ZPERF` (3건)**

| CONCERT_ID | PERF_NO | PERF_DATE |
|---|---|---|
| `C001` | `001` | 2026-11-14 |
| `C001` | `002` | 2026-11-15 |
| `C002` | `001` | 2026-12-05 |

**예매 `ZBOOKING` (6건)**

| BOOKING_ID | CONCERT_ID | PERF_NO | CUSTOMER | SEATS | STATUS |
|---|---|---|---|---|---|
| `0001` | `C001` | `001` | 정훈영 | 2 | `N` |
| `0002` | `C001` | `001` | 손흥민 | 1 | `N` |
| `0003` | `C001` | `002` | 아이유 | 3 | `N` |
| `0004` | `C001` | `002` | 유재석 | 2 | `N` |
| `0005` | `C002` | `001` | 강호동 | 4 | `N` |
| `0006` | `C002` | `001` | 차은우 | 2 | `C` |

**공연명 `ZCONCERT_T` (3건)** — `SPRAS`는 로그인 언어로 두고 `NAME`만 아래처럼 채운다.

| CONCERT_ID | NAME |
|---|---|
| `C001` | 안유진 단독 콘서트 |
| `C002` | ABAP Trio 라이브 |
| `C003` | UI5 Night 페스티벌 |

> 💡 **`C003`에 회차도 예매도 없는 건 실수가 아니다.** 아직 아무도 예매하지 않은 공연을
> 일부러 하나 남겨 뒀다. [[Cardinality]] `1:CN`이 왜 `1:n`이 아닌지가 여기서 눈에
> 보인다. 뒤 챕터에서 "예매가 한 건도 없는 공연"을 다룰 때도 이 줄을 쓴다.

### ② 확인하기

1. `ZBOOKING`에 **없는 공연 ID**(`C999`)를 넣어 보고 거부되는지 확인.
2. 공연은 맞지만 **없는 회차**(`C003` + `001`)를 넣어 보고 거부되는지 확인.
   3번 관계를 제대로 걸었다면 여기서 막힌다.
3. `ZBOOKING`의 `CONCERT_ID` 칸에서 **F4**를 눌러 붙여 둔 `ZSH_CONCERT_COLL`이 뜨는지 확인.
   첫 탭(`ZSH_CONCERT` 경로)의 목록에 코드 옆 **공연명**(`NAME`)이 함께 나오면 `ZCONCERT_T`
   연결까지 성공한 것이다. 이 열은 4)에서 `NAME`을 파라미터로 넣어 뒀기에 나온다.
4. 같은 칸에서 **탭이 두 개**인지 확인하고, 둘째 탭(`ZSH_CONCERT_ART`, 아티스트로 찾기)에서
   골라도 같은 `CONCERT_ID`가 돌아오는지 본다.

> 여기서 만든 테이블·데이터를 다음 챕터부터 계속 쓴다 — 잘 만들어 두자.

## 제작 체크리스트로 점검

각 단계를 진행하며 관계도가 자라는 걸 보고, 테스트 버튼으로 "Foreign Key를 활성화해야 없는 공연 ID가 거부된다"는 걸 직접 확인해 보자.

::embed CH09-L09-S01 | 콘서트 모델 제작 체크리스트 — 단계·관계도·테스트::

## 흔한 실수와 점검

- **활성화 누락** → 테이블·Search Help 모두 활성화해야 동작.
- **타입을 Built-In으로** → Data Element로 줘야 라벨·F4가 산다([Chapter 07 · Transparent Table 생성](CH07-L01.html)).
- **테이블마다 새 DE** → 공연 ID용 Data Element를 테이블마다 따로 만들면 Domain이 갈려 Foreign Key가 서지 않는다.
- **복합 키 대응 한 줄만** → `ZBOOKING`→`ZPERF`는 대응이 두 줄이다. 한 줄만 채우면 어긋난 회차가 새어 든다.
