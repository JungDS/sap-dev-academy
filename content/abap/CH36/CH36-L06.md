## 개발기에서 빠른 것과 운영에서 안전한 것

성능 개선은 개발 서버에서 빨라 보이는 것으로 끝나지 않는다. 운영에서 client가
섞이거나, DB 업그레이드 후 Native SQL이 깨지거나, 보안 리뷰에서 injection 위험이
나오면 그 코드는 개선이 아니라 장애 원인이 된다.

AMDP와 ADBC는 빠른 길을 열어 주지만 보호막 일부를 벗어난다. 그래서 이 레슨은
"어떻게 쓰는가"가 아니라 **"쓴 뒤 무엇을 책임지는가"**를 다룬다.

## 리스크 다섯 축

| 리스크 | AMDP 계열 | ADBC / Native SQL | 확인 기준 |
|---|---|---|---|
| DB 종속성 | HANA·SQLScript 종속 | DB vendor SQL 종속 | DB·Cloud 전환 영향 기록 |
| client | 자동 조건 없음 | `MANDT` 직접 | 현재 client만 접근하는가 |
| 보안 | 동적 SQLScript 주의(SQLScript 안에서도 문자열로 SQL을 조립·실행할 수 있어 같은 injection 위험 — 이 과정 범위 밖) | 문자열 injection | 바인딩·허용 목록·리뷰 |
| 플랫폼 보호 | SQLScript 내용은 개발자 몫 | 버퍼·CDS 접근 제어 우회 | 그 우회를 알고 선택했는가(모르고 우회했다면 사고) |
| 테스트·디버깅 | ADT·DB 도구 필요 | vendor 오류 처리 | 대표 데이터·오류 로그 |

Clean Core 관점도 다시 확인하자. "DB로 내리면 현대적"이 아니다. [[Clean Core]]의
기준은 released API와 업그레이드 안정성이라서, DB 종속 코드는 오히려 **더 엄격한
사유서**가 필요하다([Chapter 24](CH24-L08.html)).

## 운영 승인 체크리스트

AMDP/ADBC 코드가 이송 요청에 실리기 전, 아래가 전부 "완료"여야 한다.

| # | 항목 | 완료 기준 |
|---|---|---|
| 1 | 위 칸 불가 사유 | Open SQL/CDS로 안 되는 이유가 문서에 있다 |
| 2 | client 처리 | client 파라미터·`WHERE mandt` 확인 |
| 3 | injection 방어 | 값=바인딩, 동적 토큰=허용 목록 |
| 4 | 측정 근거 | 전환 전후 [ST05](CH35-L01.html) 수치 기록 |
| 5 | 오류 관찰성 | SQL code·message가 로그에 남는다([Chapter 25](CH25-L04.html)) |
| 6 | 격리 | AMDP/ADBC가 별도 클래스에 모여 있고 호출부는 인터페이스 뒤 |
| 7 | Cloud 경계 | 프로젝트의 Cloud·released API 기준 통과 |

6번 격리는 특히 값지다. DB 종속 코드가 업무 코드 곳곳에 흩어지면 나중에 걷어낼 수
없다. 한곳에 모으고 이유를 붙여 두면, DB가 바뀌는 날 그 클래스만 교체하면 된다.
모양은 [Chapter 21](CH21-L01.html)의 인터페이스 그대로다:

```abap
" 호출부는 인터페이스만 안다 — 구현이 AMDP든 Open SQL이든 교체 가능
DATA(go_stats) = CAST zif_booking_stats( NEW zcl_booking_stats_amdp( ) ).
go_stats->get_report( IMPORTING et_hot = DATA(gt_hot) ).
```

## 흔한 실수와 점검 🚧

- **"DB로 내리면 Clean Core"** → 반대다. DB 종속은 더 무거운 검토 대상이다.
- **버퍼·접근 제어를 잊음** → Native SQL은 테이블 버퍼를 지나치고 CDS 접근 제어를
  적용하지 않는다. 기대한 보호가 없다.
- **오류를 메시지 한 줄로 삼킴** → SQL code·message 없는 오류는 운영에서 재현도
  재처리도 안 된다.
- **흩어진 DB 종속 코드** → 격리 없이 퍼뜨리면 전환 비용이 폭발한다. 별도 클래스 +
  사유 기록.
- **테스트 생략** → SQLScript와 Native SQL은 ABAP 단위 테스트가 자동 보장하지
  않는다. 대표 데이터로 결과 동등성을 비교한다.

## 정리 📌

- AMDP/ADBC는 빠른 길이자 **책임이 커지는 길**이다: DB 종속·client·보안·보호 우회·
  테스트의 다섯 축.
- 배포 전 승인 체크리스트 7항목. 특히 **위 칸 불가 사유 + 측정 근거 + 격리**.
- 이 챕터의 결론: 먼저 Open SQL과 CDS로 해결하고, 강한 수단은 이유와 측정과 운영
  통제가 있을 때만.

## 🧩 도전 과제 (서브퀘스트)

> 선택 과제 — 공연별 예매 집계를 사다리 순서로 밀어 본다.

1. 공연별 예매 건수·좌석 합계를 **Modern Open SQL**(`GROUP BY` + 집계)로 구현한다.
   [ST05](CH35-L01.html)로 records·시간을 기록한다.
2. 같은 집계를 [CDS View](CH23-L01.html)로 올려 두 소비자(리포트·프로그램)가 공유하게
   한다.
3. (심화) 기간 파라미터가 필요한 버전을 [CDS Table Function + AMDP
   Function](CH36-L05.html)으로 만들고, 1번과 결과 동등성을 비교한다(두 결과를
   같은 키로 SORT한 뒤 `IF gt_a = gt_b`면 충분하다).
4. (설계) 위 세 버전에 대해 운영 승인 체크리스트 7항목을 채워 보고, 어느 버전을
   배포할지 사유와 함께 결정한다.
