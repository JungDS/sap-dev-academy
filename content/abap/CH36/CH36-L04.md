## 이름을 아는 것과 고르는 것

이제 Open SQL, CDS, AMDP, ADBC라는 네 이름을 다 안다. 실무에서 중요한 능력은
이름이 아니라 **상황을 보고 가장 단순하고 안전한 수단을 고르는 것**이다.

강한 수단은 문제를 풀면서 새 문제를 만든다. AMDP는 SQLScript·client·테스트 부담을,
ADBC는 injection·이식성·오류 처리 책임을 데려온다. 단순 집계를 AMDP로 만들면
기술적으로 돌아는 가도 좋은 설계가 아니다.

## 질문 × 수단 — 책임 순위표

| 질문 | Open SQL | CDS View | AMDP | ADBC |
|---|---|---|---|---|
| 단순 filter·join·집계인가 | **1순위** | 공유 모델이면 후보 | 보통 과함 | 부적절 |
| 여러 소비자가 재사용하는가 | 가능 | **1순위** | 보조 | 부적합 |
| DB 안 절차 로직이 필요한가 | 부족할 수 있음 | 자체로는 불가 — TF로 연결(다음 레슨) | **후보** | 보통 과함 |
| DB 고유 SQL이 불가피한가 | 불가 | 불가·제한 | 일부 가능(HANA 안 SQLScript 범위) — 다른 접속·DDIC 밖은 불가 | **후보** |
| Cloud·Clean Core 친화성 | 높음 | 높음 | 조건부(READ-ONLY 등 제약 준수 시 — L02) | 낮음 |
| 리뷰·테스트 난이도 | 낮음 | 중간 | 높음 | 매우 높음 |

이 표는 **속도 순위가 아니다. 책임 순위다.** 위쪽은 플랫폼이 보호해 주고, 아래쪽은
개발자가 직접 책임진다. 같은 결과라면 항상 위쪽이 이긴다.

> 💡 표에 두 번 등장한 "TF(Table Function)"가 궁금할 것이다. CDS 계층에서 AMDP
> 함수의 결과를 뷰처럼 읽는 다리인데, 다음 레슨에서 정식으로 배운다.

## 흔한 실수와 점검 🚧

- **"AMDP가 제일 빠르다"는 서열화** → AMDP는 빠른 이름이 아니라 실행 위치와 책임이
  다른 도구다. 속도는 이동량이 만든다([CH36-L01](CH36-L01.html)).
- **CDS를 SQL 저장소로만 취급** → CDS는 재사용·의미·권한·OData 연결까지 묶인
  모델이다([Chapter 23](CH23-L01.html)).
- **ADBC를 AMDP 대체재로 사용** → AMDP는 ABAP이 관리하는 프로시저, ADBC는 생짜
  문자열 실행이다. 관리·검증 책임의 격이 다르다.
- **선택 이유 미기록** → AMDP/ADBC를 골랐다면 "왜 위 칸으로 안 되는지"를 코드 주석과
  설계 문서에 남긴다. 다음 사람이 그 근거를 잃으면 부채가 된다.

## 정리 📌

- 선택 순서 = **Open SQL → CDS → AMDP → ADBC.** 아래로 내려가려면 근거(측정 +
  위 칸 불가 사유)가 필요하다.
- 표는 책임 순위다. 플랫폼 보호가 줄어드는 만큼 문서화·테스트가 늘어야 한다.
- 강한 수단을 고른 순간, 선택 이유를 기록하는 것까지가 선택이다.

CDS Table Function이다.
