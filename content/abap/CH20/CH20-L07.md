## 🎫 같은 데이터로, 네 도구를 나란히

지금까지는 문법을 하나씩 따로 봤다. 이번에는 **같은 콘서트 데이터 하나**를 놓고 이 챕터의 네 도구(CTE·EXISTS·EXCEPT·Window)를 **나란히 돌려 보는 종합 복습**이다. 콘서트 운영자가 실제로 궁금해할 네 가지 질문에 도구를 하나씩 대응시켜 답한다.

- 공연별 정원·예약 좌석·잔여석은?
- 예약이 있는 공연은?
- 예약이 없는 공연은?
- 예약 상세마다 공연 안 순번과 합계는?

> 🚧 **이 실습이 하지 않는 것**: 예약 저장·취소 같은 데이터 변경(DML — Data Manipulation Language, 데이터를 바꾸는 SQL 명령들)·CDS(Core Data Services)·RAP(RESTful Application Programming Model). 모두 다음 챕터들의 주제다. 여기선 **읽기·검증**까지.

## 실습 데이터

`zconcert`

| concert_id | artist | capacity |
|---|---|---:|
| C001 | 안유진 | 100 |
| C002 | ABAP Trio | 50 |
| C003 | UI5 Night | 80 |
| C004 | 김연아 | 60 |

`zbooking`

| booking_id | concert_id | seats | status |
|---|---|---:|---|
| 0001 | C001 | 2 | N |
| 0002 | C001 | 3 | N |
| 0003 | C002 | 1 | **C** |
| 0004 | C004 | 4 | N |

> ⚠️ [CTE 레슨](CH20-L02.html)과 같은 **연습용 단순화**다. 실제 앱의 잔여석 기준은 회차별 계산([Chapter 10 · 콘서트 모듈화 캡스톤](CH10-L07.html)의 `get_remaining`)이고, 여기서는 회차를 접고 공연 단위로 합산한다.

## 과제 1: CTE로 잔여석 조회

```abap
WITH
  +booked AS (
    SELECT concert_id, SUM( seats ) AS booked_seats
      FROM zbooking
      WHERE status <> 'C'
      GROUP BY concert_id )
  SELECT c~concert_id, c~artist, c~capacity,
         COALESCE( b~booked_seats, 0 )              AS booked,
         c~capacity - COALESCE( b~booked_seats, 0 ) AS remaining
    FROM zconcert AS c
    LEFT OUTER JOIN +booked AS b ON b~concert_id = c~concert_id
    INTO TABLE @DATA(gt_capacity).
```

예상 결과:

| concert_id | artist | capacity | booked | remaining |
|---|---|---:|---:|---:|
| C001 | 안유진 | 100 | 5 | 95 |
| C002 | ABAP Trio | 50 | 0 | 50 |
| C003 | UI5 Night | 80 | 0 | 80 |
| C004 | 김연아 | 60 | 4 | 56 |

검증 포인트: C002의 취소 예약 1석은 합계에서 빠진다. C003은 예약이 없어도 `LEFT OUTER JOIN` 덕분에 남는다. `COALESCE`가 없으면 예약 없는 공연은 합계 칸이 null이고, null이 섞인 뺄셈은 잔여석까지 null로 만든다. 그 null이 ABAP으로 넘어오면 `0`으로 바뀌므로, 잔여석이 0으로 잘못 보인다.

## 과제 2: EXISTS로 예약 있는 공연 찾기

```abap
SELECT c~concert_id, c~artist
  FROM zconcert AS c
  WHERE EXISTS ( SELECT concert_id
                   FROM zbooking AS b
                   WHERE b~concert_id = c~concert_id
                     AND b~status    <> 'C' )
  INTO TABLE @DATA(gt_has_booking).
```

예상 결과는 **C001, C004**다. C002는 취소 예약만 있어 제외, C003은 예약이 없어 제외.

## 과제 3: EXCEPT로 예약 없는 공연 찾기

```abap
SELECT concert_id FROM zconcert
EXCEPT DISTINCT
SELECT concert_id FROM zbooking WHERE status <> 'C'
INTO TABLE @DATA(gt_without_booking).
```

예상 결과는 **C002, C003**다. C002는 취소 예약만 있으므로 "취소 아닌 예약이 있는 공연" 집합에 들지 않는다.

## 과제 4: Window로 상세에 합계·순번 붙이기

```abap
SELECT booking_id, concert_id, seats,
       SUM( seats ) OVER( PARTITION BY concert_id )                      AS booked_total,
       ROW_NUMBER( ) OVER( PARTITION BY concert_id ORDER BY booking_id ) AS row_in_concert
  FROM zbooking
  WHERE status <> 'C'
  INTO TABLE @DATA(gt_window).
```

예상 결과:

| booking_id | concert_id | seats | booked_total | row_in_concert |
|---|---|---:|---:|---:|
| 0001 | C001 | 2 | 5 | 1 |
| 0002 | C001 | 3 | 5 | 2 |
| 0004 | C004 | 4 | 4 | 1 |

> 💡 예상 결과 표의 **행 순서**는 읽기 좋게 정렬해 둔 것이다. 문장 끝에 `ORDER BY`가 없으면 실제 행 순서는 보장되지 않는다(`OVER` 안의 `ORDER BY`는 계산 순서만 정한다). 순서가 달라도 **값**이 맞는지로 확인한다.

## 직접 해 볼 과제

1. 과제 1의 CTE에서 `WHERE status <> 'C'`를 빼 보고, 취소 예약이 합계에 섞이는지 확인한다. (검산: C002의 booked가 0 → 1, remaining이 50 → 49로 변하면 취소 1석이 섞인 것이다.)
2. 과제 2의 `EXISTS`를 `INNER JOIN`으로 바꿔 보고, 공연 행이 예약 건수만큼 중복되는지 비교한다. (검산: 결과가 세 행이 되고, 예약이 두 건인 C001이 두 번 나오면 확인 성공.)
3. 과제 3의 `EXCEPT` 좌우를 바꿔 보고 결과가 달라지는지 확인한다. (검산: 뒤집으면 "예약은 있는데 공연 마스터에 없는 ID"를 찾는 질문이 되므로, 지금 데이터에선 **빈 결과**가 나와야 맞다.)
4. (도구 고르기) 새 질문이다. **"취소 예약만 있는 공연"**을 찾으려면 네 도구 중 무엇을 고르겠는가? 정답은 하나가 아니다. "예약이 있는 공연"에서 "취소 아닌 예약이 있는 공연"을 `EXCEPT`로 빼도 되고, `EXISTS`와 `NOT EXISTS`를 조합해도 된다. 중요한 것은 질문을 집합의 말로 번역해 **도구를 스스로 고르는** 감각이다. (검산: 지금 데이터에선 **C002** 한 건이 나와야 맞다.)

## 흔한 실수와 점검 🚧

- **취소 조건 누락** → 합계·존재·차집합 모두 `status <> 'C'`가 빠지면 결과가 달라진다.
- **상태값 리터럴 하드코딩** → 연습이라 `'C'`를 그대로 썼지만, 실무에선 새 상태 코드가 추가될 것에 대비해 상수로 정의해 쓰는 관례가 일반적이다. 리터럴을 흩뿌리면 상태가 하나 늘 때마다 모든 SQL을 찾아 고쳐야 한다.
- **`COALESCE` 오해** → DB null을 대체하는 것이다. 이미 `0`인 값을 바꾸는 게 아니다.
- **`EXCEPT` 방향** → 왼쪽에서 오른쪽을 뺀다. 방향을 뒤집으면 다른 답이 나온다.
- **window를 필터로** → window는 `SELECT` list 계산 컬럼이다. `WHERE`에 직접 쓰지 않는다.
