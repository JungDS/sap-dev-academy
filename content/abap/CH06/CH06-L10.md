## 세 번 적었다, 또 적을 것이다

[앞 레슨](CH06-L09.html)에서 우리는 같은 선언을 세 번 반복했다.

```abap
DATA: gt_seoul TYPE TABLE OF ts_person,
      gt_busan TYPE TABLE OF ts_person,
      gt_all   TYPE TABLE OF ts_person.
```

지점이 대구·광주로 늘면 네 번, 다섯 번이다. 더 큰 문제는 **바뀔 때**다. 키를
`WITH NON-UNIQUE KEY name`으로 통일하기로 했다면? 세 군데(곧 다섯 군데)를 하나하나
찾아 고쳐야 하고, 하나라도 빠뜨리면 명단마다 키가 다른 괴상한 상태가 된다.

해결책은 이미 [L02](CH06-L02.html)에서 만나 봤다 — **테이블 모양 자체에 이름을
붙여 두는 것**(Table Type). 그때 이름과 기본 문법까지 봤으니, 이번엔 실전 문제에
진짜 무기로 쓸 차례다.

## 1단계 — 로컬 Table Type (이 프로그램 안에서)

```abap
TYPES tt_person TYPE TABLE OF ts_person
                WITH NON-UNIQUE KEY name.   " 모양+키를 한 번만 결정

DATA: gt_seoul TYPE tt_person,
      gt_busan TYPE tt_person,
      gt_all   TYPE tt_person.
```

- 선언이 한 단어로 줄었고, **결정이 한 곳에 모였다.** 키를 바꾸려면 `TYPES` 한 줄만 고치면
  세 테이블이 함께 바뀐다.
- [3속성](CH06-L02.html)이 전부 이 한 줄에 들어간다 — 행 모양(`ts_person`)·키(`WITH ... KEY
  name`)·종류(`TABLE OF` = STANDARD). 챕터 전반부에서 하나씩 배운 것이 여기서 한 문장으로
  합쳐지는 것이다.

## 2단계 — SE11 전역 Table Type (회사 전체에서)

로컬 `tt_person`은 이 프로그램 안에서만 보인다. 그런데 이 명단 모양을 **다른 프로그램들도**
쓴다면? [Chapter 3](CH03-L04.html)·[Chapter 5](CH05-L02.html)에서 Data Element와 Structure를
DDIC에 등록해 회사 자산으로 만들었듯, **Table Type도 SE11에 등록**할 수 있다.

`SE11`(Dictionary) → **Data type** 라디오 선택 → 이름 `ZTT_PERSON` 입력 → Create →
뜨는 팝업에서 **Table type** 선택.

- **Line Type** 칸에 행 모양이 될 이름을 적는다. 여기서는
  [Chapter 5 · DDIC Structure](CH05-L02.html)에서 만든 `ZST_PERSON`이다.
  (로컬 `ts_person`은 이 프로그램 밖에서 안 보이므로, 전역 Table Type의 행 모양도
  전역 Structure여야 한다 — 전역은 전역끼리.)
- **Primary Key** 탭에서 키 필드와 UNIQUE 여부, **Initialization and Access** 탭에서
  종류(Standard 등)를 정할 수 있다 — 화면 배치는 달라도 결정하는 것은 로컬 `TYPES`와
  똑같은 3속성이다. 학습 단계에서는 기본값(Standard·기본 키 설정)이면 충분하다.
- Short Description(짧은 설명)을 채우고 저장한 다음 **활성화**(Ctrl+F3)까지 해야 쓸 수 있다.
- 저장할 때 패키지를 물으면 학습 중에는 **Local Object**(`$TMP`)를 누른다.

활성화까지 끝나면 어느 프로그램에서든 한 단어로 선언한다.

```abap
DATA gt_person TYPE ztt_person.   " 회사 공용 Table Type
```

::embed CH06-L10-S02 | SE11에서 ZTT_PERSON 만들기 — 절차 따라 하기::

> 💡 **로컬로 할까, 전역으로 할까?** 기준은 Structure 때와 같다 — **이 프로그램만 쓰면
> 로컬(`tt_`), 여러 프로그램이 공유하면 전역(`ZTT_`)**. 전역은 편한 만큼 책임도 따른다:
> 고치면 그걸 쓰는 모든 프로그램이 영향을 받는다. 다음 챕터에서 DB 테이블을 만들면
> 이 `ZTT_PERSON`이 다시 등장하니 지워 두지 말자.

## 선언의 여섯 갈래 — 총정리

이 챕터에서 만난 Internal Table 선언 방법 전부다. 이제 지도 한 장으로 접힌다.

| # | 갈래 | 예 | 언제 |
|---|---|---|---|
| ① | 로컬 Structure 타입으로 | `TYPE TABLE OF ts_person` | 기본. 이 프로그램의 임시 모양 |
| ② | elementary 타입으로 | `TYPE TABLE OF i` | 필드 하나짜리 값 목록 |
| ③ | DDIC 타입으로 | `TYPE TABLE OF zst_person` | 회사 공용 행 모양을 빌릴 때 |
| ④ | 변수 기준으로 | `LIKE TABLE OF gs_person` · `LIKE gt_a` | 참조할 타입 이름이 없을 때 |
| ⑤ | 로컬 Table Type으로 | `TYPES tt_person ...` → `TYPE tt_person` | 같은 모양 여러 개·결정을 한곳에 |
| ⑥ | 전역 Table Type으로 | `TYPE ztt_person` | 여러 프로그램이 공유할 때 |

복잡해 보여도 갈림길은 둘뿐이다.

- **무엇을 보고 선언하나** — 타입 이름을 적나, 이미 있는 변수를 따라가나(변수 쪽은 ④뿐이다).
- **모양의 결정을 어디에 두나** — 선언 줄에 그때그때 직접 적나(①～④), 이름 붙인 타입에
  맡기나(⑤ 로컬·⑥ 전역).

한 가지 더 — 이 여섯 갈래는 **행 모양을 어디서 가져오나**의 축일 뿐이다.
[키(L03)](CH06-L03.html)와 [종류(L04)](CH06-L04.html)는 **어느 갈래에나** 그대로 얹을 수
있다. 3속성은 서로 독립된 결정이라 자유 조합이다.

```abap
" 갈래 ①(로컬 Structure) + SORTED + UNIQUE 키
DATA gt_a TYPE SORTED TABLE OF ts_person
          WITH UNIQUE KEY name.

" 갈래 ③(DDIC Structure) + HASHED + UNIQUE 키
DATA gt_b TYPE HASHED TABLE OF zst_person
          WITH UNIQUE KEY name.

" 갈래 ⑤(로컬 Table Type)에 종류·키까지 미리 구워 두기
TYPES tt_ranked TYPE SORTED TABLE OF ts_person
                WITH NON-UNIQUE KEY name.
DATA gt_c TYPE tt_ranked.       " 쓰는 쪽은 한 단어 — 3속성이 전부 따라온다
```

행 모양은 어디서 왔든, 그 위에 종류와 키를 조립하는 문법([L04의 비교](CH06-L04.html))은
언제나 같다 — 이것이 3속성 프레임([L02](CH06-L02.html))의 진짜 힘이다.

## 흔한 실수와 점검

- **전역 Table Type에 로컬 Structure** → `ZTT_...`의 Line Type엔 전역(DDIC) 타입만 들어간다.
  전역은 전역끼리.
- **활성화 잊기** → 저장만 하면 다른 프로그램에서 안 보인다. 활성화(Ctrl+F3)까지가 등록이다.
- **무엇이든 전역으로** → 공유가 확실할 때만. 이 프로그램만 쓸 모양을 전역에 올리면
  회사 공용 사전(DDIC)만 어지러워진다.
