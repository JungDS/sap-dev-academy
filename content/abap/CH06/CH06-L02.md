## Internal Table을 정하는 세 가지

앞 레슨에서는 `TYPE TABLE OF ts_person` 한 줄이면 충분했다. 그런데 이 짧은 한 줄은 사실
**세 가지 결정**을 한꺼번에 내리고 있다. 나중에 "이 테이블은 왜 이렇게 동작하지?" 하고
막히는 순간, 답은 거의 이 셋 중 하나에 있다.

그 **세 가지 속성**은 이렇다. 이 셋을 알면 테이블을 의도대로 설계할 수 있다.

1. **Line Type(행 모양)** — 한 행의 타입.
2. **Primary Key(기본 키)** — 행을 찾고 구분하는 기준.
3. **Table Kind(종류)** — 내부적으로 어떻게 저장·탐색하나.

키까지 명시하면 선언 한 줄에 셋이 다 보인다. 테이블 타입 이름은 `tt_`(table type)
접두어가 관례다.

```abap
TYPES tt_person TYPE STANDARD TABLE OF ts_person
                WITH NON-UNIQUE KEY name.

DATA gt_person TYPE tt_person.
```

## ① Line Type — 행은 꼭 Structure가 아니어도 된다

행 모양은 보통 Structure지만, **숫자 하나·문자 하나** 같은 단일(elementary) 타입일 수도 있다.

```abap
DATA gt_num    TYPE TABLE OF i.           " 행이 정수 하나
DATA gt_person TYPE TABLE OF ts_person.   " 행이 Structure
DATA gt_amt    TYPE TABLE OF zde_amount.  " 행이 DDIC Data Element
```

[Chapter 5 · DDIC Structure](CH05-L02.html)에서 본 "DDIC 타입으로 쓸 수 있는 것"과 같은
원리다. 나중에 배울 DB 테이블(Transparent Table)의 행 모양도 그대로 Line Type으로 줄 수
있다(다음 챕터에서 직접 해 본다).

## ② Primary Key — 행을 무엇으로 찾나

키는 "이 행을 **무엇으로 찾고 구분할 것인가**"이다. 사번이 유일하다면 사번이 키 후보고,
구구단이라면 `dan`+`mul` 조합이 한 줄을 식별한다.

키를 명시하지 않고 `TYPE TABLE OF`만 쓰면(지금까지 우리가 한 방식) **standard key**가
잡힌다. 행 타입에서 문자 계열 필드(문자·바이트를 담는 타입, 길이가 가변인 `string`도
포함)를 **전부** 묶어 키로 삼는 방식이다.

`ts_person`을 놓고 보면 문자인 `name`만 키가 되고 숫자인 `age`는 빠진다. 그래서 이름이 같은
사람이 둘이면 키만으로는 구분되지 않는다. "느슨하다"는 건 이런 뜻이다. 내가 원하는 키가
따로 있다면 위 예처럼 `WITH NON-UNIQUE KEY name`으로 **직접 적어 주는 편이 안전하다.**

`UNIQUE`로 선언하면 같은 키 값을 가진 행이 두 번 들어오는 것 자체를 막아 준다. 다만 어느
종류의 테이블에 `UNIQUE`를 줄 수 있는지는 종류마다 달라서, 바로 아래 ③에서 함께 정리한다.

> Internal Table의 키는 **메모리 안에서 행을 찾는 기준**이다. `UNIQUE`면 메모리 안 중복까지
> 막아 주지만 거기까지다. 저장된 데이터를 지켜 주는 DB의 Primary Key와는 다르다.

## ③ Table Kind — 세 종류

| 종류 | 저장 / 탐색 | 번호(인덱스) 접근 | 언제 |
|---|---|---|---|
| STANDARD | 입력 순서 유지, 키 탐색은 순차 | O | 기본. 대부분의 처리 |
| SORTED | 키 순서 자동 유지, 이진 탐색 | O | 정렬 유지·빠른 키/범위 탐색 |
| HASHED | 해시로 단건 탐색(행 수와 무관) | X | 유일 키 대량 데이터 단건 조회 |

표에 처음 나온 두 낱말부터 풀어 둔다.

- **이진 탐색** — 정렬된 전화번호부를 딱 반으로 갈라 "찾는 이름이 앞쪽인가 뒤쪽인가"만 보고,
  남은 쪽을 또 반으로 가르는 식으로 좁혀 간다. 첫 장부터 한 장씩 넘기는 것보다 훨씬 적게 본다.
  대신 **정렬돼 있어야** 성립한다.
- **해시** — 키 값을 계산해서 "이 값은 몇 번 칸"인지 바로 알아낸다. 앞에서부터 훑지 않으니
  행이 100개든 10만 개든 한 건 찾는 시간이 비슷하다.

종류를 고를 때 함께 기억해 둘 점들이다.

- STANDARD·SORTED는 **Index Table**이다. 행마다 번호가 붙어 "n번 행"으로 접근할 수 있다.
  이 번호는 **1번부터** 센다(0번 행은 없다). HASHED는 행을 관리하는 [[인덱스]]가 없어 번호
  접근이 안 되고 **키로만** 찾는다.
- 키의 **UNIQUE 여부**도 종류가 정한다. STANDARD는 `NON-UNIQUE`만 되고, SORTED는 둘 다 되며,
  HASHED는 `UNIQUE`만 된다. 그래서 HASHED는 키가 겹치는 데이터를 아예 담을 수 없다.
- 처음엔 **STANDARD**로 충분하다. SORTED/HASHED는 접근 패턴이 분명하고 성능이 절실할 때 다시 본다.

## 로컬 vs 전역(DDIC) Table Type

Structure처럼 테이블 타입도 로컬(`TYPES`)·전역(SE11 Table Type)으로 둘 수 있다.

`SE11`(Dictionary) → **Data type** 라디오 선택 → 이름 `ZTT_PERSON` 입력 → Create →
뜨는 팝업에서 **Table type** 선택.

- **Line Type** 칸에 행 모양이 될 이름을 적는다. 여기서는
  [Chapter 5 · DDIC Structure](CH05-L02.html)에서 만든 `ZST_PERSON`이다.
- Short Description(짧은 설명)을 채우고 저장한 다음 **활성화**(Ctrl+F3)까지 해야 쓸 수 있다.
- 저장할 때 패키지를 물으면 학습 중에는 **Local Object**(`$TMP`)를 누른다.

활성화까지 끝나면 여러 프로그램이 같은 테이블 타입을 공유한다.

```abap
DATA gt_person TYPE ztt_person.   " 전역 Table Type
```

## 흔한 실수와 점검

- **행 타입과 테이블 타입 혼동** → `ts_person`은 한 행의 모양, `TABLE OF ts_person`은
  여러 행의 모양. 행 모양을 먼저 정한다.
- **처음부터 SORTED/HASHED 남발** → 기본은 STANDARD. 이 테이블을 어떤 식으로 찾아 쓸지가
  분명해지고 속도가 실제로 문제가 될 때 바꾼다.
- **HASHED에 번호 접근** → HASHED는 인덱스가 없다. 키로만 찾는다.
- **키를 DB 제약으로 오해** → Internal Table의 키는 메모리 안 탐색 기준이다.
