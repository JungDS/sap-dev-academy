## 이름이 같은 사람이 둘이라면

`gt_person`에 정훈영이 두 명 들어 있다고 하자(동명이인은 어느 회사에나 있다).
"정훈영을 찾아라"라고 하면 테이블은 **어느 행**을 내놓아야 하나? 나이가 다른 두 행 중
하나를 고르려면, 애초에 "행을 무엇으로 구분할 것인가"가 정해져 있어야 한다.

그 기준이 3속성의 두 번째, **Primary Key(기본 키)** 다. 사번이 유일하다면 사번이 키 후보고,
구구단이라면 `dan`+`mul` 조합이 한 줄을 식별한다.

## 키를 직접 정하기 — WITH KEY

선언에 `WITH ... KEY`를 붙여 키 필드를 직접 적는다.

```abap
DATA gt_person TYPE TABLE OF ts_person
               WITH NON-UNIQUE KEY name.        " name으로 찾는다, 중복은 허용

TYPES tt_person TYPE TABLE OF ts_person
                WITH NON-UNIQUE KEY name.       " 타입에 이름 붙일 때도 똑같이
```

키 필드는 쉼표 없이 나열하면 여러 개를 묶을 수 있다(`WITH NON-UNIQUE KEY dan mul`처럼).
앞에 붙는 낱말이 중복 정책이다.

- **NON-UNIQUE** — 같은 키 값의 행이 여러 개 들어와도 된다(동명이인 허용).
- **UNIQUE** — 같은 키 값이 **두 번 들어오는 것 자체를 막는다**. 사번처럼 절대 겹치면
  안 되는 기준일 때 쓴다.

그럼 첫머리의 질문 — NON-UNIQUE라서 정훈영이 **둘 다 들어와 있는데** "정훈영을 찾아라"고
하면? 답을 여기서 못박아 두자. **키로 찾으면 테이블 앞쪽에서부터 처음 만나는 행 하나**가
나온다(두 번째 정훈영은 무시된다). 중복을 **전부** 다뤄야 한다면 그건 "찾기"가 아니라
"훑기"의 일이다 — 훑는 도구는 [순회 레슨](CH06-L08.html)에서 배운다. 찾는 문장(READ)으로
이 "첫 행" 동작을 직접 확인하는 것은 [넣기와 찾기](CH06-L05.html)에서다.

어느 종류의 테이블에 어떤 쪽을 줄 수 있는지는 종류마다 달라서, [다음 레슨](CH06-L04.html)에서
종류와 함께 표로 정리한다. 지금은 두 낱말의 뜻만 잡으면 된다.

> Internal Table의 키는 **메모리 안에서 행을 찾는 기준**이다. `UNIQUE`면 메모리 안 중복까지
> 막아 주지만 거기까지다. 저장된 데이터를 지켜 주는 DB의 Primary Key와는 다른 물건이다.

## 키를 안 적으면? — 자동으로 잡히는 standard key

그런데 우리는 L01부터 지금까지 키를 한 번도 안 적었다. 그럼 키가 없었을까? 아니다 —
**시스템이 자동으로 정해 뒀다.** 이 자동 키를 **standard key**라 부른다.

규칙은 이렇다: 행 타입에서 **문자 계열 필드**(문자·바이트를 담는 타입, 길이가 가변인
`string`도 포함)를 **전부** 묶어 키로 삼는다. 숫자 필드는 빠진다.

`ts_person`(name·age)을 놓고 보면 문자인 `name`만 키가 되고 숫자인 `age`는 빠진다.
그래서 동명이인은 키만으로 구분되지 않는다. 흔히 standard key를 두고 **"느슨하다"** 고
말하는데, 정확히 이런 뜻이다 — **내가 고른 기준이 아니라 타입 모양에서 우연히 만들어진
기준이라, 의도와 다를 수 있다.** 필드를 하나 추가하기만 해도(문자면) 키가 소리 없이 바뀐다.
원하는 키가 분명하다면 `WITH ... KEY`로 **직접 적는 편이 안전하다.**

> ✅ **여기서 확인 한 가지.** 키도 종류도 안 적은 `DATA gt TYPE TABLE OF ts_person.`은
> **종류 = STANDARD, 키 = standard key**로 선언된 것이다(`TABLE OF`는 사실
> `STANDARD TABLE OF`의 준말이다 — 종류 이야기는 다음 레슨에서). 그리고 미리 못박아 두자:
> **"standard key"와 "STANDARD(종류)"는 이름만 비슷할 뿐 서로 별개다.** 하나는 *키가 뭐냐*의
> 답이고, 하나는 *어떻게 저장하냐*의 답이다. 이 둘을 섞으면 이후 레슨의 표들이 전부 헷갈린다.

## 이름만 알아 두기 — 키의 나머지 친척들

아래 셋은 **지금 외울 필요가 전혀 없다.** 이런 게 있다는 것만 알아 두면, 실무 코드나 뒤
챕터에서 만났을 때 "아, 그때 그거"가 된다. 키는 이 레슨 이후로도 L05～L08 내내 계속
다시 만나니, 지금 다 소화하지 못해도 자연히 익는다.

- **`WITH DEFAULT KEY`** — "standard key를 쓰겠다"를 **명시적으로** 적는 표기. 안 적은 것과
  결과가 같다. 실무에서는 "문자 전부가 키"라는 의도 불명확함 때문에 권장되지 않지만,
  옛 코드에서 자주 보이니 알아만 두자.
- **`WITH EMPTY KEY`** — 키가 **아예 없는** 테이블. 순서만 중요한 임시 목록에 쓴다.
  [Chapter 18](CH18-L02.html)에서 새 문법과 함께 정식으로 만난다.
- **secondary key(보조 키)** — 키를 **여러 벌** 달아 두고 상황마다 골라 쓰는 기능. 이름용
  키·날짜용 키를 같이 갖는 식이다. [Chapter 18](CH18-L08.html)에서 만난다.

## 헷갈리는 낱말 다섯 — 한 줄씩만

이 레슨엔 생김새가 비슷한 낱말이 한꺼번에 나왔다. 표 한 장으로 갈라 두자 —
여기만 명확하면 이후 레슨의 표들이 전부 술술 읽힌다.

| 낱말 | 정체 |
|---|---|
| **Primary Key** | "행을 무엇으로 찾고 구분하나"의 답(3속성 ②) — 이 레슨의 주제 |
| **UNIQUE / NON-UNIQUE** | 그 키의 **중복 정책** — 막는다 / 허용한다 |
| **`WITH ... KEY`** | 키를 **직접 적는** 선언 문법 |
| **standard key** | 키를 **안 적었을 때** 자동으로 잡히는 키(문자 계열 필드 전부) |
| **STANDARD** | 키 아님! — 다음 레슨에 나올 **종류(Table Kind)** 의 이름 |

## 흔한 실수와 점검

- **숫자 필드가 키에 들어 있다고 착각** → standard key는 문자 계열만 모은다. `age`·금액·수량은
  자동 키에 **안 들어간다**. 숫자로 찾을 거면 직접 지정.
- **UNIQUE를 DB 제약으로 오해** → 프로그램 메모리 안에서만 유효하다. DB에 저장할 때의
  중복 방지는 별개 문제다.
- **"느슨하다"를 "없다"로 오해** → standard key도 엄연한 키다. 다만 그 구성이 내 의도와
  다를 수 있다는 게 함정이다.
