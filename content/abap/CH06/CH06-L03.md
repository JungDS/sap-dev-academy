## 행을 콕 집어 다루기

전체를 훑지 않고 **특정 한 행**을 넣고, 찾고, 고치고, 지우는 일이 잦다. 결과는
그때그때 [[sy-subrc]]로 확인한다(0=성공).

## 넣기 — APPEND vs INSERT

- `APPEND gs_... TO gt_....` — 맨 끝에 추가(STANDARD 테이블의 기본).
- `INSERT gs_... INTO gt_... INDEX n.` — n번째 위치에 끼워 넣기(Index Table 전용).
- `INSERT gs_... INTO TABLE gt_....` — **테이블 종류가 정하는 자리**에 넣기.

```abap
APPEND gs_person TO gt_person.            " 끝에
INSERT gs_person INTO gt_person INDEX 1.  " 맨 앞에
INSERT gs_person INTO TABLE gt_person.    " 종류가 정한 자리(STANDARD면 끝)
```

`INTO TABLE`이 실제로 어디에 넣는지는 **테이블 종류**가 정한다. 하나로 외우면 틀린다.

| 종류 | `INSERT ... INTO TABLE`이 넣는 자리 |
|---|---|
| STANDARD | 맨 끝. 결과가 `APPEND`와 같다(입력 순서 유지) |
| SORTED | 키 순서에 맞는 자리 |
| HASHED | 해시가 관리하는 자리(눈에 보이는 순서는 의미가 없다) |

> `INTO`(위치 기반)와 `INTO TABLE`(종류가 정한 자리)은 **다른 문장**이다. HASHED는 번호가 없어
> `INTO TABLE`만 가능하다. SORTED는 `INDEX` 문법 자체는 되지만 삽입이 정렬 순서를 깨면
> 런타임 오류가 난다. 그래서 SORTED/HASHED엔 `INTO TABLE`을 쓴다(자리는 시스템이 잡는다).

## 찾기 — READ TABLE

```abap
READ TABLE gt_person INTO gs_person WITH KEY name = '정훈영'.
IF sy-subrc = 0.
  WRITE: / '찾음:', gs_person-age.
ENDIF.
```

- `INDEX n` — n번째 행을 **번호로 직접** 읽기(예: `READ TABLE gt_person INTO gs_person INDEX 1.`).
- `WITH KEY field = ...` — 아무 필드 조합(free key)으로 찾기(STANDARD는 순차 탐색).
- `WITH TABLE KEY ...` — 선언에 **정의된 키**로 찾기(SORTED/HASHED에 최적).
- 성공 판정은 **언제나 `sy-subrc = 0`인지**로 한다. 못 찾으면 보통 4가 들어오지만,
  잠시 뒤에 배울 `BINARY SEARCH`로 찾다가 테이블 끝까지 간 경우에는 8이 들어오기도 한다.
  그래서 `IF sy-subrc = 4`로 비교하면 조용히 어긋난다.

찾기에 성공하면 시스템 필드 [[sy-tabix]]에 **그 행의 번호**가 들어온다. 몇 번 행에서
찾았는지를 시스템이 알려 주는 것이다. 번호가 있는 Index Table(STANDARD·SORTED) 기준이고,
번호가 없는 HASHED에서는 0이 들어온다. 잠시 뒤 고치기에서 바로 써먹는다.

`TRANSPORTING`은 "**어떤 필드를 옮길지 지정한다**"는 뜻이다. 뒤에 `NO FIELDS`를 붙이면
"하나도 옮기지 마라", 즉 값 복사 없이 **있는지만** 확인한다(그래서 빠르다). 같은 낱말이
잠시 뒤 고치기에서는 "이 필드만 옮겨라"로 쓰인다.

```abap
READ TABLE gt_person TRANSPORTING NO FIELDS WITH KEY name = '정훈영'.
IF sy-subrc = 0.  " 존재만 확인(Work Area 복사 없음)
ENDIF.
```

## 정렬 — SORT

키로 자주 찾을 테이블은 먼저 **정렬**해 두는 게 유리하다. 문법은 간단하다.

```abap
SORT gt_person BY name.              " name 기준 오름차순(기본)
SORT gt_person BY age DESCENDING.    " 내림차순
```

참고로 SORTED TABLE은 키 순서가 선언으로 고정돼 있어 `SORT`로 다시 정렬할 수 없다
(`SORT`의 대상은 STANDARD·HASHED).

HASHED는 번호도 순서도 없는데 정렬이 무슨 의미인가 싶다. `SORT`가 바꾸는 것은 **그 뒤의
`LOOP`가 행을 꺼내 오는 순서**다. 화면에 찍히는 차례를 정리하고 싶을 때 쓴다.

### 빠른 탐색 — BINARY SEARCH

STANDARD 테이블에서 단건을 자주 찾으면 순차 탐색이 느리다. **키로 정렬해 두고**
`BINARY SEARCH`를 붙이면 이진 탐색으로 빨라진다.

```abap
SORT gt_person BY name.                  " 반드시 같은 키로 먼저 정렬
READ TABLE gt_person INTO gs_person
     WITH KEY name = '정훈영' BINARY SEARCH.
```

> ⚠️ `BINARY SEARCH`는 **그 키로(오름차순) 정렬돼 있어야** 정확하다. 정렬 안 하고 쓰면
> 있는 행도 "없음"(`sy-subrc` ≠ 0)으로 나온다. 아래에서 직접 실패를 목격해 보자.

## 고치기 · 지우기 — MODIFY · DELETE

찾은 행을 고칠 때 가장 자주 쓰는 패턴은 이것이다. `READ`가 채워 준 `sy-tabix`로 바로 `MODIFY`.

```abap
READ TABLE gt_person INTO gs_person WITH KEY name = '정훈영'.
IF sy-subrc = 0.
  gs_person-age = 31.
  MODIFY gt_person FROM gs_person INDEX sy-tabix
         TRANSPORTING age.               " age 필드만 갱신(나머지 보존)
ENDIF.
```

- `MODIFY gt_... FROM gs_... INDEX n.` — n번 행을 통째로 교체.
- `MODIFY TABLE gt_... FROM gs_....` — 키로 행을 찾아 교체.
- `TRANSPORTING f1 f2` — **그 필드만** 갱신하고 나머지는 그대로. 위에서 본 그
  `TRANSPORTING`이 여기서는 "이 필드만 옮겨라"로 쓰인 것이다.
- `DELETE gt_person WHERE age < 20.` — 조건에 맞는 행 **모두** 삭제. 하나라도 지웠으면
  `sy-subrc = 0`, 지운 행이 없으면 4.

## 여기까지 한눈에

문장이 여럿 나왔다. 외우기 전에 "무엇을 하려는가"로 묶어 보면 훨씬 단순하다.

| 하려는 일 | 문장 | 언제 |
|---|---|---|
| 넣기 | `APPEND` | 끝에 쌓기만 하면 될 때 |
| 넣기 | `INSERT ... INDEX n` | 자리를 내가 지정할 때(Index Table) |
| 넣기 | `INSERT ... INTO TABLE` | 자리를 테이블 종류에 맡길 때 |
| 찾기 | `READ ... INDEX n` | 몇 번 행인지 이미 알 때 |
| 찾기 | `READ ... WITH KEY` | 필드 값으로 찾을 때 |
| 찾기 | `READ ... TRANSPORTING NO FIELDS` | 있는지만 확인할 때 |
| 고치기 | `MODIFY ... INDEX n` | `READ` 직후 `sy-tabix`로 |
| 고치기 | `MODIFY TABLE` | 키로 찾아 고칠 때 |
| 지우기 | `DELETE ... WHERE` | 조건에 맞는 행을 한꺼번에 |

넣기·찾기·고치기·지우기 네 갈래에, 각각 "번호로 할까 키로 할까"가 붙는 구조다.

## 흔한 실수와 점검

- **sy-subrc 미확인** → READ 실패 시 Work Area엔 **이전 값이 그대로** 남는다. 그걸 새로
  읽은 값인 줄 알고 쓰는 버그가 잦다.
- **BINARY SEARCH 전에 SORT 안 함** → 잘못된 "없음" 결과.
- **INTO vs INTO TABLE 혼동** → 위치 기반인지 키 기반인지 구분.
- **sy-tabix를 오래 보관** → 그 사이 정렬·삭제가 일어나면 번호의 의미가 바뀐다.
  READ 직후 바로 쓴다.
