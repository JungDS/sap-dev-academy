## 996번의 허탕

[종류 레슨](CH06-L04.html)의 그 장면으로 돌아가자. STANDARD 테이블 1,000행에서
`READ ... WITH KEY name = '수지'`를 하면 시스템은 앞에서부터 한 행씩 훑는다.
수지가 997번째면 996번의 허탕. 매번 이렇게 찾을 수는 없다.

SORTED나 HASHED로 그릇을 바꾸는 게 한 방법이지만([거래표](CH06-L04.html) 기억),
그릇은 STANDARD로 두고 **찾기 직전에만 정렬해서 빠르게** 찾는 수동 처방이 있다.
오늘의 주제다.

## 정렬 — SORT

```abap
SORT gt_person BY name.              " name 기준 오름차순(기본)
SORT gt_person BY age DESCENDING.    " 내림차순
SORT gt_person BY name age.          " name 같으면 age로(정렬 기준 여러 개)
```

- 기준 필드를 안 적은 `SORT gt_person.`은 **테이블의 키**(standard key였다면 문자 필드들)로
  정렬한다 — [키 레슨](CH06-L03.html)의 함정이 여기서도 이어지니, 기준은 `BY`로 직접 적자.
- 같은 값끼리의 순서까지 유지해야 하면 `SORT ... BY ... STABLE.`이 있다(동점 행의 원래
  순서 보존). 지금은 "그런 옵션이 있다"만 알아 두면 된다.

### 종류별로 되고 안 되고

| 종류 | SORT | 이유 |
|---|---|---|
| STANDARD | O | 순서가 자유라 마음대로 재배열 |
| SORTED | **X (구문 오류)** | **정렬이 곧 정체성**이다 — 항상 키 순서를 유지하는 그릇이라 손으로 다시 정렬한다는 것 자체가 모순 |
| HASHED | O | 단, 무엇이 정렬되는지가 미묘하다 — 바로 아래에서 |

### "순서가 없다"더니 SORT가 된다? — HASHED의 정체

[종류 레슨](CH06-L04.html)에서 HASHED는 "순서(행 번호)가 없다"고 했는데 SORT가 된다니,
모순처럼 들린다. 여기가 이 챕터에서 가장 헷갈리는 지점이니 정확히 갈라 두자.

**"순서가 없다"의 진짜 뜻은 "관리되는 번호표가 없다"는 것이다.** 사물함 비유로:
사물함(HASHED)은 열쇠(키)로 한 번에 열지만, "37번째 사물함 물건 줘"는 성립하지 않는다 —
번호표를 아무도 관리하지 않기 때문이다. 그런데 사물함도 **청소할 때는 왼쪽 위부터 차례로
훑을 수 있다.** 이 "훑는 길"이 곧 `LOOP`가 행을 꺼내는 **순회 순서**다. 길은 있지만
번호표는 없다 — 길이 있다고 좌표가 있는 게 아니다.

> 🔎 **[선행 사용]** `LOOP`는 테이블을 처음부터 끝까지 훑는 문장으로, 정식 도입은
> [다음 레슨](CH06-L08.html)이다. 여기서는 "훑는 길의 순서"를 관찰하는 용도로만 이름을
> 빌려 쓴다(지금 분석할 필요 없다).

`SORT`가 바꾸는 것이 바로 이 **훑는 길의 순서**다. 화면에 찍히는 차례를 정리하고 싶을 때
쓴다. 반면 `READ ... INDEX`가 요구하는 것은 **관리되는 번호표**라서 HASHED에선 여전히
불가능하다.

증거도 이미 봤다 — [L05](CH06-L05.html)에서 HASHED의 `sy-tabix`가 **0**이었다.
"행은 찾았지만 지금 몇 번째인지는 세지 않는다"고 시스템이 스스로 말해 준 것이다.
왜 번호표를 안 만들까? [거래표](CH06-L04.html) 그대로다 — 번호표를 유지하려면 중간에 넣고
뺄 때마다 뒤 번호를 전부 밀고 당겨야 한다. HASHED는 **그 비용을 버리는 대가로 열쇠 속도를
산** 그릇이다. 결함이 아니라 거래다.

## 이진 탐색 — BINARY SEARCH

STANDARD 테이블을 **키로 정렬해 뒀다면**, `READ`에 `BINARY SEARCH`를 붙여 이진 탐색
(반씩 갈라 좁히기 — [종류 레슨](CH06-L04.html)의 전화번호부)으로 찾을 수 있다.

```abap
SORT gt_person BY name.                  " 반드시 같은 키로, 오름차순으로 먼저 정렬
READ TABLE gt_person INTO gs_person
     WITH KEY name = '수지' BINARY SEARCH.
```

> ⚠️ `BINARY SEARCH`는 **그 키로(오름차순) 정렬돼 있어야** 정확하다. 정렬 안 하고 쓰면
> **있는 행도 "없음"** (`sy-subrc` ≠ 0)으로 나온다. 반쪽을 잘라 버리는 탐색이라, 순서가
> 어긋나 있으면 찾을 행이 있는 쪽을 통째로 버리기 때문이다. 아래에서 직접 실패를 목격해 보자.

::embed CH06-L07-S02 | 정렬 없이 BINARY SEARCH — 있는 행도 못 찾는 함정::

한 가지 더. [L05](CH06-L05.html)에서 "실패 값은 문장에 따라 다르니 0인지로만 판정하라"고
했는데, 그 '다른 값'의 정체가 여기 있다. `BINARY SEARCH`로 찾다 실패하면 `sy-subrc`에
**4 또는 8**이 들어온다(중간에서 못 찾으면 4, 찾다가 테이블 끝을 넘어가면 8).
구분해서 외울 필요는 없다 — 규율은 언제나 같다. **0인지로만 판정한다.**

## 무엇으로 찾느냐 × 어떤 그릇이냐 — 탐색 비용 한눈에

표에 들어갈 낱말 하나만 먼저 풀어 두자 — **선두 일치**. 키가 여러 필드일 때(구구단이라면
`dan`+`mul`), 조건을 **키의 첫 필드부터 끊김 없이** 주는 것을 말한다. `dan`만 주거나
`dan`+`mul`을 다 주면 선두 일치고, 첫 필드를 건너뛰고 `mul`만 주면 아니다. 전화번호부에서
성(첫 글자)을 알아야 반으로 가를 수 있듯, SORTED의 자동 이진 탐색은 **선두 일치일 때만**
작동한다.

| 찾는 방법 | STANDARD | SORTED | HASHED |
|---|---|---|---|
| `WITH KEY`(키 아닌 필드) | 순차 | 순차 | 순차 |
| `WITH KEY`(키 필드·선두 일치) | 순차 | **이진(자동)** | 순차* |
| `WITH TABLE KEY`(키 전체) | 순차 | **이진(자동)** | **해시(최속)** |
| `WITH KEY ... BINARY SEARCH` | **이진(정렬 필수)** | — (이미 자동) | — |

*HASHED에서는 `WITH KEY`라도 키 필드를 **전부** 주면 아랫줄(`WITH TABLE KEY`)과 똑같이
해시로 찾는다. 일부만 주면 처음부터 훑는다.

읽는 법: 같은 `WITH KEY`라도 **무엇을 지정했느냐**에 따라 비용이 다르다. SORTED/HASHED는
키 조건이면 알아서 빠르고, STANDARD만 수동 처방(`SORT` + `BINARY SEARCH`)이 필요하다.

## 흔한 실수와 점검

- **SORT 없이 BINARY SEARCH** → 잘못된 "없음". 이 함정은 에러도 안 나서 더 위험하다.
- **다른 키로 SORT 해 놓고 BINARY SEARCH** → `SORT ... BY age` 후 `WITH KEY name = ...
  BINARY SEARCH`도 같은 함정이다. 정렬 키와 탐색 키가 **같아야** 한다.
- **SORTED 테이블에 SORT** → 구문 오류. 애초에 항상 정렬돼 있는 그릇이다.
- **정렬 후 sy-tabix 재사용** → 정렬하면 행 번호가 전부 바뀐다. 이전에 봐 둔 번호는 버린다.
- **한 번 찾자고 SORT부터** → 정렬 자체도 공짜가 아니다. 딱 한 번 찾고 말 거면 그냥 순차
  탐색이 이득이고, 정렬해 두고 **여러 번** 찾을 때 비로소 본전을 뽑는다.
- **정렬해 둔 뒤 행 추가/삭제** → 중간에 행을 넣거나 지우면 정렬 전제가 깨져, 그다음
  `BINARY SEARCH`가 다시 "잘못된 없음"을 낸다. 행이 바뀌었으면 SORT부터 다시.
