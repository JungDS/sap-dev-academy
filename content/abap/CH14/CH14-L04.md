## 마스터 데이터를 담당자가 직접

[Chapter 7 · Transparent Table](CH07-L01.html)에서 SE11의 Create Entries로 한 건씩 넣어 봤다.
학습 초반엔 편하지만, 실무에서는 개발자가 매번 운영 값을 대신 넣을 수 없다. 공연 코드·회차·좌석 등급처럼 **업무 담당자가 관리할 기준 데이터**는 표준 화면으로
유지보수할 수 있어야 한다. 게다가 서로 연결된 테이블이면 어느 순서로 열고 어떤 key가
이어지는지 기억해야 해서 실수도 잦다.

[[Maintenance View]]는 관련 테이블을 **하나의 유지보수 관점**으로 묶는 도구다.

## Maintenance View — 조회가 아니라 유지보수

[[Maintenance View]]는 **extended table maintenance**(확장 테이블 유지보수)를 위한 DDIC
View다. Open SQL로 읽는 대상이 아니고, 표준 유지보수 흐름에서 화면의 바탕으로 쓴다.

핵심은 [[Database View]]와 **목적부터** 다르다는 점이다.

| 구분 | Database View | Maintenance View |
|---|---|---|
| 핵심 목적 | 프로그램 **조회**용 공통 관점 | 표준 **유지보수**용 관점 |
| Open SQL 읽기 | 가능 | **대상 아님** |
| 연결 근거 | join condition | **Foreign Key dependency** |
| 사용 화면 | SELECT·Data Browser | SE54·SM30·SM31 |
| 설계 질문 | 어떤 필드를 읽을까 | 어떤 데이터를 같이 관리할까 |

표 오른쪽 아래에 T코드 세 개가 한꺼번에 나왔다. 지금은 **이름만** 알아 두자.
**SE54**는 유지보수 화면을 정의하고 생성하는 도구다(다음 레슨과
[Chapter 14 · View Cluster](CH14-L06.html)에서 직접 쓴다). **SM30**은 그렇게 만들어진
화면을 열어 데이터를 손보는 자리다([다음 레슨](CH14-L05.html)). **SM31**은 같은 표준
유지보수 화면으로 가는 예전 입구인데, 요즘은 대개 SM30을 쓴다.

> ⚠️ Maintenance View를 "join 조회의 대안"으로 외우지 말자(흔한 오해). 결합만 보면
> Maintenance View는 Database View와 같은 **inner join**이다. 그래서 짝이 안 맞는 행,
> 예를 들어 회차가 하나도 없는 공연은 유지보수 화면 목록에 안 올라온다. 주 테이블 행을
> 남겨 두는 outer join은 [Chapter 14 · Help View](CH14-L03.html)의 성질이지 이쪽이 아니다.
> 그리고 결합이 무엇이든 조회에 써먹을 방법이 없다. Open SQL이 읽을 수 있는 대상이
> 아니기 때문이다. **결합은 inner, 용도는 유지보수**로 기억하자.

> 🧷 이름이 닮은 둘을 미리 갈라 두자. **Maintenance View**는 지금 만드는 **DDIC 객체**(무엇을
> 함께 유지보수할지 적어 둔 설계도)이고, **Maintenance Dialog**는 [다음 레슨](CH14-L05.html)에서
> 도구가 그 설계도를 보고 **실제로 찍어 내는 화면**이다. 설계도와 건물의 관계다.

## Foreign Key가 설계 기준

여러 테이블을 아무 조건으로나 붙이는 게 아니라 **[[Foreign Key]] 관계**로 연결한다.
[Chapter 9 · Foreign Key와 Check Table](CH09-L01.html)에서 배운 그 관계가 여기서 다시
쓰인다. 같은 개념을 다른 자리에서 또 만나는 건 정상이다. 그때는 "값이 맞는지 검사하는
장치"로 배웠고, 지금은 "무엇과 무엇을 함께 관리할지 정하는 기준"으로 만나는 것뿐이다.

Foreign Key가 실제로 평가되는 자리는 셋이다.

- **input check**(입력 검증) — 화면에서 값을 넣을 때 그 값이 Check Table에 있는지 확인한다.
- **input help**(입력도움말) — 그 칸에서 **F4**를 누르면 Check Table의 값이 목록으로 뜬다.
  앞 레슨의 [[Search Help]]와는 **다른 경로**다. 한 칸에 둘 다 걸려 있으면 무엇이 먼저
  뜨는지 순서가 정해져 있다([Chapter 9 · Input Help 호출 우선순위](CH09-L07.html)).
- **view 생성** — 지금 만들 Maintenance View처럼 DDIC View의 조인 조건을 채우는 근거가 된다.

반대로 Foreign Key가 **하지 않는 일**도 분명히 해 두자. Foreign Key는 DB에 걸리는 제약이
아니라 DDIC가 들고 있는 **설계 정보**다. 그래서 화면과 표준 도구 안에서는 강하게 작동하지만,
그 바깥은 막지 못한다. `SELECT`는 Foreign Key를 자동으로 평가하지 않는다. 프로그램이 값을
직접 저장하는 경로(문법은 [Chapter 25 · 데이터 변경](CH25-L01.html)에서 배운다)나 SE16N
직접 편집도 검사를 거치지 않는다. 그래서 **공연 마스터에 없는 `concert_id`를 가진 회차 행**,
곧 부모 없는 고아 행은 여전히 생길 수 있다. "FK를 걸었으니 이제 안전하다"가 아니라 "화면으로
들어오는 값은 걸러진다"가 정확한 이해다.

### 직접 만들어 보기 (SE11 → SE54)

공연과 그 회차를 함께 손보는 Maintenance View `ZMV_CONCERT`를 만들어 보자.

1. `SE11` → **View** 칸에 `ZMV_CONCERT` → Create → 종류는 **Maintenance view**.
2. **Tables** 칸 첫 줄에 primary table로 `ZCONCERT`를 적는다.
3. **Relationships** 버튼으로 `ZPERF`를 붙인다. `zperf-concert_id → zconcert-concert_id`
   Foreign Key([Chapter 9 · 실습에서 건 그 관계](CH09-L09.html))가 조인 조건이 된다.
4. **View Flds** 탭에서 필드를 고른다. 먼저 **key**다. primary table `ZCONCERT`의 key는
   **전부** 넣어야 하고(`CONCERT_ID`. 맨 앞의 `MANDT`는 SE11이 알아서 챙긴다), 조인 조건에
   쓰이지 않은 `ZPERF`의 key(`PERF_NO`)도 반드시 넣는다. key가 있어야 화면이 **어느 공연의
   몇 회차인지** 행을 식별하고, 새로 입력한 행도 제자리에 저장된다. 그다음 화면에 보일
   `ARTIST`·`VENUE`·`PERF_DATE`를 더한다.
5. **Maint.Status** 탭에서 유지보수 허용을 **읽기·쓰기 가능**으로 둔다. 이게 막혀 있으면
   화면을 만들어도 저장이 안 된다.
6. 저장 → 활성화. 여기까지가 **설계도**다. 실제 입력 화면은 [다음 레슨](CH14-L05.html)에서 붙인다.

> 💡 만드는 입구가 두 개로 보여 헷갈릴 수 있다. `SE11`에서 테이블·View를 열어 둔 채 Utilities
> 메뉴로 부르는 길과 `SE54`에 이름을 직접 넣고 들어가는 길은 **같은 도구로 가는 다른 문**이다.
> 어느 쪽으로 들어가도 결과는 같다.

아래에서 `zperf-concert_id → zconcert-concert_id` Foreign Key를 켜고 끄며, 회차 유지보수
화면에서 존재하지 않는 공연 코드를 입력했을 때 input check가 어떻게 막는지 보자.

## 흔한 실수와 점검

- **유지보수 = 조회로 혼동** → Database View는 읽기, Maintenance View는 유지보수 토대.
  이름이 같아도 목적이 다르면 완전히 다른 도구다.
- **Foreign Key를 문서용 선으로** → input check·input help·view 생성에서 실제로 평가된다.
- **Foreign Key를 만능 자물쇠로** → 화면 밖의 저장 경로는 막지 않는다. 고아 행이 생길 수
  있다는 전제로 데이터를 다룬다.
- **권한 없이 판단** → View·화면이 있어도 authorization(권한)이 부족하면 못 연다. 표준
  유지보수는 **설정 + 권한**이 함께 필요하다.

## 정리

- [[Maintenance View]]는 조회 편의가 아니라 **유지보수 흐름**을 위해 존재한다.
- [[Foreign Key]]로 연결된 테이블을 표준 유지보수 화면에서 함께 다룬다.
- Open SQL의 일반 데이터 소스로 읽는 View가 **아니다**.
