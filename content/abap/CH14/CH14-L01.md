## 같은 JOIN을 또 짜기 싫다

[Chapter 13 · JOIN](CH13-L01.html)에서 여러 테이블을 코드의 JOIN으로 붙였다. 즉시
이해하기는 좋지만, **같은 결합을 여러 프로그램이 반복**하면 문제가 생긴다. 공연 조회·
예매 확인·정산 리포트가 모두 `zconcert`와 `zperf`를 같은 조건으로 붙인다면, 필드명이
바뀌거나 조인 조건을 보강할 때 **프로그램마다** 고쳐야 한다.

[[Database View]]는 이 반복 조회 구조를 **DDIC에 이름 붙여 등록**하는 방법이다.

> 🗺️ **이 챕터의 지도 — 두 갈래.** 앞의 네 레슨은 DDIC에 등록하는 **View 네 종류**를
> 하나씩 본다. 세 개는 **보여 주는 쪽**(조회용 Database·필드를 줄이는 Projection·입력도움말용
> Help)이고, 하나는 **고치는 쪽**(유지보수용 Maintenance)이다. 그다음 레슨들은 그 유지보수
> 관점에 **실제 화면과 도구**를 붙인다(입력 화면 자동 생성 → 여러 테이블 묶어 관리 → 빠른 조회
> 브라우저). 마지막에 현대 도구와의 경계를 긋고, 공연 등록 실습으로 전부 이어 붙인다.

## Database View — JOIN을 DDIC에 등록

[[Database View]]는 하나 이상의 **basis table**(기반 테이블, View가 값을 실제로 읽어 오는
원본 테이블)에서 필요한 컬럼을 골라 만드는 DDIC 객체다. 여러 테이블이면 **inner join**으로
결합한다. 활성화하면 DB 쪽에도 SQL View가 만들어져 [[Open SQL]]의 `FROM` 자리에서
**테이블처럼** 읽을 수 있다.

> 📎 **Open SQL과 ABAP SQL은 같은 것이다.** [Chapter 8 · DB에서 읽어 오기](CH08-L01.html)에서
> 배운 그 SQL인데, 최신 릴리스의 SAP 문서·화면은 같은 대상을 ABAP SQL이라고 부른다. 이름만
> 바뀌었을 뿐이라 둘 중 무엇을 보든 당황하지 않아도 된다.

### 이 챕터가 쓸 View — `ZV_PERF`

챕터 내내 쓸 View 하나를 먼저 정해 두자. 회차 `zperf`에 공연 마스터 `zconcert`를 붙인
`ZV_PERF`다. 조인 조건은 `concert_id`이고, View Field는 **다섯**이다.

| View Field | 어느 basis table에서 | 뜻 |
|---|---|---|
| `CONCERT_ID` | `ZPERF` | 공연 코드 |
| `PERF_NO` | `ZPERF` | 회차 번호 |
| `PERF_DATE` | `ZPERF` | 공연 날짜 |
| `ARTIST` | `ZCONCERT` | 아티스트 |
| `VENUE` | `ZCONCERT` | 공연장 |

회차만 있던 목록에 아티스트와 공연장이 함께 붙어 나온다. 이 다섯이 이 챕터가 계속
전제하는 `ZV_PERF`의 구성이다. [실습 레슨](CH14-L09.html)의 조회 코드도 이 구성을 그대로 읽는다.

### 직접 만들어 보기 (SE11)

1. `SE11` → **View** 칸에 `ZV_PERF`를 넣고 Create → 종류는 **Database view**.
   (View 이름은 테이블과 마찬가지로 **16자까지**다. 길게 지으면 저장 자체가 안 된다.)
2. **Tables** 칸에 `ZPERF`, `ZCONCERT` 순으로 적는다. 먼저 적은 쪽이 기준 테이블이다.
3. **Relationships** 버튼을 누른다. 두 테이블 사이에 이미 걸어 둔 [[Foreign Key]]
   ([Chapter 9 · 실습에서 건 그 관계](CH09-L09.html))를 찾아 조인 조건을 자동으로 채워 준다.
4. **View Flds** 탭에서 Table Fields 버튼으로 위 표의 다섯 필드를 고른다.
5. 저장하고 패키지를 지정한 뒤 **활성화**한다. 활성화해야 DB에 SQL View가 생겨 `SELECT`가 통한다.

> 💡 조인 조건 줄을 보면 우리가 지정한 `CONCERT_ID` 말고 **`MANDT`도 함께** 들어가 있다.
> 두 테이블 다 client별로 데이터가 갈리는 테이블이라 SE11이 클라이언트 대응 줄을 자동으로
> 넣어 준다([Chapter 8 · client 자동 종속](CH08-L01.html)). 우리가 신경 쓸 조건은 `CONCERT_ID` 하나다.

만든 View는 프로그램에서 테이블처럼 읽는다.

```abap
DATA: gt_perf TYPE STANDARD TABLE OF zv_perf,
      gs_perf TYPE zv_perf.

SELECT * FROM zv_perf
  INTO TABLE gt_perf.

LOOP AT gt_perf INTO gs_perf.
  WRITE: / gs_perf-concert_id, gs_perf-perf_no,
           gs_perf-perf_date,  gs_perf-artist,
           gs_perf-venue.
ENDLOOP.
```

프로그램은 JOIN 조건을 **모르는 채로도** 결합된 결과를 읽는다. 조인 정의가 View 안에
들어 있기 때문이다.

> ⚡ 이 예제는 배우는 자리라 View를 통째로 읽었다. 실제 리포트에서는 **조건과 필드를 좁혀
> 읽는 게 기본**이다. 조건 없는 `SELECT *`는 행이 수십만인 테이블에서 그대로 응답 시간이 된다.

> 📌 중요한 제한 둘. ① Database View는 **데이터를 새로 저장하지 않는다**(결과는 basis
> table에서 읽힌다). ② 여러 테이블 View는 **inner join**이라, 공연 코드는 있는데 공연
> 마스터가 없으면 그 행은 **결과에서 사라진다**.

> ⚠️ 이름이 주는 오해 하나. 다른 데이터베이스에서 `CREATE VIEW`로 하던 일을 여기서 다 할 수는
> 없다. classic Database View가 하는 일은 **basis table을 inner join으로 붙이고 필드를 고르는
> 것**까지다. 계산 컬럼·합계·outer join·여러 조회 결과 합치기는 대상이 아니다.
> (**Selection Conditions** 탭에서 "상태가 `N`인 행만" 같은 **고정 조건**은 걸 수 있다. 다만
> 프로그램마다 달라지는 조건은 View가 아니라 `SELECT`의 `WHERE`에 거는 게 맞다.)

## View vs 코드 JOIN — 책임 위치가 다르다

| 비교 | Database View | 코드 JOIN |
|---|---|---|
| 정의 위치 | SE11의 DDIC 객체 | ABAP 프로그램 소스 |
| 재사용 | 여러 프로그램이 같은 View | 프로그램마다 작성 |
| 결합 | DDIC에 고정된 inner join | inner·left outer 등 선택 |
| 변경 영향 | View 쓰는 프로그램 전체 | 해당 프로그램 중심 |
| 실행 속도 | 결국 DB가 같은 JOIN을 수행 | 결국 DB가 같은 JOIN을 수행 |
| 적합 | 안정적인 공통 조회 관점 | 조건·결합이 매번 다른 조회 |

표의 다섯째 줄이 중요하다. **둘 중 무엇이 더 빠른가는 선택 기준이 아니다.** 어느 쪽이든
DB가 같은 조인을 수행하기 때문이다. 갈리는 지점은 "이 결합을 여러 프로그램이 공유하는가,
아니면 이 프로그램에서만 쓰는가"다.

아래에서 같은 결과가 "코드 JOIN"과 "Database View" 두 정의에서 나오는 걸 확인하고,
마스터가 빠졌을 때 inner join에서 행이 어떻게 빠지는지 직접 보자.

## 흔한 실수와 점검

- **테이블 복사본으로 오해** → View엔 데이터가 없다. basis table이 바뀌면 결과도 바뀐다.
- **모든 JOIN을 View로** → 조건이 매번 다르거나, 누락 행도 보존해야 하거나, 계산
  컬럼이 필요하면 View가 답이 아니다. 한쪽만 있어도 남기려면 코드의 **LEFT OUTER
  JOIN**([Chapter 13 · LEFT OUTER JOIN](CH13-L02.html))이나 별도 검증 리포트를 쓴다.
- **View Field 과다 노출** → View Field는 외부 프로그램의 **구조 계약**이다. 실제 읽는
  필드만 노출한다(나중에 제거하면 쓰던 프로그램이 깨진다).

## 정리

- [[Database View]]는 반복 JOIN을 DDIC의 공통 조회 관점으로 옮기는 도구다.
- 여러 테이블이면 **inner join** 성격이다. 짝 없는 행은 빠진다.
- 저장소가 아니며, 누락 보존·복잡 계산의 만능 도구도 아니다.

여러 테이블을 합치는 View는 봤다. 그럼 **한 테이블에서 필요한 필드만** 좁게 보여 주는 View는? → 다음 레슨(Projection View).
