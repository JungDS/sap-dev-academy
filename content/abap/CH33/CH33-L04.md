## 📄 "엑셀 그대로 넣어 주세요"

현업은 자주 엑셀로 데이터를 준다. 신규 예매 목록, 좌석 일괄 변경 대상, 고객 명단…
그리고 요청은 늘 같다. "이거 그대로 SAP에 넣어 주세요."

여기서 초보 개발자가 하는 착각이 **"엑셀을 읽었다 = 등록해도 된다"**이다. 외부 파일은
신뢰할 수 없다. 필수값이 비어 있고, 숫자처럼 보이는 문자가 있고, 날짜 형식이 제각각이고,
같은 key가 두 번 있고, 이미 SAP에 있는 데이터가 섞여 있다. **Excel Upload의 본질은 파일
읽기가 아니라 검증 관문이다.**

## 읽고 — 나누고 — 검증한다

classic 정석은 엑셀을 **탭 구분 텍스트(또는 CSV)**로 저장하게 한 뒤, SAP GUI가 실행 중인
**PC의 파일**을 읽어 한 줄씩 파싱하는 것이다.

```abap
DATA gt_raw TYPE TABLE OF string.

cl_gui_frontend_services=>gui_upload(
  EXPORTING  filename = gv_path
             filetype = 'ASC'
  CHANGING   data_tab = gt_raw
  EXCEPTIONS OTHERS   = 1 ).

IF sy-subrc <> 0.
  MESSAGE '파일을 읽지 못했습니다.' TYPE 'E'.
ENDIF.

LOOP AT gt_raw INTO DATA(gv_line).
  IF sy-tabix = 1.
    CONTINUE.                        " 1행 = 헤더(컬럼 제목) 건너뜀
  ENDIF.

  SPLIT gv_line AT cl_abap_char_utilities=>horizontal_tab
    INTO DATA(gv_concert) DATA(gv_customer) DATA(gv_seats).

  " 행 단위 검증 → 통과한 행만 내부 테이블에 APPEND
ENDLOOP.
```

- `cl_gui_frontend_services=>gui_upload` — **사용자 PC**의 파일을 읽는다. 서버 파일을
  읽는 `OPEN DATASET`([다음 레슨](CH33-L05.html))과 대상 위치가 다르다. background
  job은 사용자 PC에 접근할 수 없다는 점이 두 방식을 가르는 기준이다.
- `SPLIT ... AT ... INTO` — 한 줄을 구분자로 나눈다([Chapter 4 · 문자열](CH04-L02.html)).
  탭 구분이면 `cl_abap_char_utilities=>horizontal_tab`. CSV는 따옴표·쉼표 escape 규칙이
  복잡해 단순 `SPLIT AT ','`가 항상 안전하진 않다. 파일 형식을 먼저 못 박는 게 낫다.

행 단위 검증에서 볼 것들:

| 검증 | 예 |
|---|---|
| 필수값 | 공연 ID·고객명이 비었나 |
| 타입·범위 | 좌석 수가 숫자인가, 1 이상인가 |
| 중복 key | 같은 예매가 파일 안에 두 번 있나 |
| 참조 존재 | `C001`이 실제 있는 공연인가 |

> 💡 `.xls`를 셀 단위로 직접 읽는 옛 표준 함수 `ALSM_EXCEL_TO_INTERNAL_TABLE`도
> 현장에서 만난다(행·열·값으로 반환). 다만 신형 포맷·대량 처리엔 탭 텍스트 방식이나
> `abap2xlsx` 같은 검증된 라이브러리 정책을 확인하는 편이 안정적이다.

## 어떻게 확인하는가

1. **파일 형식 합의** — 진짜 엑셀 바이너리인지, CSV인지, 탭 텍스트인지. "확장자가
   xlsx"라는 말로 처리 방식을 정하지 않는다.
2. **헤더 처리** — 1행이 제목인지 데이터인지. 제목을 데이터로 읽으면 첫 행부터 타입
   오류, 최악은 잘못된 값 등록.
3. **검증만 먼저(dry run)** — 저장 없이 오류 목록부터 보여 주는 "검증만 실행"을 둔다.
   대량 파일은 한 번 등록되면 되돌리기 어렵다.
4. **오류는 행 번호와 사유로** — "데이터 오류"가 아니라 "12행: 좌석 수가 숫자가 아님"
   처럼, 사용자가 파일을 **고칠 수 있는** 메시지를 돌려준다.
5. **성공/실패 분리 정책** — 전체를 한 LUW로 묶을지, 성공 행만 등록하고 실패 행만
   돌려줄지 업무와 함께 정한다.

## 업로드·검증 체험

원본(헤더+정상+오류+중복)을 올려 **검증만 실행**으로 오류 목록을 먼저 보고, 성공 행만
등록해 보라.

## 흔한 실수와 점검 🚧

- **업로드 직후 바로 등록** → 검증 없이 BAPI/DML을 부르면 대량 Return 오류나
  "일부 성공" 상태가 된다. 관문이 먼저다.
- **엑셀 화면 값 = 파일 값이라는 믿음** → 엑셀은 날짜·앞자리 0·큰 숫자를 표시 형식으로
  바꿔 보여 준다. 검증은 파일의 **원본 문자열** 기준으로.
- **PC 파일 ↔ 서버 파일 혼동** → `gui_upload`는 대화형 GUI 세션 전용. 자동 배치 요구가
  나오면 서버 파일 인터페이스([다음 레슨](CH33-L05.html))로 설계를 바꾼다.
- **행 번호 없는 오류 피드백** → 사용자는 몇 행을 고쳐야 하는지 모른다. 행 번호+원본
  값+사유가 한 세트.

## 정리 📌

- Excel Upload = **검증 관문**. 읽기(`gui_upload`)와 나누기(`SPLIT`)는 시작일 뿐.
- 루틴: 형식 합의 → 헤더 skip → 행 검증(필수·타입·중복·참조) → dry run → 성공/실패
  분리 등록 → 고칠 수 있는 오류 피드백.
- `gui_upload`는 PC 파일 전용. 자동화가 필요하면 서버 파일로.

---

사람이 버튼을 눌러 올리는 파일은 여기까지. 이제 **서버에 쌓이는 파일을 야간 배치가
자동으로** 읽고, 실패를 보관하고, 다시 처리하는 운영 구조로 간다.
