## ⌨️ API가 없고 화면만 있을 때

오래된 표준 업무 중에는 쓸 만한 BAPI가 없고 **트랜잭션 화면만** 있는 경우가 있다. 수천
건을 사람이 손으로 입력할 수는 없으니, 프로그램이 **사용자의 화면 입력을 흉내** 내야
한다. 그 classic 수단이 [[BDC]](Batch Data Communication)다.

먼저 못을 박자. BDC는 "편한 자동화 도구"가 아니라 **API가 없을 때 조심해서 쓰는 레거시
대응 수단**이다. 화면 번호·필드 이름·OK code에 의존하므로, 표준 화면이 바뀌거나 권한·
customizing으로 흐름이 달라지면 깨진다. BAPI가 있으면 언제나 BAPI가 먼저다.

## BDCDATA — 화면 입력의 악보

`BDCDATA` 테이블에는 화면 진입과 필드 입력이 **순서대로** 쌓인다. 세 종류의 행이 있다.

| 행 종류 | 핵심 필드 | 뜻 |
|---|---|---|
| 화면 시작 | `program`·`dynpro`·`dynbegin = 'X'` | 어느 프로그램의 어느 화면으로 들어가나 |
| 필드 입력 | `fnam`·`fval` | 어떤 화면 필드에 어떤 값을 넣나 |
| OK code | `fnam = 'BDC_OKCODE'`·`fval = '=SAVE'` 등 | Enter·저장·뒤로 같은 사용자 동작 |

```abap
DATA gt_bdc TYPE TABLE OF bdcdata.
DATA gt_msg TYPE TABLE OF bdcmsgcoll.
DATA gs_opt TYPE ctu_params.

" 화면·필드·동작을 차곡차곡(헬퍼 FORM으로)
PERFORM fill_bdc USING 'X' 'SAPMZBOOK'     '0100'.    " 화면 진입
PERFORM fill_bdc USING ' ' 'ZBOOK-CONCERT' 'C001'.    " 필드 입력
PERFORM fill_bdc USING ' ' 'ZBOOK-SEATS'   '2'.
PERFORM fill_bdc USING ' ' 'BDC_OKCODE'    '=SAVE'.   " 저장 동작

gs_opt-dismode = 'N'.                " 화면 표시 모드
gs_opt-updmode = 'S'.                " update 방식

CALL TRANSACTION 'ZBK01'
  USING gt_bdc
  OPTIONS FROM gs_opt
  MESSAGES INTO gt_msg.
```

- **`dismode`(MODE)**: `A`=모든 화면 보며 실행(개발 확인용) · `E`=오류 때만 화면 ·
  `N`=무화면(운영 배치). 개발 중 `A`→`E`→운영 `N` 순서로 검증한다.
- **`updmode`(UPDATE)**: `S`(synchronous)는 update가 끝난 뒤 결과를 받아 확인이
  확실하다. 운영 인터페이스에서 아무 생각 없이 두면 안 되는 옵션이다.
- **`MESSAGES INTO`**: 실행 중 화면이 낸 메시지가 `BDCMSGCOLL` 테이블로 모인다.
  **BDC 실패 원인은 대부분 이 메시지에 있다.** 빼먹으면 운영 지원이 불가능해진다.

## 두 실행 방식 — Call Transaction vs Session

| 방식 | 성격 | 어울리는 곳 |
|---|---|---|
| **Call Transaction** | 즉시 실행하고 결과를 바로 받음 | 온라인 처리·소량·즉시 판정 |
| **Session Method** | 큐(세션)에 쌓아 두고 나중에 실행 | 대량·야간 배치·실패 건 재처리 |

```abap
CALL FUNCTION 'BDC_OPEN_GROUP'
  EXPORTING client = sy-mandt
            group  = 'ZBOOK'.

CALL FUNCTION 'BDC_INSERT'
  EXPORTING tcode     = 'ZBK01'
  TABLES    dynprotab = gt_bdc.

CALL FUNCTION 'BDC_CLOSE_GROUP'.
" → SM35에서 세션을 실행하고, 실패 건은 화면으로 재처리
```

`SM35`는 세션 큐의 관제탑이다. 실패한 건을 골라 화면 모드로 다시 돌려 원인을 눈으로
확인하고 고칠 수 있다. 대량 인터페이스에서 "실패 건 재처리"가 필요하면 Session이
자연스럽다.

## 어떻게 확인하는가

1. **API 우선순위** — BAPI·공개 API가 있으면 BDC를 접는다. BDC는 장기 운영 비용이 크다.
2. **`SHDB` 녹화** — 손으로 처음부터 쓰지 말 것. `SHDB`(Transaction Recorder)로
   트랜잭션을 녹화하면 실제 화면 번호·필드 이름·OK code가 담긴 뼈대 코드가 나온다.
   그걸 시작점으로 입력값·메시지·예외 처리를 다듬는다.
3. **모드 단계 검증** — `A`로 흐름 확인 → `E`로 오류 화면 확인 → `N`으로 운영 검증.
4. **메시지·재처리 설계** — `BDCMSGCOLL`의 메시지 ID·번호·변수 + 입력 key를 로그로.
   실패 건을 별도 테이블에 둘지, Session으로 넘겨 `SM35`에서 볼지 정한다.

## 직접 녹화해 보기

"다음 동작"으로 `BDCDATA`가 한 줄씩 쌓이는 걸 보고 실행해 보라. **필수 필드를 빠뜨린
채** 실행하면 `BDCMSGCOLL`에 어떤 오류가 남는지, Session으로 보내면 어떻게 큐에 쌓이는지도.

## 흔한 실수와 점검 🚧

- **BDC를 신규 개발 기본 수단으로** → 마지막 선택지다. API 먼저.
- **화면 흐름이 항상 같다고 가정** → 같은 트랜잭션도 권한·customizing·popup에 따라
  달라진다. 테스트는 화면 변형을 넓게 잡는다.
- **`MESSAGES INTO` 생략** → `sy-subrc`만 보면 *어느 화면의 어떤 메시지*로 실패했는지
  알 길이 없다.
- **update 모드 방치** → 결과 확인이 필요한 인터페이스에서 update 방식을 모르고 돌리면
  "성공 판정했는데 저장 안 됨" 같은 유령 장애를 만난다.
- **정상 한 건만 테스트** → 운영에선 popup·경고·권한·숨은 필드로 깨진다.

## 정리 📌

- BDC = 화면 입력을 `BDCDATA`(화면 시작·필드·OK code 행)로 악보처럼 쌓아 실행하는
  레거시 수단. 실행은 `CALL TRANSACTION ... USING` 또는 Session(`SM35`).
- 실무 세트: `SHDB` 녹화 → `MODE`/`UPDATE` 단계 검증 → `MESSAGES INTO`로
  `BDCMSGCOLL` 수집 → 실패 건 재처리 설계.
- 그리고 항상: **BAPI가 있으면 BAPI가 먼저.**
