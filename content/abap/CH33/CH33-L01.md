## 🌐 시야를 시스템 밖으로

지금까지 우리는 우리 프로그램 안에서 데이터를 다뤘다. 그런데 실무 개발자의 일감 절반은
**바깥**에서 온다. 외부 쇼핑몰 주문을 SAP에 넣고, 다른 시스템에서 예매 현황을 조회해 오고,
현업이 준 엑셀을 검증해 등록하고, 서버에 쌓이는 파일을 야간 배치로 처리한다.

이 챕터에서 가장 먼저 버려야 할 생각이 하나 있다. **"호출이 성공하면 인터페이스도
성공"이라는 생각.** 인터페이스의 성공은 함수 호출이 끝났다는 뜻이 아니다. 받은 데이터가
유효하고, 업무 규칙을 통과했고, **저장 확정 여부가 올바르게 결정**되었고, 실패 이유가
로그에 남았고, 운영자가 재처리할 수 있어야 성공이다.

첫 주제는 표준 데이터 쓰기다. [Chapter 25 · DML](CH25-L01.html)에서 "표준 테이블 직접
DML 금지"를 배웠다. 판매오더 하나만 해도 header·item·일정·파트너·가격·상태가 얽혀 있어,
테이블 하나를 직접 `UPDATE`하면 당장은 들어간 듯 보여도 **후속 테이블과 상태가 깨진다**.

## BAPI — 표준이 공개한 진입점

[[BAPI]](Business Application Programming Interface)는 SAP 업무 객체의 데이터와
프로세스를 외부·고객 프로그램이 쓸 수 있게 공개한 **표준 인터페이스**다. 보통
Remote-Enabled Function Module로 구현되며 이름은 `BAPI_<업무객체>_<동작>` 꼴이다
(예: 판매오더 생성 `BAPI_SALESORDER_CREATEFROMDAT2`).

그런데 BAPI는 호출이 끝이 아니다. 결과를 **Return 메시지**로 돌려주고, 그걸 읽고
저장을 확정할지 취소할지는 **호출한 우리 몫**이다.

```abap
DATA gt_return TYPE TABLE OF bapiret2.

CALL FUNCTION 'BAPI_..._CREATE'
  EXPORTING is_header = gs_header
  TABLES    return    = gt_return.

" Return 판정 — 오류(E/A)가 하나라도 있나?
IF line_exists( gt_return[ type = 'E' ] )
   OR line_exists( gt_return[ type = 'A' ] ).
  CALL FUNCTION 'BAPI_TRANSACTION_ROLLBACK'.
ELSE.
  CALL FUNCTION 'BAPI_TRANSACTION_COMMIT'
    EXPORTING wait = abap_true.
ENDIF.
```

`BAPIRET2`는 BAPI가 결과 메시지를 담아 주는 표준 구조다.

| 필드 | 뜻 | 실무에서 |
|---|---|---|
| `type` | 메시지 유형 | `E`·`A`=실패. `W`=경고(정책 필요). `S`=성공 안내 |
| `id`·`number` | 메시지 클래스·번호 | 원문·번역을 찾는 key |
| `message` | 조립된 메시지 텍스트 | 운영 로그·사용자 피드백 |
| `message_v1`～`v4` | 메시지 변수 | 원인 key·필드·값 추적 |

- 많은 BAPI는 **스스로 COMMIT하지 않는다**. `BAPI_TRANSACTION_COMMIT`을 불러야 확정.
  `wait = abap_true`는 update가 끝날 때까지 기다리는 옵션이다(직후에 로그를 쓰거나
  재조회한다면 기다리는 편이 확실하다). [SAP LUW](CH25-L03.html) 감각 그대로다.
- **`W`(경고) 정책을 정해야 한다.** 모든 경고가 통과는 아니다. 가격 조건 누락·한도 관련
  경고가 업무상 치명적이면 실패로 처리한다. 정책이 없으면 같은 입력이 배치에선 성공,
  화면에선 실패처럼 흔들린다.

## 어떻게 확인하는가

1. **BAPI 문서부터** — `SE37`에서 필수 입력·Return 구조(단일/테이블)·commit 필요 여부를
   확인한다. "아는 예제와 비슷하겠지"가 사고의 시작이다.
2. **오류 케이스도 테스트** — 정상 입력만 넣으면 commit 경로만 검증된다. 없는 고객·필수값
   누락·중복 key를 일부러 넣어 Return에 어떤 메시지가 오는지 본다.
3. **commit 뒤 재조회** — 생성된 문서 번호로 표준 조회·SELECT로 확인한다. "호출
   `sy-subrc = 0`"과 "업무 데이터 확정"은 다른 말이다.
4. **실패 로그** — 입력 key·BAPI 이름·Return 전체·commit/rollback 결정·시각을 남긴다.
   운영자가 개발자 없이도 원인을 읽을 수 있어야 한다.

## 흔한 실수와 점검 🚧

- **Return 안 보고 COMMIT** → 오류 메시지를 무시하고 확정하면 일부만 반영된 깨진 상태가
  남는다. 판정이 먼저, 확정은 그다음.
- **COMMIT 누락** → "호출은 성공했는데 데이터가 없어요"의 단골 원인. 단, commit 정책은
  BAPI마다 다를 수 있으니 문서를 확인한다.
- **경고 정책 부재** → `W`를 항상 통과시킬지, 특정 메시지는 실패로 볼지 프로젝트 기준을
  문서로 정한다.
- **BAPI = 만능 공개 계약으로 오해** → classic에선 직접 DML보다 훨씬 안전하지만, ABAP
  Cloud 관점에선 그 BAPI가 [Released API](CH24-L08.html)인지가 별도 판단 기준이다.

## 정리 📌

- 표준 데이터 쓰기는 직접 DML이 아니라 **BAPI**로. 이름은 `BAPI_객체_동작` 꼴.
- 실무의 중심은 호출문이 아니라 **Return 판정**: `E`/`A` → ROLLBACK, 깨끗하면 COMMIT
  (`wait`), `W`는 업무 정책으로.
- 확인 루틴: 문서 → 오류 케이스 테스트 → commit 후 재조회 → 실패 로그.
