## 정형 화면을 넘어서

[Selection Screen UI 구성](CH15-L09.html)까지의 선택화면(PARAMETERS·SELECT-OPTIONS)은
SAP이 정해 준 틀이다. 조회 조건을 빠르게 받기엔 좋다.

그런데 이런 화면을 떠올려 보자. 공연을 고르고, 좌석 수를 넣는다. **예매** 버튼을 누르면
검증이 돌고, **뒤로** 버튼을 누르면 화면이 닫힌다. 이렇게 **내가 직접 설계한 업무 화면**은
선택화면만으로는 만들 수 없다.

그 화면이 [[Dynpro]](Dynamic Program — 화면 하나의 레이아웃 + 흐름 로직)이고, 화면 중심
프로그램이 [[Module Pool]]이다. 사실 우리가 써 온 선택화면도 **특수한 형태의 Dynpro**였다 —
이제 Screen Painter로 화면을 직접 그리는 일반 Dynpro로 넘어간다.

> ℹ️ Dynpro는 **classic SAP GUI** 화면 기술이다. 기존 시스템 유지보수와 classic 화면
> 이해를 위해 배운다(최신 UI는 Fiori/UI5). 숨기지 않고 경계를 분명히 해 둔다.

## 리포트 vs Module Pool

> 🪧 아래 표에 **PBO/PAI**와 **OK_CODE**가 먼저 나온다. PBO/PAI는 바로 다음 절에서,
> OK_CODE는 [화면 요소 — 입력·버튼·체크박스·라디오·드롭다운](CH16-L03.html)과
> [PAI 처리 흐름 — OK_CODE와 화면 떠나기](CH16-L07.html)에서 풀이한다. 지금은
> "리포트와 이름부터 다르구나" 정도로만 훑고 지나가자.

| | Report(실행형) | Module Pool |
|---|---|---|
| 시작 | `REPORT`·F8 | **T-code로 실행**(정식 진입점) |
| 중심 흐름 | 이벤트(`START-OF-SELECTION`…) | 화면 sequence · **PBO/PAI** |
| 화면 | 선택화면 자동 생성 | **Screen Painter로 직접 설계** |
| 사용자 행동 | 실행·variant·조건 입력 | 버튼·메뉴·입력 필드·탭·컨트롤 |
| 대표 실수 | 이벤트 위치 혼동 | T-code/시작 화면/OK_CODE 누락 |

- Module Pool은 **실행할 T-code가 반드시 있어야** 한다([T-code 생성 기초 (SE93)](CH01-L07.html)에서
  본 T-code가, 이번엔 **필수**다). `SE80`(또는 `SE51` Screen Painter)에서 화면을 그린다.
- "T-code로만"은 **사용자가 여는 정식 진입점**이 T-code라는 뜻이다. 기술적으로는 다른 ABAP
  프로그램이 화면을 직접 부르는 문장(`CALL SCREEN`)도 있지만, 배포된 화면 프로그램을 업무
  사용자가 실행하는 길은 T-code다. 지금은 이름만 알아 두면 된다.

> 📁 **소스는 한 파일이 아니다.** `SE80`에서 Module Pool을 만들면 소스가 여러 **include**로
> 나뉜다. 선언은 `...TOP`, PBO 모듈은 `...O01`, PAI 모듈은 `...I01`, FORM은 `...F01` 같은
> 식이다. 이 챕터의 코드도 실제로는 이 조각들에 나뉘어 들어간다. 만드는 순서는
> [실습 — 예매 입력 화면 (Dynpro)](CH16-L10.html)에서 번호대로 따라 한다.

## 화면의 두 박자 — PBO / PAI

화면 하나가 뜨고 처리되는 흐름은 **두 박자**다.

- **PBO**(Process Before Output) — 화면을 **그리기 직전**(초기값·상태 준비).
- **PAI**(Process After Input) — 사용자가 **버튼·Enter를 누른 뒤**(입력 처리).

이 두 박자는 화면이 닫힐 때까지 **반복**된다. "위에서 아래로 한 번 실행"이 아니라,
**화면이 보이고 → 사용자가 반응하고 → 다시 화면이 준비되는 순환**으로 생각해야 한다.

> 🧩 다른 화면 개발(Swing·WPF·React 등)을 해 본 적 있다면 이렇게 겹쳐 볼 수 있다. PBO는
> 화면을 그리기 직전에 도는 **준비 단계**, PAI는 사용자의 행동을 받아 처리하는 **이벤트
> 처리 단계**에 가깝다. 처음 듣는 이야기라면 이 줄은 건너뛰어도 된다.

## 흔한 실수와 점검

- **T-code 없이 실행** → Module Pool은 리포트처럼 F8로 못 연다. 사용자가 여는 길은
  T-code다(`SE93`로 생성).
- **리포트 이벤트 기대** → `START-OF-SELECTION`이 아니라 PBO/PAI 흐름이다.
- **PBO/PAI를 `AT SELECTION-SCREEN OUTPUT`/`AT SELECTION-SCREEN`과 같다고 치환** → "전/후"
  감각은 비슷해도, Dynpro flow logic + dialog module은 **다른 구조**다.
- **화면 번호 `0100`을 규칙으로 오해** → 0100은 관례적 예시일 뿐, 시스템이 꼭 0100만 쓰는 건 아니다.

## 정리

- **Module Pool**은 화면이 중심인 프로그램이다. 리포트처럼 F8로 실행하지 않고, 사용자는
  **T-code**로 시작 화면을 연다.
- 화면 하나는 **PBO**(그리기 직전 준비)와 **PAI**(사용자 행동 뒤 처리)라는 **두 박자**로
  돌아가고, 이 두 박자는 화면이 닫힐 때까지 **순환**한다.
- 화면은 [[Dynpro]]라 부르고, `SE80`(또는 `SE51` Screen Painter)에서 직접 그린다.
