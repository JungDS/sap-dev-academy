## 🎫 필요한 예매만

[Chapter 11 · SALV](CH11-L01.html)에서 예매 목록 **전체**를 표로 봤다. 하지만 실제
업무에서는 "특정 공연·특정 상태"만 필요할 때가 더 많다. 강호동 담당자가 공연 C001의
예약 건만 보고 싶다면, 전체 6건을 띄워 놓고 눈으로 찾는 방식은 곧 한계에 부딪힌다.

이번 실습은 이 챕터에서 배운 [[Range Table]] 지식을 콘서트 예매 앱에 연결한다.
사용자가 공연ID·상태를 입력하면, 프로그램은 그 조건을 `WHERE ... IN`에 연결해
**필요한 예매만** 가져온 뒤 SALV로 보여 준다.

> 🔎 **[선행 사용]** 아래 코드에는 아직 정식으로 안 배운 조각이 섞여 있다. `TABLES`와
> [[START-OF-SELECTION]], 그리고 SALV를 띄우는 `TYPE REF TO`·`TRY`/`CATCH` 묶음이다.
> **분석하거나 외울 필요 없다.** 이번에 읽을 곳은 `SELECT-OPTIONS` 두 줄과
> `WHERE ... IN` 두 줄, 딱 네 줄이다. 나머지는 [Chapter 11 · SALV](CH11-L02.html)와
> [Chapter 15 · 이벤트와 선택화면](CH15-L01.html)에서 정식으로 배운다.

```abap
TABLES zbooking.

SELECT-OPTIONS: so_conc FOR zbooking-concert_id,
                so_stat FOR zbooking-status.

DATA: gt_book TYPE TABLE OF zbooking,
      go_alv  TYPE REF TO cl_salv_table.

START-OF-SELECTION.
  SELECT * FROM zbooking INTO TABLE gt_book
    WHERE concert_id IN so_conc
      AND status     IN so_stat.

  TRY.
      cl_salv_table=>factory(
        IMPORTING r_salv_table = go_alv
        CHANGING  t_table      = gt_book ).
      go_alv->get_functions( )->set_all( abap_true ).
      go_alv->display( ).
    CATCH cx_salv_msg.
      MESSAGE '예매 목록 ALV 생성 실패' TYPE 'I'.
  ENDTRY.
```

여기서 핵심은 SALV가 아니라 위에서 **이 두 줄**이다.

```abap
SELECT-OPTIONS: so_conc FOR zbooking-concert_id,
                so_stat FOR zbooking-status.
```

그리고 조건이다. 두 줄 사이는 `AND`라 **둘 다** 만족하는 예매만 남는다.

```abap
WHERE concert_id IN so_conc
  AND status     IN so_stat.
```

> 상태값은 업무 의미가 있다 — **`N` = 예약, `C` = 취소**. 이 두 글자를 어디에 정해 두는지
> 가물가물하면 [Chapter 03 · Domain](CH03-L01.html)을 다시 열어 Domain의 **고정값**을 확인하자.
> `SELECT *`는 [WHERE … IN](CH12-L03.html)에서 말한 학습용 형태 그대로다.

조건을 바꾸면 결과는 얼마나 줄어들까? `sy-subrc`·`sy-dbcnt`까지 눈으로 확인해 보자.

## 직접 해 볼 과제

먼저 위젯의 예제 버튼을 **왼쪽부터 차례로** 눌러 본다.

1. **`전체 (빈 범위)`** → 6건 전부 나오는지 확인(빈 range는 true).
2. **`공연 C001만 (EQ)`** → C001 예매만 남는지 확인.
3. **`공연 C002~C003 (BT)`** → `BT`는 **사이**다. 결과가 1번(전체)보다 **줄어드는지** 보고,
   몇 건이 왜 걸리는지 [EQ / BT / CP 옵션 이해](CH12-L05.html)의 `BT` 설명으로 확인해 보기.
4. **`예약만 (status=N)`** → N 상태만 남는지 확인.
5. **`취소 제외 (E)`** → C 상태가 빠지는지 확인. 포함(I) 행이 하나도 없는데 결과가
   나오는 이유는 [Multiple Selection과 Include/Exclude](CH12-L04.html)의 평가 규칙 **3번**이다.

여기까지가 눌러서 확인하는 과제다. 이제 직접 써 볼 차례다.

6. **(직접 써 보기)** 좌석 수 조건을 하나 더 붙여 보자. 위 코드에 `SELECT-OPTIONS` **한 줄**
   (`so_seat FOR zbooking-seats`)을 추가하고, `WHERE`에도 **한 줄**을 더해 좌석 수로도 걸러
   낼 수 있게 만든다. 조건이 셋이 되면 `AND`는 몇 개가 필요할까? 위젯 말고 실제 코드에
   직접 써 보는 과제다.
7. **(직접 써 보기)** 화면 없이 코드로도 만들어 보자. `so_stat` 자리를
   [Selection Table 직접 조작 기초](CH12-L06.html)의 `TYPE RANGE OF` + `APPEND`로 바꿔 쓰면,
   "취소는 항상 제외"를 사용자 입력 없이 고정할 수 있다.
8. **(도전)** `+ 범위 행 추가`로 `I` `CP` `C*` 행을 직접 만들어 보고, 패턴 조건이 어떤 예매를
   남기는지 설명해 보기.

## 흔한 실수와 점검

- **빈 SELECT-OPTIONS** → 비우면 전체 조회(빈 range는 모두 통과). 막고 싶으면
  [Chapter 15 · 이벤트와 선택화면](CH15-L01.html)의 입력 필수 검증을 쓴다.
- **두 조건을 OR로 오해** → 코드에 `AND`가 있으니 공연·상태 **둘 다** 만족해야 한다.
- **0건과 SALV 오류 혼동** → 조회가 0건이어도 SALV는 **빈 표**를 띄운다. SALV 생성
  실패(`cx_salv_msg`)와는 다른 문제다.
- **classic 유지** → `IN so_conc`는 classic range다. `@`를 붙이는 요즘 방식은
  [Chapter 19 · Modern Open SQL](CH19-L01.html)에서 배운다.

## 정리

- [[SELECT-OPTIONS]]가 공연·상태 조건을 selection table로 만든다.
- `WHERE concert_id IN so_conc AND status IN so_stat`는 **두 조건을 모두** 만족하는 예매만 조회한다.
- 빈 range는 전체 통과가 될 수 있으니 주의한다.
- [Chapter 11 · SALV](CH11-L01.html) 표시와 결합하면 **조건 입력형 예매 목록 리포트**가 된다.
