## 셋 중 무엇을

여러 데이터를 합치는 길은 셋이다. DB의 [[JOIN]], [[FOR ALL ENTRIES]](FAE),
그리고 ABAP에서 읽어와 직접 맞추기. 상황별로 정리한다.

## 한눈에

| 방법 | 일을 누가 | 적합 |
|---|---|---|
| **JOIN** | DB | 두 테이블을 키로 합쳐 한 번에 — 보통 1순위 |
| **FAE** | DB(1회 이상, 목록 크기·설정에 따라 나뉨) | 이미 메모리에 있는 목록 기준으로 조회 |
| **ABAP 루프** | 앱 서버 | 단순·소량, 또는 JOIN/FAE가 부적절할 때 |

## 원칙(직관)

- **가능하면 JOIN** — DB가 합치게 둔다(데이터 이동 최소).
- 합칠 대상이 **이미 Internal Table로 있으면** FAE(빈 테이블·중복 주의).
- **루프 안에서 `SELECT`** — 이 형태는 피한다. 성능을 무너뜨리는 대표적인 [[안티패턴]]이다.
  안티패턴은 "얼핏 자연스러워 보이지만 실제로는 문제를 만드는, 피해야 할 전형적인
  코드 모양"을 말한다.

## ABAP에서 직접 맞춘다면 — 두 가지 모양

같은 "ABAP에서 처리"라도 모양에 따라 결과가 하늘과 땅 차이다. 두 예제는 같은 그릇을 쓴다.

```abap
DATA: gt_flight   TYPE TABLE OF sflight,   " 앞 단계에서 읽어 둔 운항편
      gs_flight   TYPE sflight,
      gt_carr     TYPE TABLE OF scarr,
      gs_carr     TYPE scarr,
      gv_carrname TYPE scarr-carrname.
```

```abap
" ❌ 안티패턴 — 행마다 DB에 다녀온다
LOOP AT gt_flight INTO gs_flight.
  SELECT SINGLE carrname FROM scarr
    INTO gv_carrname
    WHERE carrid = gs_flight-carrid.
ENDLOOP.
```

```abap
" ✅ 권장형 — 필요한 목록을 미리 한 번에 읽어 두고, 메모리에서 맞춘다
SELECT carrid carrname FROM scarr
  INTO CORRESPONDING FIELDS OF TABLE gt_carr.

LOOP AT gt_flight INTO gs_flight.
  READ TABLE gt_carr INTO gs_carr
       WITH KEY carrid = gs_flight-carrid.
ENDLOOP.
```

위쪽은 운항편이 1만 건이면 DB에 1만 번 다녀온다. 아래쪽은 딱 두 번 읽고 나머지는 전부
메모리에서 끝난다([Chapter 06 · 단일 행 제어](CH06-L03.html)에서 배운 `READ TABLE`이 그
역할이다). [INNER JOIN 레슨](CH13-L01.html) 도입부에서 JOIN 없이 해 본 코드가 바로 이
권장형이었다. 그러니 "ABAP 루프는 무조건 나쁘다"가 아니라, **DB 왕복이 루프 안에 들어가
있느냐**가 갈림길이다.

다만 권장형도 공짜는 아니다. `READ TABLE ... WITH KEY`는 STANDARD 테이블을 첫 행부터
차례로 훑는 **순차 탐색**이라, 조회해 둔 목록이 크면 DB 왕복이 사라진 자리에 **메모리
탐색 비용**이 들어선다. 항공사 목록처럼 작은 표는 문제없지만, 큰 목록을 행마다 반복해서
찾는다면 [Chapter 06 · 단일 행 제어](CH06-L03.html)에서 배운 `SORT` 후 `BINARY SEARCH`나
SORTED·HASHED 테이블([Chapter 06 · Internal Table의 3속성](CH06-L02.html))로 탐색
자체를 빠르게 해 두자.

## 흔한 실수와 점검

- **LOOP 안에 SELECT** → 행마다 DB 왕복이다. 1만 건이면 1만 번 왕복한다. 목록 한 번에
  더해 행마다 한 번씩 더 조회한다고 해서 **N+1 문제**라고도 부른다(다른 언어·프레임워크
  에서도 같은 이름으로 통한다). 성능 문제는 보통 문법보다 이 **왕복 횟수**에서 시작하니,
  JOIN이나 FAE로 바꾸자.
- **무조건 JOIN** → 테이블을 너무 많이 붙인 JOIN도 DB에 부담이다. 필요한 테이블만 붙이고,
  결과가 정말 그만큼 필요한지 따져 보자.
