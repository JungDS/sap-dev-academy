## 이미 가진 목록으로 조회

화면이나 앞 단계에서 만든 **[[Internal Table]]의 값들**을 조건으로 DB를 조회하고 싶다.
[[FOR ALL ENTRIES]](FAE)가 그 도구다. 단, **함정이 많아 규칙을 지켜야** 한다.

## 기본형 (classic)

```abap
TYPES: BEGIN OF ts_carr,
         carrid TYPE sflight-carrid,
       END OF ts_carr.

TYPES: BEGIN OF ts_flight,
         carrid TYPE sflight-carrid,
         connid TYPE sflight-connid,
         fldate TYPE sflight-fldate,
       END OF ts_flight.

DATA: gt_carr   TYPE TABLE OF ts_carr,     " 조회 기준이 될 목록(드라이버)
      gt_flight TYPE TABLE OF ts_flight.   " 결과를 담을 그릇

" 전제: gt_carr에 조회하고 싶은 carrid들이 이미 담겨 있다
IF gt_carr IS NOT INITIAL.          " ← 필수!
  SELECT carrid connid fldate
    FROM sflight
    INTO CORRESPONDING FIELDS OF TABLE gt_flight
    FOR ALL ENTRIES IN gt_carr
    WHERE carrid = gt_carr-carrid.
ENDIF.
```

조건이 될 값을 담은 `gt_carr`를 **드라이버 테이블**이라고 부른다. DB는 이 목록의 값을
하나씩 `WHERE` 자리에 끼워 넣어 조회한 뒤, 나온 결과를 한 그릇에 모아 돌려준다.

## 반드시 지킬 규칙

- **빈 테이블 금지** → `gt_carr`가 비어 있으면 FAE는 **WHERE를 무시하고 전체
  조회**한다(대형 사고). 항상 `IS NOT INITIAL` 확인.
- **중복 자동 제거** → FAE 결과는 **완전히 같은 행(모든 필드 동일)**이 자동으로 제거된다. 그래서 기준 테이블에 같은 키를 두 번 넣어도 결과가 **2배로 늘지 않는다**(중복 건수가 의미 있는 집계라면 주의).
- **WHERE에 기준 테이블 필드** → `gt_carr-carrid`처럼 기준 테이블 필드를 조건에.

## 중복 제거가 무는 함정 — 읽을 필드에 키를 넣자

방금 본 "중복 자동 제거"는 편의 기능처럼 보이지만, **읽을 필드를 조금만 적으면**
멀쩡한 행끼리 같아 보여서 사라진다. 원래 다른 행이었는데 결과에서는 한 줄로 뭉개지는
것이다. 오류도 경고도 없다.

```abap
" 위험 — 예약 좌석 수만 읽으면 좌석 수가 같은 운항편들이 한 줄로 뭉개진다
SELECT seatsocc FROM sflight ...

" 안전 — 행을 구분해 주는 키를 함께 읽는다
SELECT carrid connid fldate seatsocc FROM sflight ...
```

읽을 필드에 **그 테이블의 키가 다 들어 있으면** 서로 다른 행은 절대 같아질 수 없으니
중복 제거에 지워지지 않는다. "건수가 왜 이것밖에 안 되지?" 싶을 때 가장 먼저 볼 곳이다.

## 드라이버는 미리 다듬어 둔다

드라이버 테이블에 같은 값이 여러 번 들어 있으면 DB는 같은 조회를 그만큼 반복한다.
결과는 어차피 중복 제거되니 **일만 늘고 얻는 건 없다.** 그래서 FAE 앞에 정리 두 줄을
넣는 것이 실무 습관이다.

```abap
SORT gt_carr BY carrid.
DELETE ADJACENT DUPLICATES FROM gt_carr COMPARING carrid.

IF gt_carr IS NOT INITIAL.
  SELECT ...
ENDIF.
```

`DELETE ADJACENT DUPLICATES`는 **붙어 있는** 중복만 지우니 `SORT`가 먼저다
([Chapter 06 · 명단 합치기와 중복 제거](CH06-L09.html)에서 배운 그 짝이다).

> 💡 **DB에 몇 번 다녀올까?** FAE는 드라이버 값을 한 묶음씩 나눠 조회할 수 있다. 목록이
> 짧으면 한 번에 끝나고, 길면 시스템 설정에 따라 여러 번으로 나뉜다. 몇 번이 될지는
> 코드만 보고 정해지지 않는다는 것만 기억하자. 드라이버를 작게 다듬는 일이 왜 이득인지도
> 여기서 나온다.

## 빈 목록일 때 무슨 일이? — 직접 실험

`gt_carr`를 비운 채 안전장치를 끄고 실행하면, FAE는 `WHERE`를 통째로 무시하고
**전체 테이블을 조회**한다. 운영 DB에서는 화면이 멈추거나 배치 시간이 폭증하는
사고로 이어진다. 안전장치(`IS NOT INITIAL`)가 왜 선택이 아니라 필수인지 직접 보자.

> ⚠️ 아래는 **시뮬레이션**이다. 실제 운영 DB에서 빈 목록 + 안전장치 OFF를 실험하면 안 된다.

## 흔한 실수와 점검

- **`IS NOT INITIAL` 누락** → 목록이 비면 조건이 통째로 무시돼 전체 테이블을 읽는다.
  FAE를 볼 때 1순위로 확인할 줄이다.
- **읽을 필드에 키가 빠짐** → 서로 다른 행이 중복으로 몰려 조용히 사라진다. 건수가
  기대와 다르면 여기부터 의심하자.
- **드라이버를 다듬지 않음** → 같은 값이 여러 번 들어 있으면 같은 조회를 반복한다.
  `SORT` 후 중복을 지우고 넘기자.
