## 🏗️ 빠른 SELECT로도 부족한 세계

[1+N](CH35-L04.html)을 없앴는데도 수백만 건 처리는 여전히 위험하다. 전부를 내부
테이블에 담으면 메모리가 터지고, 한 트랜잭션이 너무 오래 [잠금](CH26-L01.html)을 잡고,
중간에 실패하면 **처음부터 다시** 돌려야 한다. 대량 처리는 속도 문제가 아니라 **설계
문제**다: 속도와 안정성을 함께 본다.

설계는 네 가지 질문으로 갈린다.

| 질문 | 예 | 방향 |
|---|---|---|
| DB가 잘하는 일인가 | 집계·정렬·필터·JOIN | **푸시다운** — DB에서 줄여서 결과만 |
| 한 번에 메모리에 담아도 되나 | 수천 건 vs 수백만 건 | 크면 **패키지 처리** |
| 실패 후 이어서 시작해야 하나 | 야간 배치·파일 처리 | **재시작 key·상태 로그** |
| 독립 분할이 가능한가 | 공연별·기간별·번호 구간별 | **병렬 후보**(조건부) |

## 푸시다운 — 데이터를 끌어오지 말고 일을 내려보내라

[[Code Pushdown]](가공을 ABAP이 아니라 DB에서 하게 하는 원칙)의 출발은 이미 배웠다.
[Chapter 13 · GROUP BY와 Aggregate](CH13-L03.html)의 집계와 [Chapter 20](CH20-L01.html)의
고급 SQL이 그 도구다. 원칙은 하나: **ABAP으로 100만 행을 끌어와 LOOP로 합산하지 말고, DB에서 합계를
만들어 결과 몇 줄만 받아라.** `GROUP BY`와 집계는 DB에서 만들어져 ABAP 서버로 옮길
데이터 양 자체를 줄인다.

```abap
" ❌ 전 행을 끌어와 ABAP에서 합산 (네트워크·메모리 낭비)
" ✅ DB에서 집계해 결과만 — 공연별 예매 좌석 합계
SELECT concert_id,
       SUM( seats ) AS total_seats
  FROM zbooking
  WHERE status = 'N'
  GROUP BY concert_id
  INTO TABLE @DATA(gt_seat_sum).
```

더 강한 푸시다운 수단(AMDP·ADBC)은 [Chapter 36](CH36-L01.html)의 주제다. 이 레슨은
"어떤 일을 DB로 내릴지" **판단 기준**까지만이다.

## 패키지 처리 — 전체를 한 번에 대신, 안전한 단위로

ABAP 쪽 업무 검증이 꼭 필요해서 데이터를 가져와야 한다면, **끊어서** 가져온다.
[Chapter 25 · Package 처리](CH25-L05.html)에서 본 그 정신이다.

```abap
DATA gv_last_id   TYPE zbooking-booking_id.
DATA gv_pack_size TYPE i VALUE 10000.

DO.
  SELECT booking_id, customer, status
    FROM zbooking
    WHERE booking_id > @gv_last_id
    ORDER BY booking_id
    INTO TABLE @DATA(gt_pack)
    UP TO @gv_pack_size ROWS.

  IF gt_pack IS INITIAL.
    EXIT.                            " 더 없음 — 종료
  ENDIF.

  " 한 패키지 검증·DB 반영(UPDATE 등) + 성공/실패 로그(재시작 근거)
  " → 이 변경분을 아래 COMMIT WORK가 패키지 단위로 확정

  gv_last_id = gt_pack[ lines( gt_pack ) ]-booking_id.
  COMMIT WORK.                       " 패키지 단위 확정
ENDDO.
```

- 마지막 처리 key(`gv_last_id`)를 로그에 남기면, 실패해도 **그 지점부터 재시작**할 수
  있다. 실패는 예외가 아니라 설계 대상이다([Chapter 25 · 재처리](CH25-L04.html)).
- **패키지 크기는 트레이드오프**다: 너무 작으면 commit·왕복 횟수가 폭증하고, 너무 크면
  메모리·잠금·실패 시 재처리 범위가 커진다. 정답 수치는 없고, 운영 최대 건수를 알고
  실측으로 정한다.

## 병렬 — 마지막에, 조건이 맞을 때만

작업을 나눠 동시에 돌리면(aRFC 등) 시간이 줄 수 있다. 하지만 병렬은 성능 만능 키가
아니라 **조건부 카드**다.

- **독립 분할이 가능**하고(공연별·기간별처럼 서로 안 겹침),
- **같은 key·같은 잠금을 동시에 잡지 않고**([Chapter 26](CH26-L01.html)의 충돌이
  병렬에서는 배로 위험),
- **패키지 단위로 실패를 추적**할 수 있을 때만 검토한다.

그리고 병렬 수를 늘리면 DB·work process·잠금·RFC 자원을 **시스템 전체와 나눠** 쓴다.
"내 프로그램만 빨라지는가"가 아니라 "시스템에 부담을 주지 않는가"까지가 판단이다.

## 흔한 실수와 점검 🚧

- **전부 메모리로** → 테스트에선 되고 운영에선 터진다. 규모 추정(건수·건당 크기)이
  설계의 첫 단추.
- **ABAP에서 집계** → 합계·개수·정렬·필터는 DB가 잘한다. DB에서 100건으로 줄일 것을
  100만 건 끌어오지 말 것.
- **commit이 너무 잦거나 너무 늦거나** → 잦으면 성능·원자성이, 늦으면 잠금·롤백
  부담이 커진다. "업무상 함께 성공해야 하는 단위"와 "재시작 가능한 단위"를 같이 본다.
- **병렬 만능주의** → 같은 key를 갱신하는 작업의 병렬화는 충돌 제조기다. 독립 분할이
  먼저다.
- **AMDP/ADBC 앞당기기** → 이 장에서는 배운 SQL(`GROUP BY`·집계)의 푸시다운까지만.
  구현 문법은 [Chapter 36](CH36-L01.html)에서.

## 정리 📌

- 대량 처리 = **줄이고(푸시다운) → 끊고(패키지) → 남기고(재시작 로그) → 조건이 맞으면
  나눈다(병렬)**.
- 패키지 크기는 commit 횟수 ↔ 메모리·재처리 범위의 트레이드오프. 실측으로 정한다.
- 병렬은 독립 분할 + 잠금 무충돌 + 실패 추적이 될 때만.
