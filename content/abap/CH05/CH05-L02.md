## Structure도 전역으로

[Chapter 3](CH03-L01.html)에서 타입을 전역([[Domain]]·[[Data Element]])으로 올렸듯, **Structure Type**도 전역으로
올릴 수 있다. 여러 프로그램·화면·테이블이 같은 Structure를 공유하게 하는 게
[[DDIC]] [[Structure]]다.

앞으로 이 둘을 이렇게 부른다. 프로그램 안에 선언한 것은 **Local Structure**([앞 레슨](CH05-L01.html)의
`BEGIN OF`), 사전에 등록해 둔 것은 **DDIC Structure**다. 참고로 **ABAP Dictionary ·
DDIC · SE11**은 셋 다 같은 곳을 가리킨다. 정식 이름이 ABAP Dictionary, 줄임말이 DDIC,
그 사전을 여는 T-code가 SE11이다.

## SE11에서 Structure 만들기

`SE11`(Dictionary) → **Data type** 라디오 선택 → 이름 `ZST_PERSON` 입력 → Create →
뜨는 팝업에서 **Structure** 선택.

> 🖱️ 순서를 헷갈리기 쉽다. 첫 화면에서 "Structure"라는 줄부터 찾지 말자. 라디오는
> **Data type**을 고르고 **이름을 먼저 적은 다음** Create를 누르면, 그때 무엇을 만들지
> 묻는 팝업이 뜬다([Chapter 3 · Data Element — 의미·라벨 입히기](CH03-L02.html)에서
> Data Element를 만들 때와 똑같은 순서다).

- Short Description(짧은 설명)을 적고, **Components** 탭에서 [[Component]](구성 요소)를
  한 줄씩 추가한다. 각 Component의 타입은 보통 [[Data Element]]로 지정한다
  (라벨·도움말까지 상속).
- 저장을 누르면 어느 패키지에 넣을지 묻는다. 학습 중이라면
  [Chapter 1 · T-code와 SE38 첫 실행](CH01-L02.html)에서처럼 **Local Object**(`$TMP`)를
  누르면 이송요청 없이 저장된다.

| Component | Typing | 예 | 데이터 타입 | 길이 | 설명 |
|---|---|---|---|---|---|
| NAME | Data Element | `ZDE_NAME` | CHAR | 20 | 이름 |
| AGE | Data Element | `ZDE_AGE` | NUMC | 3 | 나이 |
| AMOUNT | Data Element | `ZDE_AMOUNT` | DEC | 8 (소수 2) | 금액 |

데이터 타입·길이는 Data Element가 참조하는 [[Domain]]에서, 설명(라벨)은 Data
Element에서 온다. [Chapter 3](CH03-L02.html)의 계층이 여기서 그대로 재사용된다.

앞 레슨의 Local 선언과 타입이 조금씩 다른 게 눈에 띌 것이다. 사전에서는 **길이가 정해진**
타입을 쓰기 때문이다.

- `name`은 Local에서 `TYPE string`(길이 제한 없음)이었지만 여기서는 **CHAR 20**이다.
  화면 칸이나 테이블 칸은 폭이 정해져 있어야 하기 때문이다.
- `age`는 Local에서 `TYPE i`(정수)였지만 여기서는 **NUMC 3**이다. NUMC는
  [Chapter 3 · Domain — 기술 속성 정의](CH03-L01.html)에서 봤듯 **숫자만 담는 문자**라
  자릿수가 고정되고 앞의 0이 살아 있다(`7`이 아니라 `007`). 계산이 목적이면 정수(`i`)가,
  자릿수를 맞춰 보여 주는 게 목적이면 NUMC가 어울린다.
- `AMOUNT`의 길이 8은 **자릿수 8자리**를 뜻한다. Local의 `TYPE p LENGTH 8`에서 8은
  **바이트 수**라([Chapter 2 · Incomplete 타입(C·N·P)](CH02-L03.html)) 같은 8이어도
  담기는 크기가 다르다.

> 📝 **참고** — 예제라서 금액을 단순한 `DEC`로 잡았다. 실무의 금액 필드는 보통
> **CURR**(통화 금액) 타입으로 만들고, 그 값이 어느 통화인지 알려 주는 **통화 키 필드**와
> 짝을 지어 둔다([Chapter 3 · Domain — 기술 속성 정의](CH03-L01.html)에서 예고한 그
> 짝이다). 실제로 짝을 맺는 방법은 테이블을 만드는 챕터에서 다룬다.

활성화하면 전역 Structure Type이 된다.

## 프로그램에서 쓰기

```abap
DATA gs_person TYPE zst_person.

gs_person-name = '정훈영'.
WRITE gs_person-name.
```

Local Structure(`BEGIN OF`)와 **쓰는 법은 똑같다**. 차이는 **어디에 생성했는가**뿐이다.
프로그램 내부에 생성(선언)하면 Local Structure, ABAP Dictionary(SE11)에서 생성(정의)하면
DDIC Structure이고, 이때 "Global(전역)"이라는 말이 붙는다. 여기서의 Global은 **여러
프로그램이 함께 쓴다**는 뜻이라, 앞 레슨에서 본 접두어 `gs_`의 global(한 프로그램 안
어디서나)보다 훨씬 넓은 범위다. 전역으로 정의해 두면 여러 프로그램이 같은 모양을
공유하고, 한 곳만 고치면 전부 반영된다. 아래에서 그 차이를 직접 비교해 보자.

> ⚠️ **"한 곳만 고치면 전부 반영"은 뒤집으면 위험이기도 하다.** 그 Structure를 쓰는
> 모든 프로그램·화면이 함께 영향을 받기 때문이다. 필드 길이를 줄이면 이미 들어 있던 값이
> 잘리고, 필드 이름을 바꾸면 그 이름으로 값을 넣던 코드가 한꺼번에 깨진다. 전역 객체를
> 고치기 전에 **어디서 쓰고 있는지부터 확인**하는 것이 규율이다(SE11 화면의
> "사용처 조회 / Where-Used List" 버튼).

모습을 트리로 확인해 보자. `gs_person-name`에 값을 넣는 대입도 눌러 볼 수 있다.

## DDIC 타입으로 쓸 수 있는 것 — Domain만 빼고

변수나 Component의 타입으로 줄 수 있는 DDIC 객체는 여럿이다. 단 **Domain은 직접 못 준다**([Chapter 3](CH03-L02.html)에서 봤듯 Domain은 Data Element를 통해서만).
지금까지 배운 것만 추리면 이렇다.

| DDIC 객체 | 변수/Component 타입으로? | 비고 |
|---|---|---|
| **Data Element** | ✅ | 가장 흔함(라벨·도움말 상속) |
| **Structure** | ✅ | Structure 안에 Structure(중첩) |
| **Domain** | ❌ | 변수 타입 직접 불가(Data Element를 거쳐야) |

- Component에 Data Element 대신 **다른 Structure**를 주면 **중첩 Structure**가 된다(다음 레슨에서 INCLUDE·APPEND와 함께).
- 아직 배우지 않은 DDIC 객체들도 대부분 타입으로 쓸 수 있다. 그 객체들은 다음 챕터부터
  하나씩 직접 만들어 보니, 지금은 **Domain만 예외**라는 것만 기억하면 된다.

> 💡 **심화(지금은 가볍게)** — Component가 **전부 문자 계열**(`C`는 글자, `N`은 숫자만
> 담는 문자)인 Structure는 통째로 한 문자 변수처럼 다룰 수도 있다. 예를 들어
> `year`(4자리)·`month`(2자리)·`day`(2자리)로 8자리를 채운 Structure에 오늘 날짜
> (`sy-datum`, 시스템이 채워 주는 오늘 날짜)를 통째로 넣으면 앞에서부터 4·2·2자리로
> 나뉘어 각 칸에 담긴다. "그런 트릭이 있다" 정도만 알아 두자.

## 언제 Local, 언제 DDIC?

- 그 프로그램에서만 잠깐 쓰는 **임시 묶음** → Local Structure(`BEGIN OF`). 만드는 데
  30초, 지우는 데 3초다. 이 챕터의 남은 레슨들도 설명에 집중하려고 예제를 대부분 Local로 든다.
- 아래 중 **하나라도** 해당하면 → **DDIC Structure**
  - 여러 프로그램·화면이 **같은 모양**을 써야 한다.
  - 화면 칸이나 테이블의 구조와 **짝을 맞춰야** 한다.
  - 나중에 필드가 바뀔 때 **한 곳만 고쳐 전부 반영**되게 하고 싶다.
- 대신 DDIC 객체에는 값이 따라붙는다. 이름을 전사 규칙에 맞춰 지어야 하고, 다른 서버로
  옮기려면 이송요청에 실어야 하고, 고칠 때는 쓰는 곳을 전부 확인해야 한다.

실무 팀이 "공유할 낌새가 조금이라도 보이면 DDIC"로 기우는 건 사실이다. 다만 그건 위
비용을 알고 내리는 선택이지, 묶음이 생길 때마다 무조건 사전에 등록하라는 뜻은 아니다.

## 흔한 실수와 점검

- **Component에 Built-in Type 직접 지정** → SE11에서 Component 타입은 Data Element
  대신 **Built-in Type**(CHAR·NUMC 같은 DDIC 기본 타입을 직접 지정)으로도 줄 수 있다.
  동작은 하지만 라벨·도움말을 잃는다. 가능하면 Data Element를 참조한다.
- **이름 규칙/활성화** → `Z`/`Y` 시작, 활성화(Ctrl+F3) 안 하면 사용 불가.
- **밑줄(`_`) 위치 제한** → DDIC Structure·테이블 이름은 **2·3번째 자리에 `_`가 올 수
  없다**(이름 끝 `_`도 불가). `ZS_PERSON`(3번째가 `_`)은 거부되고 `ZST_PERSON`(4번째부터)은
  되는 이유다. 실무에서는 `ZSMM`·`ZSSD`·`ZSPP`나 `ZMMS`·`ZSDS`·`ZPPS`처럼 앞자리를
  밑줄 없이 채운 이름을 자주 본다.
