## 🧾 주문서를 주방 언어로

Fiori 화면이 공연 목록을 요청하면 이런 URL이 창구로 들어온다.

```text
/sap/opu/odata/sap/ZCONCERT_SRV/ConcertSet?$filter=Venue eq '서울'&$top=10&$skip=20
```

읽어 보면 주문서다: "서울 공연을, 앞에서 20건은 건너뛰고, 10건만." 이 주문서를 받아
DB 조회로 번역하고 결과를 돌려주는 주방 메서드가 `GET_ENTITYSET`이다(한 건 조회는
`GET_ENTITY`).

여기서 버려야 할 생각: **"SELECT 해서 전부 넘기면 되겠지."** 창구는 화면 속 작은
리스트가 아니다. 호출자가 많고, 네트워크를 타고, 응답 크기가 곧 성능이다. 주문서의
조건을 무시하면 사용자는 자기가 고른 것과 다른 결과를 받는다.

## 주문서 항목 → SELECT 번역표

| URL 쿼리 | 뜻 | SELECT에서 |
|---|---|---|
| `$filter=Venue eq '서울'` | 조건 | `WHERE venue IN ...` |
| `$top=10` | 최대 10건 | `UP TO 10 ROWS` ([Chapter 8](CH08-L03.html)의 그것) |
| `$skip=20` | 앞 20건 건너뛰기 | `OFFSET 20` ← **이번에 새로 배우는 부분** |
| `$orderby=ConcertId` | 정렬 | `ORDER BY concert_id` |

**`OFFSET`** 은 결과에서 앞 n건을 건너뛰는 New Open SQL 문법이다. `UP TO`(몇 건)와
짝을 이뤄 **페이징**(목록을 페이지 단위로 나눠 주기)을 만든다. 공식 규칙이 하나 있다:
**`OFFSET`은 `ORDER BY`가 있어야 쓸 수 있다.** 정렬 없는 결과는 순서 자체가 보장되지
않아서, 페이지를 넘길 때마다 같은 행이 중복되거나 빠질 수 있기 때문이다.

## 구현 흐름 — 학습용 뼈대

주방 클래스(`*_DPC_EXT`)에서 해당 EntitySet의 `..._GET_ENTITYSET` 메서드를
재정의한다. 아래는 **흐름을 보여 주는 학습용 뼈대**다. 파라미터·타입 이름은 생성된
서비스마다 다르니 "주문서 읽기 → 번역 → 결과 채우기" 골격으로 읽는다.

```abap
METHOD concertset_get_entityset.
  DATA lr_venue TYPE RANGE OF zconcert-venue.
  DATA lv_top   TYPE i VALUE 100.          " 서버 상한(기본값)

  " ① 주문서 읽기 — URL의 $filter를 조건 목록으로
  DATA(lt_filter) =
    io_tech_request_context->get_filter( )->get_filter_select_options( ).

  READ TABLE lt_filter INTO DATA(ls_filter)
       WITH KEY property = 'Venue'.
  IF sy-subrc = 0.
    lr_venue = CORRESPONDING #( ls_filter-select_options ).
  ENDIF.

  " ② $top 상한 정책 — 소비자가 보낸 값을 무제한 신뢰하지 않는다
  IF iv_top IS NOT INITIAL AND iv_top <= 100.
    lv_top = iv_top.
  ENDIF.

  " ③ 번역된 SELECT — 조건·정렬·페이징을 전부 반영
  SELECT concert_id, artist, venue, capacity
    FROM zconcert
    WHERE venue IN @lr_venue               " Range는 비어 있으면 전체 허용
    ORDER BY concert_id                    " OFFSET의 전제 = 안정적 정렬
    INTO CORRESPONDING FIELDS OF TABLE @et_entityset
    UP TO @lv_top ROWS
    OFFSET @iv_skip.
ENDMETHOD.
```

- `$filter`는 [Chapter 12 · Range Table](CH12-L01.html)에서 배운 **Range 조건**으로
  변환돼 `WHERE ... IN`에 들어간다. Range가 비어 있으면 전체 허용이라 분기 없이 한
  SELECT로 처리된다.
- 결과는 `et_entityset`(모델 구조의 목록)에 채워 돌려준다. 응답 필드명은 ABAP
  필드명이 아니라 **메뉴판(모델)의 이름**으로 나간다는 것, 지난 레슨 그대로다.

## 어떻게 확인하는가

1. **계약서부터** — `$metadata`에 `ConcertSet`과 필드 이름이 기대대로 노출되는지.
   바깥 이름(`Venue`)과 안 이름(`venue`)이 다르면 매핑 지점을 의심한다.
2. **창구 테스트를 단계로** — 쿼리 없이 → `$filter`만 → `$top` 추가 → `$skip` 추가
   순서로 실행하며 건수가 기대대로 변하는지 본다. 같은 요청을 두 번 보내 **순서가
   흔들리면 정렬 부족**이다.
3. **주방 디버깅** — 메서드에 breakpoint를 걸고 주문서(요청 컨텍스트)에 조건이 어떻게
   들어오는지 본다.
4. **오류 로그** — 500이면 오류 로그·덤프부터([지난 레슨](CH34-L04.html)의 HTTP 분류
   그대로).
5. **성능** — 조건 없는 전체 조회·상한 없는 `$top`·정렬 없는 페이징이 없는지. 실제
   SELECT가 WHERE·ORDER BY·행 제한을 쓰는지는 [Chapter 35 · 성능 분석](CH35-L01.html)
   도구로 확인하게 된다.

## 직접 번역해 보기

조건·`$top`·`$skip`을 바꾸면 URL과 대응 SELECT 줄이 함께 바뀐다. **정렬 끄기**를 눌러
페이지가 흔들리는 사고와, **filter 미반영** 상태에서 조건을 바꿔도 결과가 그대로인
사고를 꼭 겪어 보라.

## 흔한 실수와 점검 🚧

- **`$filter` 무시** → 처음엔 화면에 데이터가 보여 성공 같지만, 조건을 바꿔도 결과가
  안 바뀌고 데이터가 늘면 느려진다. 주문서는 계약이다.
- **`$top`/`$skip` 무시** → 목록 화면은 페이지 단위로 부른다. 늘 전체를 보내면
  네트워크·메모리·응답 시간이 모두 나빠진다.
- **정렬 없는 페이징** → `OFFSET`은 `ORDER BY`가 전제다. 순서가 흔들리면 행이
  중복되거나 빠진다.
- **소비자의 `$top` 무제한 신뢰** → `$top=100000`이 와도 그대로 응답할 것인가? 서버
  상한 정책을 둔다(예제의 `lv_top`).
- **바깥 이름↔안 이름 혼동** → 요청은 모델의 필드 이름으로 온다. ABAP 필드명과 다르면
  변환이 필요하다.
- **base 클래스에 구현** → 지난 레슨 원칙 그대로, 조회 로직은 `_EXT`의 재정의 메서드에.

## 정리 📌

- `GET_ENTITYSET` = OData 주문서를 SELECT로 **번역**하는 지점. `$filter`→WHERE(Range),
  `$top`→`UP TO`, `$skip`→`OFFSET`, `$orderby`→`ORDER BY`.
- **`OFFSET`(신규)**: `UP TO`와 짝지어 페이징. 반드시 `ORDER BY`와 함께.
- 확인 루틴: 계약서($metadata) → 단계별 창구 테스트 → 디버깅 → 오류 로그 → 성능.

> ℹ️ 신규 개발이라면 [RAP](CH24-L08.html)이 같은 OData를 훨씬 적은 코드로 노출한다.
> SEGW/`GET_ENTITYSET`은 현장의 기존 자산을 읽고 고치기 위한 무기다.

## 🧩 도전 과제 (서브퀘스트)

> 선택 과제 — 예매 데이터를 표준 메시지·서비스로 연계한다.

1. 예매 확정 시 **IDoc**(Outbound)으로 파트너에 통지하는 흐름을 설계한다.
   봉투 구조([L01](CH34-L01.html))와 배송망 부품([L02](CH34-L02.html))을 그림으로 그린다.
2. 수신 실패(51) IDoc을 모니터에서 찾아 **원인 수정 후** 재처리한다([L03](CH34-L03.html)).
3. (심화) 공연 목록을 OData로 노출하고 `$filter`·페이징까지 구현한다([L04](CH34-L04.html)
   · 이 레슨). 신규 시스템이라면 [RAP](CH24-L08.html)과 비교해 본다.
