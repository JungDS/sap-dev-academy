## 🍽️ 이번엔 봉투가 아니라 창구

IDoc/ALE는 시스템끼리 **봉투를 주고받는** 방식이었다. 그런데 웹 화면·모바일 앱·Fiori가
"지금 예매 목록 좀 보여 주세요"라고 요청할 때는 봉투보다 **창구**가 자연스럽다. HTTP로
묻고 즉시 답을 받는 것이다.

[[OData]](Open Data Protocol)는 그 문답의 표준 규약이고, [[Gateway]](SAP Gateway)는
ABAP 시스템을 OData 창구로 열어 주는 틀이다. 신형 방식으로는
[Chapter 24 · RAP](CH24-L08.html)의 Service Binding이 있지만, 현장에는 전통 방식인
**SEGW 프로젝트**로 만든 OData V2 서비스가 아주 많다. 유지보수자는 이 구조를 읽을 수
있어야 한다.

> 🖥️ 이 레슨도 Gateway가 구성된 시스템이 있어야 실습이 가능한 영역이라, 구조 읽기와
> 시뮬레이터로 체험한다.

이 레슨의 목표는 화면 버튼 암기가 아니다. **URL 하나가 열리기까지 다섯 부품이 이어져야
한다**는 구조를 이해하는 것이다. 식당에 비유하면: 메뉴판을 정하고, 주방을 만들고,
카운터에 등록하고, 시식해 보고, 불만 접수창구를 두는 일이다.

## 다섯 부품 — 메뉴판부터 불만 접수까지

| 부품 | 식당 비유 | 내용 |
|---|---|---|
| **Data Model** | 메뉴판 설계 | 바깥에 보여 줄 데이터 모양 — `EntityType`·`EntitySet`·Association |
| **Runtime 클래스** | 주방 | 생성된 Provider 클래스 — 모델 담당 `*_MPC(_EXT)`·데이터 담당 `*_DPC(_EXT)` |
| **Service 등록** | 카운터 개시 | Gateway에 서비스를 등록·활성화해야 URL이 열림 |
| **테스트** | 시식 | `$metadata`와 실제 요청을 창구 테스트 도구로 확인 |
| **오류 로그** | 불만 접수 | HTTP 오류의 원인 추적 |

메뉴판의 두 용어부터 확실히:

| 개념 | 뜻 | 콘서트 예 |
|---|---|---|
| **EntityType** | 한 건의 데이터 **모양** | `Concert` (ConcertId·Artist·Venue·Capacity) |
| **EntitySet** | 그 모양의 **목록** | `ConcertSet` |

외부 소비자는 `/sap/opu/odata/sap/ZCONCERT_SRV/ConcertSet` 같은 URL로 **목록**을
부른다. 그리고 `$metadata`는 "이 창구가 무슨 메뉴를 파는가"를 알려 주는 **계약서**다.
데이터 코드가 아무리 맞아도 메뉴판(모델)과 어긋나면 소비자 요청은 실패한다.

## 주방의 규칙 — base는 두고 EXT에 쓴다

SEGW가 클래스를 생성하면 base(`*_MPC`·`*_DPC`)와 확장(`*_MPC_EXT`·`*_DPC_EXT`)이
쌍으로 나온다. **내 로직은 반드시 `_EXT` 쪽에 쓴다.** 이유는 재생성이다: 모델을 고쳐
runtime을 다시 생성하면 base 클래스는 덮일 수 있다. [Chapter 32](CH32-L02.html)에서
본 "생성물은 직접 고치지 않는다"와 같은 철학이다. 재정의(REDEFINITION)는
[Chapter 21 · 상속](CH21-L07.html)에서 배운 그 문법이다.

## URL이 안 열릴 때 — 세 가지 단골 상태

1. **창구 미등록** — 프로젝트와 클래스가 있어도 등록·활성화 전이면 404다. "코드는
   완성"과 "URL이 열림"은 다른 사건이다.
2. **메뉴판 불일치** — `$metadata`에 없는 필드를 응답에 채우려 하거나, 이름이 어긋난
   경우. 데이터 로직을 보기 전에 모델부터 본다.
3. **주방 미구현** — URL은 열리는데 목록이 늘 비어 있다면, `_EXT`에 조회 로직이 아직
   없는 상태일 수 있다(다음 레슨의 주제).

HTTP 상태로 1차 분류하는 감각도 여기서 생긴다: **404**=등록/URL, **403**=권한,
**400**=요청 문법(쿼리·필드명), **500**=주방 내부 오류(오류 로그·덤프 확인).

## 화면 참조표 🗂

| 역할 | T-code |
|---|---|
| SEGW 프로젝트(모델·생성) | `SEGW` |
| 서비스 등록·활성화 | `/IWFND/MAINT_SERVICE` |
| 창구 테스트(요청 실행) | `/IWFND/GW_CLIENT` |
| 오류 로그 | `/IWFND/ERROR_LOG` · `/IWBEP/ERROR_LOG` |

## 흔한 실수와 점검 🚧

- **base 클래스를 직접 수정** → 재생성 때 덮인다. 로직은 `_EXT`에.
- **EntityType↔EntitySet 혼동** → 한 건의 모양 vs 그 목록. 다음 레슨의
  `GET_ENTITY`/`GET_ENTITYSET` 구분이 여기서 갈린다.
- **등록 생략** → 활성화까지 해야 URL이 준비된다.
- **RAP과 한 문장에 섞기** → SEGW는 생성 클래스+재정의 중심, RAP은 CDS+Service
  Binding 중심. 둘 다 OData를 만들지만 개발 모델이 다르다. 신규는
  [RAP](CH24-L08.html)부터 검토.
- **$metadata 확인 없이 코드만 수정** → 계약서(모델)가 틀리면 주방을 고쳐도 소용없다.

## 정리 📌

- Gateway/OData = ABAP의 HTTP 창구. **메뉴판(모델)→주방(MPC/DPC_EXT)→카운터
  등록→시식($metadata·테스트)→불만 접수(오류 로그)**가 다 이어져야 URL이 열린다.
- EntityType = 한 건의 모양, EntitySet = 목록. 내 로직은 항상 `_EXT`에.
- HTTP 상태로 1차 분류: 404 등록 · 403 권한 · 400 요청 · 500 내부.
