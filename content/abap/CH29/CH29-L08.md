## 🛡️ 운영팀의 Quality Gate

정훈영의 최종 요청이다. "파트너에서 들어오는 텍스트를 등록 전에 한 번 거르는 **품질
게이트**를 만들어 주세요. 통과/반려만 말고, **뭐가 왜 걸렸는지**까지요."

검사 대상은 세 종류다.

| 대상 | 요구 | 사용 부품 | 레슨 |
|---|---|---|---|
| 운영 로그 | 오류 코드 `E***`를 전부 찾아 위치 표시 | `FIND ALL ... RESULTS` | [L03](CH29-L03.html) |
| 이메일 | 이메일처럼 보이는지 1차 검증 | `matches( pcre )` | [L07](CH29-L07.html) |
| 코드 텍스트 | obsolete 명령 `SEARCH` 사용 적발 | `FIND PCRE` + `\b` | [L01](CH29-L01.html)·[L03](CH29-L03.html) |

## 설계 — 패턴·입력·결과·피드백의 분리

정규식 도구의 안전 설계는 네 가지를 분리하는 것이다. 결과 행 타입부터 정의한다.

```abap
TYPES:
  BEGIN OF ts_check,
    category TYPE string,     " LOG / EMAIL / CODE
    input    TYPE string,     " 검사한 원문
    ok       TYPE abap_bool,  " 통과 여부
    message  TYPE string,     " 왜 통과/반려인지
  END OF ts_check,
  tt_check TYPE STANDARD TABLE OF ts_check WITH EMPTY KEY.

DATA gt_result TYPE tt_check.
```

들어올 입력 샘플은 이런 네 줄이라고 하자.

```text
E100 booking failed for hunyoung@example.com
W210 retry scheduled
E404 concert missing
SEARCH gv_text FOR 'ABAP'.
```

## 검사 ① 로그 오류 코드 — 위치까지 표로

```abap
DATA(gv_log) =
  `E100 booking failed, W210 retry scheduled, E404 concert missing`.

FIND ALL OCCURRENCES OF PCRE `E\d{3}`
     IN gv_log
     RESULTS DATA(gt_error).

LOOP AT gt_error INTO DATA(gs_error).
  APPEND VALUE #(
    category = `LOG`
    input    = substring( val = gv_log
                          off = gs_error-offset
                          len = gs_error-length )
    ok       = abap_false
    message  = |오류 코드 발견 (offset { gs_error-offset })|
  ) TO gt_result.
ENDLOOP.
```

오류 코드는 "발견 = 반려 신호"이므로 `ok = abap_false`로 적재한다. offset을 메시지에
남겨 두면 원문 어디를 보라는 안내가 된다.

## 검사 ② 이메일 1차 검증 — matches

```abap
DATA(gv_email)   = `hunyoung@example.com`.
DATA(gv_pattern) = `[\w.+-]+@[\w.-]+\.[A-Za-z]{2,}`.

APPEND VALUE #(
  category = `EMAIL`
  input    = gv_email
  ok       = xsdbool( matches( val = gv_email pcre = gv_pattern ) )
  message  = COND #( WHEN matches( val = gv_email pcre = gv_pattern ) = abap_true
                     THEN `이메일 1차 형식 통과`
                     ELSE `이메일 형식 아님` )
) TO gt_result.
```

패턴을 `gv_pattern` 변수로 분리한 것에 주목하라. [L07](CH29-L07.html)의 습관이다. 그리고
이건 여전히 **1차 검사**다. 게이트의 역할은 "명백히 이상한 것 거르기"지 국제 표준
검증기가 아니다.

## 검사 ③ obsolete 명령 적발 — word boundary

[Chapter 4 · 문자열 다루기](CH04-L02.html)에서 "`SEARCH`는 옛 명령, 우리는 `FIND`"라고
배웠다. 코드 리뷰 게이트로 만들어 보자.

```abap
DATA(gv_code) = `SEARCH gv_text FOR 'ABAP'.`.

FIND PCRE `\bSEARCH\b`
     IN gv_code
     IGNORING CASE
     MATCH OFFSET DATA(gv_offset).

IF sy-subrc = 0.
  APPEND VALUE #(
    category = `CODE`
    input    = gv_code
    ok       = abap_false
    message  = |obsolete 명령 SEARCH (offset { gv_offset }) — FIND로 교체|
  ) TO gt_result.
ENDIF.
```

새 얼굴 `\b`는 word boundary(단어 경계: 단어 문자와 비단어 문자의 사이 지점)다.
이게 없으면 `RESEARCH` 안의 `SEARCH`까지 잡는 오탐이 난다. `IGNORING CASE`는
`search`라고 소문자로 써도 잡기 위해서다.

## 결과 출력

```abap
LOOP AT gt_result INTO DATA(gs_check).
  WRITE: / gs_check-category,
           COND string( WHEN gs_check-ok = abap_true
                        THEN `✔` ELSE `✘` ),
           gs_check-message.
ENDLOOP.
```

| category | 판정 | message |
|---|---|---|
| LOG | ✘ | 오류 코드 발견 (offset 0) |
| LOG | ✘ | 오류 코드 발견 (offset 44) |
| EMAIL | ✔ | 이메일 1차 형식 통과 |
| CODE | ✘ | obsolete 명령 SEARCH (offset 0) — FIND로 교체 |

## 직접 게이트를 돌려 보기

검사 종류를 바꿔 실행하고, IGNORING CASE 토글·마스킹 미리보기까지 확인해 보라.

## 확인 체크리스트

| 입력 | 기대 결과 |
|---|---|
| `E100 ...`, `E404 ...` 로그 | LOG 반려 행 2건 + offset 표시 |
| `W210 retry scheduled` | `E\d{3}` 미해당 — 결과 행 없음 |
| `hunyoung@example.com` | EMAIL 통과 |
| `SEARCH ...` / `search ...` | CODE 반려(IGNORING CASE 덕에 둘 다) |
| `RESEARCH 계획` | `\b` 덕에 **미적발**(오탐 방지) |

## 흔한 실수와 점검 🚧

- **정규식 만능주의** — 로그 검사는 파서가 아니다. 필드가 구조화될 수 있으면 구조가
  먼저고, 정규식은 텍스트로만 올 때의 차선이다.
- **완벽한 이메일 정규식 추구** — 끝이 없는 길이다. 게이트의 요구 수준을 먼저 정한다.
- **사용자 입력을 패턴으로 그대로 실행** — 빈 패턴 예외·`CX_SY_REGEX_TOO_COMPLEX`·
  성능 문제의 입구다. 패턴은 개발자가 관리하는 목록에서만.
- **성공 케이스만 시연** — 검사기의 가치는 **반려 사유 안내**에 있다. 실패 피드백이
  없는 게이트는 절반짜리다.

## 정리 📌

- 검증기의 뼈대 = **패턴·입력·결과·피드백의 분리**. 결과는 `ts_check` 같은 행 타입으로.
- 도구 선택 복습: 전부 찾아 표로 = `RESULTS` · 전체 형식 판정 = `matches` · 단어 단위
  적발 = `\b` + `IGNORING CASE`.
- 정규식은 강력하지만 읽기 어려운 도구다. 좋은 코드는 "짧은 패턴 한 줄"이 아니라
  패턴 이름·테스트 케이스·실패 피드백이 함께 있는 코드다.
