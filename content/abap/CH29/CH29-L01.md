## 📮 운영팀의 새 요청

콘서트 예매 시스템에 제휴 티켓 파트너가 생겼다. 파트너사에서 넘어오는 접수 텍스트에는
**접수번호**가 섞여 있다. 우리 시스템의 예매번호는 `0001`처럼 4자리지만, 파트너 접수번호는
형식이 다르다.

```text
Booking B-2026-0007 failed for user HUNYOUNG
```

운영팀 정훈영이 요청한다. "접수 텍스트가 `B-연도4자리-일련번호4자리` 형식인지 **검사**해
주세요. 형식이 깨진 건 반려해야 해요."

[Chapter 4 · 문자열 다루기](CH04-L02.html)에서 배운 `FIND`를 먼저 떠올려 보자.

```abap
DATA(gv_text) = `Booking B-2026-0007 failed`.

FIND `failed` IN gv_text.
IF sy-subrc = 0.
  WRITE / `실패 로그 발견`.
ENDIF.
```

이 코드는 충분히 좋다. `failed`라는 **고정 단어**를 찾는 요구에는 이걸로 끝이다.
그런데 접수번호 검사는 사정이 다르다.

- `B-2026-0007`도, `B-2026-0008`도, `B-2027-1234`도 **전부 통과**해야 한다.
- `B-26-7`, `X-2026-0007`, `B-2026-ABCD`는 **전부 반려**해야 한다.

`FIND 'B-2026-0007'`처럼 글자 그대로 찾는 방식으로는 접수번호가 하나 늘 때마다 코드를
고쳐야 한다. 우리가 찾고 싶은 건 특정 글자가 아니라 **"이런 모양의 글자들"**, 즉 형식이다.

## 정규식 — 형식을 표현하는 작은 언어

이럴 때 쓰는 도구가 [[정규식]](Regular Expression, 문자열의 '모양'을 표현하는 작은 언어)이다.
접수번호 형식을 정규식으로 쓰면 이렇게 된다.

```text
B-\d{4}-\d{4}
```

기호를 하나씩 읽어 보자. 지금은 이 세 개면 충분하다(전체 문법은 다음 레슨).

| 표현 | 의미 | `B-2026-0007`에서 |
|---|---|---|
| `B-` | 문자 `B-` 그대로 | 맨 앞 `B-` |
| `\d` | 숫자 한 자리 | `2`, `0`, `7`... |
| `\d{4}` | 숫자 정확히 네 자리 | `2026`, `0007` |

ABAP에서 정규식을 쓸 때는 `FIND` 뒤에 `PCRE`를 붙인다. [[PCRE]](Perl Compatible Regular
Expressions, ABAP가 채택한 표준 정규식 문법)는 "이 검색어는 글자 그대로가 아니라
패턴이다"라는 선언이다.

```abap
DATA(gv_text) = `Booking B-2026-0007 failed`.

FIND PCRE `B-\d{4}-\d{4}` IN gv_text.

IF sy-subrc = 0.
  WRITE / `접수번호 형식 발견`.
ENDIF.
```

`FIND`가 성공/실패를 [[sy-subrc]]로 알려 주는 건 substring 검색 때와 똑같다.
달라진 건 **무엇을 찾느냐**뿐이다.

## 함정 — "포함"과 "전체 형식"은 다르다

그런데 위 패턴에는 함정이 하나 있다. 맞는 것만 통과시키는지, **틀린 것도 걸러내는지**
같이 확인해야 한다.

| 입력 | `B-\d{4}-\d{4}` 결과 | 기대 |
|---|---|---|
| `B-2026-0007` | ✅ 발견 | 통과 |
| `B-2026-1234` | ✅ 발견 | 통과 |
| `B-26-0007` | ❌ 없음 | 반려 |
| `X-2026-0007` | ❌ 없음 | 반려 |
| `안내: B-2026-0007 접수됨` | ✅ 발견?! | **반려해야 하는데?** |

마지막 행이 문제다. 문장 **안에** 접수번호 모양이 들어 있기만 해도 `FIND`는 성공한다.
"이 텍스트 전체가 접수번호인가"를 물으려면 [[Anchor]](닻: 패턴의 시작 `^`과 끝 `$`을
고정하는 기호)를 붙인다.

```abap
DATA gt_text TYPE STANDARD TABLE OF string WITH EMPTY KEY.

gt_text = VALUE #(
  ( `B-2026-0007` )
  ( `B-26-0007` )
  ( `X-2026-0007` )
  ( `안내: B-2026-0007 접수됨` )
).

LOOP AT gt_text INTO DATA(gv_line).
  FIND PCRE `^B-\d{4}-\d{4}$` IN gv_line.

  IF sy-subrc = 0.
    WRITE / |통과: { gv_line }|.
  ELSE.
    WRITE / |반려: { gv_line }|.
  ENDIF.
ENDLOOP.
```

- `^` = 문자열의 **시작**부터
- `$` = 문자열의 **끝**까지

이제 `안내: B-2026-0007 접수됨`은 시작이 `B-`가 아니므로 반려된다. **"일부에 포함되어
있는가"는 anchor 없이, "전체가 이 형식인가"는 anchor를 붙여서**. 이 구분이 정규식
검증의 첫 습관이다.

## 흔한 실수와 점검 🚧

- **고정 단어에 정규식** — `FIND 'failed'`로 충분한 곳에 정규식을 쓰면 읽기만 어려워진다.
  정규식은 **형식을 찾을 때만**.
- **anchor 빠뜨림** — `^`·`$` 없는 검증은 "포함 검사"다. 전체 형식 검증이 목적이면 반드시
  붙인다.
- **빈 패턴** — PCRE 패턴이 빈 문자열이면 실행 중 오류가 날 수 있다. 사용자 입력을
  패턴으로 쓸 일이 있으면 비어 있지 않은지 먼저 확인한다.
- **옛 문법(POSIX)** — ABAP에는 `PCRE` 이전의 POSIX 정규식 문법도 남아 있지만
  obsolete(구식 판정)다. 새 코드는 항상 `PCRE`.

## 정리 📌

- substring 검색 = "이 글자가 그대로 있는가". 정규식 = "**이런 모양**의 글자가 있는가".
- ABAP 정규식은 `FIND PCRE '패턴' IN 텍스트`. 성공/실패는 여전히 `sy-subrc`.
- `^`(시작)·`$`(끝) anchor를 붙여야 "포함"이 아니라 "전체 형식" 검증이 된다.
