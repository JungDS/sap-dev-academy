## "실패했습니다"만 남은 새벽

야간 정산 잡이 Canceled로 끝났다. 운영자가 아침에 확인할 수 있는 것: "실패했다."
끝이다. 어떤 예매가, 어느 단계에서, 왜 실패했는지가 없다. 개발자가 코드에 임시로
넣어 둔 `WRITE`는 잡이 끝나면 볼 수 없고, Internal Table에 모아 둔 오류 목록은
프로그램이 죽는 순간 메모리와 함께 사라졌다.

[Chapter 25 · 오류 로그와 재처리 구조](CH25-L04.html)에서 "오류는 검색 가능한
기록으로 남긴다"는 원칙과 우리만의 로그 테이블 설계를 배웠다. 이 레슨은 그 원칙의
**SAP 표준 구현**이다. 직접 만든 로그 테이블은 우리 프로그램만 알지만, 표준 로그는
**운영자가 이미 아는 화면 하나로 모든 프로그램의 로그를 검색**할 수 있다.

## BAL — 표준 로그의 구조

그 표준이 [[BAL]](Business Application Log. SAP의 표준 업무 로그 저장·조회
체계)이고, 조회 화면이 `SLG1`이다. 로그 한 건의 뼈대는 다섯 조각이다.

| 구성 | 의미 | 우리 예 |
|---|---|---|
| **Object** | 큰 업무 영역(검색의 대분류) | `ZBOOK`(예매 업무) |
| **Subobject** | 세부 처리 영역(중분류) | `SETTLE`(정산)·`CANCEL`(취소) |
| **External number** | 실행 한 판을 식별하는 값 | `RUN-20260801-020000`(그날 그 잡) |
| **Message** | 실제 성공/경고/오류 메시지 | "예매 0001 정산 실패: 정원 초과" |
| **Context** | 재처리 판단용 부가 정보(구조로 첨부 — 정의가 필요해 이 과정에선 개요만, 예제는 msgv의 key까지) | 공연 ID·예매 ID·단계 |

이 구조가 곧 검색 조건이다. 운영자는 `SLG1` 선택화면의 같은 이름 필드(Object·
Subobject·기간)에 "ZBOOK·SETTLE·오늘"을 넣고 실행해, 결과 트리에서 로그를 펼쳐
어젯밤 정산의 전말을 본다. External number가 잡 한 판을 식별하니, [앞
레슨](CH38-L05.html)의 job log(기술 증거)와 이 업무 로그가 같은 실행으로
연결된다(잡이 자기 식별자를 알게 하는 가장 단순한 길은 **실행 일시로 문자열을
조립하는 것**이고, 아래 예제 코드가 정확히 그렇게 한다).

> Object/Subobject는 **미리 등록해 두는 분류 체계**다(등록 화면 = `SLG0` —
> Object 이름과 설명을 새로 만들고, 그 아래 Subobject들을 추가하는 단순한 목록
> 화면이다. 프로젝트에서는 보통 정해진 체계를 받아 쓰고, 연습 시스템이라면
> `ZBOOK`을 직접 만들어 볼 수 있다). 등록되지 않은 이름으로 로그를 만들려 하면
> 생성 단계부터 실패하니, 코드보다 등록이 먼저다. 그리고 이 등록도 **이송 대상
> 오브젝트**다 — 코드만 이송하고 등록을 안 태우면 QAS에서 `BAL_LOG_CREATE`가
> 실패한다([Chapter 38 · Transport](CH38-L04.html)에서 경고한 "객체 누락" 사고의
> 한 사례). 우리가 설계할 것은 "어떤 분류와 실행 식별자로 남길 것인가"다.

## 남기는 코드 — 만들고, 담고, 저장한다

기록 흐름은 3박자다: **로그 생성 → 메시지 추가(반복) → DB 저장**(SAP Help의 표준
흐름).

```abap
DATA gs_log    TYPE bal_s_log.       " 로그 머리(분류·식별자)
DATA gv_handle TYPE balloghndl.      " 생성된 로그를 가리키는 손잡이

" ① 로그 생성 — 분류와 실행 식별자를 머리에 담는다
gs_log-object    = 'ZBOOK'.
gs_log-subobject = 'SETTLE'.
gs_log-extnumber = |RUN-{ sy-datum }-{ sy-uzeit }|.  " 실행 일시로 식별자 조립
CALL FUNCTION 'BAL_LOG_CREATE'
  EXPORTING  i_s_log      = gs_log
  IMPORTING  e_log_handle = gv_handle
  EXCEPTIONS OTHERS       = 1.
IF sy-subrc <> 0.
  MESSAGE '로그를 생성할 수 없습니다' TYPE 'E'.  " Object 미등록(SLG0)이 단골 원인
ENDIF.

" ② 메시지 추가 — 처리 중 오류가 날 때마다 반복 호출
"    (message class ZBOOK 001: '예매 &1 정산 실패: 단계 &2' — CH15의 SE91.
"     msgv1~msgv4가 &1~&4 자리에 순서대로 들어간다)
CALL FUNCTION 'BAL_LOG_MSG_ADD'
  EXPORTING
    i_log_handle = gv_handle
    i_s_msg      = VALUE bal_s_msg(
      msgty     = 'E'      " 오류(S/W/E — CH15의 메시지 타입 그대로)
      probclass = '1'      " 문제 등급(1=매우 중요~4=참고) — SLG1의 핵심 필터
      msgid     = 'ZBOOK'  " message class
      msgno     = '001'
      msgv1     = '0001'   " &1 = 실패한 예매의 key
      msgv2     = '저장' ) " &2 = 실패한 단계
  EXCEPTIONS OTHERS = 1.

" (처리 루프가 끝나면) 성공 요약도 한 줄로 담는다
"  예: msgty 'S' + '&1건 중 &2건 성공, &3건 실패' — 세어 둔 카운터를 msgv로

" ③ DB 저장 — 이게 없으면 SLG1에서 영원히 못 찾는다
"   i_save_all = 이 세션의 '모든' 로그 저장(교육용 최소형 — 실무는
"   핸들 목록을 넘겨 내 로그만 저장하는 쪽을 쓴다)
CALL FUNCTION 'BAL_DB_SAVE'
  EXPORTING  i_save_all = abap_true
  EXCEPTIONS OTHERS     = 1.

" ④ 확정 — 로그도 DB 변경이므로 커밋으로 확정한다(CH25의 LUW 그대로)
COMMIT WORK.
```

부품은 전부 아는 것의 조합이다: 메시지는 [Chapter 15의 message
class](CH15-L04.html)(SE91) 그대로이고, ①～④는 CH37-CH38에서 반복해 본
"열고-쓰고-닫고" 리듬이다. **함정은 ③④다.** ①②는 메모리 안에서만 일어나고,
③ `BAL_DB_SAVE`가 DB에 쓰며, ④ `COMMIT WORK`가 확정한다([Chapter 25 ·
LUW](CH25-L02.html) 규칙 그대로 — 답을 분명히 하면, **저장 후 커밋까지 내가
쓴다**).

여기서 CH25를 배운 사람이라면 무서운 질문이 하나 나온다: **정산이 실패해서
`ROLLBACK WORK`를 하면, 실패 이유를 담은 로그도 같이 쓸려가지 않나?** 정확히
가르자. 메모리 위의 로그(①②)는 DB 롤백과 무관하니 안 쓸려간다. 위험한 조합은
둘이다: ⓐ **저장(③)까지 했는데 커밋 전에 롤백이 돌면** 저장분이 취소되고,
ⓑ 반대로 로그를 커밋하는 그 `COMMIT WORK`가 **실패한 업무 변경까지 함께 확정**해
버릴 수 있다. 그래서 순서가 규칙이다:

```abap
" 실패 처리의 순서 — 업무는 되돌리고, 로그만 확정한다
IF gv_settle_failed = abap_true.
  ROLLBACK WORK.                       " ⓐ 업무 변경 취소가 먼저
  CALL FUNCTION 'BAL_LOG_MSG_ADD'      " ⓑ 그 다음 실패 로그를 담고
    EXPORTING i_log_handle = gv_handle
              i_s_msg      = gs_fail_msg
    EXCEPTIONS OTHERS = 1.
  CALL FUNCTION 'BAL_DB_SAVE'
    EXPORTING  i_save_all = abap_true
    EXCEPTIONS OTHERS     = 1.
  COMMIT WORK.                         " 이 커밋은 로그만 확정한다
ENDIF.
```

같은 이유로 대량 처리에서는 끝에 한 번이 아니라 **구간마다 저장·커밋**한다(구간 =
CH25에서 정한 업무 커밋 단위 그대로 — 정산 N건을 커밋할 때 로그도 같이 저장).
그래야 프로그램이 중간에 죽어도 거기까지의 로그는 남는다 — 도입부의 "죽으면
사라지는 Internal Table"과의 진짜 차이가 이 지점이다.

이 예제는 `SE38` 수동 실행으로 연습하는 전제다(message class `ZBOOK`이 없다면
[SE91에서 먼저 만들자](CH15-L04.html) — 준비물이다). 야간 잡 안에서 돈다면
`MESSAGE TYPE 'E'` 같은 화면 의존은 쓰지 않는다 — background에서 E 메시지는
**잡을 그 자리에서 Canceled로 끝낸다**([앞 레슨](CH38-L05.html)의 그 상태). 오류는
로그에 담고 조용히 다음 건으로 넘어가는 구조가 잡용 프로그램의 기본형이다.

## 좋은 로그의 조건 — 재처리가 되는가

로그의 품질 기준은 하나다: **운영자가 이 로그만 보고 다음 행동을 정할 수 있는가.**

- **key가 있는가** — "정산 실패 17건"은 행동 불가. "예매 0001·0007·0012 실패"라야
  재처리 대상을 고를 수 있다(메시지 변수 `msgv1`～`msgv4`에 key를 싣는 이유).
- **단계가 있는가** — 같은 실패라도 "조회 단계"와 "저장 단계"는 대응이 다르다.
- **성공도 요약으로** — "10,000건 중 9,983건 성공, 17건 실패" 한 줄이 있어야 실패
  17건의 무게를 안다. 단, 성공 1만 건을 낱개로 남기면 노이즈다.
- **민감정보는 남기지 않는다** — 로그는 오래 보관되고 여러 사람이 본다. 비밀번호·
  카드번호·개인정보는 절대 금지다.

## 흔한 실수와 점검 🚧

- **`WRITE`를 로그로 착각** → 화면 출력은 잡이 끝나면 추적이 약하다. 운영 기록은
  BAL로.
- **`BAL_DB_SAVE` 누락** → 로그를 열심히 담고도 SLG1에서 못 찾는 1순위 원인.
- **"실패" 한 단어 메시지** → key·단계·원인 없는 로그는 재처리를 막는다
  ([Chapter 25](CH25-L04.html)와 [Chapter 37](CH37-L05.html)에서 반복한 그 원칙).
- **전 건 성공 로그** → 노이즈에 실패가 묻힌다. 성공은 요약, 실패는 낱개.
- **민감정보 기록** → 로그 정책 위반. 남기기 전에 "이 값이 화면에 떠도 되나"를
  묻는다.
- **쌓기만 하고 안 지움** → 로그 헤더에는 만료일(삭제 예정일)이 있고, 비워 두면
  사실상 영구 보존이다. 야간 잡이 매일 수만 건씩 남기면 로그 테이블이 수백 GB로
  자라 **DB 용량 장애**가 된다. 보관 기간을 정하고 표준 삭제(SLG2 계열)를 주기
  잡으로 돌리는 것까지가 로그 설계다.

## 정리 📌

- Application Log(BAL) = **운영자가 SLG1 한 화면으로 검색하는 표준 업무 로그.**
  구조 = Object/Subobject(분류) + External number(실행 식별) + Message/Context.
- 기록 리듬 = `BAL_LOG_CREATE` → `BAL_LOG_MSG_ADD`(반복) → **`BAL_DB_SAVE` +
  `COMMIT WORK`(잊으면 전부 증발).** 실패 시 순서 = **ROLLBACK 먼저, 로그
  저장·커밋은 그 다음**(로그가 롤백에 쓸려가지 않게).
- 좋은 로그 = key + 단계 + 성공 요약 + 민감정보 0. 기준은 "**재현 없이 다음 행동을
  정할 수 있는가.**"

## 🧩 도전 과제 (서브퀘스트)

> 선택 과제 — 야간 정산을 운영 품질 체인 위에 올린다.

1. 정산 로직의 업무 약속 2개를 [ABAP Unit 테스트](CH38-L02.html)로 남기고, 잔여
   좌석 조회의 DB 의존을 [SQL Test Double](CH38-L03.html)로 격리한다.
2. [ATC](CH38-L01.html)를 실행해 finding을 수정/예외로 분류하고, 이송
   release([L04](CH38-L04.html)) 전 3점검(object list·의존 순서·게이트)을 수행한다.
3. 정산 리포트를 [Background Job](CH38-L05.html)으로 예약한다(variant 포함). 실패
   상황을 가정해 job log·spool·SLG1 세 겹의 증거로 원인을 좁히는 시나리오를 적어
   본다.
4. (설계) 정산 로그의 Object/Subobject/External number 체계와 "성공 요약 + 실패
   낱개" 메시지 설계를 표로 만든다.
