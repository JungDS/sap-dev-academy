## Mock을 직접 못 끼우는 코드들

[Chapter 27](CH27-L05.html)의 방법을 복습하면: DB 접근을 interface로 분리하고,
테스트에서는 가짜 구현(Mock)을 주입했다. **interface가 있으면** 이 방법이 가장
단순하고 읽기 쉽다.

문제는 interface가 없는 코드다. 실무에서 테스트를 막는 의존성은 이런 모양이다.

- 메서드가 `zbooking`을 **직접 `SELECT`** 한다(분리된 repository 없음).
- CDS view 결과에 의존한다.
- 오래된 legacy 코드라 구조를 뜯기가 겁난다.

이럴 때 쓰는 대체물을 통틀어 [[Test Double]](테스트 중 실제 의존 대상을 대신하는
가짜 — Mock은 그중 한 갈래)이라 부른다. 목적은 "대충 통과시키기"가 아니라, 입력과
결과를 테스트가 **통제**해서 검증하려는 로직만 깨끗하게 확인하는 것이다. 이 레슨은
의존성 모양별로 어떤 double을 고르는지의 지도다.

| 의존성의 모양 | 우선 선택 | 비고 |
|---|---|---|
| interface 뒤로 분리된 의존 | **직접 만든 Mock**(CH27 방식) | 가장 단순 — 항상 1순위 후보 |
| interface는 있는데 메서드가 많다 / 상호작용 검증이 필요하다 | `CL_ABAP_TESTDOUBLE` | 가짜 class를 손으로 안 만들어도 됨 |
| 코드가 테이블·CDS view를 **직접 SELECT** | **ABAP SQL Test Double** | SELECT 결과를 테스트 데이터로 통제 |
| CDS entity 자체의 로직 검증 | CDS Test Double(개요만) | CDS 의존을 격리 |
| 분리가 어려운 legacy 코드 | `TEST-SEAM`(최후 수단) | 새 코드에는 쓰지 않는다 |

## CL_ABAP_TESTDOUBLE — 가짜를 자동으로 만들어 주는 공장

CH27에서는 Mock class를 손으로 썼다(`ltd_booking_repo`). 메서드가 두 개라 짧았지만,
메서드 열 개짜리 interface라면 가짜 만들기가 일이 된다.
[[CL_ABAP_TESTDOUBLE]](ABAP OO Test Double Framework의 중심 class. 가짜 객체
생성과 응답 설정을 표준화한다)이 그 노동을 대신한다(공식 cheat sheet 확인 패턴).

시연은 우리에게 익숙한 `zif_booking_repo`(CH27에서 만든 **글로벌** interface —
SE24/ADT에서 열리는 그것)로 한다. 메서드 2개짜리라 실전이라면 직접 Mock이 더
낫지만(위 표의 원칙 그대로), **리듬을 보여 주기 위한 시연**이라는 점을 감안하고
읽자.

```abap
METHOD remaining_with_framework_double.
  " ① 가짜 생성 — 손으로 class를 만들지 않는다
  "   이름은 문자열로 넘긴다: 오타는 활성화가 못 잡고 실행 때 터지니 주의
  "   create는 범용 참조를 돌려주므로 CAST로 우리 interface 타입에 받는다
  DATA(lo_double) = CAST zif_booking_repo(
    cl_abap_testdouble=>create( 'ZIF_BOOKING_REPO' ) ).

  " ② 응답 예약 — [설정] 다음 [그 메서드 호출]이 한 쌍이다.
  "   설정 직후의 호출은 실행이 아니라 "방금 설정은 이 메서드·이 인자 것"이라는
  "   지정으로 기록된다. 메서드마다 이 두 줄 쌍을 반복한다.
  cl_abap_testdouble=>configure_call( lo_double )->returning( 100 ).
  lo_double->get_capacity( iv_concert = 'C001' ).

  cl_abap_testdouble=>configure_call( lo_double )->returning( 50 ).
  lo_double->get_booked( iv_concert = 'C001' iv_perf = '01' ).

  " ③ 가짜를 주입하고 로직만 검증 (CH27과 동일한 그림)
  DATA(lo_mgr) = NEW zcl_booking_manager(
    iv_concert = 'C001'
    iv_perf    = '01'
    io_repo    = lo_double ).
  cl_abap_unit_assert=>assert_equals(
    act = lo_mgr->remaining( )      " 정원 100 − 예약 50
    exp = 50 ).
ENDMETHOD.
```

②의 리듬이 처음엔 직관에 반한다. (참고로 `RETURNING`이 있는 메서드도 결과를 받지
않고 문장 하나로 호출하는 것 자체는 원래 유효한 문법이다 — 오타가 아니다.) 호출 =
실행이라는 지금까지의 규칙이 여기서만 다르게 동작하는 이유는, **가짜 객체의
메서드에는 실행할 몸통이 없기 때문**이다.
framework는 그 "빈 호출"을 실행 대신 기록으로 받아, 직전 `configure_call`의 설정을
그 메서드에 붙인다. 이때 **넘긴 인자값도 조건으로 함께 기록**된다: 테스트 본편에서
같은 인자로 불러야 예약한 값이 나오고, 인자를 조건에서 빼고 싶으면
`ignore_parameter`를 설정에 끼운다(공식 예제 패턴). 반환값 외에 export 값·예외·
"몇 번 불렸는지"(상호작용) 검증도 설정할 수 있다(세부는 ADT에서 class 문서 확인).

한계도 분명하다: **local class/interface는 지원하지 않는다** — 즉 CH27의 로컬
`ltd_` Mock 세계와 달리, 이 framework는 `ZIF_…` 같은 **글로벌 interface**를
대상으로 쓴다(우리 `zif_booking_repo`는 글로벌이라 가능). `FINAL`·`FOR TESTING`·
`CREATE PRIVATE` 선언이 있는 class, 필수 생성자 파라미터가 있는 class도 지원하지
않는다(공식 제약). 그리고 **메서드 한두 개짜리 가짜는 CH27처럼 직접 만드는 쪽이
더 읽기 쉽다** — framework가 항상 정답이 아니다.

## ABAP SQL Test Double — SELECT 자체를 가로채기

interface 분리가 안 된 코드는 이렇게 생겼다. (`zcl_booking_reader`는 "분리를 안
한 나쁜 예"를 보여 주려고 이 레슨에서 만든 가상의 class다 — manager와 달리 DB를
직접 읽는다.)

```abap
METHOD count_booked_seats.
  SELECT COALESCE( SUM( seats ), 0 )
    FROM zbooking
    WHERE concert_id = @iv_concert
      AND status    <> 'C'
    INTO @rv_booked.
ENDMETHOD.
```

(집계 SELECT의 성질 하나 복습: 대상이 0건이어도 결과 한 행이 돌아와
`sy-subrc = 0`이다 — 그래서 `COALESCE`로 빈 합계를 0으로 받는다,
[Chapter 27](CH27-L05.html)의 그 코드와 같은 모양.)

주입할 자리가 없다. 이때 [[SQL Test Double|ABAP SQL Test Double]](테스트 실행
동안 ABAP SQL이 읽는 테이블/CDS view를 테스트 데이터로 바꿔치는 프레임워크.
`CL_OSQL_TEST_ENVIRONMENT`)은 **SELECT가 바라보는 대상 자체**를 테스트 환경으로
격리한다. 실 DB를 건드리는 게 아니라, 테스트가 도는 동안만 `zbooking`이라는 이름이
가짜 데이터를 가리키게 하는 것이다(공식 예제 패턴).

실행은 L02와 같다(`Ctrl+Shift+F10`). 아래에서 `cl_…create`의 결과를
`if_…` 타입 변수로 받는 것은 오타가 아니라 **interface 참조로 받는 것**이다(CH21
그대로. OSQL = Open SQL의 줄임).

```abap
CLASS ltcl_reader DEFINITION
  FOR TESTING RISK LEVEL HARMLESS DURATION SHORT.
  PRIVATE SECTION.
    CLASS-DATA go_sql_env TYPE REF TO if_osql_test_environment.
    " setup 계열 = 정해진 이름의 특수 메서드. 테스트 전/후에 자동 실행된다
    CLASS-METHODS class_setup.     " 전체 테스트 시작 전 1회
    CLASS-METHODS class_teardown.  " 전체 테스트 종료 후 1회
    METHODS setup.                 " 각 테스트 메서드 직전마다
    METHODS booked_from_test_data FOR TESTING.
ENDCLASS.

CLASS ltcl_reader IMPLEMENTATION.
  METHOD class_setup.
    " zbooking을 테스트 환경으로 격리 — 이후 SELECT는 가짜를 읽는다.
    " 여러 개면 괄호를 이어 붙인다: VALUE #( ( 'ZBOOKING' ) ( 'ZCONCERT' ) )
    " CDS view도 이름을 그대로 넣는다(이름 목록 테이블이다)
    go_sql_env = cl_osql_test_environment=>create(
      i_dependency_list = VALUE #( ( 'ZBOOKING' ) ) ).
  ENDMETHOD.

  METHOD setup.
    go_sql_env->clear_doubles( ).   " 이전 테스트의 데이터가 남지 않게
  ENDMETHOD.

  METHOD booked_from_test_data.
    " 테스트 데이터 — 정훈영 30 + 유재석 20 = 50석, 그리고 "실패해야 하는
    " 케이스"용으로 취소(C) 40석을 함께 심는다. WHERE status <> 'C'가 일하지
    " 않으면 90이 나와 red가 된다 — L02에서 넘어온 '취소 약속'의 검증이 이것.
    " (안 채운 필드는 초기값으로 들어간다)
    DATA lt_bookings TYPE STANDARD TABLE OF zbooking WITH EMPTY KEY.
    lt_bookings = VALUE #(
      ( booking_id = '0001' concert_id = 'C001' customer = '정훈영'
        seats = 30 status = 'N' )
      ( booking_id = '0002' concert_id = 'C001' customer = '유재석'
        seats = 20 status = 'N' )
      ( booking_id = '0003' concert_id = 'C001' customer = '강호동'
        seats = 40 status = 'C' ) ).   " 취소 건 — 세어지면 안 된다
    go_sql_env->insert_test_data( lt_bookings ).

    DATA(lo_reader) = NEW zcl_booking_reader( ).
    cl_abap_unit_assert=>assert_equals(
      act = lo_reader->count_booked_seats( iv_concert = 'C001' )
      exp = 50 ).                      " 90이 아니라 50 — 취소가 걸러졌다
  ENDMETHOD.

  METHOD class_teardown.
    go_sql_env->destroy( ).         " 격리 해제 — 반드시 짝
  ENDMETHOD.
ENDCLASS.
```

처음 보는 조각은 `setup` 계열이다. **정해진 이름의 특수 메서드**로, 프레임워크가
테스트 전후에 자동으로 불러 준다(class_setup/teardown = 전체 1회, setup = 매 테스트
직전). 격리 환경처럼 "준비와 정리"가 필요한 테스트의 표준 자리다. 그리고
`insert_test_data`는 실 테이블에 한 줄도 쓰지 않는다 — 격리 환경 안의 데이터라
테스트가 끝나면 환경째 사라진다.

"이게 interface 분리보다 쉬워 보이는데 왜 1순위가 아니지?"라는 의문이 들 수 있다.
답은 **격리는 되지만 설계는 그대로**이기 때문이다. SELECT가 코드 곳곳에 흩어진
구조 자체는 이 도구가 고쳐 주지 않는다. 새 코드는 분리(DI)로 설계를 바로잡는 것이
정답이고, SQL Test Double은 **분리가 안 된(또는 못 하는) 코드를 검증하는
수단**이다.

경계 둘도 분명히 하자. ① 격리는 `create`의 **목록에 넣은 이름에만** 적용된다 —
목록에서 빠진 테이블을 읽고 쓰는 코드는 격리 없이 **실 DB로 그대로 나간다**(목록
누락 하나가 QAS 데이터를 오염시킬 수 있다는 뜻이고, 이런 테스트를 운영에서 절대
돌리지 않는 이유이기도 하다). ② 가로채는 것은 **ABAP SQL뿐**이다 — [Chapter
36](CH36-L03.html)에서 배운 Native SQL(ADBC)과 AMDP는 DB에서 직접 돌기 때문에 이
double이 낄 자리가 없다.

CDS entity 로직을 검증하는 자매 도구로 **CDS Test Double
Framework**(`CL_CDS_TEST_ENVIRONMENT`)가 있다는 것까지만 알아 두자(사용 리듬은
같다: create → 테스트 데이터 → 검증 → 정리). 두 도구의 갈림은 **무엇을 검증
하느냐**다: 검증 대상이 **내 ABAP의 SELECT문**이면 그 SELECT가 CDS view를 읽더라도
SQL Test Double이고, **CDS view 안에 적어 둔 계산·조인 로직 자체**를 검증하려면
CDS Test Double이다.

## TEST-SEAM — legacy를 위한 최후의 완충재

구조를 뜯기 어려운 오래된 코드에는 마지막 수단이 있다.
[[TEST-SEAM]](production 코드 안에 "테스트 때 갈아끼울 수 있는 구간"을 표시하는
문법. 테스트의 TEST-INJECTION이 그 구간을 대체한다)은 코드에 교체 가능 구간을
직접 박는다(공식 keyword doc 확인).

```abap
" zcl_booking_reader의 오래된 메서드라고 가정 — 구조를 못 뜯는 상황
METHOD read_booked_seats.
  TEST-SEAM select_booking.          " 이 구간은 테스트가 갈아끼울 수 있다
    SELECT SUM( seats )
      FROM zbooking
      WHERE concert_id = @iv_concert
        AND status    <> 'C'
      INTO @rv_booked.
  END-TEST-SEAM.
ENDMETHOD.
```

```abap
" 주의: TEST-INJECTION은 seam이 있는 그 개발 객체의
" 로컬 테스트 클래스 안에서만 쓸 수 있고(같은 컴파일 단위),
" 대체 효력은 이 테스트 메서드가 도는 동안만이다 — 다른 테스트에선 원래 코드
METHOD booked_seats_without_db.
  TEST-INJECTION select_booking.     " seam 구간을 이 코드로 대체
    rv_booked = 50.
  END-TEST-INJECTION.

  cl_abap_unit_assert=>assert_equals(
    act = NEW zcl_booking_reader( )->read_booked_seats( iv_concert = 'C001' )
    exp = 50 ).
ENDMETHOD.
```

눈치챘겠지만 이 테스트는 약속 검증이라기보다 **"seam 교체가 되는지"의 배선
확인**이다(50을 주입하고 50이 나오는지 — 주입한 값을 그대로 본다). seam의 진짜
용도는 이렇게 배선을 확보한 뒤, DB를 끊은 상태에서 **그 메서드의 나머지 로직**을
검증하는 것이다.

단순해 보여서 매력적이지만, **production 코드에 테스트용 흔적이 남는다**는 큰
대가가 있다. 공식 문서도 test seam을 "분리가 부족해 unit test가 어려운 legacy
코드의 보완 수단"으로 규정하고, **ABAP Cloud의 제한 언어 버전에서는 아예 쓸 수
없다** — 최후 수단일 뿐 아니라 미래로 가져갈 수 없는 수단이다. **새로 쓰는 코드에
seam부터 넣는 것은 설계가 잘못됐다는 경고 신호다** — 먼저 interface 분리(CH27)를
검토하라.

## 흔한 실수와 점검 🚧

- **framework부터 집는 습관** → 메서드 한두 개면 직접 Mock(CH27)이 가장 읽기 쉽다.
  단순한 수단 먼저, framework는 그게 부족할 때.
- **새 코드에 TEST-SEAM** → legacy 보완용이다. 새 설계에서 seam이 필요해 보이면
  의존성 분리부터 다시 생각한다.
- **테스트 데이터 정리 생략** → 이전 테스트의 데이터가 다음 테스트를 오염시키면
  실행 순서에 따라 결과가 달라진다. `clear_doubles`/`destroy`를 짝으로.
- **상호작용 검증 남용** → "몇 번 불렸는지"까지 전부 검증하면 내부 구현만 바꿔도
  테스트가 깨진다. 바깥에서 보이는 결과 검증을 우선한다.
- **double로 테스트를 "통과시키려는" 발상** → double은 통제 장치이지 면죄부가
  아니다. 정상 케이스와 **실패해야 하는 케이스**를 모두 다뤄야 약속 검증이다.

## 정리 📌

- 선택 기준 = **의존성의 모양**: interface 있음 → **직접 Mock(1순위)**, 메서드가
  많거나 상호작용 검증이 필요할 때만 `CL_ABAP_TESTDOUBLE` · 직접 SELECT → **SQL
  Test Double** · CDS 로직 → CDS Test Double · 못 뜯는 legacy →
  `TEST-SEAM`(최후).
- 새 코드의 정답은 언제나 **DI + interface 분리**(CH27). framework와 seam은 그게
  안 될 때의 도구다.
- 격리 환경은 준비·정리가 생명: `setup` 계열 특수 메서드 +
  `clear_doubles`/`destroy`.
