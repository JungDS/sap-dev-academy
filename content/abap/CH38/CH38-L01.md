## 리뷰를 통과한 코드가 운영에서 터졌다

정훈영의 정산 프로그램이 코드 리뷰를 통과하고 운영에 나갔다. 그런데 한 달 뒤,
데이터가 쌓이자 밤 정산이 몇 시간씩 걸리기 시작했다. 원인은 반복문 안에 숨어 있던
`SELECT` 하나. 리뷰어도 봤던 코드다. **사람은 피곤하면 놓친다.** 조건 없는 SELECT,
빠진 권한 검사, 쓰다 만 변수 같은 것들을 매번 눈으로 전부 찾아내는 것은 불가능에
가깝다.

더 나쁜 것은 발견 시점이다. 운영 반영 직전이나 반영 후에 발견되면, 급하게 고치다
다른 기능을 깨고 "이번만 예외"가 쌓이며 품질 기준 자체가 무너진다.

그래서 필요한 것이 **자동 품질 게이트**다. "내가 보기엔 괜찮다"가 아니라, 팀이 정한
검사 기준을 기계가 매번 같은 눈으로 적용하고, 기준 미달이면 **운영으로 가는 문
자체를 잠근다.**

> 🧰 **이 챕터의 준비물** — CH38의 여섯 레슨은 같은 소재를 공유한다: 정산 리포트
> `ZBOOK_SETTLE`(이 챕터의 가상 주인공 — 실습은 [Chapter 27](CH27-L05.html)의
> `zcl_booking_manager`류로 대신해도 된다), `zbooking` 테이블([Chapter
> 9](CH09-L09.html)), message class `ZBOOK`([Chapter 15](CH15-L04.html)의 SE91),
> 그리고 도구는 **ADT**([Chapter 23](CH23-L01.html)에서 설치·사용한 그
> Eclipse)와 SAP GUI를 오간다. 각 레슨에서 처음 만나는 화면(`SLG0` 등록, variant
> 저장)은 그 레슨에서 안내한다.

## ATC — 검사들을 모아 실행하는 조종석

그 게이트가 [[ATC]](ABAP Test Cockpit. 여러 품질 검사를 모아 실행하고 결과를
관리하는 SAP의 검사 프레임워크)다. 이름의 Cockpit(조종석)이 정체를 잘 말해 준다:
검사 하나가 아니라, **여러 검사를 한 자리에서 실행하고 결과를 한 형식으로 모아
주는 틀**이다. 그 안에 들어가는 검사들은 이미 아는 것도 있다.

| ATC가 실행하는 검사 | 어디서 온 검사인가 |
|---|---|
| 확장 구문 검사(extended program check) | 활성화 때 도는 구문 검사를 더 깐깐하게 넓힌 검사 |
| [[Code Inspector]](`SCI`. ATC 이전부터 있던 정적 코드 검사 도구 — 성능·보안·관례 검사 묶음) 검사 | 이 레슨에서 처음 만남 — ATC의 검사 엔진 상당수가 여기서 온다 |
| ABAP Unit 테스트 | [Chapter 27 · Testable Class와 ABAP Unit](CH27-L05.html) — [다음 레슨](CH38-L02.html)에서 운영 관점으로 |
| Cloud readiness(released API) 검사 | [Chapter 24 · ABAP Cloud](CH24-L08.html)의 released API 규율 |

Code Inspector(`SCI`)와의 관계를 한 줄로 정리하면: SCI는 **오래된 정적 검사
도구**이고, ATC는 SCI의 검사들을 포함해 **더 넓은 품질 프로세스(이송 게이트까지)에
연결하는 상위 틀**이다. 오래된 시스템에는 SCI variant가 그대로 살아 있어서 둘 다
이름을 알아 둬야 한다.

## 결과를 읽는 다섯 단어

ATC를 실행하면 쏟아지는 것은 "합격/불합격"이 아니라 **finding 목록**이다. 다섯
단어만 잡으면 결과 화면이 읽힌다.

| 용어 | 쉬운 뜻 | 확인 질문 |
|---|---|---|
| **Check variant** | 어떤 검사 묶음을 돌릴지 정한 설정 | 성능·보안·Cloud readiness가 포함돼 있는가 |
| **Finding** | 검사가 발견한 문제 한 건 | 어느 객체, 어느 줄, 어떤 종류인가 |
| **Priority** | finding의 심각도 — 보통 1～3단계(P1=오류급, P2=중요 경고, P3=참고). 검사·variant가 정해서 **개발자에겐 "정해져 오는 값"**이다 | P1/P2를 막는 급으로 취급하는 것이 원칙 — 실제로 버튼을 잠그는 강제는 게이트 설정의 몫 |
| **Exemption** | 승인된 예외("이건 수정 안 해도 됨") | 근거·승인자·만료가 기록돼 있는가 |
| **Release gate** | 이송 release 시점의 자동 검사 연동 | 기준 미달이면 release 버튼이 막히는가 |

정산 프로그램에서 실제로 만나는 finding은 이런 모양이다.

| Finding | 의미 | 조치 |
|---|---|---|
| SELECT without WHERE | 조건 없이 대량 데이터를 읽을 수 있음 | 조건·인덱스 확인([Chapter 35 · ST05](CH35-L01.html)) |
| Missing authorization check | 권한 검증 누락 가능 | `AUTHORITY-CHECK` 확인([Chapter 15 · 권한](CH15-L07.html)) |
| Unreleased API used | Cloud/Clean Core 위반 가능 | released API로 대체 또는 예외 검토([Chapter 24](CH24-L08.html)) |
| Unused variable | 유지보수 노이즈 | 삭제 또는 실제 사용 확인 |

한 가지 현실 정보: 보안 계열 검사(권한 누락 탐지 등)의 상당수는 별도 라이선스
애드온(Code Vulnerability Analyzer)에서 온다. **그 라이선스가 없는 시스템에서는
이런 finding이 아예 안 뜬다** — "ATC 통과 = 보안 문제 없음"이 아닐 수 있다는
뜻이다.

직접 한 번 돌려 보는 경로는 이렇다(도구 조작이지만 최소 경로는 알아 두자).

1. ADT에서 검사할 **대상**(클래스·프로그램, 또는 패키지 통째)을 프로젝트 트리에서
   우클릭 → **Run As → ABAP Test Cockpit**. variant 선택 창이 뜨면 팀이 지정한
   것을, 지정이 없으면 시스템 기본 variant로 실행된다.
2. 결과 목록에서 finding을 **더블클릭하면 해당 소스 줄로 이동**한다 — 고치고 다시
   1을 실행해 **finding이 사라졌는지 확인**하는 것까지가 한 사이클이다(결과
   화면에는 어떤 variant로 검사했는지도 함께 표시된다).
3. 예외가 필요한 finding은 결과 화면에서 그 finding을 선택해 **exemption을
   신청**한다(근거·승인자를 입력하는 절차가 이어진다 — 승인 후 만료일이 지나면
   예외도 끝난다. 임시 허용이 영구가 되지 않게 하는 장치다).

> 🔭 **기대 관리** — SAP GUI 쪽 관리 화면(트랜잭션 `ATC`)과 check variant를 만들어
> 팀 기준으로 등록하는 일은 품질 담당·운영 정책 영역이라 이 과정 범위 밖이다.
> **release gate 연동 여부도 시스템 설정**이라 개발자가 켜는 것이 아니다 — 내
> 시스템에 켜져 있는지는 간단히 알 수 있다: 이송 release를 시도할 때 검사가
> 자동으로 돌면 켜진 것이다(모르면 품질 담당에게 한 번 물어보면 된다).

## 판단이 필요한 곳 — 수정인가, 예외인가

finding이 나왔다고 전부 고치는 것은 아니다. 판단의 갈림길은 둘뿐이다.

1. **수정** — P1/P2(높은 심각도)는 원칙적으로 고친다. release gate가 연결돼 있으면
   고치기 전엔 이송이 나가지 않는다.
2. **Exemption(예외 승인)** — 근거가 있을 때만. 예: 표준 프로그램을 복사한 코드의
   관례 위반, 도구가 오탐한 경우. 승인자는 보통 팀 리더·품질 담당이고(신청하면
   그쪽으로 넘어간다), **근거·승인자·만료**가 기록으로 남는다. 주의: 만료는 도구가
   강제해 주는 것이 아니라 **무기한 예외도 신청 가능**하다 — 기한을 다는 것은 팀
   규율이다. "귀찮아서 무시"가 쌓이면 게이트는 장식이 된다.

참고로 오래된 코드에 ATC를 처음 켜면 finding이 수천 건 쏟아지는데, 그때의 표준
대응은 예외 수천 건이 아니라 **baseline(기준선)**이다: 기존 finding은 기준선
아래 묻어 두고, **오늘 이후 새로 생기는 finding만 게이트로 막는다.** 그리고 운영
규모에서는 각자 돌리는 게 아니라 **중앙 ATC 시스템이 여러 시스템을 원격 검사**해
같은 variant를 강제한다 — "팀이 정한 기준을 기계가 같은 눈으로"가 실제로 성립하는
방식이다.

## 흔한 실수와 점검 🚧

- **마지막 날 한 번만 실행** → 반영 직전의 ATC는 이미 늦다. 개발 중·이송 release
  전에 여러 번 돌려 작게 고친다.
- **경고를 전부 꺼 버림** → variant를 느슨하게 만들면 통과는 쉬워지지만 게이트의
  의미가 사라진다. 통과 이력이 품질 근거가 되려면 기준이 살아 있어야 한다.
- **근거 없는 exemption** → 예외는 운영 기록이다. 근거·승인자·만료 없는 예외는
  나중에 아무도 책임지지 못한다.
- **ATC가 리뷰를 대체한다는 착각** → 기계는 패턴을 잡는다. 업무 규칙 누락·설계
  문제·장애 대응 절차는 여전히 사람이 본다.
- **Cloud readiness 무시** → classic 시스템에서 도는 코드도 Cloud로 갈 때 막힐 수
  있다는 예고다. 지금 고칠지는 판단이지만, 모르고 지나치면 안 된다.

## 정리 📌

- ATC = 여러 검사를 모아 실행하고 **이송 게이트까지 연결**되는 품질 조종석. Code
  Inspector(SCI)는 그 검사 엔진의 뿌리.
- 실행 사이클 = 대상 우클릭 → 실행 → finding 더블클릭·수정 → **재실행해 초록
  확인.**
- 결과 읽기 = **variant → finding → priority → 수정/exemption → release gate.**
  variant를 만드는 건 품질 담당의 일이지만, **어느 variant로 검사됐는지 읽는 것**은
  결과 화면에 있는 정보다 — 그걸 말할 수 있으면 된다.

---

정적 검사는 코드의 모양을 본다. 그런데 모양이 멀쩡해도 **동작이 약속을 깨는**
변경이 있다. 고친 코드가 기존 기능을 깨지 않았는지 자동으로 확인하는 장치로 간다.
