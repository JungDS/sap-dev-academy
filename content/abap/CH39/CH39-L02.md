## 입문 장의 ZI_Booking, 무엇이 모자란가

[Chapter 24](CH24-L02.html)에서 만든 `ZI_Booking`은 여섯 필드짜리 최소 모델이었다.
입문에는 충분했지만, 이 챕터의 완료 기준(동시 수정 통제·Draft 복구)을 대려면 두
가지가 모자란다.

1. **관계가 안 보인다** — 공연·회차와의 association을 정의만 하고 노출하지 않으면,
   뒤의 projection·service가 그 길을 따라갈 수 없다.
2. **"언제 바뀌었나"가 없다** — 동시 수정을 감지하는 ETag([L08](CH39-L08.html)에서
   정식으로)는 **변경 시각 필드**를 기준으로 삼는다. 지금 `zbooking`의 감사
   필드는 날짜(`changed_on`)와 시각(`changed_at`)이 나뉘어 있어 비교 기준으로
   불안하다.

## 걸음 1 — 테이블에 변경 추적 필드 추가

`zbooking`에 필드 **둘**을 더한다(표준 관례 그대로 — 둘의 용도는
[L08](CH39-L08.html)에서 갈라진다):

```abap
" ADT 테이블 DDL의 필드 목록 맨 끝에 두 줄 추가
local_last_changed_at : timestampl;   " 이 건의 변경 표식(ETag용)
last_changed_at       : timestampl;   " 초안 복귀 비교 표식(total ETag용)
```

타입은 **TIMESTAMPL**(날짜+시각+소수초가 **한 값**인 timestamp. 날짜·시각 두
필드로 비교하면 자정 경계에서 순서가 꼬일 수 있지만, 한 값이면 비교가 항상 한
번에 끝난다). 기존 감사 필드(`created_*`·`changed_*`)는 그대로 둔다 — [Chapter
25](CH25-L01.html)의 classic 프로그램들이 채워 온 기록이고, RAP 경로에서는
`@Semantics`가 붙은 관리 필드가 그 역할을 이어받는다(자동 갱신의 스위치는 필드가
아니라 **annotation + CDS 노출 + BDEF mapping**의 세 박자다 — 기존 필드에 그
세 박자를 안 갖췄으니 자동이 아니었던 것).

절차: ① ADT(또는 SE11)에서 `zbooking`을 열어 위 두 줄 추가 → ② 활성화(`Ctrl+F3`)
— 데이터가 있는 테이블이라도 필드 **추가**는 대개 시스템이 알아서 조정하고, 기존
행의 새 필드는 초기값으로 남는다(각 행이 다음에 변경될 때 채워진다 — 비교에
문제없다). 드물게 활성화가 조정 오류로 막히면 `SE14`(DB 조정 도구)에서 조정한다
→ ③ 테이블 확장이니 [Chapter 38의 짝 변경 규율](CH38-L06.html) 그대로, CDS·BDEF
변경과 같은 request로 간다.

"나중에 추가하지 말라더니 우리가 지금 나중에 추가하고 있지 않나?"라는 의문이
들었다면 정확하다 — 입문 장 시점에는 ETag가 배움 밖이라 뺐던 것이고, 지금이 우리
커리큘럼의 "처음"이다. 실무 신규 설계라면 이 필드는 첫 설계에 들어간다.

## 걸음 2 — Interface View에 관계와 추적 필드 노출

association의 상대인 `ZI_Concert`·`ZI_Perf`는 입문 장에서 만들지 **않았다** — 지금
만든다([Chapter 23](CH23-L01.html) 문법 그대로의 단순 view라 아래 최소 정의면 충분하다).

(만들기: ADT에서 **New → Core Data Services → Data Definition** — 이 경로는
Chapter 23에서 쓰던 그대로다.)

```cds
// ZI_Concert — 최소 정의(신규)
@AccessControl.authorizationCheck: #NOT_REQUIRED  // 연습용(세 view 공통)
define view entity ZI_Concert
  as select from zconcert
{
  key concert_id as ConcertId,
      artist     as Artist,
      capacity   as Capacity
}
```

```cds
// ZI_Perf — 최소 정의(신규)
@AccessControl.authorizationCheck: #NOT_REQUIRED
define view entity ZI_Perf
  as select from zperf
{
  key concert_id as ConcertId,
  key perf_no    as PerfNo,
      perf_date  as PerfDate
}
```

(필드 이름은 각자의 실습 테이블 정의에 맞춘다 — 요점은 "association 상대가 실존
해야 한다"는 것.) 이제 `ZI_Booking`은 **입문 장에서 만든 DDL 소스를 ADT에서 열어** 아래
완성형으로 고친다(새 파일이 아니라 기존 것의 확장이다).

```cds
@AccessControl.authorizationCheck: #NOT_REQUIRED  // 연습용 — 운영은 #CHECK + DCL(접근 제어 장)
@EndUserText.label: 'Booking Interface View'
define root view entity ZI_Booking
  as select from zbooking
  association [0..1] to ZI_Concert as _Concert
    on $projection.ConcertId = _Concert.ConcertId
  association [0..1] to ZI_Perf as _Perf
    on  $projection.ConcertId = _Perf.ConcertId
    and $projection.PerfNo    = _Perf.PerfNo
{
  key booking_id      as BookingId,
      concert_id      as ConcertId,
      perf_no         as PerfNo,
      customer        as Customer,
      seats           as Seats,
      status          as Status,

      @Semantics.user.createdBy: true   // 이것도 관리 필드 — 런타임이 자동으로
      created_by      as CreatedBy,     // 채운다(L08 소유자 판정의 근거가 된다)

      @Semantics.systemDateTime.localInstanceLastChangedAt: true
      local_last_changed_at as LocalLastChangedAt,  // 이 건의 변경 표식(ETag)

      @Semantics.systemDateTime.lastChangedAt: true
      last_changed_at as LastChangedAt,             // 초안 복귀 표식(total ETag)

      _Concert,     // 관계를 '노출'해야 뒤 계층이 따라간다
      _Perf
}
```

카디널리티를 `[0..1]`로 쓴 이유도 짚자. `[1..1]`은 "상대가 반드시 존재한다"는
선언이라, 시스템이 그걸 믿고 조회를 최적화하다가 **마스터가 없는 예매 행이
목록에서 소리 없이 빠질 수 있다.** DB가 외래키를 강제하지 않는 우리 Z 테이블에선
`[0..1]`(있을 수도)이 정직한 선언이다.

입문 장 대비 새 조각만 짚는다(기준선: 그때는 key+업무 5필드의 여섯 필드였다. 신규 =
association 2 + 감사 필드 노출(`CreatedBy`) + 변경 추적 필드 둘(`LocalLastChangedAt`·`LastChangedAt`)).

- **association을 select list에 노출**(`_Concert`, `_Perf`) — 정의만 하고 노출을
  빼먹으면 projection·Fiori에서 그 관계가 보이지 않는다([Chapter 23](CH23-L03.html)에서 배운 association
  문법 그대로, 이번엔 노출까지가 요점).
- **`@Semantics.systemDateTime.…` 두 annotation** — "이 필드가 이 건의 마지막 변경
  시각"(localInstance…)·"초안 복귀 비교용 변경 시각"(lastChangedAt)이라는 의미를 밝힌다. **채우는 주체는 managed 런타임이다**: 이렇게
  의미가 선언된 관리 필드는 변경이 저장될 때마다 프레임워크가 자동으로
  갱신한다(그래서 [L04](CH39-L04.html)에서 이 필드들을 readonly로 잠근다 — 사람도
  우리 코드도 아닌 시스템의 필드다). 우리가 채우는 코드는 챕터 끝까지 나오지
  않는 것이 **정상**이다.
- `$projection.ConcertId` — ON 조건은 **CDS가 노출한 별칭 기준**이다. 테이블
  원필드명(`concert_id`)과 섞으면 활성화 오류가 난다.

## composition — 지도만 미리 본다

우리 예매는 root 하나로 충분하다. 하지만 실무 문서(주문+품목 등)에서는 root가
여러 줄의 자식을 **생명주기까지 책임지는** 구조가 흔하고, 그때 쓰는 것이
composition이다. 문법 모양만 지도로 봐 두자(이 챕터에서 만들지는 않는다).

```cds
define root view entity ZI_Order
  as select from zorder
  composition [0..*] of ZI_OrderItem as _Items   // 자식의 생명주기를 책임짐
{ key order_id as OrderId, _Items }

define view entity ZI_OrderItem
  as select from zorder_i
  association to parent ZI_Order as _Order       // 자식 → 부모로 가는 길
    on $projection.OrderId = _Order.OrderId
{ key order_id as OrderId, key item_no as ItemNo, _Order }
```

**association vs composition**: association은 "따라갈 수 있는 관계"(공연은 예매가
지워져도 남는다), composition은 "root가 지워지면 자식도 함께"인 강한 포함이다.
자식 쪽에는 `association to parent`가 짝으로 붙는다.

## 확인하는 법

1. 활성화 후 Data Preview에서 두 추적 필드가 보이는가(값은 비어 있는 게 정상 —
   채우는 주체는 managed 런타임이고, 그 계약이 완성되는 것은 L04의 mapping까지다).
2. association 노출 확인: preview에서 `_Concert`를 따라 공연명이 열리는가.
3. key가 인스턴스를 안정적으로 식별하는가([Chapter 24 · 모델 설계](CH24-L02.html)의 그 질문 — 여전히 유효).

## 흔한 실수와 점검 🚧

- **association 정의만 하고 노출 생략** → 뒤 계층에서 "관계가 없다"로 보인다.
  select list의 `_Concert` 한 줄까지가 정의다.
- **별칭과 원필드명 혼용** → `$projection.` 뒤에는 노출한 별칭만.
- **변경 추적 필드를 나중에 추가** → 테이블·CDS·BDEF·draft 테이블이 전부 다시
  흔들린다. **처음부터 설계에 넣는 것**이 이 레슨의 존재 이유다.
- **composition 남용** → 함께 죽어야 할 관계에만. 공연↔예매처럼 각자 사는 관계는
  association이다.

## 정리 📌

- 입문 장 뼈대에 두 가지를 더했다: **관계 노출**(_Concert·_Perf)과 **변경 추적 필드
  둘**(`local_last_changed_at`·`last_changed_at` TIMESTAMPL + `@Semantics` — 채움은
  managed 런타임).
- ETag([L08](CH39-L08.html))가 앉을 자리를 지금 만들었다 — 나중에 넣으면 전 계층이
  다시 흔들린다.
- composition/to-parent는 지도만: root가 자식의 생명주기를 책임질 때 쓰는 강한
  포함 관계.
