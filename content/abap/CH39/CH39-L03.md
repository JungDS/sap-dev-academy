## 보여 줄 모델과 저장할 모델은 다르다

[Chapter 24](CH24-L03.html)에서 projection의 존재 이유를 배웠다: Interface View는
업무 객체의 중심 모델이라 그대로 내보내기엔 너무 내부에 가깝다. Capstone에서는 그
원칙을 **의도적인 계약**으로 끌어올린다 — 어떤 필드를 목록에, 무엇을 상세 화면에,
어떤 관계를 소비자에게 허용할지 전부 결정의 결과여야 한다.

## ZC_Booking — 소비 계약 완성형

CH24의 `ZC_Booking` DDL 소스를 열어 아래 완성형으로 고친다.

```cds
@AccessControl.authorizationCheck: #NOT_REQUIRED  // 연습용 — 운영은 #CHECK + DCL(CH23-L06)
@Metadata.allowExtensions: true
@EndUserText.label: 'Booking Consumption View'
define root view entity ZC_Booking
  provider contract transactional_query
  as projection on ZI_Booking
{
  key BookingId,

      @UI.lineItem:       [ { position: 10, label: 'Concert' } ]
      @UI.identification: [ { position: 10, label: 'Concert' } ]
      ConcertId,

      @UI.lineItem:       [ { position: 20, label: 'Performance' } ]
      @UI.identification: [ { position: 20, label: 'Performance' } ]
      PerfNo,

      @UI.lineItem:       [ { position: 30, label: 'Customer' } ]
      @UI.identification: [ { position: 30, label: 'Customer' } ]
      Customer,

      @UI.lineItem:       [ { position: 40, label: 'Seats' } ]
      @UI.identification: [ { position: 40, label: 'Seats' } ]
      Seats,

      @UI.lineItem:       [ { position: 50, label: 'Status' } ]
      @UI.identification: [ { position: 50, label: 'Status' } ]
      Status,

      LocalLastChangedAt,  // 화면 컬럼은 아니지만 '노출'은 한다 — ETag 표식으로
      LastChangedAt,       // 주고받아야 하므로(표시≠노출. 값은 HTTP 헤더로 오가고
                           // 충돌은 412 응답으로 돌아온다 — Fiori가 자동 처리)

      _Concert,        // 소비자에게 허용하기로 '결정'한 관계만
      _Perf
}
```

CH24 대비 새 조각은 하나다. **`provider contract
transactional_query`** — "이 projection은 트랜잭션형 UI·서비스 소비용"이라는
계약 선언이다. 안 붙이면 이 view의 용도가 불명확해져 활성화·서비스 단계에서 용도
검사가 제대로 서지 못한다 — 뒤(L04)의 `strict` 모드와 같은 철학: **용도를 밝힌
계약만이 검사받을 수 있다.** 나머지 `@UI.lineItem`(목록 컬럼)·
`@UI.identification`(상세 화면 필드)은 CH24에서 본 그대로, 이번엔
**position·label을 의도적으로** 배치했다.

## Annotation이 늘어나면 — Metadata Extension

`@UI`가 쌓이면 view 본문이 화면 배치 코드로 뒤덮인다. 그래서 화면용 annotation은
**Metadata Extension**(별도 파일로 annotation만 얹는 확장)으로 분리하는 것이
관례다(CH23에서 존재를 배웠다 — 여기서 실제로 쓴다). 머리의
`@Metadata.allowExtensions: true`가 그 허가다. 만들기: ADT에서 **New → Core Data
Services → Metadata Extension**, 이름은 대상 view와
같게 지어도 된다(오브젝트 종류가 달라 충돌하지 않는다 — 헷갈리면
`ZC_BOOKING_MDE`처럼 접미어를 붙여도 무방). 만든 뒤 **활성화까지** 해야 화면에
반영된다.
`@Metadata.layer`는 "이 확장이 어느 층의 것인가"의 표시다 — SAP 표준(#CORE) 위에
고객(#CUSTOMER)이 겹쳐 얹는 층 구조라, 우리가 만드는 것엔 `#CUSTOMER`를 쓴다.

배치의 최종 결론도 분명히 하자: **최종형은 화면 annotation 전부를 MDE로 옮기는
것**이다. 이 레슨의 view 본문 코드는 각 annotation의 뜻을 한 화면에서 읽게 하려는
이해용 최소형이고, 실습 마무리에서 `@UI.lineItem`·`identification`도 facet처럼
MDE로 옮겨 보라(view 본문에는 데이터 계약만 남는다). 같은 annotation이 양쪽에
있으면 **더 높은 layer(MDE) 쪽이 우선**하므로 옮기는 중간 상태도 안전하고,
다 옮긴 뒤에도 **화면은 똑같아야 정상**이다(선언의 자리만 옮긴 것이니까).

```cds
@Metadata.layer: #CUSTOMER
annotate entity ZC_Booking with
{
  @UI.facet: [ { id:       'Booking',
                 purpose:  #STANDARD,
                 type:     #IDENTIFICATION_REFERENCE,
                 label:    'Booking',
                 position: 10 } ]
  BookingId;
}
```

`@UI.facet`은 Object Page(상세 화면)의 **구역**을 정의한다 —
`#IDENTIFICATION_REFERENCE` facet이 있어야 `@UI.identification` 필드들이 그
구역에 나타난다. "identification을 달았는데 상세 화면이 비어요"의 1순위 원인이
facet 누락이다. (facet이 `BookingId`에 붙어 있는 것은 그 필드의 장식이 아니라
**annotation을 얹을 자리가 필드 단위**라서다 — 구역 정의는 화면 전체에 작용한다.)

## 확인하는 법

1. 활성화 → [L07](CH39-L07.html)에서 Preview로 실물 확인(지금은 선언까지).
2. `@UI.lineItem` 필드들이 position 순서대로 목록 컬럼 후보가 된다.
3. `_Concert`·`_Perf` 노출이 **결정**인지 자문 — 소비자가 공연 정보를 따라가야
   하는가? (우리는 예, 목록에 공연명을 보여 줄 것이므로.)

## 흔한 실수와 점검 🚧

- **Interface View 복사본 projection** → 계약이 아니라 복제다. 노출 필드·관계·
  주석 하나하나가 결정이어야 한다.
- **`@UI`에 업무 규칙 기대** → `@UI.lineItem`은 컬럼을 만들 뿐, 정원 초과를 막는
  것은 [Behavior의 validation](CH39-L05.html)이다. 화면 주석과 업무 규칙을 섞지
  말 것.
- **facet 없이 identification만** → Object Page가 비어 보인다. 구역(facet) 먼저,
  필드 배치는 그 다음.
- **annotation을 view 본문에 계속 쌓기** → Metadata Extension으로 분리 —
  데이터 계약과 화면 배치는 다른 관심사다.

## 정리 📌

- projection = **소비자 계약.** `provider contract transactional_query`로 용도를
  선언하고, 노출·주석·관계를 의도적으로 결정한다.
- 화면 배치 annotation은 **Metadata Extension**으로 분리. Object Page 구역은
  `@UI.facet`이 만든다.
- 추적 필드 둘(`LocalLastChangedAt`·`LastChangedAt`)은 노출하되 화면 컬럼은
  아니다 — 표시와 노출을 구분해 나른다.
