## 두 사람이 같은 예매를 열었다

운영 첫 주에 반드시 만나는 장면: 담당자 정훈영이 예매 0031을 편집하는 동안,
유재석이 같은 건을 연다. 누가 이기는가? 정훈영이 편집하다 퇴근했다가 내일
이어서 쓰면? 그 사이 유재석이 먼저 고쳤다면?

[L04](CH39-L04.html)에서 계약으로 선언만 했던 네 장치가 이 장면의 답이다. 넷은
**다른 질문에 답하는 다른 물건**이다 — 이 구분이 이 레슨의 전부다.

| 장치 | 답하는 질문 | 방식 |
|---|---|---|
| **Lock** | 편집 중인 지금, 남이 끼어드는가 | 비관적 — 먼저 잡은 사람이 배타 점유 |
| **ETag** | 내가 읽은 뒤 남이 바꿨는가 | 낙관적 — 저장 시점에 비교·감지 |
| **Draft + total ETag** | 쓰다 만 것으로 돌아와도 안전한가 | 초안 보관 + 복귀 시점 비교 |
| **Authorization** | 애초에 볼/할 자격이 있는가 | 서버 판정(global/instance) |

## Lock — 편집 중의 배타 점유

[Chapter 26](CH26-L02.html)에서 classic ENQUEUE를 배웠다. RAP의 `lock master`는
같은 목적의 **선언형** 장치다: 사용자가 편집을 시작하면 framework가 그 instance에
배타 잠금을 잡고, 유재석의 편집 시도는 "정훈영이 편집 중"으로 거부된다.
"CH26처럼 내가 ENQUEUE를 직접 부르면 안 되나?"라는 의문이 정당한데, 답은 **잠금의
주인이 이미 있다**는 것이다 — RAP 런타임이 편집 시작·초안 전환·만료까지 잠금의
생애를 관리하므로, 우리가 따로 부르면 이중 관리가 되어 서로를 방해한다. 계약이
선언하면 런타임이 수행한다.

단, 잠금은 **만료된다.** Draft를 켠 BO에서 사용자가 자리를 비우면 배타 잠금이
영원히 유지되지 않는다(자원 보호 — 만료까지의 시간은 시스템 설정이 정하며, 정확한
값은 Basis 영역이다). 잠금이 끝난 뒤의 세계를 문서들은 **optimistic
phase**(낙관 국면)라 부른다 — 여기부터는 ETag의 시간이다.

## ETag — 저장 시점의 충돌 감지

[[ETag]](내가 읽은 데이터의 "버전 표식". 저장 요청 시 서버의 현재 표식과 비교해,
다르면 그사이 남이 바꿨다는 뜻이므로 거부한다)의 동작은 단순하다.

1. 유재석이 예매 0031을 읽는다 — 그때의 `LocalLastChangedAt`이 함께 온다(표식).
2. 그 사이 정훈영이 좌석을 고쳐 저장 — `LocalLastChangedAt`이 갱신된다.
3. 유재석이 저장을 시도 — 자기가 읽었던 표식과 서버의 현재 표식이 다르다 →
   **거부.** 이 거부는 우리 코드가 아니라 런타임이 만든다 — 서비스 차원에서는
   HTTP **412**(Precondition Failed)로 돌아오고, Fiori는 그것을 "다른 사용자가
   변경했습니다" 류의 표준 안내로 보여 준다.

덮어쓰기 사고(마지막 저장자가 조용히 이김)를 **감지·거부**로 바꾸는 장치다.
`etag master LocalLastChangedAt`이 그 표식 필드의 지정이었다.

**total etag**는 같은 원리를 **Draft 복귀 시점**에 적용한다: 초안을 만들어 두고
자리를 비운 사이(잠금은 만료) active 데이터가 바뀌었다면, Resume 순간 total
ETag가 그것을 감지해 위험한 이어쓰기를 막는다. draft BO에서 필수인 이유가
이것이다. L02에서 필드를 **둘** 만든 이유가 여기서 완성된다: 개별 변경
감지용(`local_last_changed_at` = etag master)과 초안 복귀 비교용
(`last_changed_at` = total etag)은 **다른 질문에 답하는 다른 표식**이라 각자의
필드를 갖는다 — 표준 관례 그대로다.

## Authorization과 Features — 자격과 상태는 다른 판정

권한은 두 질문으로 갈린다. **"어떤 행을 볼 수 있나"는 DCL**([Chapter
23](CH23-L06.html)의 접근 제어 — 우리 연습 view는 `#NOT_REQUIRED`로 두었으니 운영
전환 때 `#CHECK` + DCL로 승급하는 항목이다)이, **"무엇을 할 수 있나"는 BDEF
authorization**이 맡는다. 그리고 셋째 판정이 따로 있다: "지금 이 건의 **상태**에서
그 동작이 가능한가"는 권한이 아니라 **features**의 자리다(L04에서
`( features : instance )`로 선언한 그것). 자격은 사람에 대한 판정, 상태는 데이터에
대한 판정 — 갈라서 구현한다.

```abap
METHOD get_global_authorizations.
  " ⚠ 실습 지시: 이 메서드는 **비워 둔다**(비어 있으면 전부 허용 — 연습에 적합).
  "   아래 주석 코드는 운영에서 채울 '모양'의 참고다. 권한 오브젝트가 없는
  "   시스템에서 그대로 살리면 AUTHORITY-CHECK가 실패해 나 자신의 생성까지
  "   전부 막힌다(L06 실습이 통째로 죽는 원인이 된다).
  "
  " IF requested_authorizations-%create = if_abap_behv=>mk-on.
  "   AUTHORITY-CHECK OBJECT 'ZBOOKAUTH'    " SU21에서 만든 권한 오브젝트 전제
  "     ID 'ACTVT' FIELD '01'.
  "   IF sy-subrc = 0.
  "     result-%create = if_abap_behv=>auth-allowed.      " 허용도 명시가 관례
  "   ELSE.
  "     result-%create = if_abap_behv=>auth-unauthorized.
  "   ENDIF.
  " ENDIF.
  " (요청 안 된 operation은 판정하지 않아도 된다 — 런타임이 요청한 것만 묻는다.
  "  auth 핸들러는 역할·프로파일이라는 기본 보호 '위에' 얹는 추가 제한 장치라
  "  기본값이 개방이다)
ENDMETHOD.

METHOD get_instance_authorizations.
  " instance '자격': 이 건에 대한 사람의 권리 — 예: 본인이 만든 예매만 취소 가능
  " (연습 단순화 — 운영에선 '본인 또는 관리자 권한'으로 넓힌다: 배치·통신
  "  사용자가 소비자가 되는 순간 '본인만'은 바로 깨지는 규칙이다)
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    FIELDS ( CreatedBy ) WITH CORRESPONDING #( keys )
    RESULT DATA(lt_bookings).

  result = VALUE #(
    FOR ls_booking IN lt_bookings
    ( %tky = ls_booking-%tky
      %action-cancelBooking = COND #( WHEN ls_booking-CreatedBy = sy-uname
                                      THEN if_abap_behv=>auth-allowed
                                      ELSE if_abap_behv=>auth-unauthorized ) ) ).
ENDMETHOD.

METHOD get_instance_features.
  " instance '상태': 이 건의 형편 — 예: 이미 취소된 예매는 취소 버튼 비활성
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    FIELDS ( Status ) WITH CORRESPONDING #( keys )
    RESULT DATA(lt_bookings).

  result = VALUE #(
    FOR ls_booking IN lt_bookings
    ( %tky = ls_booking-%tky
      %action-cancelBooking = COND #( WHEN ls_booking-Status = 'C'
                                      THEN if_abap_behv=>fc-o-disabled
                                      ELSE if_abap_behv=>fc-o-enabled ) ) ).
ENDMETHOD.
```

정리하면: global auth = 자격 자체(권한 오브젝트), instance auth = 이 건에 대한
권리(소유자), **features = 이 건의 상태에 따른 가용성**(취소 건 재취소 금지 —
화면 버튼 비활성까지 만들어 준다). **버튼 숨김·비활성은 features의 산물이지만,
그것만 믿으면 안 된다** — 화면을 우회한 EML([L06](CH39-L06.html))도 이 서버
판정들을 정면으로 만나기에 보호가 성립한다.

## 확인 시나리오 — 완료 기준 두 줄의 증명

재현 가능성도 정직하게 갈라 두자. 같은 계정의 두 창(일반+시크릿)으로 **확실히
재현되는 것은 ETag 충돌 행**이다(한 창에서 상세를 열어 둔 채, 다른 창에서 같은
건을 고쳐 저장 → 첫 창에서 저장 시도). 잠금·소유자 행은 같은 계정이면 자기 초안
Resume으로 흘러가는 등 기대와 다르게 보일 수 있어 **테스트 사용자 두 개가 있을
때의 확인 항목**이고, 잠금 만료 행은 만료 시간을 기다려야 해 실습보다는 **원리
확인용**이다 — 아래 표의 "재현" 칸이 그 구분이다.

| 시나리오 | 기대 | 재현 |
|---|---|---|
| A 편집 중 B가 같은 건 편집 시도 | 잠금 거부("편집 중") | 두 사용자 필요 |
| A가 초안 두고 이탈(잠금 만료) → B가 active 수정 → A Resume | **total ETag가 감지·차단** | 원리 확인용(만료 대기) |
| B가 읽은 뒤 A가 저장 → B 저장 시도 | ETag 충돌·거부(412) | **두 창으로 지금 가능** |
| 남이 만든 예매에 취소 시도 | instance **auth**가 거부(소유자 아님) | 두 사용자 필요 |
| 취소된 건에 다시 취소 | **features**가 버튼 비활성(+action 자체 방어) | **지금 가능** |

경계 하나를 정직하게 긋는다. **서로 다른 두 예매의 마지막 좌석 경합**(둘 다 잔여
2석을 보고 각자 2석 예매)은 위 네 장치의 보호 범위 **밖**이다 — 잠금과 ETag는
"같은 인스턴스"를 지키는 장치이기 때문이다. 이 경합의 방어는 [Chapter 26](CH26-L01.html)의
감각을 RAP save 로직에 결합하는 심화 주제다 — 방향만 남기면, **회차 단위 잠금
오브젝트를 저장 단계에서 ENQUEUE**하거나 좌석 카운터를 별도 테이블로 두고
갱신하는 것이 실무 해법이고, 이 과정 범위 밖이다 — 완료 기준 1번이 보장하는 것은 "한 요청 안에서의
차단"까지라는 사실을 알고 릴리스 보드를 채점하자.

## 흔한 실수와 점검 🚧

- **네 장치를 "동시성" 한 단어로 뭉개기** → 각자 다른 질문의 답이다. 위 표가
  기준.
- **잠금이 있으니 ETag 불필요라는 판단** → 잠금은 만료된다. 만료 후 세계(optimistic
  phase)의 보호가 ETag다 — 둘은 대체재가 아니라 릴레이다.
- **버튼 숨김 = 권한 처리** → UI는 경험이고 보호는 서버(DCL·BDEF auth·features)다.
- **자격과 상태를 한 메서드에 뭉개기** → 소유자 판정(auth)과 상태 판정(features)을
  섞으면 "왜 거부됐는지"가 흐려진다. 질문이 다르면 자리도 다르다.
- **authorization을 빈 채로 운영 이행** → 비어 있으면 전부 허용이다. 연습에선
  global을 비워 두지만(위 실습 지시), 운영 이행 때 채우는 것까지가 계약 이행이다.
- **draft table 직접 정리** → L04에서 못 박은 그대로 — framework의 영역이다.

## 정리 📌

- **Lock(편집 중·비관) → 만료 → ETag(저장 시점·낙관) → Draft 복귀는 total
  ETag** — 릴레이로 이어지는 보호.
- 판정 삼분법 = **DCL(볼 자격) + BDEF authorization(할 자격 — global/instance) +
  features(상태에 따른 가용성)**, 전부 서버에서.
- 완료 기준의 동시성·권한 두 줄이 증명됐다(단, 서로 다른 건의 좌석 경합은 보호
  범위 밖 — 정직한 경계). 남은 것은 운영 노출 한 줄이다.
