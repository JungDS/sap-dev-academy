## 입문 BDEF와 운영 BDEF의 거리

[Chapter 24](CH24-L04.html)의 BDEF는 이랬다: `managed` + `lock master` +
`create; update; delete;` + validation·determination·action 선언. 앱은 돌지만,
[L01](CH39-L01.html)의 완료 기준을 대면 구멍이 보인다 — 쓰다 만 예매는 날아가고,
잠금이 풀린 뒤의 충돌은 무방비이고, 권한은 계약에 없다.

운영 BDEF는 그 구멍을 **계약 조항**으로 막는다. 완성형을 먼저 보고 조항을 하나씩
읽는다.

```bdef
managed implementation in class zbp_i_booking unique;
strict ( 2 );
with draft;

define behavior for ZI_Booking alias Booking
persistent table zbooking
draft table zbooking_d
etag master LocalLastChangedAt
lock master total etag LastChangedAt
authorization master ( global, instance )
{
  create;
  update;
  delete;

  field ( readonly : update ) BookingId;             " 생성 땐 입력, 이후 변경 금지
  field ( readonly ) Status;                         " 상태는 action으로만 — 완료 기준 2의 계약적 실현
  field ( readonly ) CreatedBy,
                     LocalLastChangedAt, LastChangedAt; " 시스템이 쓰는 필드

  determination setDefaults on modify { create; }
  validation validateCapacity on save { create; field ConcertId, PerfNo, Seats; }
  action ( authorization : instance, features : instance )
    cancelBooking result [1] $self;

  draft action Activate optimized;
  draft action Discard;
  draft action Edit;
  draft action Resume;
  draft determine action Prepare
  {
    validation validateCapacity;   " 초안 확정 전에 검증을 미리 돌린다(필수 배정)
  }

  mapping for zbooking
  {
    BookingId     = booking_id;
    ConcertId     = concert_id;
    PerfNo        = perf_no;
    Customer      = customer;
    Seats         = seats;
    Status        = status;
    CreatedBy          = created_by;
    LocalLastChangedAt = local_last_changed_at;
    LastChangedAt      = last_changed_at;
  }
}
```

## 새 조항 읽기

| 조항 | 뜻 | 없으면 |
|---|---|---|
| `strict ( 2 )` | 엄격 문법 모드(숫자 = 규칙 묶음의 버전 — 2가 현재 표준) — 계약 누락·모호함을 활성화 단계에서 잡아 준다. CH24의 느슨한 BDEF를 열고 이걸 켜면 오류가 우수수 나올 수 있는데, **그 오류 목록이 곧 "운영 계약에 모자란 것" 목록**이다 | 느슨한 계약이 런타임 사고로 |
| `with draft;` | 이 BO 전체를 [[Draft]](쓰다 만 데이터를 임시 보관하는 RAP의 초안 메커니즘. active 데이터와 별도 테이블에 산다)-enabled로. **존재 이유가 검증과 맞물린다**: 미완성 입력은 검증(on save)에 걸려 저장할 수 없는데, Draft는 검증 없이 보관된다 — "저장은 못 하지만 잃어버리지도 않는" 상태를 만드는 장치. 검증은 확정(Activate)의 저장 단계에서 돈다 | 쓰다 만 입력은 증발 |
| `draft table zbooking_d` | 초안이 저장되는 별도 테이블 | draft 켜면 필수 |
| `lock master total etag LastChangedAt` | 잠금의 기준(root) 선언 + **draft BO의 필수 조항**인 total etag — 초안에서 돌아올 때 그사이 active가 바뀌었는지 비교할 기준. total etag는 독립 절이 아니라 **lock 지정에 붙는 절**이라 한 줄로 쓴다 | draft BO 활성화 불가 |
| `etag master LocalLastChangedAt` | 낙관적 충돌 감지의 기준 필드([L08](CH39-L08.html)에서 동작 원리) — total etag와 **다른 필드**를 쓰는 것이 표준 관례(그래서 L02에서 둘을 만들었다) | 잠금 풀린 뒤 충돌 무방비 |
| `authorization master ( global, instance )` | 권한 판단의 계약 — global(이 BO를 다룰 자격)·instance(이 건을 다룰 자격). 둘 다 켜는 이유: "예매를 만들 수 있는 사람"과 "**이** 예매를 취소할 수 있는 사람"은 다른 질문이라서다 | 권한이 UI 장식에 머묾 |
| `draft action …` 5종 | Draft의 표준 동작(편집 시작 Edit·재개 Resume·확정 Activate·폐기 Discard). **Prepare는 확정 전에 검증을 미리 돌려 오류를 초안 단계에서 보여 주는 자리** — 그래서 우리 `validateCapacity`를 Prepare에 **배정했다**(strict 모드는 미배정 검증을 활성화 오류로 잡는다) | draft 흐름 미완·활성화 오류 |

세 가지를 정직하게 짚는다.

- **draft table은 손으로 안 만든다.** 순서는 이렇다: BDEF에 `draft table
  zbooking_d`를 먼저 적으면 "테이블이 없다"는 오류 마커가 뜨고, 그 자리에서
  **quick fix(`Ctrl+1`)** 를 부르면 ADT가 초안 관리 필드까지 포함해 생성해
  준다(생성된 테이블 활성화까지 확인). 이 테이블은 **직접 SQL로 고치는 대상이
  아니다** — RAP framework가 관리한다.
- **readonly에는 결이 둘 있다.** `readonly : update`(BookingId)는 "생성할 때는
  소비자가 주고, 그 뒤로는 못 바꾼다"(key의 결 — CH24-L04에서 본 그것), 그냥
  `readonly`(CreatedBy·LastChangedAt)는 "소비자는 언제나 못 쓴다"다. 후자도
  **내부**는 예외다: behavior 구현이 `IN LOCAL MODE`로 다룰 때는 feature 통제가
  억제되어 채울 수 있다([L05](CH39-L05.html)의 setDefaults가 CreatedBy를 채우는
  근거 — 단, `@Semantics` 관리 필드(CreatedBy 등)는 그럴 필요조차 없다: 런타임이
  채우는 필드라 우리 코드가 손대지 않는 것이 정답이다).
- **etag와 total etag는 다른 필드다.** L02에서 만든 두 추적 필드가 각자의 자리에
  배정됐다 — 개별 변경 감지(`LocalLastChangedAt` = etag master)와 초안 복귀
  비교(`LastChangedAt` = total etag). 왜 둘이 다른 질문인지는
  [L08](CH39-L08.html)에서 동작으로 가른다.

## 소비 계약에도 동작을 — projection behavior

계약이 하나 더 필요하다. [L03](CH39-L03.html)의 `ZC_Booking`은 소비 계약인데,
**어떤 동작을 소비자에게 통과시킬지도 계약**이어야 한다. ZI의 BDEF만 있으면
화면(L07)에는 Create 버튼도 Draft 흐름도 뜨지 않는다 — 소비 층의 동작 계약,
**projection behavior**가 그 다리다(ADT에서 `ZC_Booking`에 대해 New Behavior
Definition을 만들면 유형이 projection으로 잡힌다).

```bdef
projection;
strict ( 2 );
use draft;

define behavior for ZC_Booking alias Booking
use etag
{
  use create;
  use update;
  use delete;

  use action cancelBooking;
}
```

읽기는 한 단어면 된다: **`use`** — "ZI 계약의 이 동작을 소비자에게 통과시킨다".
새 동작을 만드는 게 아니라 **통과 목록**이다(그래서 여기 없는 동작은 화면·서비스
에서 보이지 않는다 — 노출도 결정이라는 L03의 원칙이 동작에도 적용된 것).
`use draft;`가 또 있는 이유도 같다: ZI에 draft가 있어도 **이 소비 경로에 초안
흐름을 통과시킬지**는 별도의 결정이다.

BDEF에 `authorization master`를 선언하면 behavior pool에 구현 자리가 생긴다
(ADT quick fix가 skeleton을 만들어 준다 — CH24-L05에서 본 그 리듬).

```abap
CLASS lhc_booking DEFINITION
  INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.
    METHODS setDefaults
      FOR DETERMINE ON MODIFY
      IMPORTING keys FOR Booking~setDefaults.

    METHODS validateCapacity
      FOR VALIDATE ON SAVE
      IMPORTING keys FOR Booking~validateCapacity.

    METHODS cancelBooking
      FOR MODIFY
      IMPORTING keys FOR ACTION Booking~cancelBooking
      RESULT result.

    " authorization master가 만든 새 자리 둘 — 구현은 L08에서
    METHODS get_global_authorizations
      FOR GLOBAL AUTHORIZATION
      IMPORTING REQUEST requested_authorizations FOR Booking
      RESULT result.
    METHODS get_instance_authorizations
      FOR INSTANCE AUTHORIZATION
      IMPORTING keys REQUEST requested_authorizations FOR Booking
      RESULT result.

    " action의 ( features : instance )가 만든 자리 — 역시 L08에서
    METHODS get_instance_features
      FOR INSTANCE FEATURES
      IMPORTING keys REQUEST requested_features FOR Booking
      RESULT result.
ENDCLASS.
```

## 확인하는 법

1. BDEF 활성화 — `with draft`를 켠 상태에서 draft table·total etag가 없으면
   활성화가 막힌다(계약 누락을 시스템이 알려 주는 경험을 일부러 해 보라).
2. ADT quick fix로 behavior pool skeleton 생성 — authorization 메서드 둘과
   features 메서드 하나가 추가로 생겼는지(CH24의 mapping·기존 선언은 그대로 두고
   위 완성형과 대조해 **다른 줄만** 고친다).
3. **projection behavior**를 만들고 활성화 — `use` 목록에 cancelBooking이
   있는지(없으면 L07에서 취소 버튼이 안 뜬다).
4. `field ( readonly )`에 두 추적 필드가 있는지 — 변경 추적 필드는 사용자가
   아니라 시스템이 쓴다.

## 흔한 실수와 점검 🚧

- **draft table을 SE16/SQL로 정리** → framework 관리 대상이다. 초안 폐기는
  `Discard` draft action으로.
- **`lock master`면 동시성 끝이라는 착각** → 잠금은 만료된다. 그 뒤는
  ETag의 세계다([L08](CH39-L08.html)) — 그래서 두 조항이 함께 있다.
- **authorization 선언만 하고 구현 방치** → 선언은 자리를 만들 뿐이다. 비워 두면
  "권한 설계 완료"가 아니라 "권한 없음 통과"다.
- **ETag 필드를 수정 가능으로 노출** → readonly가 빠지면 사용자 입력이 변경
  추적을 오염시킨다.

## 정리 📌

- 운영 BDEF = 입문 CUD 계약 + **Draft(with draft·draft table·draft action) +
  total etag(draft BO 필수) + etag master + authorization master.**
- **projection behavior** = ZI 계약을 소비자에게 통과시키는 `use` 목록 — 이게
  없으면 화면에 동작이 뜨지 않는다.
- draft table은 ADT가 만들고 framework가 관리한다 — 직접 SQL 금지. readonly는
  두 결(`: update` = 생성만 허용 / 무인자 = 시스템 전용, 내부 IN LOCAL MODE는
  예외).
- 계약(BDEF)은 구현 자리(behavior pool)를 만든다 — 검증·기본값·취소 구현이 다음
  레슨, 권한·features·동시성의 동작 원리는 L08이다.
