## 계약은 있는데 판단이 비었다

[Chapter 24-L09](CH24-L09.html)에서 세 로직의 역할을 나눴다: 기본값은
determination, 저장 가부는 validation, 사용자 명령은 action. Capstone에서는 그
구현을 **운영 기준**으로 완성한다 — 운영 기준이란 두 가지다: ① 어떤 요청이 와도
(한 건이든 백 건이든) 안전할 것, ② 실패가 **사용자가 이해할 메시지**로 돌아갈 것.

문법 부품(`%tky`·`%control`·`READ/MODIFY ENTITIES IN LOCAL MODE`)은 전부
[CH24-L05](CH24-L05.html)에서 배운 그대로이고, 코드가 들어갈 자리도 그때 그
파일이다: **`zbp_i_booking`의 로컬 handler class**(`lhc_booking`) IMPLEMENTATION
— [L04](CH39-L04.html)의 DEFINITION과 한 벌이다(CH24 때의 구현이 남아 있으면
같은 이름 메서드는 **교체**, 새 메서드는 추가). readonly인 `Status`를 여기서
채우고 바꿀 수 있는 근거 = L04에서 정리한 "내부 IN LOCAL MODE 예외" — readonly는
바깥(소비자) 기준의 잠금이다.

## 기본값 — setDefaults (determination)

```abap
METHOD setDefaults.
  " 생성된 건들을 읽어(다건!) 상태가 빈 것만 채운다
  " (CreatedBy·LastChangedAt은 @Semantics 관리 필드라 런타임이 채운다 — L02)
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    FIELDS ( Status )
    WITH CORRESPONDING #( keys )
    RESULT DATA(lt_bookings).

  DATA lt_updates TYPE TABLE FOR UPDATE ZI_Booking.

  LOOP AT lt_bookings INTO DATA(ls_booking)
       WHERE Status IS INITIAL.
    APPEND VALUE #(
      %tky            = ls_booking-%tky
      Status          = 'N'
      %control-Status = if_abap_behv=>mk-on
    ) TO lt_updates.
  ENDLOOP.

  MODIFY ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    UPDATE FROM lt_updates
    FAILED   DATA(ls_failed)      " 내부 갱신 실패 — 이 최소형에선 받기만 한다
    REPORTED DATA(ls_reported).   " (기본값 세팅 실패는 뒤 validation이 잡는다)
ENDMETHOD.
```

## 정원 검증 — validateCapacity (validation)

CH24 실습에서 "정원 계산 기준"을 설계 질문으로 남겨 뒀다. 여기서 답한다:
**공연 정원([Chapter 9](CH09-L09.html)의 `zconcert-capacity` — 우리 앱은 모든
회차가 같은 정원을 쓰는 설계다) − 같은 회차의 기존 예약 합계(취소 제외) ≥ 이번
요청 좌석**. 정원은 공연 단위 값이지만 소진은 회차별로 세는 것이니, 회차마다
정원이 다른 공연장이라면 정원 필드를 `zperf`로 옮기는 확장이 필요하다(설계
판단의 문제 — 우리는 관통예제 정본을 따른다).

```abap
METHOD validateCapacity.
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    FIELDS ( BookingId ConcertId PerfNo Seats )
    WITH CORRESPONDING #( keys )
    RESULT DATA(lt_bookings).

  LOOP AT lt_bookings INTO DATA(ls_booking).
    " ① 공연 정원(전 회차 공통)
    SELECT SINGLE capacity
      FROM zconcert
      WHERE concert_id = @ls_booking-ConcertId
      INTO @DATA(lv_capacity).

    " ② 같은 회차의 기존 예약 합계 — 취소 제외, 그리고 자기 자신 제외.
    "    자기 제외의 이유: 수정 건의 '옛 좌석 수'는 이 시점(on save, 커밋 전)
    "    까지 DB에 남아 있다 — 그걸 빼고 새 값을 더해 판정해야 이중 계산이
    "    없다(신규 건에는 이 조건이 그냥 무해하게 지나간다)
    SELECT COALESCE( SUM( seats ), 0 )
      FROM zbooking
      WHERE concert_id  = @ls_booking-ConcertId
        AND perf_no     = @ls_booking-PerfNo
        AND status     <> 'C'
        AND booking_id <> @ls_booking-BookingId
      INTO @DATA(lv_booked).

    " ③ 판정 — 넘치면 거부(failed)와 이유(reported)를 함께 채운다
    IF lv_booked + ls_booking-Seats > lv_capacity.
      APPEND VALUE #( %tky = ls_booking-%tky ) TO failed-booking.
      APPEND VALUE #(
        %tky = ls_booking-%tky
        %element-Seats = if_abap_behv=>mk-on   " 화면에서 이 필드에 오류 표시
        %msg = new_message_with_text(
                 severity = if_abap_behv_message=>severity-error
                 text     = '남은 좌석보다 많은 좌석은 예약할 수 없습니다.' )
      ) TO reported-booking.
    ENDIF.
  ENDLOOP.
ENDMETHOD.
```

validation의 계약은 명확하다: **고치지 않는다, 판정한다.** 거부는
`failed-booking`(어느 건이), `reported-booking`(왜)의 짝으로 돌려준다 — 이 짝이
Fiori 메시지 영역과 [EML consumer](CH39-L06.html)의 FAILED/REPORTED로 그대로
흘러간다. `new_message_with_text( )`는 handler 기반
class(`cl_abap_behavior_handler`)가 물려주는 헬퍼로, message class 없이 즉석
텍스트 메시지를 만든다 — **연습용 지름길**이고, 운영에서는 [Chapter
15](CH15-L04.html)의 message class(SE91)로 승급해 번역·재사용이 되게 한다.

이 최소형의 **정직한 한계 둘**도 그어 둔다. ① 이 `SELECT`는 **DB만 본다** —
같은 요청(트랜잭션 버퍼)에 함께 들어온 다른 신규 예매는 아직 DB에 없어 합계에
안 잡힌다. 그래서 같은 회차 예매 여러 건이 한 요청에 오면 합계 초과가 뚫릴 수
있다. 운영형은 buffer의 요청분을 `READ ENTITIES … IN LOCAL MODE`로 함께 모아
합산에 더한다(도전 과제로 남긴다 — RAP behavior 안에서 자기 테이블을 직접
SELECT하는 것 자체가 "버퍼를 못 본다"는 대가를 치르는 일이라는 게 교훈이다).
② LOOP 안 SELECT는 [Chapter 35](CH35-L04.html) 기준의 개선 대상이다 — 회차
목록을 모아 한 번에 읽는 개선도 같은 과제다. 그리고 설계 사실 하나: **초안
상태의 예매는 초안 테이블에 있어 이 합계에 안 잡힌다** — "초안은 좌석을 점유하지
않는다"는 우리 설계의 결정이다(점유가 필요하면 별도 설계가 필요하다). **서로 다른 두 사용자의 마지막 좌석 동시 경합**은 이 validation도
[L08](CH39-L08.html)의 네 장치도 다 막지 못하는 별개 주제인데, L08 끝에서 경계를
긋는다.

## 취소 — cancelBooking (action)

```abap
METHOD cancelBooking.
  " 이미 취소된 건은 걸러낸다 — 화면 버튼은 features(L08)가 비활성해 주지만,
  " 상태 전이의 마지막 방어선은 action 자신이다
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    FIELDS ( Status ) WITH CORRESPONDING #( keys )
    RESULT DATA(lt_check).
  LOOP AT lt_check INTO DATA(ls_check) WHERE Status = 'C'.
    APPEND VALUE #( %tky = ls_check-%tky ) TO failed-booking.
  ENDLOOP.

  " 상태를 C로 — 사용자가 명시적으로 누른 업무 명령
  MODIFY ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    UPDATE FROM VALUE #(
      FOR ls_ok IN lt_check WHERE ( Status <> 'C' )   " 방어를 통과한 건만
      ( %tky            = ls_ok-%tky
        Status          = 'C'
        %control-Status = if_abap_behv=>mk-on ) )
    FAILED   DATA(ls_failed)
    REPORTED DATA(ls_reported).

  " action result: 바뀐 뒤의 모습을 돌려준다(result [1] $self 계약)
  READ ENTITIES OF ZI_Booking IN LOCAL MODE
    ENTITY Booking
    ALL FIELDS WITH CORRESPONDING #( keys )
    RESULT DATA(lt_changed).

  result = VALUE #( FOR ls_changed IN lt_changed
                    ( %tky   = ls_changed-%tky
                      %param = ls_changed ) ).
ENDMETHOD.
```

BDEF의 `result [1] $self`는 "실행 후 자기 자신 한 건을 돌려준다"는 약속이었다
— 채우지 않으면 Fiori 화면이 실행 후 최신 상태를 못 받는다.

취소에는 반가운 뒷면이 있다. 검증의 합산이 **취소 제외**(`status <> 'C'`)이므로,
누군가 취소하는 순간 그 좌석은 **자동으로 잔여석에 되살아난다** — 별도 코드 없이.
매진(잔여 0)이던 회차에서 유재석이 2석을 취소하면, 대기하던 손흥민의 2석 예매가
다음 검증을 통과한다. [콘서트 서사](CH09-L01.html)의 "매진 → 취소표"가 바로 이
장면이고, 이 챕터가 쌓은 검증 한 줄이 그 서사를 공짜로 구현하고 있었던 셈이다.
(취소를 기다렸다 자동 배정하는 **대기열**은 별도 설계다 — 이 과정 범위 밖.)

## 확인하는 법

| 확인 | 방법 |
|---|---|
| 기본값 | 생성 직후 Status가 `N`인가 |
| 정원 초과 | 잔여보다 큰 Seats 저장 → 거부 + 메시지가 보이는가 |
| 취소 | action 실행 후 Status `C` + 화면이 최신 상태로 갱신되는가 |
| 다건 | 한 요청에 여러 건을 넣어도 전 건이 각각 판정되는가 |
| 실패 짝 | 거부된 건의 failed와 reported가 **둘 다** 채워지는가 |

## 흔한 실수와 점검 🚧

- **validation에서 데이터 수정** → 판정과 보정이 섞이면 추적 불능. 보정은
  determination의 몫.
- **`keys`의 첫 건만 처리** → 단건 테스트는 통과하고 다건 요청(OData batch)에서
  깨진다. **모든 handler는 다건이 기본**이다.
- **다건을 각각만 판정** → "각각 판정"으로도 부족한 케이스가 위의 한계 ①이다.
  같은 회차 다건은 **묶어 합산**해야 진짜 다건 안전이다.
- **failed만 채우고 reported 생략** → 거부는 되는데 사용자는 이유를 모른다.
  거부와 이유는 항상 짝.
- **action 없이 상태 필드 직접 update 허용** → "취소는 action으로만"이라는 완료
  기준이 깨진다. 상태 전이는 명시적 명령으로. 재취소 방어는 이중이다 —
  화면 가용성은 [L08](CH39-L08.html)의 features가, 최종 방어선은 action 자신이
  갖는다(위 코드의 첫 블록).

## 정리 📌

- 세 로직의 완성 기준 = **다건 안전 + failed/reported 짝(+%element로 필드 지목) +
  result 계약 이행.** action은 상태 전이의 마지막 방어선을 스스로 갖는다.
- 정원 검증의 실체 = 공연 정원 − 같은 회차 기존 합계(취소·자기 제외) 비교.
  판정만 하고 고치지 않는다. 남긴 한계(같은 회차 다건 합산·LOOP 밖 SELECT)는
  도전 과제다.
- 이 판단들은 화면 전용이 아니다 — 다음 레슨에서 **화면 없이(EML)** 같은 규칙이
  작동하는 것을 확인한다.
