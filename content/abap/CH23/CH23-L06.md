## 왜 모델에 권한을 붙일까

데이터 모델을 만들고 UI 힌트까지 붙였다고 끝이 아니다. 실제 시스템에서는 **"누가 어떤 데이터를 볼 수
있는가"**가 중요하다. 같은 `ZI_Concert`라도 서울 담당자는 서울 공연장의 행만, 부산 담당자는 부산 공연장의 행만
봐야 할 수 있다.

이 권한 필터를 프로그램마다 [AUTHORITY-CHECK](CH15-L07.html)와 WHERE 조건으로 반복하면 위험하다. 어떤
프로그램은 권한을 적용하고, 어떤 프로그램은 빠뜨릴 수 있다. CDS의 장점은 **읽기 모델 가까이에 접근 제어를
선언**해, 그 뷰를 읽는 프로그램마다 권한 코드를 다시 쓰지 않아도 된다는 점이다.

## 무엇인가 — DCL로 행 단위 권한

[[DCL]](Data Control Language, 접근을 *제어*하는 언어)은 CDS entity에 대한 [[Access Control|접근 규칙]]을 별도 DCL source로 정의한다.

```dcl
@MappingRole: true
define role ZI_Concert_Role {
  grant select on ZI_Concert
    where ( venue ) = aspect pfcg_auth( Z_VENUE, VENUE, ACTVT = '03' );
}
```

| 코드 | 뜻 |
|---|---|
| `@MappingRole: true` | 이 role을 (클라이언트 구분 없이) **모든 사용자에게 매핑(배정)한다**는 선언. `define role` 앞에 **필수**로 붙는다. 사용자별 차이는 뒤의 조건이 만든다. |
| `define role ZI_Concert_Role` | 접근 규칙 이름을 정의. |
| `grant select on ZI_Concert` | `ZI_Concert`를 SELECT할 때의 허용 조건. |
| `where ( venue ) = aspect pfcg_auth( … )` | 왼쪽 소문자 `venue`는 **뷰의 요소**. 오른쪽 `aspect pfcg_auth`는 사용자의 classic 권한(PFCG: 권한 role을 관리하는 T-code)에서 허용된 값을 가져온다. 결과는 SELECT에 **추가 선택 조건**으로 붙어, 허용된 공연장의 행만 남는다. 괄호 안은 세 조각이다. |
| └ `Z_VENUE` | 참조할 **권한 객체** 이름. [Selection Screen 권한/존재 여부 검증 기초](CH15-L07.html)에서 본 그 권한 객체다. |
| └ `VENUE` | 그 권한 객체의 **권한 필드**(대문자). 사용자가 이 필드에 허가받은 값 목록이 뷰 요소 `venue`와 비교된다. |
| └ `ACTVT = '03'` | **활동** 조건. `'03'`은 조회(Display)를 뜻하는 표준 활동 코드다(CH15에서 쓴 그 값). |

대상 CDS 뷰는 권한 검사를 의도에 맞게 선언해야 한다.

```cds
@AccessControl.authorizationCheck: #CHECK
define view entity ZI_Concert
  as select from zconcert
{
  key concert_id,
      artist,
      venue,
      capacity
}
```

`#CHECK`는 access control이 **있어야 한다**는 기대를 분명히 드러낸다. `#NOT_REQUIRED`는 access control이
없어도 된다는 뜻으로 초기 단순 조회 예제에 적합하다. 여기서 입문자가 가장 많이 틀리는 지점이 있다. **`#NOT_REQUIRED`는
"DCL 끄기"가 아니다.** DCL이 이미 있으면 `#NOT_REQUIRED`에서도 **똑같이 평가**된다. 둘의 런타임 동작은 같고, 차이는
DCL이 없을 때 `#CHECK`만 활성화 경고를 낸다는 것뿐이다. 존재하는 DCL을 무시하게 하는 값은 따로 있다(`#NOT_ALLOWED`).

| 값 | DCL이 **있을 때** | DCL이 **없을 때** |
|---|---|---|
| `#CHECK` | 평가한다(권한 필터 적용) | 활성화 시 **경고**("있어야 하는데 없다") |
| `#NOT_REQUIRED` | **똑같이 평가한다** | 경고 없음("없어도 된다"). 생략 시 기본값 |
| `#NOT_ALLOWED` | **무시한다**(필터 미적용, 경고) | 아무 일 없음. 권한 검사가 해로운 기술 entity용 |

이 챕터에서는 이 셋의 차이만 확실히 잡는다.

> 🚨 **DCL은 위 계층으로 상속되지 않는다.** `ZI_Concert`에 접근 제어를 걸었다고 해서, 그 위에 얹은
> `ZC_Concert`가 **자동으로 보호되지는 않는다.** 소비 뷰를 `SELECT`하면 기반의 DCL을 거치지 않고 데이터에
> 그대로 접근한다. [L02](CH23-L02.html)에서 본 "필드의 annotation은 위로 물려받는다"와는 반대 방향이니 헷갈리지
> 말자. 뜻(annotation)은 따라올 수 있어도 **접근 제어(DCL)는 entity마다 별도**다. 그래서 공식 규칙은 **"보호가
> 필요한 entity마다 각각 DCL을 정의하라"**이다. 기반 하나만 막고 안심하는 것이 CDS 권한에서 가장 위험한 착각이다.

중요한 구분이 하나 있다 — **DCL role은 사용자에게 PFCG role을 배정하는 행위 그 자체가 아니다.** DCL은 CDS
access rule이고, `aspect pfcg_auth`는 classic PFCG 권한 객체의 *값을 조건으로 참조*할 뿐이다. 권한 객체 설계와
사용자 권한 부여(SU01: 사용자 계정 관리 T-code, PFCG: 권한 role 관리 T-code)는 별도 보안 설정이다.

## 직접 비교해 보기

아래에서 사용자를 바꾸고 `@AccessControl`을 `#CHECK` ↔ `#NOT_ALLOWED`로 토글해 보자. **같은 SELECT**인데
사용자 권한에 따라 보이는 행이 달라지고, `#NOT_ALLOWED`면 존재하는 DCL이 무시되어 권한 밖 공연장까지 노출되는 것을
직접 확인할 수 있다. `#NOT_REQUIRED`로 바꿔 봐도 DCL이 있는 한 결과는 `#CHECK`와 같다. 그 값은 "DCL 끄기"가 아니다.

## 어떻게 확인하는가

1. **DCL source 활성화** — `@MappingRole: true` 누락, role 이름 오류, 대상 entity 오타, 권한 객체·필드명 오류가
   있으면 활성화 단계에서 드러난다.
2. **대상 뷰의 `@AccessControl`** — 권한을 보여 주는 예제에서는 `#CHECK`로 의도를 명확히 한다.
3. **사용자별 결과 비교** — 같은 `SELECT FROM ZI_Concert`를 실행했을 때 담당 지역이 다른 사용자 A와 B가 보는
   행이 달라져야 한다.
4. **권한 없는 행이 안 보이는가** — 단순히 오류가 없다고 통과가 아니다. 행 단위 권한은 **결과집합의 내용**이
   핵심이다.

## 정리 📌

- DCL은 `define role` + `grant select on … where …`로 **행 단위 접근 조건**을 entity에 붙인다. `@MappingRole: true`는
  필수다.
- `#CHECK`와 `#NOT_REQUIRED`는 DCL이 있으면 **둘 다 평가**한다. 존재하는 DCL을 무시하는 값은 `#NOT_ALLOWED`뿐이다.
- DCL은 위 계층으로 **상속되지 않는다**. 보호가 필요한 entity마다 각각 정의한다.

## 흔한 실수와 점검 🚧

- **DCL이 위 계층까지 지켜 준다고 생각** → 상속되지 않는다. 기반 `ZI_`에만 걸고 소비 `ZC_`에 안 걸면,
  `ZC_`를 읽는 소비자는 필터 없이 데이터를 본다. **보호가 필요한 entity마다 각각** 정의한다.
- **DCL을 만들면 자동으로 무조건 적용된다고 생각** → entity가 `#NOT_ALLOWED`로 선언됐거나, 소비 쪽이 privileged
  access(권한 검사를 건너뛰겠다고 선언한 특수 접근. 뒤 과정에서 다룬다)로 읽으면 존재하는 DCL도 무시된다. 적용 여부를
  확인해야 한다.
- **`#NOT_REQUIRED`를 "DCL 끄는 스위치"로 착각** → 아니다. DCL이 있으면 `#NOT_REQUIRED`에서도 **평가된다**(`#CHECK`와
  런타임 동일. 차이는 DCL이 없을 때 경고 여부뿐). 존재하는 DCL을 무시하는 값은 `#NOT_ALLOWED`다. 권한 예제에서는
  `#CHECK`를 써서 의도를 분명히 한다.
- **DCL role과 사용자 role assignment 혼동** → `define role`은 CDS access rule이지, SU01/PFCG에서 사용자에게
  role을 부여하는 작업이 아니다.
- **권한을 UI에서만 막기** → 버튼·컬럼을 숨겨도 모델을 직접 읽는 다른 소비처가 있으면 우회된다. 행 단위 권한은
  데이터 모델 가까이에서 일관되게 적용해야 한다.
