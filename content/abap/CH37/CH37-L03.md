## 양식이 있는데 왜 안 나가지?

L01에서 양식을 만들어 호출했고, L02에서 PDF 데이터까지 만들었다. 하지만 실무의
예매 확인서는 개발자가 리포트를 실행해서 나가는 게 아니다. **예매가 확정되는 순간 시스템이 알아서** 보내야 한다.
그러려면 시스템이 알아야 할 것이 있다: 어떤 업무 이벤트에서, 누구에게, 어떤
양식으로, 인쇄인지 이메일인지, 지금 보낼지 모아서 보낼지.

이 결정을 담당하는 층이 [[Output Control]](업무 이벤트 발생 시 출력 여부·양식·
수신자·채널·시점을 결정하는 메커니즘)이다. **양식은 문서의 모양이고, Output
Control은 그 문서의 발송 결정이다.** 층이 다르다는 것을 아는 순간, "양식은 멀쩡한데
왜 안 나가지?"라는 질문의 답 찾을 곳이 달라진다.

조건을 ABAP 코드에 `IF`로 박아 넣으면 안 되나? 처음엔 되지만, 문서 종류와 조건이
늘수록 코드가 비대해지고 **운영자가 조건을 바꿀 때마다 개발·이송이 필요**해진다.
출력 결정을 설정·규칙의 영역으로 분리하는 이유다.

## 두 갈래 — 전통 NAST와 S/4HANA Output Management

낯선 명사 셋을 먼저 풀고 표로 가자.

- **출력 유형(output type)** — "예매 확인서", "주문서"처럼 **출력물의 종류에 붙는
  이름**. 어떤 양식을 쓰고 어떤 채널이 기본인지가 이 이름 밑에 등록된다.
- **조건 레코드(condition record)** — "이 문서 유형이 이 조건이면 이 출력 유형을
  실행하라"를 코드가 아니라 **데이터 한 줄(레코드)로 저장**해 둔 것. 운영자가
  설정 화면에서 등록하므로, 조건이 바뀌어도 **코드 수정·이송이 없다**(위에서
  `IF`로 박지 않는 이유가 바로 이것이다). 단 경계 하나: 이송이 없는 것은 이
  **레코드(데이터)**까지다. 출력 유형 같은 **설정 틀 자체는 Customizing**이라
  일반 설정처럼 이송 경로를 탄다.
- **output item** — S/4HANA Output Management에서 **출력 요청 한 건**을 가리키는
  단위. 규칙이 "출력하라"고 판정하면 문서에 output item이 생기고, 그 상태(성공·
  오류·대기)로 진행을 추적한다.

참고로 이 동네에서 **"메시지(message)"는 오류 문구가 아니라 "출력물 한 건"**을
가리키는 용어다(그래서 Message Control이 출력 결정 방식의 이름이다).
[Chapter 15에서 배운 `MESSAGE` 문](CH15-L04.html)과 이름만 같고 다른 물건이니
헷갈리지 말자.

| 관점 | 전통 [[NAST]](Message Control) | [[BRFplus]] 기반 Output Management |
|---|---|---|
| 결정 방식 | 출력 유형 + 조건 레코드(condition record) | 비즈니스 규칙·decision table(조건→결과를 표로 적는 규칙 표) 평가 |
| 대표 산출물 | NAST 레코드·메시지 상태 | output item·rule 결과 |
| 주 무대 | 기존 SD/MM 등 classic 영역 | S/4HANA 표준 전환 영역 |
| 문제 확인 | 문서의 메시지 상태·조건 레코드 | output item 상태·rule/채널 설정 |

`NAST`는 **판정 결과(메시지 상태)가 저장되는 테이블 이름**에서 온 통칭으로, 이
전통 방식 전체(Message Control)를 가리키는 말로 굳었다(테이블이니 SE16으로 열어
직접 볼 수도 있다). 조건 레코드의 판정도 한 줄만 알아 두자: 레코드는
**"구체적인 조건부터 일반 조건 순서로"** 탐색되고, 먼저 맞은 쪽이 이긴다.
그래서 "전체 기본 설정을 바꿨는데 VIP 고객만 옛날 방식대로 나가네?" 류의
수수께끼가 생긴다 — VIP용 구체 레코드가 먼저 맞아서 기본 설정 변경이 그
고객에게는 안 닿는 것이다.

S/4HANA가 새 방식을 만든 이유도 한 줄로: 조건 레코드 방식은 업무 영역마다 설정
체계가 제각각이어서, 문서 종류가 늘수록 **하나의 규칙 프레임워크로 통일**할 필요가
커졌기 때문이다. 위치 감각 하나만 더: 새 Output Management 환경은 전용 양식
기술을 **주로** 전제해서(릴리스·응용에 따라 예외는 있다) 그쪽 양식은 이 과정
범위 밖이고, 우리가 만드는 Smart Forms 양식의 주 무대는 **전통 NAST 계열**이다.

[[BRFplus]](Business Rule Framework plus. 비즈니스 규칙을 정의·평가하는
프레임워크)는 여기서 처음 만나는 이름인데, 위치를 정확히 잡자. **ABAP 문법이
아니다.** `COND`나 `SWITCH` 같은 문법 차원이 아니라, "이 조건이면 어떤 출력이 어떤
채널로"를 규칙 표로 관리하는 별도 프레임워크이고, Output Management가 출력 결정에
그것을 쓴다. 이 과정에서는 **역할과 확인 지점까지만** 배우고, BRFplus로 규칙을
만드는 것 자체는 범위 밖이다(모듈·운영 설정 심화 영역).

한 가지 더: 한 시스템 안에서도 업무 영역별로 두 방식이 **공존**할 수 있다.
"S/4니까 무조건 BRFplus"도, "구형이니까 무조건 NAST"도 아니다. 대상 업무 문서가
어느 프레임워크를 쓰는지부터 확인한다(가장 빠른 확인법은 그 문서를 담당하는
**업무 모듈**(SD=영업·판매, MM=구매·자재처럼 업무 영역별 표준 기능 묶음)
담당자·운영자에게 묻는 것이다 — 문서마다 다르고, 설정 화면도 모듈마다 다르다).

> 🔭 **기대 관리** — 조건 레코드·rule을 **등록하는 설정 화면은 업무 모듈(SD/MM
> 등)·운영 설정 영역**이라 이 과정 범위 밖이다(모듈마다 화면이 다르다). 문서의
> 메시지 상태·output item도 해당 **업무 문서 화면의 출력(Output) 메뉴**에서 보는
> 것이라, 화면 위치는 실습하는 모듈에 따라 다르다. 이 레슨에서 고정할 것은 화면이
> 아니라 **층의 구분과 추적 순서**다.

## 그럼 개발자인 나는 뭘 하나

이 층의 설정은 운영·모듈 영역이라고 했다. 그렇다고 개발자가 구경만 하는 것은
아니다. 예매 확인서가 자동으로 나가기까지 역할이 이렇게 나뉜다.

1. **개발자** — 양식(`ZSF_TICKET`)을 만든다(L01). 전통 NAST
   방식에서는 그 양식을 부르는 **출력 프로그램**도 개발자가 만든다. 조회 후 동적
   호출이라는 뼈대는 L01 리포트와 같지만, **진입 계약이 다르다**: 시스템이 정해진
   이름의 서브루틴(관례상 `ENTRY`)을 호출하면서 "어느 문서를 출력할지"가 담긴
   NAST 정보를 채워 준다(내가 `SELECT`로 고르는 게 아니다). 낯설게 느껴질 텐데,
   [Chapter 10](CH10-L02.html)의 FORM 문법 그대로에 **호출 방향만 반대**다: 내가
   `PERFORM`으로 부르는 대신 프레임워크가 내 프로그램의 정해진 FORM을 찾아
   부른다. 참고로 문서 정보는 FORM의 파라미터가 아니라 프로그램의 공용
   영역(`TABLES nast` 선언)으로 건너온다 — 실물 작성은 표준
   출력 프로그램을 참고하는 영역이라 이 과정 범위 밖이고, 여기서는 "실행형
   리포트가 아니라 정해진 진입 루틴"이라는 사실만 고정하자.
2. **설정 담당(모듈·운영)** — 출력 유형을 정의하고, 거기에 개발자가 만든 **양식
   이름과 출력 프로그램(+진입 루틴 이름)**을 등록하고, 조건 레코드나 rule로 "언제
   누구에게 어떤 채널"을 정한다. 등록하는 이름은 언제나 안정적인 쪽(Form 이름)이다
   — 생성 함수명이 아니다(L01의 규칙 그대로).
3. **장애가 나면** — 개발자는 층을 판별한다. 양식·매핑 문제면 내 몫, 결정·채널
   문제면 설정 담당과 함께 본다. 이 판별이 이 레슨과 L05의 목적이다.

## 결정에서 전달까지 — 흐름 한 장

::embed CH37-L03-S01 | Output Control 결정 흐름 | 470::

흐름의 각 마디가 곧 확인 지점이다.

1. **업무 이벤트** — 예매 확정·주문 저장처럼 출력이 시작될 사건이 있었는가. 수동
   미리보기는 되는데 저장 시 안 나가면, 양식이 아니라 여기부터다.
2. **조건/규칙 평가** — 조건 레코드(NAST) 또는 rule(BRFplus)이 "출력하라"고
   판정했는가. 판정이 없으면 output item 자체가 안 생긴다. NAST 쪽은 **전송
   시점**도 함께 본다: "즉시 전송"이 아니라 "모아서 전송"으로 설정돼 있으면,
   메시지는 생겼는데 **정기 발송 작업이 돌 때까지 안 나가는 게 정상**이다.
   "안 나가요"의 단골 원인 중 하나다.
3. **양식·채널 연결** — 결정된 출력이 어느 양식으로(우리 예제는 `ZSF_TICKET`),
   인쇄·이메일 중 어디로 가는가. 같은 양식이라도 채널이 다르면 실패 지점이 다르다.
4. **생성 결과** — NAST면 메시지 상태, Output Management면 output item 상태. 인쇄
   채널이면 스풀([이 챕터의 오류 추적 레슨](CH37-L05.html)에서 SP01로 본다)까지.

## 흔한 실수와 점검 🚧

- **양식만 만들고 결정 미설정** → 시스템 입장에선 그 양식을 언제 쓸지 정해진 적이
  없다. 자동 출력엔 결정 층이 필수.
- **BRFplus를 ABAP 문법처럼 학습** → rule 프레임워크다. 이 과정에선 역할·확인
  지점까지. 규칙 authoring은 별도 심화.
- **한 방식만 있다고 단정** → 같은 시스템에 NAST와 Output Management가 공존할 수
  있다. 문서별 프레임워크부터 확인.
- **채널을 가볍게 봄** → output item은 생겼는데 전달이 안 되면 채널(수신자 주소·
  프린터·설정) 문제다. 양식 잘못이 아니다.

## 정리 📌

- **양식 ≠ 출력 결정.** Output Control이 언제·무엇을·누구에게·어떤 채널로를 정한다.
- 두 갈래 = 전통 **NAST**(조건 레코드) · S/4HANA **BRFplus 기반 Output
  Management**(rule). 공존 가능, 문서별로 확인.
- BRFplus는 ABAP 문법이 아니라 rule 프레임워크. 여기서는 역할과 확인 지점까지만.
- 역할 분담 = 개발자는 **양식(+NAST 방식이면 출력 프로그램)**, 설정 담당은 **출력
  유형·조건·채널 등록**, 장애 시 개발자는 **층 판별**.
- 추적 순서 = 이벤트 → 조건/규칙 → 양식·채널 → 생성 결과(상태·스풀).
